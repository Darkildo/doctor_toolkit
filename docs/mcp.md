# MCP: игра для ИИ-клиента

Этапы 50, 51 и 57: сервер [Model Context Protocol](https://modelcontextprotocol.io),
через который ИИ-клиент (Claude Code, Claude Desktop, любой клиент MCP)
работает с игрой средствами тулкита: ищет ресурсы, смотрит их содержимое в
JSON, идёт по графу логики, перечисляет объекты уровня, читает рабочее
пространство и проект, видит запущенную игру через живую связь и открытый
редактор через мост. **По умолчанию только чтение.** Два флага включают
запись (этап 51):

- `--allow-edits` — правки **только в рабочем пространстве** (объекты
  SimGroup, строки, скрипты-графы, навигационные графы; этап 57 — новые
  потоки, SimGroup, ресурсы, импорт моделей, текстур, звука, видео, файлов
  выгрузки и связи логики), каждая — одна операция с отменой и сравнением
  в ответе; сборка проекта и мода, проверка правок;
- `--allow-game` — запись рабочего пространства в файлы игры и откат,
  запуск игры на собственном X-сервере (на рабочем столе ничего не
  появляется), снимок кадра, действия в запущенной игре через живую связь,
  менеджер модов;
- `--output-dir DIR` (этап 57) — папка, куда инструменты выгрузки
  (`export`, `media`) пишут файлы; без неё они отказывают.

Код: `crates/doctor-toolkit-mcp/` (библиотека сервера),
`crates/doctor-toolkit-cli/src/mcp_cmd.rs` (подкоманда). Настройка клиентов —
глава руководства [22](guide/22-mcp.md).

## 1. Запуск

```sh
doctor-toolkit mcp ИГРА [--workspace DIR] [--project DIR] [--no-cache] [--max-response-chars N]
                        [--allow-edits] [--allow-game] [--output-dir DIR]
```

| Флаг | Что делает |
|---|---|
| `ИГРА` | папка игры (с `godfather2.exe` и `gf2/`) |
| `--workspace DIR` | рабочее пространство; по умолчанию — из `project.toml` проекта, иначе `<игра>/_doctor_toolkit/workspace` |
| `--project DIR` | проект мода (`docs/project.md`) для `project_status` и для выбора рабочего пространства |
| `--no-cache` | строить индекс игры в памяти, не трогая кэш `~/.cache/doctor-toolkit/` |
| `--max-response-chars N` | предел одного ответа инструмента, символов (по умолчанию 40 000, не меньше 4 000) |
| `--allow-edits` | инструменты записи в рабочее пространство, сборки и проверки (§3.2) |
| `--allow-game` | запись в файлы игры, запуск и остановка игры, снимок кадра, запись в запущенную игру, менеджер модов (§3.3) |
| `--output-dir DIR` | папка для файлов `export` и `media` (создаётся); без неё они отвечают ошибкой с этим флагом |

Без флагов сервер такой же, как на этапе 50, плюс чтение живой связи и
моста с редактором (они ничего не меняют в данных). Флаги независимы:
`--allow-game` без `--allow-edits` даёт запустить игру с уже готовым
рабочим пространством, но не править его.

Транспорт — stdio: клиент запускает процесс и говорит с ним JSON-RPC по
строке на сообщение. Сети нет. В stdout идут только сообщения протокола,
всё для человека — в stderr (тест `mcp_serves_over_stdio_and_prints_only_protocol_messages`).
Отдельного бинарника нет: настраивать клиент проще одной программой, которая
уже стоит у пользователя, а в выпуске она одна и та же.

## 2. Устройство

**SDK — официальный `rmcp` 3.8.0** (Apache-2.0, совместима с GPL-3.0;
последняя версия старше двух недель на 2026-11-13: 3.9.0 и 3.10.0 вышли
позже, версия закреплена `=3.8.0`, `rmcp-macros` тоже 3.8.0). Минимальная
версия Rust — 1.88, у нас 1.97.1. Функции: `server`, `macros`,
`transport-io` без функций по умолчанию — HTTP, OAuth и клиент не
собираются. Новые зависимости: `tokio` (уже был в дереве), `schemars` 1
(схемы параметров), `futures`, `chrono`, `darling` и мелочи макросов. Свой
JSON-RPC не понадобился: SDK сам ведёт согласование версии протокола
(клиенты 2025-06-18, 2025-11-25 и новые 2026-07-28 без `initialize`),
`tools/list` со схемами из типов Rust, отмену и ошибки.

| Модуль | Что в нём |
|---|---|
| `state.rs` | `Toolkit`: игра (сканируется при старте) и то, что строится один раз при первом обращении — индекс игры (`GameIndex`, из кэша как в CLI), таблица ресурсов, словарь имён, индекс сообщений (пересобирается, когда рабочее пространство сохранено снова), каталог диалогов, GUID всех объектов SimGroup (для новых объектов). Рабочее пространство и проект открываются заново при каждом вызове, поэтому правки в редакторе видны сразу. `write_workspace` — доступ на запись (§5) |
| `tools/` | инструменты: функции `(&Toolkit, параметры) → JSON, текст или картинка`, по модулю на группу: чтение (`game`, `search`, `json`, `logic`, `level`, `workspace`), правки (`edit`), сборка и проверка (`build`), игра (`play`), живая связь (`live`) |
| `game.rs` | игра, запущенная `play`: Xvfb с `-displayfd`, группа процессов, остановка SIGTERM → SIGKILL, снимок кадра (`GetImage` по протоколу X11, PNG) |
| `bridge.rs` | мост с открытым редактором со стороны сервера (§6) |
| `server.rs` | сервер `rmcp`: маршрутизаторы инструментов (`#[tool_router]`) — чтение, живая связь и редактор всегда, правки с `--allow-edits`, игра с `--allow-game` (`ToolRouter` складываются); ресурсы; инструкции для модели (дополняются по флагам); каждый вызов идёт в отдельном потоке (`spawn_blocking`), паника в разборе превращается в ошибку инструмента, сервер продолжает работу |
| `resources.rs` | MCP-ресурсы |
| `output.rs` | ограда данных игры, пределы размера, страницы |
| `build.rs` | встраивает документы `docs/` в бинарник |

Индекс игры начинает строиться в фоне сразу после старта: первый вызов на
GF2 ждёт 0,5 с (индекс из кэша), без кэша — построение с нуля (§1.3 `docs/navigation.md`).

Когда клиент отключается (stdin закрыт), сервер останавливает игру,
запущенную `play`, и убирает всё, что `play` положил в папку игры (§3.3).
С `--allow-edits` фоновый поток после индекса читает GUID всех объектов
игры (несколько секунд на GF2), чтобы первая правка не ждала.

## 3. Инструменты

Имена, параметры и описания — по-английски, их читает модель. У
инструментов чтения аннотации `readOnlyHint: true`, `destructiveHint:
false`, `idempotentHint: true`, `openWorldHint: false`; у записи
`readOnlyHint: false`, `destructiveHint: true` — у `remove_object`,
`remove_stream`, `apply`, `unapply`, `stop`, `send_message`, `lua`,
`set_money`, `set_variable`, `stream_unload`, `mods_manage`. `export` и
`media` есть без флагов, но пишут файлы в папку вывода: у них
`readOnlyHint: false`, `destructiveHint: false`.

### 3.1 Чтение (всегда)

| Инструмент | Параметры | Что возвращает |
|---|---|---|
| `game_info` | — | папка, профиль, число потоков, оглавлений, миссий; ресурсов в индексе, неразобранных; 40 самых частых типов; области (`gf2/miami`, …); рабочее пространство и проект; предел ответа; подсказки |
| `list_streams` | `prefix`, `offset`, `limit` (200, ≤ 1000) | потоки с размером и числом ресурсов |
| `search` | `query`, `offset`, `limit` (30, ≤ 200) | ключ, подпись, тип, поток, номер и почему подошёл; всего найдено. Запрос — как в CLI и редакторе (`docs/navigation.md` §3) |

| `project_status` | `all`, `offset`, `limit` (100, ≤ 500) | записи проекта и их состояние (`unchanged`, `built`, `modified`, `out of sync`, `missing`), неизвестные файлы, предупреждения |
| `check_refs` | `streams` (имена или префиксы, ≤ 400 потоков), `limit` (100, ≤ 1000) | ссылки ресурсов игры, которые не находятся в потоке и загружаемых до него (`check-refs`); правки и новые потоки проверяет `validate` |
| `export` | `resource` (ключ, `<поток>#<номер>` или запрос; ключ ресурса, добавленного рабочим пространством, тоже), `format`, `name`, `original` | файлы в папке вывода (§3.4) |
| `media` | `kind` (`movies` или `sounds`), `name`, `filter`, `wav`, `frames`, `key_frames`, `original`, `offset`, `limit` | ролики `.vp6` и потоковые звуки и речь архивов `.viv`: список; с `name` — сведения (кадры, частота, звук; субтитры речи) и выгрузка звука в WAV и кадров в PNG (§3.4) |

| `player` | — | игрок: положение, оси, курс в градусах; камера |

| `editor_open` | `resource` — ключ или запрос с одним результатом | показать ресурс во вкладке потока редактора |
| `editor_show_object` | `object`, `view` (`level` или `logic`) | показать и выделить объект во вкладке уровня или графа логики |

Живая связь — тот же клиент, что у CLI и панели «Связь» (`docs/analysis/live-link.md`):
порт и ключ берутся у модуля, поставленного `play`, иначе из
`scripts/doctor_live.cfg` папки игры (модуль поставил «Играть» редактора
или `doctor-toolkit play --live`).

**`resource_json` по типам.** SimGroup, metamodel, variabledictionary,
partsdb, graph (навигационный граф), mobface — тот же JSON, что
`logic-export`; `lh2` — записи `hash` и текст по колонкам; `dlg` — отчёт
диалога, как `dialogue --json` (дерево, реплики с речью и английскими
субтитрами, варианты с текстами, кто запускает); `trinity_seq_master` —
кадр ролика (`cutscene-export`); `tob`, `rcb`, `bnk`, `hkx`, `chv`, `smb`,
`sbk`, `ffn` — их разбор; `material` — шейдеры, параметры и затенение;
`tg4h` — заголовок текстуры; `lua` — исходник, декомпилированный в Lua 5.0
(текст, а не JSON). Версия рабочего пространства, если оно меняет ресурс,
иначе файл игры; `original: true` — только файл игры. Для остальных типов
(`tg4d`, `mesh`, `meshvolatile`, …) — ошибка с советом взять `resource_info`.

**`logic_graph`.** С `object` — id `<поток>#<ресурс>:<объект>` (его печатают
`level_objects` и сам `logic_graph`) или имя объекта: пины объекта с
сообщениями (сколько у каждого отправителей и слушателей, называет ли
сообщение движок) и обход на `depth` шагов: `down` — слушатели того, что
объект посылает, `up` — отправители того, что он слышит. На сообщение
обходится не больше 25 концов (остальные перечислены в `not_followed`),
объектов — не больше `limit`. С `message` — все отправители и слушатели по
игре, при ненайденном — похожие имена. Со `scope` (`mission:`,
`checkpoint:`, `stream:`, `group:`, `level:`) — сводка графа
(`logic-graph`), сообщения (сначала висящие) и объекты; вся игра (`game`)
отклоняется — слишком велика для одного ответа. Индекс сообщений
читает все SimGroup игры с правками рабочего пространства (0,4 с на GF2).

### 3.2 Правки (`--allow-edits`)

Все правки пишутся **только в рабочее пространство**: файлы игры не
меняются (`apply` из §3.3 или редактор пишут их потом). Каждый вызов —
**одна операция** рабочего пространства: где запись состоит из нескольких
шагов (клон модели и объект; граф и графы соседей; скрипт, его ресурс и
объект `LuaAudioScript`), шаги склеиваются `Workspace::squash`. Ответ —
что сделано, имя операции, что отменит `undo`, и **сравнение**
(`workspace_diff`) каждого затронутого ресурса с оригиналом; `game_files:
unchanged`. Ошибка ничего не записывает.

| Инструмент | Параметры | Что делает (как в CLI) |
|---|---|---|
| `set_attribute` | `object`, `values` (`"Class.attribute": "значение"`, класс и атрибут по имени или хэш и номер), `model`, `force` | атрибуты и модель объекта SimGroup (`simgroup-set`); пустое значение — атрибут по умолчанию; модель, которую класс не покажет, отклоняется без `force` |
| `move_object` | `object`, `position` или `offset`, `rotation` (градусы X, Y, Z), `scale` | матрица `CMD_LoadMatrix` (`level::edit::set_transform`) |
| `duplicate_object` | `object`, `offset` | копия объекта в его группе с новым GUID (`level duplicate`); в ответе id копии |
| `add_object` | `group`, `template` (из любой группы), `model` или `clone_model` (+ `collision`: `mesh`, `hull`, `box`), `position`, `force` | новый объект по образцу (`level add`) |
| `remove_object` | `object` | удаление (`level remove`); сколько атрибутов других объектов ещё ссылаются на его GUID |
| `edit_string` | `entry` (хэш или имя), `text`, `language`, `table` | текст записи во всех таблицах, где она есть, или в одной; во всех колонках или одной (имена колонок — как у `strings`) |
| `add_string` | `name`, `text`, `translations`, `tables` | новая запись в таблицы языков игры (`text-add`); хэш для атрибутов SimGroup и `$NAME` для роликов интерфейса |
| `edit_script` | `stream`, `graph` (граф этапа 28 в JSON) или `remove` (имя) | компиляция графа в Lua 5.0 и байт-код, ресурс `lua` и объект `LuaAudioScript` в SimGroup потока (`script-deploy`); граф хранится в `scripts/` рабочего пространства; ошибки компиляции — ошибка инструмента с диагностикой, ничего не записано |
| `scripts` | `stream` | скрипты-графы потока и сохранённые графы (только чтение) |
| `graph_edit` | `graph` (ключ), `move_nodes`, `add_nodes`, `attach` (+ `max_links`, `max_distance`), `link`, `two_way`, `unlink`, `link_flags`, `node_flags`, `graph_flags`, `remove_node`, `rebuild_rtree` | навигационный граф (`graph-edit`); при удалении узла ссылки соседних графов перенумеровываются той же операцией; в ответе `problems()` графа |
| `undo`, `redo` | — | отмена и возврат последней операции рабочего пространства (чьей угодно: сервера, редактора, CLI) со сравнением её ресурсов |
| `project_build` | `only`, `force`, `dry_run` | сборка проекта (`--project`) в рабочее пространство одной операцией (`project build`) |
| `mod_build` | `name`, `id`, `version`, `author`, `description`, `changes` | мод формата 2 (замены, новые ресурсы и потоки) из изменений проекта, названных или всех — **только** в `mods/<id>-<версия>.zip` рабочего пространства, путь от клиента не принимается |
| `live_objects_to_workspace` | `forget` | этап 47: передвинутое в игре через связь — матрицами записей SimGroup, одной операцией со сравнением; скрытие не пишется; `forget` чистит журнал модуля |
| `validate` | `filter` | проверки: каждый изменённый ресурс читается своим разборщиком (SimGroup, `lh2`, граф, metamodel, Lua, диалог); объекты SimGroup могут показать свои модели (`level::compat::check_edit`, иначе игра падает); `problems()` графов; ссылки, **добавленные правкой**, находятся в потоке или в загруженных до него (с учётом ресурсов, добавленных рабочим пространством); конфликты с файлами игры, потоки, изменённые вне рабочего пространства; проект — что не собрано, пропавшие файлы. `ok`, `errors`, `warnings`; только чтение |

Объект называется так, как его печатают `level_objects` и `logic_graph`:
`<поток>#<ресурс>:<объект>`; группа — `<поток>#<ресурс>`. SimGroup,
которую добавило рабочее пространство и которой ещё нет в файлах игры
(`add_simgroup`, в новом потоке или в потоке игры), называется своим
ключом (`gf2/doctor/area:simgroup:5a1f0c22`), её объекты — `<ключ>:<n>`;
так их печатают `add_simgroup`, `add_object` и `level_objects`, и так их
принимают `add_object` (`group` и `template`), `move_object`,
`set_attribute`, `duplicate_object`, `remove_object`.

**Новые уровни (этап 57).** Те же соглашения: одна операция с отменой и
сравнением, в игру ничего до `apply`. Файлы читаются по абсолютному пути,
который даёт клиент.

| Инструмент | Параметры | Что делает (как в CLI) |
|---|---|---|
| `add_stream` | `name`, `parent`, `with_parent`, `tocs` (`toc[=родитель]`), `guid` | новый поток (`add-stream`, ядро `create::new_stream`): GUID с незанятым хэшем, записи во всех оглавлениях, где есть родитель; по умолчанию загружается по запросу (`StreamSet` или `stream_load`), `with_parent` — дочерний (`new-resources.md` §3.1) |

| `add_simgroup` | `stream`, `copy_of` (группа), `objects` | новая SimGroup в потоке (новом или игры): пустая или с копиями объектов другой группы под новыми GUID; атрибуты-GUID и связи между копиями переводятся на копии (`level::edit::add_group`); в ответе ключ |
| `add_resource` | `stream`, `type`, `file`, `ids`, `before`, `policy`, `alignment`, `compress` | ресурс из файла сырых данных под новыми незанятыми ids (`add-resource`) |

| `import_model` | `file` (glTF/GLB, OBJ, FBX, USD), `template` (metamodel или меш), `name`, `stream`, `collision` (`mesh`, `hull`, `box`), `format`, `retarget`, `dry_run` | `model-import`: без `name` заменяет меши образца, с `name` — новый набор (metamodel, меши, материалы, импортированные текстуры), со `stream` — в другом потоке (`ImportPlan::put_into`; общие с образцом материалы и текстуры остаются в его потоке, поэтому образец берётся из цепочки родителей — иначе предупреждение), с `collision` — своя коллизия из геометрии; в ответе id новой metamodel для `add_object` |
| `import_texture` | `texture` (ключ `tg4h`/`tg4d` или запрос), `file` (PNG, DDS) | `texture-import` |
| `collision_build` | `metamodel`, `kind`, `from` (файл модели), `dry_run` | `collision-build`: новая `hkx` из меша metamodel или файла |

В новом потоке ресурсы пишутся в порядке добавления, но SimGroup — после
всех остальных (`workspace::file_order`): как в потоках игры, цели ссылок
(текстуры, материалы, меши, коллизия, модели) идут раньше групп, которые
их ставят, даже если объект добавлен до импорта модели. `validate`
проверяет ссылки ресурсов новых потоков по их родителям
(`Workspace::load_scope`); раньше новые потоки пропускались.

Порядок для новой зоны: `add_stream` (родитель — поток уровня, например
`gf2/cuba`) → `add_simgroup` → `import_model` с `name`, `stream` и
`collision` (образец — metamodel с частью коллизии из потока-родителя или
его предков) → `add_object` (`group` — ключ группы, `template` — объект
нужного класса, `model` — id из ответа) → `validate` → `play` и
`stream_load` нового потока, или `mod_build`.

**`play`.** Способ запуска — из настроек «Играть» редактора для этой игры
(`settings.toml`, `games.<папка>.play.method`), иначе найденный
автоматически, как у CLI. Способы, которые передают игру другой программе
(Steam, лаунчеры), отклоняются: она показала бы игру на рабочем столе.
Порядок: проверка, что игра не запущена; **X-сервер игры** — Xvfb с
экраном в памяти (`-displayfd`, `-nolisten tcp`), без него `play`
отказывает до любой записи; под Wine игра идёт в виртуальном рабочем столе
размера экрана (`play::in_virtual_desktop`, как у вкладки «Игра»);
файлы прошлых запусков убираются (`restore_stale`); **без записи в игру
(этап 46)**, если модуль собран, загрузчик есть и издание известно (или
`write_game: false`, `mods: true`): рабочее пространство или моды и
`cmd.txt` собираются в папку подмен вне игры, и модуль подставляет их
игре (`docs/analysis/live-link.md` §14; в ответе `through_live_module` —
сколько файлов), иначе рабочее пространство записывается в игру
(`apply`) и `cmd.txt` для старта в уровне (этап 32) — тоже, с причиной в
`notes`;
модуль живой связи с разрешённой записью (есть загрузчик ASI) — он же
даёт игроку двигаться после старта прямо в уровне; DXVK по флагу или
настройкам. Сбой на любом шаге убирает уже записанное. Затем `play` ждёт,
пока живая связь не увидит игрока (`Status.player`), игра не завершится
или не выйдет время. Без модуля связи ждать нечего — ответ советует
снимок кадра. Процессы X-сервера получают SIGKILL, когда поток сервера,
запустивший их, завершается (`PR_SET_PDEATHSIG`): убитый сервер MCP не
оставляет невидимую игру.

**Снимок — с X-сервера `play`.** Модуль связи кадров не отдаёт, а вкладка
«Игра» редактора держит свой X-сервер; поэтому `screenshot` снимает игру,
запущенную этим сервером. Вне Unix игра запускается обычным окном, снимка
нет.

## 5. Безопасность

- **Флаги.** Без флагов — только чтение (ниже). Инструменты записи не
  попадают в `tools/list`, пока их флаг не задан; вызов по имени —
  ошибка «нет такого инструмента» (тест `the_flags_turn_the_writing_tools_on`).
  Запись в живую игру — два ключа: `--allow-game` и разрешение записи в
  самом модуле (модуль, поставленный редактором без записи, отказывает).
- **Правки — только рабочее пространство.** Инструменты `--allow-edits`
  пишут только в папку рабочего пространства (`--workspace`, проекта или
  по умолчанию); тест `every_edit_is_one_undoable_operation_and_the_game_is_untouched`
  сравнивает файлы игры до и после всех правок, корпусный тест — все файлы
  настоящей игры. Мод пишется только в `mods/` рабочего пространства.
- **Один писатель.** Рабочее пространство пишет одна программа за раз:
  блокировка ОС на файле `lock` в папке рабочего пространства
  (`WorkspaceLock`, `File::try_lock`; уходит вместе с процессом, даже
  убитым), кто держит — в `lock.holder`. Редактор держит её, пока у него
  открыто рабочее пространство; команды CLI, которые пишут (правки,
  `workspace apply/revert/undo/redo`, `project build`, `play --apply`), — на
  время команды; сервер MCP — на время одного вызова записи. Занято —
  понятная ошибка с именем держателя («open for writing in the editor
  (process N)»), ничего не записано (`a_workspace_open_in_the_editor_is_not_written`);
  если держит редактор с мостом — запрос подтверждения в редакторе (§6).
  Внутри сервера вызовы записи идут по одному (мьютекс): параллельные
  вызовы с трёх клиентов — 12 операций, ни одна не потеряна
  (`concurrent_calls_are_written_one_after_another`). Поверх этого
  остаётся проверка ревизии манифеста рабочего пространства.
- **Игра.** `apply`, `unapply` и `play` отказывают, пока игра запущена;
  `play` — только на собственном X-сервере (основной дисплей не
  используется), всё положенное в папку игры снимается `stop`, отключением
  клиента или следующим `play`/CLI (`restore_stale`).
- **Только чтение (без флагов).** Рабочее пространство открывается
  `Workspace::open_read_only`: обычное `open` чинит на диске прерванное
  сохранение, здесь починка остаётся в памяти. Состояние проекта —
  `Project::status_read_only`: обычное `status` дописывает кэш сборки.
  Если рабочего пространства нет, оно не создаётся. Пишется только кэш
  индекса в `~/.cache/doctor-toolkit/` (вне игры, как у CLI; `--no-cache`
  отключает). Тест `every_tool_answers_and_nothing_is_written` сравнивает
  каждый файл игры, рабочего пространства и проекта (размер, время, хэш
  содержимого) до и после серии вызовов всех инструментов; корпусный тест —
  размеры и время всех файлов игры.
- **Пути.** Запись — только в заданные при запуске папки: мод — в
  `mods/` рабочего пространства, граф скрипта — в `scripts/`, выгрузка —
  в `--output-dir` (имя — относительный путь без `..`). Путь к файлу
  принимают только инструменты импорта `--allow-edits` и `mods_manage`
  (`--allow-game`): они **читают** этот файл (модель, текстуру, звук,
  ролик, JSON, мод). Потоки ищутся
  только среди потоков игры (`find_stream`) и новых потоков рабочего
  пространства, имена с `..` отклоняются;
  ресурсы — только из фиксированного списка URI, путь в URI ничего не
  открывает. Читаются только файлы игры, рабочего пространства и проекта,
  заданные при запуске.
- **Данные игры — не инструкции.** Каждый ответ инструмента начинается
  с предупреждения и заключает данные в `<game-data source="инструмент">…</game-data>`;
  закрывающий тег внутри данных обезвреживается (`<\/game-data>`), так что
  строка из игры или мода не может выйти из ограды. То же сказано в
  инструкциях сервера (`initialize`). Динамические ресурсы (`game/…`)
  огорожены так же; документы и схема — наши файлы, без ограды.
- **Размер.** Списки — страницами (`offset`, `limit` с верхними пределами),
  `resource_json` — страницами по символам с `next_offset` или частью по
  `pointer`; любой ответ обрезается по `--max-response-chars` с пометкой,
  как получить остальное. 40 000 символов — около 10 000 токенов: Claude
  Code предупреждает о больших ответах и по умолчанию отклоняет ответы
  длиннее 25 000 токенов.
- **Ошибки** — результат инструмента с `isError: true` и текстом, что
  сделать (модель его видит); паника разбора не роняет сервер.

## 6. Мост с открытым редактором

Редактор (`doctor-toolkit-gui`) слушает локальный сокет Unix
`editor.sock` в своей папке настроек (`DOCTOR_TOOLKIT_CONFIG_DIR`, иначе
`~/.config/doctor-toolkit/`; `DOCTOR_TOOLKIT_BRIDGE` задаёт другой путь,
`DOCTOR_TOOLKIT_BRIDGE=off` выключает мост). Код: `doctor_toolkit::bridge`
(протокол, клиент и сервер), `crates/doctor-toolkit-gui/src/app/bridge.rs`
(сторона редактора), `crates/doctor-toolkit-mcp/src/bridge.rs` (сторона
MCP). Протокол — строка JSON на запрос и строка на ответ:

| Запрос | Ответ редактора |
|---|---|
| `{"op":"hello"}` | версия, игра, рабочее пространство |
| `{"op":"selection"}` | игра, рабочее пространство, ресурс вкладки потока (`key`), объект вкладки уровня (`<поток>#<ресурс>:<объект>`) |
| `{"op":"open","key":…}` | вкладка потока с ресурсом |
| `{"op":"show_object","object":…}` | вкладка уровня, объект выделен (`open_level_for`) |
| `{"op":"show_logic","object":…}` | вкладка графа логики, объект выделен |
| `{"op":"lend","client":…,"summary":…}` | окно «ИИ-клиент просит изменить рабочее пространство» с описанием правки; «Разрешить» — редактор отпускает блокировку и отвечает `ok`, «Отмена» — ошибка |
| `{"op":"return"}` | редактор снова берёт блокировку, перечитывает рабочее пространство, обновляет вкладки; в строке состояния — «Записано ИИ-клиентом: …» |

**Запись через редактор.** Когда вызов записи находит блокировку у
редактора, сервер MCP спрашивает его по мосту (`lend`, ждёт ответа
пользователя до 3 минут), берёт блокировку, записывает одну операцию и
отдаёт рабочее пространство (`return`). Правка оказывается в истории
редактора: «Отменить» в редакторе её убирает. Отказ или молчание —
ошибка инструмента, ничего не записано. Без моста (редактор старый, на
Windows) — ошибка с именем держателя. Режим «Прямо в игру» редактора к
правкам ИИ-клиента не применяется: они записываются только в рабочее
пространство.

Только локально: сокет в папке настроек пользователя с правами `0600`;
второй редактор мост не перехватывает (сокет отвечает — не трогать),
оставшийся от упавшего редактора файл заменяется. Windows (именованный
канал) — не сделано.
