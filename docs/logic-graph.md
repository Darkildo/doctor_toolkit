(`docs/formats/mission-logic.md` §4). Здесь она показана и правится как граф,

## 1. Шина сообщений в exe [П]

| Адрес | Что делает |
|---|---|
| 0x4DAFD0 | `sdbm(lower(имя))` |
| 0x408260 | ищет хэш в глобальной таблице сообщений `*0x1162380` (4096 корзин), создаёт запись, кладёт хэш в «ручку» объекта и увеличивает счётчики |
| 0x408980 | ручка из строки: хэш + запись в таблицу, без подписки |
| 0x4089B0 | то же и подписка объекта-получателя (0x407E60 → 0x4084D0) |
| 0x473EC0 | то же с типом данных сообщения (`"BasePtrMsgData*"`) |
| 0x408240 | ручка из строки-литерала в коде движка (`iMsgChaseStarted`, …) |
| 0x408A00 | отправка: обход подписчиков записи и вызов их обработчика (vtable +4) |
| 0x4833A0 | регистрация класса SimGroup: хэш, имя, фабрика, размер (все вызовы — из 0x688AF0) |

Каждый класс читает свой пакет атрибутов функцией-читателем (обходит пакет
через 0x43AFF0, `switch` по индексу). Строковый атрибут, который читатель
пропускает через 0x4DAFD0 → 0x408260, — имя сообщения той же глобальной
таблицы, которую рассылает 0x408A00. Так устроены атрибуты сообщений у 124
классов-пакетов из 136, у которых есть атрибуты-сообщения: гипотеза этапа 16
(«хэш `sdbm(lower)` и одна шина у всех классов») **подтверждена кодом** для
них. У остальных 12 читатель держит строку и хэширует её позже (например
`AndEventGate` 0–3, `MessageRelay` 0); для них направление выведено по
данным.

Направление: если читатель после записи ручки подписывает объект (0x4089B0,
0x407E60, 0x4084D0, 0x473EC0 или встроенная подписка у `MultiManager`) —
объект **слушает** это сообщение (пин `in`); если только записывает ручку —
**посылает** (`out`). Строка, которая хэшируется без таблицы сообщений
(0x4DAFD0 без 0x408260: имена анимаций, категорий семей), — параметр.

## 2. Схема пинов: `data/gf2/logic_schema.toml`

Генерируется `research/logic_schema.py` из декомпилированных читателей
(`research/logic_readers.py`, скрипты Ghidra в `research/ghidra/`) и SimGroup
всей игры:

```toml
[class]                      # класс объекта → категория (цвет узла)
MultiManager = "logic"
[layout]                     # пакеты нового объекта: хэш класса:число атрибутов
MultiManager = ["8a157691:1", "ffd2e5b1:1", "6df50074:19"]
[packet.MultiManager]        # атрибуты пакета класса (наследуются)
hash = "6df50074"
attrs = [
  { i = 0, pin = "in", conf = "exe", name = "trigger", name_conf = "exe", kind = "string" },
  { i = 3, pin = "out", conf = "exe", name = "send_1", name_conf = "exe", delay = 4, kind = "string" },
  …
]
```

Пины: `in` (слушает), `out` (посылает; `delay` — индекс атрибута задержки в
секундах), `link` (GUID другого объекта: больше половины значений — GUID
объектов SimGroup), `asset` (ссылка на ресурс: id, повторённый 4 раза),
`param`. Для строк без кода в читателе (или без найденного читателя)
сообщением считается атрибут, у которого не меньше половины значений — имена
сообщений exe-пинов; сторона — по тому, чьи имена совпадают (`data`).
Проверка этого правила на exe-пинах: 190 из 223 угаданы верно, 33 —
наоборот (там, где у сообщения много слушателей одного класса), поэтому
`data` слабее `exe`.

Покрытие (`doctor-toolkit logic-schema`):

## 2.1 Типы: сообщения, смысл атрибутов, перечисления (этап 73)

Имя сообщения, хэш семьи, номер заведения в атрибуте — просто строка или
число. Типы говорят, **что** это, откуда это известно и насколько надёжно.
Источник один — файлы `data/gf2/`; из них `build.rs` крейта `doctor-toolkit`
делает типы Rust (`doctor_toolkit::game_types`), а команда `types-gen` —
модуль Python с заглушкой и JSON Schema. Те же данные дают выпадающие списки
редактора логики и редактора скриптов и заметки базы знаний.

| Файл | Что в нём | Кто пишет |
|---|---|---|
| `engine_messages.txt` | 571 имя сообщения из `godfather2.exe` | скрипты Ghidra (§2) |
| `game_messages.tsv` | 41 872 имени сообщений из SimGroup игры: кто шлёт, кто слушает, где, кто ещё называет | `research/message_catalog.py` |
| `messages.toml` | описания отдельных сообщений: что делает, данные, отправители вне SimGroup, источник | руками |
| `enums.toml` | 8 перечислений значений | `research/enum_values.py` |
| `attr_types.toml` | смысл 468 атрибутов SimGroup | `research/attr_types.py` |
| `schema/gf2-types.schema.json` | JSON Schema перечислений и имён сообщений | `doctor-toolkit types-gen` |

Правило: ничего не выдумывается. У каждого списка есть источник и
уверенность (`exe`, `data`, `guess`); чего не знаем — остаётся без имени
или со словом `unknown`.

### Сообщения: открытое перечисление

`game_types::MessageId` — четыре группы:

| Группа | Что это | Сколько | Уверенность |
|---|---|---:|---|
| `Engine(имя)` | имя названо литералом в `godfather2.exe` | 571 (198 из них стоят и в SimGroup) | `exe` |
| `Game(имя)` | имя стоит в атрибутах SimGroup игры и не названо в exe | 41 674 | `data` |
| `Custom { owner, name, hash }` | новое имя мода: в игре его нет, хэш проверен | — | — |
| `Unknown(хэш)` | известен только хэш (сообщение с шины запущенной игры) | — | — |

`MessageId::from_name` и `from_hash` относят имя или хэш к группе.
`MessageId::custom(мод, имя)` — проверенное создание: имя непустое, из
печатных символов ASCII, не имя сообщения игры, и его `sdbm(lower(имя))` не
совпадает с хэшем сообщения игры (иначе игра не отличит одно от другого).
`message::collision(имя)` отдаёт сообщение игры с тем же хэшем и другим
именем. В самих файлах игры таких совпадений нет: 41 872 имени — 41 872 хэша
(проверяет `build.rs` и скрипт каталога).

`MessageId::info()` — всё известное о сообщении (`MessageInfo`):

- `senders`, `listeners` — кто шлёт и кто слушает по всей игре: класс
  пакета, номер атрибута, число объектов (`MultiManager.3 ×7`);
- `usage` — как им пользуются SimGroup всей игры: `sent_and_heard`
  (32 933), `heard_from_engine` (150), `sent_to_engine` (34),
  `heard_never_sent` (1 182), `sent_never_heard` (7 573), `engine_only`
  (373 имени exe, которых в SimGroup нет), `not_in_game`;
- `scope` — общий каталог потоков, в которых оно встречается (один поток —
  его имя; `gf2` — несколько городов; `*` — общего нет), и число потоков;
- `mentions` — какие ещё ресурсы называют имя: скрипты Lua (327 сообщений
  каталога), база очков `score` (42), ролики `trinity_seq_master` (14).
  Это строка в ресурсе, а не доказанная отправка, но она подсказывает, кто
  второй конец: из 1 182 «слышат, но не посылают» так названы 77, из 7 573
  «посылают, но не слышат» — 173;
- `data` — данные сообщения (слово `u32`). **Пока `unknown` у всех
  сообщений**: типы данных не разобраны (этапы 74 и 78);
- `summary`, `sent_by`, `conf`, `source` — из `messages.toml`, если
  сообщение там описано (сейчас 9 сообщений); иначе уверенность — `exe` для
  `Engine` и `data` для `Game`.

Каталог хранится в библиотеке сжатым (5,3 МБ текста — 0,3 МБ) и
разворачивается при первом обращении.

### Смысл атрибутов

`LogicSchema::semantic(класс, атрибут)` отдаёт смысловой тип
(`game_types::SemanticType`) и уверенность:

| Тип | Что значит значение | Откуда | Сколько |
|---|---|---|---:|
| `MsgIn`, `MsgOut` | имя сообщения, которое объект слушает или шлёт | пины `in` и `out` схемы (§2) | 210 и 143 |
| `Ref<Класс>` | GUID объекта, у которого есть пакет этого класса | не меньше 90 % значений — GUID объектов игры, и не меньше 95 % найденных объектов имеют пакет класса; берётся самый частный общий класс | 267 |
| `Res<тип>` | id ресурса этого типа (`Res<metamodel>` у `Entity.1` — `CMD_SetModel`) | id найден среди ресурсов игры, не меньше 95 % — одного типа | 115 |
| `Enum<список>` | значение перечисления | все значения атрибута есть в списке | 41 |
| `Seconds` | секунды | атрибут задержки выхода (`delay` схемы; шина берёт задержку в секундах, `0x004404F0`) и несколько прочитанных руками | 35 |
| `Money` | деньги | прочитано руками, все — `guess` | 4 |
| `Bool` | флаг | названный целый атрибут, у которого в игре встречаются только 0 и 1, — `guess` | 6 |

Уверенность 468 типов из `attr_types.toml`: `data` — 306, `exe` — 29,
`guess` — 133 (меньше трёх значений в игре или допущение). Поле `seen` —
«сколько значений подходит / сколько всего в игре». Атрибуты аудио
(`CarAudio`, `Door` 19–21 и другие) ссылаются на id, которых среди ресурсов
нет, — они остались без типа.

### Проверка правок

`logic_graph::check` сравнивает каждую изменённую SimGroup рабочего
пространства с оригиналом и с каталогом игры:

- **ошибка** — новое имя с хэшем сообщения игры (или два новых имени с
  одним хэшем);
- **предупреждение** — после правки сообщение слышат, но ни один объект
  SimGroup его не шлёт, или шлют, но никто не слышит. Сообщается только то,
  что правка ухудшила: новый слушатель «немого» сообщения или убранный
  последний отправитель. Сообщения движка не проверяются; если имя называет
  ролик или скрипт Lua, об этом сказано в тексте;
- список новых сообщений правки (`custom`).

Проверку делают `doctor-toolkit logic-check GAME`, инструмент MCP
`validate`, `doctor_toolkit.logic_check(game)` и сборка мода: новые
сообщения попадают в поле `messages` файла `mod.json`, а мод с именем,
которое совпадает по хэшу с сообщением игры, не собирается и не ставится
(`docs/mods.md` §1.1).

### Где это видно

- Вкладка «Logic»: у пина-сообщения кнопка `▾` — список имён движка и
  файлов игры, в которых есть набранный текст (в подсказке — группа, хэш,
  число отправителей и слушателей); у параметра-перечисления `▾` — значения
  списка, рядом с полем — имя текущего значения (`corleone` при `0637b907`);
  у прочих типизированных параметров — тип (`Ref<Gun>`, `Seconds`).
- Редактор скриптов: `▾` у сообщения узлов «On message», «Send message».
- `logic-graph --json`, MCP `logic_graph`, Python `logic_graph`: у пина
  поля `ty` и `label`, у сообщения — `origin` (`engine`, `game`, `custom`).
- Заметки базы знаний: `docs/kb/enums/`, `docs/kb/messages/game-messages.md`,
  колонка «Смысл» в заметках классов.

### Как обновлять

```sh
doctor-toolkit dump --type simgroup -o sg GAME      # и так же auc, pad, lua, score, trinity_seq_master
python3 research/message_catalog.py sg --mentions lua=lua --mentions score=score \
        --mentions seq=trinity_seq_master > data/gf2/game_messages.tsv
python3 research/enum_values.py sg <auc.bin> <pad.bin> > data/gf2/enums.toml
doctor-toolkit search GAME "type:<все теги type_tags.txt через запятую>" --keys --limit 0 > keys.txt
python3 research/attr_types.py sg keys.txt > data/gf2/attr_types.toml
doctor-toolkit types-gen        # JSON Schema и модуль Python
doctor-toolkit kb-gen           # заметки базы знаний
```

`build.rs` проверяет данные при сборке (два имени с одним хэшем, неизвестный
список или тип ресурса, сообщение `messages.toml`, которого нет в игре).
Корпусные тесты (`tests/corpus/types.rs`) читают игру заново и сверяют:
каталог — те же 41 872 сообщения с тем же числом отправителей и слушателей;
списки семей, городов, заведений и предметов; у каждого из 468
типизированных атрибутов — ровно столько подходящих значений, сколько
записано в `seen`.

## 3. Граф

`GraphBuilder` собирает SimGroup и сопоставляет отправителей со слушателями
по хэшу имени (регистр не важен, как в игре). Узел — объект (класс, имя
`CMD_SetName`, поток, GUID, положение, пины со значениями); виртуальные
узлы — «game code» (движок) и хаб сообщения (у сообщения больше 48 пар
«отправитель × слушатель» — провода идут через один узел). Провода:
сообщение, движок (пунктир), ссылка (точки).

Состояния сообщения в области: `connected` (посылают и слышат),
`from_engine`, `to_engine`, `never_sent` (слышат, никто не посылает),
`never_heard` (посылают, никто не слышит). `MessageIndex` — все сообщения
игры (все 2006 SimGroup, 0,5 с в release): кто посылает и кто слушает;
`LogicGraph::annotate` добавляет каждому сообщению число отправителей и
слушателей вне области, и «висящее во всей игре» отличается от «висящего
здесь».

Области (`ScopeSpec`, тот же текст в CLI, GUI и Python):

| Текст | Что |
|---|---|
| `mission:<имя>` | все потоки каталога миссии под `objectives/` или `checkpoints/` (имя — каталог, можно часть: `killingcastro`) |
| `checkpoint:<номер>` | потоки, в имени которых `cp_<номер>` |
| `stream:<поток>` | SimGroup одного потока |
| `group:<поток>#<ресурс>` | одна SimGroup |
| `level:<поток>` | поток и его предки по TOC (что загружено вместе с ним) |
| `game` | вся игра |

Запросы: кто посылает и слышит сообщение (`LogicGraph::message`,
`MessageIndex::who`, `search`), путь по проводам между двумя узлами
(`LogicGraph::path`), сводка (`overview`: узлы по категориям и потокам,
сообщения по состояниям), DOT для Graphviz (`to_dot`).

### Статистика корпуса

Вся игра: 41 872 сообщения, 57 881 отправка и 72 633 подписки в SimGroup;
32 933 сообщения посылают и слышат, 150 слышат от движка, 34 слышит движок,
1 182 слышат, но никто не посылает, 7 573 посылают, но никто не слышит
(часть из них называют Lua-скрипты, ролики и база очков `score`, см. §2.1
и §8). Числа закреплены корпусным тестом
`the_message_catalogue_is_the_messages_of_the_game`; до этапа 73 здесь стояли
числа старой схемы пинов (41 871, 58 013, 72 302).

74 миссии: 6 390 узлов, 7 052 провода, 3 278 сообщений; 1 884 связаны внутри
миссии, 220 — с движком, 1 174 висят в миссии, из них 446 — во всей игре
(тест `logic_graphs_of_every_mission_build_and_resolve_messages`).

## 4. Правка

Провод нигде не хранится: он есть, потому что `out` отправителя и `in`
слушателя содержат одно имя. Поэтому:

- **соединить** `out → in`: пустая сторона получает имя другой (у
  отправителя пусто — он становится ещё одним отправителем имени слушателя;
  у слушателя пусто — он начинает слушать сообщение отправителя); заняты обе —
  слушатель переходит на сообщение отправителя (старое он больше не слышит);
  пусты обе — обе получают новое имя (`<узел>_<пин>`, без повторов в графе);
- **разъединить**: если у сообщения один слушатель, очищается отправитель
  (исчезает ровно этот провод), иначе — слушатель;
- **очистить пин**, **задержка** (атрибут из поля `delay` схемы),
  **параметры** — запись значения атрибута;
- **добавить узел**: копия объекта того же класса (из графа, иначе из любого
  места игры: пакеты, компоненты и параметры шаблона, сообщения и ссылки
  очищены) или новый объект с пустыми пакетами раскладки `[layout]` схемы
  (`SimGroup::push_object`); вставка — как в редакторе уровня (этап 11),
  новый GUID машины `XDOCTORTKX` (`simgroup.md` §5);
- **удалить узел** — `level::edit::remove`, ссылки других объектов на GUID
  остаются (их число сообщается).

`logic_graph::edit::apply` меняет SimGroup так, как их видит рабочее
пространство, проверяет каждую `level::compat::check_resource_data` (этап
21) и записывает все изменённые группы одной операцией (Ctrl+Z). Тест
`logic_graph_edits_round_trip_in_every_mission`: 263 разъединения в 74
миссиях — у сообщения ровно на один конец меньше, возврат значения
восстанавливает все значения (в 1 случае из 263 — с другим порядком пакетов,
см. §8).

## 5. Виджет графа узлов (API для этапа 28)

`crates/doctor-toolkit-gui/src/node_graph/` не знает об игре. Вызывающий
держит `Graph`, рисует его `GraphView::show` и превращает события в правку
своей модели; сам виджет двигает только узлы и комментарии. Им пользуются
граф логики, редактор скриптов (этап 28) и граф анимации (этап 43,
`anim_graph_view.rs`: дерево входа банка `bnk`, провода — от родителя к
детям, рисовать провода нельзя — `can_connect` отказывает всем).

| Тип | Что |
|---|---|
| `Graph { nodes, wires, comments }` | всё, что рисуется; `bounds()`, `node(id)`, `comment_around(ids, text)` |
| `Node { id: NodeId, pos, title, subtitle, header_color, lines, inputs, outputs, badges, ghost }` | узел; `Node::new(id, title).input(pin).output(pin)`; размер — `size()`, место пина — `pin_pos(output, i)` |
| `Pin { label, ty, color, set, tooltip }` | пин; провод соединяет выход и вход одного `ty` (или `ANY`) |
| `Wire { from: (NodeId, выход), to: (NodeId, вход), color, style, label }` | провод; `WireStyle::{Solid, Dashed, Dotted}` |
| `Comment { id, rect, text, color }` | рамка с заголовком; перетаскивание заголовка двигает узлы внутри, угол меняет размер, двойной щелчок — переименовать |
| `GraphView` | состояние: `pan`, `zoom`, `show_minimap`, `can_connect` (своё правило), выделение (`selection`, `set_selection`), `frame_all`, `frame_selection`, `center_on` |
| `GraphView::show(ui, &mut graph, &mut menu) -> GraphResponse` | рисует и обрабатывает ввод; `menu(ui, ContextTarget)` заполняет контекстное меню |
| `GraphEvent` | `Connect { from, to }`, `Disconnect { wire }`, `Moved(ids)`, `Delete(ids)`, `Copy(ids)`, `Paste(точка)`, `Activate(id)` (двойной щелчок), `Selection(ids)`, `CommentsChanged` |
| `ContextTarget` | `Canvas(точка)`, `Node`, `Pin(PinAddr)`, `Wire(i)`, `Comment(id)` |
| `layered(&graph, only, &LayoutOptions) -> позиции` | послойная раскладка: компоненты связности полками, разрыв циклов, слои по самому длинному пути, порядок барицентрами, длинные слои — в несколько столбцов |
| `LayoutStore { positions, comments }` | файл рядом с данными: `load`, `save`, `capture(graph, ключ)`, `restore(graph, ключ)` (возвращает узлы без места) |

Мышь: левое перетаскивание узла двигает выделение, с пина — тянет провод
(зелёный пунктир, когда отпускание его создаст), по пустому месту — рамка
выделения (Shift добавляет); средняя или правая кнопка — сдвиг; колесо —
масштаб вокруг курсора; правый щелчок — меню; миникарта в углу — щелчок и
перетаскивание переносят вид. Клавиши над холстом: Delete, Ctrl+A,
Ctrl+C / Ctrl+V (события), F — к выделению, Home — всё. Узлы и провода вне
вида не рисуются; при масштабе меньше 0,35 текст не выводится.

`egui-snarl` (последняя 0.12 — под egui 0.36, Rust 1.92) и
`egui_node_graph2` (0.7 — egui 0.29) с egui 0.37 не собираются, поэтому
виджет свой.

## 6. Вкладка «Logic»

Открыть: Tools → Logic graph (Ctrl+G), кнопка «Logic graph» в просмотре
SimGroup (выбранный объект выделяется) и в панели объекта редактора уровня.
Двойной щелчок по узлу с положением (или «Show in level») открывает уровень
на зоне объекта и выделяет его; «Logic graph» там возвращает в граф потока.

- Сверху: область (Enter — загрузить), список миссий, «Auto layout»
  (выделенные узлы или все), «Frame all», переключатели Minimap, Engine,
  Links, Hubs, Empty pins, поиск сообщения или узла (Enter выделяет найденные;
  совпавшие пины помечены `»`).
- Узел: заголовок цвета категории, класс, поток, ресурс и индекс объекта;
  пины — `имя: сообщение (+задержка)`; три названных параметра; значок `!`,
  если у узла есть сообщение, которое никто во всей игре не посылает или не
  слышит. Цвет пина: голубой — сообщение, жёлтый — движок, красный — висит
  во всей игре, серый — ссылка. У списков (`send_1`…`send_8`) показаны
  занятые пины и один свободный — из него тянут новую отправку.
- Справа: выбранный узел — пины с полями (Enter записывает), задержки,
  параметры, «Show in level», «Open SimGroup», «Remove node» и «In the whole
  game»: отправители и слушатели каждого сообщения во всей игре (щелчок
  открывает поток с этим объектом). Без выделения — сводка и список висящих
  сообщений (щелчок выделяет их узлы).
- Правый щелчок: по пустому месту — добавить узел (по категориям и
  классам; в SimGroup выделенного узла), вставить, комментарий вокруг
  выделения, раскладка; по узлу — показать в уровне, открыть SimGroup,
  удалить; по пину — очистить сообщение; по проводу — разъединить.
- Каждая правка — одна операция рабочего пространства (Ctrl+Z / Ctrl+Y);
  граф перечитывается.
- Положения узлов и комментарии хранятся в
  `<рабочее пространство>/logic_layout/<область>.json` (ключ узла —
  `поток#ресурс/GUID`), данные игры не трогаются. Без файла граф
  раскладывается автоматически; новые узлы ставятся туда, где их создали.

Снимок без пользователя: `DOCTOR_TOOLKIT_GUI_LOGIC=<область>[;find=<текст>][;show]`
открывает вкладку на всё окно (`show` — затем показать найденный узел в
уровне), вместе с `DOCTOR_TOOLKIT_GUI_SHOT` (`docs/viewers.md` §5).

### 6.1 Вживую: сообщения игры на графе (этап 35)

Переключатель **«Вживую»** под панелью инструментов включает слой
`logic_live.rs` (`LiveOverlay`): пока есть живая связь с игрой
(`docs/analysis/live-link.md` §11–§12), сообщения шины игры подсвечивают
граф по мере прохождения. Источник — общая форма
`doctor_toolkit::logic_graph::trace::TraceEvent` («сообщение `hash` от A к
B в момент t», строки JSON), её же может давать прогон логики без игры
(этап 38): слой не знает, откуда события.

- **Сопоставление** (`TraceMap`): получатели — по GUID узлов (GUID может
  быть в двух SimGroup — зажигаются оба); провода — сообщения с этим хэшем
  в узлы-получатели (через хаб: в хаб и из хаба к получателю; от узла
  движка, если слушателей больше, чем объектов среди получателей);
  отправители — источники зажжённых проводов (игра отправителя не называет:
  у сообщения SimGroup нет поля «кто»), а если провода нет — узлы с выходом
  этого сообщения. Известный отправитель (у прогона) сужает провода до
  своих.
- **Без потерь при высокой частоте** (`Activity`): событие только
  прибавляет счётчики узлов и проводов и обновляет время последнего
  попадания; свечение (1,6 с) рисуется от этого времени, поэтому сотни
  сообщений в секунду стоят столько же, сколько одно. Лента хранит
  последние 400. Частые сообщения, которые журнал не пишет по одному,
  приходят счётчиками (`MessageCounts`) и зажигают все провода своего
  сообщения с нужным числом.
- **Рисунок** (поверх виджета, `GraphView::graph_to_screen`,
  `wire_screen_points`): получатель — зелёная рамка, отправитель —
  оранжевая, провод — голубой с бегущей точкой, над узлом — «in N out M»;
  красная точка — узел-получатель точки останова, красная рамка —
  получатель сообщения, на котором стоит игра.
- **Справа**, над свойствами узла, — «Вживую: сообщения игры»: где стоит
  игра, сколько сообщений, сколько на этом графе, сколько потерял журнал;
  «Только выделенное» (события выделенных узлов), «И вне графа»,
  «Очистить», «Сохранить…» (лента строками JSON); у выделенного узла —
  кнопки точек останова на сообщениях, которые он слушает (сообщение +
  GUID объекта); лента: наведение подсвечивает узлы и провода строки,
  щелчок выделяет их и наводит вид.
- **Стоп-кадр** — картинка и лента замирают, события копятся (до 20 000)
  и входят, когда его отпускают. **Пауза**, **Продолжить**, **Кадр** —
  управление игрой (`Control` модуля).

Приложение (`app/live_debug.rs`) каждый кадр отдаёт вкладкам новые
события, сообщает состояние связи и точек (`LinkView`) и отправляет их
запросы (`LiveRequest`: добавить или снять точку, пауза…); пока хотя бы
одна вкладка «вживую», поток связи просит у модуля сообщения и счётчики.

Снимок без пользователя: `DOCTOR_TOOLKIT_GUI_LOGIC=<область>;live` и
`DOCTOR_TOOLKIT_GUI_LIVE=ПОРТ:ТОКЕН` (подключиться при старте).

  отправителя можно по стеку вызова шины (объект, чей обработчик сейчас

## 9. Прогон без игры (этап 38)

Логику области (миссии, чекпоинта, потока) можно прогнать без игры: по
шагам видно, какой объект какое сообщение послал, кто его получил и что
сделал, как менялись переменные игры и таймеры. Код —
`crates/doctor-toolkit/src/logic_graph/run/`, CLI `logic-run`, вкладка
«Logic» — режим **Run**, Python `logic_run`; руководство — §24.

### 9.1 Модель исполнения

- **Акторы** — объекты SimGroup области, у которых есть сообщение на входе
  (`in`-пин схемы §2) или модель класса (§9.2). Подписка — по хэшу имени
  `sdbm(lower)`, как в шине `0x00408A00`.
- **Шина синхронная, в глубину**, как в игре: отправка вызывает обработчики
  слушателей по очереди, а то, что обработчик посылает без задержки,
  проходит целиком до того, как сообщение получит следующий слушатель
  (`0x004404F0`: задержка ≤ 0 — сразу `0x00408980`, адресно `0x00408B70`).
  В прогоне это стек работ: шаг — одна отправка или одна доставка.
- **Задержки и таймеры** — очередь по игровому времени (`0x004404F0`
  ставит сообщение на «сейчас + задержка × 1000 мс» игрового времени
  `0x010F6F2C`). Когда стек пуст, время переходит к ближайшему событию
  очереди (отложенное сообщение, конец `MissionTimer`, таймер Lua, событие
  ввода).
- **Цикл без задержки** (A → B → A) в игре переполнил бы стек; прогон
  обрывает отправки глубже 64 и пишет предупреждение. Цикл с задержкой
  идёт, пока не кончится время или шаги.
- **Детерминированность**: порядок слушателей — порядок объектов в
  области, очередь упорядочена по времени и номеру постановки, `rand()`
  `TriggerRandom` — формула `rand()` библиотеки C игры с зерном (`--seed`, по умолчанию 1).
  Одинаковый ввод даёт побайтно одинаковый журнал (тесты).
- **Переменные игры** — по хэшу имени; начальные значения и имена — из
  всех ресурсов `variabledictionary` игры (имя сопоставляется по
  `sdbm(lower(имя))`). Переменная, которой нет ни в словарях, ни в прогоне,
  читается как 0 с пометкой в журнале (в игре такой `VariableSwitch` не
  реагирует и отписывается: `0x00408840`).

### 9.2 Классы: что моделируется и на чём основано

Поведение взято из обработчиков сообщений (`vtable+4` слушателя объекта,
`объект+0x3C`) и читателей атрибутов в `godfather2.exe`; адреса — ниже.
Чего в коде не видно, то не выдумывается.

| Класс | Обработчик | Что делает в прогоне |
|---|---|---|
| `MultiManager` | `0x0047A1C0` (читатель `0x0047A320`) | по `trigger` шлёт все пары `send_N`/`delay_N` по порядку; флаг 1 атрибута 2 — по одной паре на срабатывание по кругу; атрибут 1 — остаток срабатываний (уменьшается, −1 — без конца, 0 — больше не срабатывает) |
| `MessageRelay` | `0x004CF8D0` → `0x004CF950` (общая база реле `0xE794215B`) | по `trigger` шлёт `send` сразу; с GUID в атрибуте 3 — только этому объекту. С атрибутом 2 (хэш) или 4 (GUID) — «чёрный ящик»: эти режимы не разобраны |
| `AndEventGate` | `0x00479B60` | помнит пришедшие условия 0–3; когда пришли все заданные — `send` с задержкой 5 и сброс; `reset` (6) забывает |
| `OrEventGate` | `0x00479E30` | любое заданное условие — `send` с задержкой; затем условия игнорируются `lockout` секунд (атрибут пакета `0x9DC66782`); `reset` снимает блокировку |
| `TriggerAuto` | `0x00477EF0`, подписка `0x00477DA0` | один раз по `iMsgPostSpawnInitialize` (движок шлёт его объектам загруженной SimGroup, `0x0110064C`, имя задаёт `0x00445530`) шлёт `send` с задержкой 1 |
| `TriggerRandom` | `0x0047AF60` | по `trigger` выбирает пару по весам (`rand()`) и шлёт её с задержкой |
| `VariableOperator` | `0x00476980` → `0x004768D0` | по `trigger` (0) меняет переменную (атрибут 2); операция (атрибут 3): 0 — прибавить операнд (4), 1 — вычесть, 2 — присвоить, 3 — переключить 0/1 (у операции 3 аргументы двух ветвей выведены, не прочитаны); `trigger_2` (1) подписан, но обработчик на него не реагирует |
| `VariableSwitch` | `0x00476E50` | по `trigger` шлёт **все** случаи, чьё значение равно переменной; ни одного — `default` с задержкой 4 |
| `VariableWatcher` | `0x00477B80`, `0x00477A90`, `0x00477BE0` | после `activate` (или `iMsgPostSpawnInitialize` с флагом 1 атрибута 7) проверяет переменную сразу и при каждом изменении: биты атрибута 5 — 2 равно, 1 меньше, 4 больше значения 6; шлёт `send` с задержкой 3 и перестаёт следить (флаг 4 — следит дальше); атрибут 8 — предел срабатываний |
| `MissionTimer` | `0x0090DF30` (читатель `0x0090DA30`) | `start` (0) — через `seconds − start_at` (атрибуты 3 и 9) `on_expired` (7); `stop` (1) — отмена и `on_stopped` (8); пауза (10) и продолжение (11) |
| `TestCurrentCheckpoint` | `0x008FF590` → `0x008FF4F0` | по `test` сравнивает текущий чекпоинт с атрибутом 1 (операция 0: `N < cp`, 1: `N ≤ cp`, 2: `=`, 3: `cp ≤ N`, 4: `cp < N`) и шлёт `on_true`/`on_false`; текущий чекпоинт — ввод `checkpoint:N`, без него — реакция неизвестна |
| триггеры с пакетом `TriggerBase` (`TriggerBox`…) | `0x004C1260` | 0 переключает, 1 включает, 2 выключает; вход игрока — ввод `enter:`, шлёт `on_enter` с задержкой 5, выход — `on_exit` (7). Начальное состояние не известно: пока сообщение его не задало, вход срабатывает с пометкой |
| `EnterExitTrigger` | `0x00900B30` | включение 4, выключение 5; вход и выход игрока — ввод (`on_enter` 0, `on_exit` 1); задержка 3 не применяется (не прочитана) |
| `LuaAudioScript` | `mission-logic.md` §3.2, §3.5 | `start` (1) выполняет чанк ресурса из атрибута 3 и `startup`, флаг 1 атрибута 0 — при загрузке; `stop` (2) — `shutdown` |
| остальные | — | **«чёрный ящик»**: сообщение дошло, реакция не известна; реакцию можно задать вручную (§9.4) |

Адреса сверены с exe 1.0.789.0: каждый — начало функции (функция в Ghidra или
слот таблицы методов класса). Два адреса сверку не прошли и оставлены как были:
`0x0090DF30` (`MissionTimer`) и `0x00900B30` (`EnterExitTrigger`) лежат внутри
функций `0x0090DF00` и `0x00900A70`, точки входа их обработчиков не установлены
(вопрос `docs/kb/questions/missiontimer-enterexittrigger-handlers.md`). Читатель
`0x0090DA30` начинается после заполнения, но ссылок на него в таблицах методов
не найдено.

Действия в мире (спавн, интерфейс, ролики, звук, `Checkpoint` — его
загрузка `0x008FC6F0` — дело движка и потоков) прогон не изображает: такие
объекты — «чёрные ящики», а сообщения движка (`iMsgNewCheckpointLoaded`…)
подаются как ввод. Корпус: в `mission:killingcastro` 239 акторов, из них
127 «чёрных ящиков»; во всех 74 миссиях — 4 374 и 2 725.

### 9.3 Lua

Все `LuaAudioScript` области работают в одной ВМ Lua 5.0 тулкита
(`resource/lua/vm.rs`) с макетом API игры этапа 28 (`script::sim`), как
в игре — в общем состоянии. Чанк берётся по id ресурса из GUID атрибута 3
(версия рабочего пространства, если есть). `SendMessage` скрипта идёт в
шину прогона, получатели `NewMessageReceiver` получают сообщения шины,
`FindVariable`/`VariableSet` работают с переменными прогона (изменение
будит `VariableWatcher`), таймеры `CreateTimer`/`StartTimer` стоят в той же
очереди времени. Вызовы звука, пробы `loadfile` и ошибки Lua (в игре они
глотаются) идут в журнал. В макет добавлены пустые `debug_print` и
`debug_screenprint` из Lua-кода exe: без них библиотека `aud_utils.lua`
падала на первой строке. В `gf2/globals_global` по `load` стартуют 5
звуковых скриптов игры; `aud_pc_car.lua` останавливается на
`aud_utils.lua:237` — макет не знает всех функций машины.

### 9.4 Управление и ввод

Ввод (CLI `--events`, поле **Start** и **Input now** в GUI, Python
`events`): `load` (скрипты с запуском при загрузке, затем
`iMsgPostSpawnInitialize`), `send:СООБЩЕНИЕ` (сообщение движка или любое
другое), `enter:ОБЪЕКТ`/`exit:ОБЪЕКТ` (игрок входит в триггер и выходит),
`var:ИМЯ=N`, `checkpoint:N`, `wait:СЕКУНДЫ` (сдвинуть время следующих),
`at:T:ВВОД`; через `;` или `,`. Объект — GUID (32 цифры или в скобках),
имя `CMD_SetName`, `#номер_актора` (`logic-run --actors`) или
`поток#ресурс:объект`.

Шаги: **Step** — одна отправка или доставка (или переход времени к
следующему событию), **Next message** — до следующей отправки, **To time**
— до игрового времени, **Continue** — пока есть что делать. Точки
останова — на сообщении (перед отправкой) и на объекте (перед доставкой
ему). Реакция вручную — «на сообщение X (любое) послать Y через D с»;
для «чёрных ящиков» она заменяет «неизвестно», у известных классов
добавляется к модели. В CLI — файл `--reactions`:

```json
[{"object": "#23", "on": "m8_spawn_cash", "send": [{"message": "m8_cash_spawned", "delay": 1.5}]}]
```

```sh
doctor-toolkit logic-run GAME checkpoint:737 --actors
doctor-toolkit logic-run GAME checkpoint:737 \
  -e "load; send:cp_737_loaded; send:cp_737_was_started; wait:5; enter:#19" --until 60
doctor-toolkit logic-run GAME mission:killingcastro --json -o run.json --break-message cp_739_start_now
doctor-toolkit logic-run GAME checkpoint:737 -e load --compare game.json
```

`--steps` — предел шагов (20 000), `--seed`, `--no-lua`, `--json`
(`--lines` — по записи в строке), `-o` — журнал в файл, `--original` —
без правок рабочего пространства.

В GUI режим **Run** на панели вкладки «Logic» открывает панель снизу:
кнопки шагов, ввод, точки останова, у выбранного узла — «Break on this
object» и ручная реакция, экспорт журнала (по умолчанию
`<рабочее пространство>/logic_runs/<область>.json`), сравнение, журнал
(щелчок по строке выделяет объект), очередь и переменные. На графе
провода прошедших сообщений — зелёные (ярко — в последней команде), узлы
с полученными сообщениями — значок `»N` (оранжевый у «чёрного ящика»),
точка останова — `BP`. Снимок без пользователя:
`DOCTOR_TOOLKIT_GUI_LOGIC=checkpoint:737;run=load,send:cp_737_loaded;until=12`.

```python
import doctor_toolkit as dt
r = dt.logic_run(game, "checkpoint:737", events=["load", "send:cp_737_loaded"], until=60)
[e["message"] for e in r["journal"] if e["kind"] == "send"]
```

### 9.5 Журнал и сравнение с игрой

Журнал — записи `{seq, step, time, kind, …}`: `send` (`from`, `message`,
`hash`, `to` — все получатели по порядку, `target`, `depth`), `schedule`
(`due`), `deliver` (`to`, `from`, `took`: `known`/`unknown`/`manual`,
`reaction` — что сделал объект), `variable` (`name`, `old`, `value`, `by`),
`input`, `lua`, `warning`. Участник (`from`, `to`, `by`) —
`{kind: object|engine|input|lua, label, actor, guid, class}`.

Сравнение (`--compare`, кнопка **Compare**, Python `compare=`) берёт
сообщения журнала игры и выравнивает их с отправками прогона по самой
длинной общей подпоследовательности хэшей: совпавшие (со сдвигом времени
и разницей получателей по GUID), только в прогоне, только в игре.
Сообщения игры, которых область не посылает и не слышит, по умолчанию не
сравниваются (`--compare-all` — все). Время игры и прогона совмещается по
первому совпавшему сообщению.

Журнал игры — JSON: массив событий, объект с массивом `events` (или
`journal`) или по событию в строке. Событие-сообщение — с `kind` (или
`type`, `event`) = `message`/`send` или без него; имя — `hash` (число или
шестнадцатеричная строка) или `message`/`name`; время — `sim_time_ms` или
`time` (секунды); получатели — `receivers` (или `to`): GUID строкой (32
цифры в порядке памяти или `{…}`) или объекты с `guid`. Так читается и
журнал самого прогона. Источник в игре — журнал живой связи этапа 49:
события «сообщение шины» модуля (протокол 2) несут хэш, игровое время в
мс, число слушателей и GUID до 8 получателей-объектов SimGroup — то есть
поля выше; отправителя шина не знает, поэтому сравниваются сообщения и
получатели, а не «кто послал».

### 9.6 Ограничения

- Lua `SendMessage` в игре синхронный (слушатели отработали, когда он
  вернулся); в прогоне сообщения скрипта уходят в шину после возврата из
  вызова Lua — код скрипта после `SendMessage` видит состояние до реакции.
- Порядок слушателей одного сообщения в игре — порядок подписки в таблице
  шины; прогон берёт порядок объектов области (не сверено с игрой).
- Сравнение с игрой проверено на синтетическом журнале: журнал живой
  связи этапа 49 ещё не записан на стенде.
- Начальное состояние триггеров, позиция игрока (`TriggerDistance`), время
  суток, очки, задания, ролики — вне прогона; `MissionTimer` с таймером на
  экране (флаг атрибута 6) идёт через `0x0090D790`, его конец считается тем
  же временем (не прочитано).
- Вес пар `TriggerRandom` без сообщения: игра пропускает такие пары, но
  сумма весов `+0x9C` считается в читателе (не прочитано) — прогон берёт
  сумму пар с сообщением.
