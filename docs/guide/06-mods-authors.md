# 6. Моды для авторов

## 6.1 Что такое мод

Мод — один файл `.zip`: манифест `mod.json` (название, версия, автор,
описание, адрес, игра и список заменяемых ресурсов с SHA-256 новых данных и
ожидаемых оригиналов), новые данные и, по желанию, картинка. Мод не содержит
файлов игры целиком — только заменённые ресурсы, поэтому он маленький и
совместим с другими модами, если они не трогают те же ресурсы.

## 6.2 Сборка

Сначала сделайте правки в рабочем пространстве (раздел [5](05-editing.md)) и
проверьте их в игре. Затем:

```sh
doctor-toolkit mods build "$GAME" -o hq-billboards.zip --name "HQ Billboards" \
    --mod-version 1.2 --author me --url https://example.org --preview shot.png
doctor-toolkit mods build "$GAME" -o text-fix.zip --name "Text fix" gf2/text/dd7d7050
```

Ключи (или их части) в конце выбирают, какие правки войдут в мод; без них —
все. В редакторе: **Mods** → **Build a mod from the workspace** → поля →
**Save mod file…**, или мастер **Собрать мод…** (раздел [15](15-wizards.md)).

Версия мода — номер вида `1.2`, `1.2.3` или `1.2.3-beta` (формат 3 требует
семантическую версию).

## 6.3 Проверка перед публикацией

```sh
doctor-toolkit mods info hq-billboards.zip --resources
```

показывает манифест и проверяет каждый ресурс по его SHA-256. Чтобы
проверить мод вместе с другими модами, поставьте рабочее пространство как
мод: `doctor-toolkit mods install-workspace "$GAME" --name "HQ Billboards"`
(или **Install as mod**). Он встанет последним в порядке загрузки, и
`mods apply` запишет его вместе с остальными.

Рабочее пространство и менеджер модов не пишут в игру одновременно: если
одно из них держит свои изменения в игре, другое попросит сначала вернуть
оригиналы (`workspace revert --game` или `mods unapply`).

## 6.4 Публикация

- Выкладывайте только `.zip` мода. В нём нет файлов игры, только ваши данные.
- По умолчанию мод подходит любому изданию игры: менеджер сверяет каждый
  ресурс с оригиналом игрока побайтно, и мод данных работает везде, где
  ресурсы совпадают. Если мод проверен только на определённых изданиях,
  перечислите их: `--edition 1.0.789.0 --edition 1.0.764.0` (`--edition
  this` — издание вашей игры; в окне сборки — кнопка **Only this
  edition**). На другом издании Open Mod Manager покажет «Не подходит к
  этой версии игры», и записать мод можно будет только с флажком
  «игнорировать совместимость».
- Номер версии мода (`--mod-version`) увеличивайте с каждым выпуском:
  повторная установка мода с тем же `id` его обновляет, а другие моды могут
  требовать вашу версию (`>=1.2`).

## 6.5 Зависимости и патчи поверх модов

Мод может опираться на другой мод: менять то, что тот уже изменил, или
добавлять ресурсы в созданный им поток. Сделайте так:

1. Установите и запишите в игру мод-основу (Open Mod Manager или `mods
   apply`).
2. Правьте в редакторе как обычно — вы видите игру с этим модом.
3. Соберите мод: зависимость от основы с условием `>=<её версия>`
   подставится сама (CLI напишет `depends on … >=…`), а для изменённых
   ресурсов в мод запишутся данные основы как «оригинал».

Такой мод у игрока сверяется с игрой **плюс** основой, стоит ниже неё в
списке и без неё не записывается («Нужен мод … ≥1.1»). Остальное задаётся
ключами или полями раздела **Dependencies, editions and load order**:

| Что | CLI | Смысл |
|---|---|---|
| нужен мод | `--depends id=">=1.1 <2"` | без него (выключен, не установлен) мод не записывается; версия не та — только с флажком совместимости |
| рекомендую | `--recommends id` | только подсказка игроку |
| несовместим | `--incompatible "id=<3:причина"` | пока оба включены, запись невозможна; причину видит игрок |
| порядок | `--load-after id`, `--load-before id` | пожелания: выполняются, если те моды установлены и ничто важнее не мешает |
| нужный менеджер | `--requires-manager ">=0.0.5"` | по умолчанию — эта версия программы или новее |

Условия на версии: `*`, `1.2` (ровно), `>=1.1`, `<2`, `^1.2` (до 2.0),
`~1.2` (до 1.3), через пробел — все сразу (`>=1.1 <2`). Подробно —
`docs/mods.md` §1.3, §3.2, §3.3.

Формат и правила проверки — `docs/mods.md`.

## 6.6 Мод с исполняемым кодом

Мод может нести код — модули `.asi` (32-битные DLL) для папки `scripts`
игры: нативный мод платформы `doctor_platform.asi` с новыми классами
объектов и функциями Lua (`docs/analysis/asi-platform.md`, пример —
`examples/native-class`) или обычный ASI-плагин.

```sh
doctor-toolkit mods build "$GAME" -o my-mod.zip --name "My mod" \
    --native target/i686-pc-windows-gnu/release/my_mod.dll --native-required
```

| Что | CLI | Смысл |
|---|---|---|
| модуль | `--native [имя.asi=]файл` | DLL мода; имя в `scripts/` — строчные буквы, цифры, `_`, `-` и `.asi`; не имя модуля тулкита (`doctor_live.asi` и др.) |
| без кода мод не работает | `--native-required` | пока код не поставлен, мод не записывается совсем. Без ключа игрок может взять только данные |
| обычный ASI-плагин | `--native-plain` | модуль не пользуется платформой; `doctor_platform.asi` для него не ставится |

В редакторе — поле **Executable code (.asi)** в разделе **Dependencies,
editions and load order**.

Что важно знать автору:

- такой мод пишется в формате версии 5; программы старше его не откроют и
  предложат обновиться (они поставили бы мод без кода);
- у игрока менеджер **спросит согласие** и покажет имена, размеры и
  SHA-256 ваших модулей — опубликуйте эти суммы рядом с модом
  (`doctor-toolkit mods info my-mod.zip` их печатает);
- код ставится только в издание игры 1.0.789.0;
- согласие игрок даёт один раз на мод; обновление мода с новой сборкой DLL
  ставится без нового вопроса;
- платформу и ASI-загрузчик в мод класть не нужно (и нельзя): их ставит
  менеджер;
- файл классов мода (`classes.toml`, переменная `DOCTOR_TOOLKIT_CLASSES`)
  нужен только инструментам автора, в мод он не входит.

Подробно — `docs/mods.md` §1.6.
