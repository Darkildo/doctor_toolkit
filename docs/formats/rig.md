# Риги, скелеты и скиннинг (`rcb`, `hkx`)

## 1. Где лежат скелеты

**Проверено на GF2 PC.** Скелеты лежат в ресурсах `rcb`, а не в Havok `hkx`:
все 11 258 `hkx` содержат только физику (§4). Хэши костей из таблиц мешей
находятся только в `rcb`.

| Риг | Ресурсов | Скелеты |
|---|---:|---|
| человек (`be9a8908` и др.) | 33 | `this_lod1`, `puppet`, `this_lod2`, `this_lod3` — по 102 кости |
| машины | 24 | 1–2 скелета по 20 костей (`vehicle`, двери, окна, колёса, капот, багажник) |
| реквизит роликов и уровней | 65 | 1–3 скелета по 1–13 костей (`keys`, `lighter`, `door1`, `sniper`) |

Всего 14 561 кость, 190 разных хэшей костей.

## 2. Раскладка `rcb`

`rcb` — перемещаемый образ памяти 32 бит: указатели — смещения от начала
ресурса, первый `u32` — смещение таблицы релокаций в конце: смещения всех
полей-указателей по убыванию и `0` в конце. Тот же образ используют `bnk`.
Версии 24 (9 ресурсов) и 25 (113), раскладка скелетов одинакова.

```
0x00  u32  смещение таблицы релокаций
0x04  u32  версия, 24 или 25
0x08  u32  хэш (у реквизита 0x50F92C54, как поле 0x0C у bnk; вход неизвестен)
0x0C  3 × u32  0
0x18  u32  число скелетов S
0x1C  ptr  S × скелет (24 байта)
0x20  u32  число наборов костей B
0x24  ptr  B × {u32 хэш имени, ptr → {ptr слова битовой маски, u32 число бит}}
           (фильтры скелета: число бит = число костей скелета 0, 594 из 594)
0x28..0x34 указатели и счётчик времени выполнения, в файлах 0
0x38  f32  базовый масштаб: 1.88 у людей (33 рига; их поза привязки ровно
           1.0 по высоте), 1.0 у остальных
0x3C  i32  0
0x40  ptr  локаторы: на каждый скелет {u32 число, ptr}; локатор 0x30 байт
           {u32 id, 3 × u32 0, 4 × f32, 3 × f32, i32 кость или −1}; 1 861 шт.
0x44 / 0x48  u32 / ptr  ids контейнеров, на которые ссылается риг (233 у 32
           ригов; что это за ids — не выяснено)
0x4C / 0x50  u32 / ptr  поправки позы {i32 id, u32 n, ptr n × {кватернион,
           3 × f32, i32 кость}} (2 у 46 ригов; id парами X / ~X)
0x54 / 0x58  u32 / ptr  привязки скелета: по 0x20 байт {кватернион,
           4 × f32 смещение с w = 0}, выравнивание 16 (66 у 33 ригов людей)
0x5C  ptr  {u32 число, ptr} детали blend shape — всегда пусто
0x60 / 0x64  u32 / ptr  атрибуты костей — всегда пусто
```

Имена полей `0x34…0x64` взяты из сверки с другим редактором игр EARS (этап 39) и
проверены на всех 122 `rcb`: указатель не равен нулю ровно тогда, когда он в
таблице релокаций (122 из 122), числа совпадают с размерами таблиц.
Кватернионы поправок позы и привязок единичные (5 674 и 2 178 из всех);
«поворот» локатора — нет (572 из 1 861 не единичные), его смысл не
подтверждён. Поле `0x34` (по ним — число переменных экземпляра) всегда 0.

Скелет:

```
u32 хэш имени (SDBM: "this_lod1" → 0xC109F3F1), ptr имя, u32 число костей N,
ptr иерархия, ptr обратные матрицы привязки, ptr поиск
```

- **Иерархия**, N × 16 байт: `i32 родитель` (−1 у корня, всегда меньше своего
  индекса), `i32 индекс привязки`, `i32 −1`, `u32 тип привязки`. Тип 1 —
  кость не привязана (индекс −1, 11 063 кости), тип 2 — привязана: индекс —
  номер в привязках скелета `0x54/0x58` (3 498 костей, все индексы меньше
  числа привязок, а число привязок = наибольший индекс + 1 у всех 33 ригов
  людей). В коде — `Bone::bind_index`/`bind_type`, в JSON прежние ключи
  `link`/`kind`.
- **Обратные матрицы привязки**, N × 16 f32: построчно для вектора-строки
  (Direct3D), модель → кость; последний столбец (0, 0, 0, 1). Те же 16 чисел —
  это матрица для вектора-столбца по столбцам, то есть ровно формат glTF.
- **Поиск**, N × 20 байт: `u32 хэш имени кости, 3 × u32 0, u32 индекс кости`,
  отсортирован по хэшу (двоичный поиск по хэшу).

Хэш имени кости — SDBM имени в нижнем регистре. Известные имена (111 из 190)
— `data/gf2/bone_names.txt`: строки из `godfather2.exe` (`m_pelvis`,
`l_wrist`, мышцы лица `orboris_tl`), подобранные по схеме (`l_index1..3`,
`jo_wheel_fl`), каждое проверено по иерархии, и подтверждённые хэшем на
этапе 40 (`research/name_candidates.py`) `l_elbowtwist`, `r_elbowtwist`,
`m_pelvisnull`. Неизвестны, например, кости скручивания плеча, подмышки,
волосы, клапаны одежды, руль и вспомогательные кости вокруг таза.

Поза привязки: глобальная матрица кости — обратная к её обратной матрице;
локальная — `IBM(родитель) × глобальная`. Человек стоит в T-позе, ось Y вверх,
лицом к +Z, левая сторона в +X, рост ≈ 1,0 (голова 0,83–1,0), таз на 0,54.

## 3. Связь меша со скелетом

**Проверено на GF2 PC.** Таблица костей меша (`geometry.md`, заголовок `0x38`,
`0x60`) — пары `{u32 хэш имени кости, u32 индекс кости в скелете}`. Она совпадает
с поиском скелета: для каждой пары `bones[индекс].hash == хэш`. Так находится
риг модели (в том же потоке может не быть `rcb`; тулкит ищет по всей игре).

- Записи со скиннингом (`0x06` — число влияний 1–4) хранят у вершины индексы
  **палитры** записи; палитра (`0x44`) — пары `{u8 кость скелета, u8 индекс в
  таблице костей}`. Индекс сустава для glTF — `палитра[i].0`, то есть прямо
  индекс кости скелета. Для всех палитр выполняется `таблица[индекс].1 == кость`.
- Записи без весов, привязанные к одной кости (`0x24` ≠ 0xFF, например волосы
  и голова к `m_neck2`), получают эту кость с весом 1.
- Статические записи — кость 0 (`m_root`, единичная матрица) с весом 1.

Вершины всех записей лежат в пространстве модели в позе привязки (проверено:
вершины рук в среднем в 4,5 см от `l_wrist`/`r_wrist`, вершины лица в 1 см от
своих мышц).

Экспорт в glTF (`doctor-toolkit models`): узлы костей в порядке скелета с
локальными матрицами позы привязки, `skins[0]` с обратными матрицами из `rcb`,
`JOINTS_0` (u16) и `WEIGHTS_0` (нормированы до суммы 1) у каждого примитива.
Файлы проходят glTF Validator 2.0 без ошибок.

**Для новых моделей.** Новая модель персонажа должна использовать скелет
`be9a8908` (102 кости, имена и порядок — в выгрузке `skeletons`), хранить хэши
костей в таблице костей меша и ограничивать палитру записи (в проверенных мешах до 42 костей
на запись; предел движка не установлен). Для импорта glTF → меш нужен только этот скелет; менять `rcb` не
требуется.

## 4. Havok `hkx`

**Проверено на GF2 PC**: все 11 258 файлов.

```
0x00  u32 0x57E0E057, u32 0x10C0C010
0x08  i32 пользовательская метка = 0
0x0C  i32 версия файла = 5
0x10  u8×4 правила раскладки: 4 (указатель), 1 (little-endian), 0, 1
0x14  i32 число секций = 3
0x18  i32 секция содержимого (2), i32 смещение (0)
0x20  i32 секция имён классов (0), i32 смещение имени корневого класса
0x28  char[16] "Havok-5.5.0-r1"
0x38  i32 −1, i32 −1
0x40  секции по 0x30 байт: char[19] тег + 0xFF, u32 начало данных и
      смещения от него: локальные, глобальные, виртуальные исправления,
      экспорт, импорт, конец
```

Секции: `__classnames__` (`{u32 подпись, u8 0x09, имя, NUL}`), `__types__`
(пусто), `__data__`. Виртуальные исправления `{u32 смещение объекта, u32
секция, u32 смещение имени класса}` задают класс каждого объекта; локальные
`{откуда, куда}` и глобальные `{откуда, секция, куда}` — указатели.

Классы (число файлов): `hkRootLevelContainer`, `hkpPhysicsData`,
`hkpPhysicsSystem`, `hkpRigidBody` — 11 258; `EAMaterialArray` 11 236;
`EAMaterial` 11 196; `hkpMoppBvTreeShape` + `hkpMoppCode` 7 773;
`hkpSimpleMeshShape` 4 558; `hkpStorageExtendedMeshShape` 3 193;
`hkpConvexVerticesShape` 3 024; ящики, цилиндры, сферы, капсулы, списки форм;
один файл с `hkxScene`/`hkxMesh` и ограничениями рэгдолла. Классов `hka*`
(скелеты, анимации) нет.

Полный разбор (раскладки классов, порядок записи, MOPP, запись новых
коллизий) — `docs/formats/havok.md`.
