# Havok: коллизии (`hkx`)

Редакция от 2026-11-12 (этап 18). Источники: все 11 258 ресурсов `hkx`
The Godfather II (PC), декомпиляция `godfather2.exe` (Ghidra, адреса ниже).
Код: `crates/doctor-toolkit/src/resource/hkx.rs` и `hkx/` (`graph`, `physics`,
`mopp`, `geometry`, `collision`), `import/collision.rs`; команды
`collision-export`, `collision-build`, `model-import --collision`,
`level add --collision`.

**Проверено на GF2 PC** (корпусный тест
`every_havok_packfile_parses_and_holds_physics_only`): все 11 258 файлов
разбираются и записываются обратно побайтно на трёх уровнях — секции и
таблицы исправлений, граф объектов с раскладкой заново, типизированная
физика (11 233 из 11 257 прочитанных; 24 файла с `hkxScene` не пишутся,
один файл с ограничениями рэгдолла не читается типизированно).

## 1. Пакфайл Havok 5.5

```
0x00  u32 0x57E0E057, u32 0x10C0C010
0x08  i32 пользовательская метка = 0
0x0C  i32 версия файла = 5
0x10  u8×4 правила раскладки: 4 (указатель), 1 (little-endian), 0, 1
0x14  i32 число секций = 3
0x18  i32 секция содержимого (2), i32 смещение корня (0)
0x20  i32 секция имён классов (0), i32 смещение имени корневого класса
0x28  char[16] "Havok-5.5.0-r1", NUL, 0xFF
0x38  i32 −1, i32 −1
0x40  3 × заголовок секции (0x30 байт): char[19] тег (нули), 0xFF,
      u32 начало данных, затем смещения от него: локальные, глобальные,
      виртуальные исправления, экспорт, импорт, конец
```

Секции: `__classnames__`, `__types__` (пустая), `__data__`. Каждая таблица
кончается байтами `0xFF` до кратности 16.

- **Имена классов**: записи `{u32 подпись, u8 0x09, имя, NUL}`. Это все
  классы, которые писатель Havok прошёл при сохранении (вместе с
  `hkClass`, `hkClassMember` и вложенными структурами), а не только классы
  объектов: у файла с мешем 55 имён. Подписи классов в корпусе одинаковы
  (115 разных имён).
- **Локальные исправления** `{откуда, куда}` — указатели на данные внутри
  секции (массивы, строки). **Глобальные** `{откуда, секция, куда}` —
  указатели на объекты. **Виртуальные** `{объект, секция, смещение имени
  класса}` — класс каждого объекта. Записи с `откуда = 0xFFFFFFFF` не
  используются: писатель оставляет их в конце глобальной таблицы (их
  количество надо сохранять для побайтной записи).
- В бинарном пакфайле нет описаний классов (`__types__` пуста), а в
  `godfather2.exe` нет таблиц членов: игра знает только имена, подписи и
  функции «доделки» объектов (у `hkpMoppBvTreeShape` — `0x00C08290`:
  ставит таблицы виртуальных методов и копирует `m_moppData`, размер кода и
  `m_codeInfo` из объекта кода). Раскладки ниже выведены из данных.

### 1.1 Порядок раскладки данных

Писатель Havok раскладывает объекты в глубину (проверено на всех файлах:
граф объектов, разложенный заново, совпадает побайтно):

1. объект, выравнивание 16;
2. данные, на которые он указывает локально, в порядке полей; блок сразу
   продолжается своими данными (вложенные массивы); локальное исправление
   записывается при размещении блока;
3. глобальные исправления — в порядке встречи указателей;
4. затем объекты, на которые указывают глобальные указатели, тем же
   способом (сначала потомки первого, потом второго).

Строки обычно выровнены на 16, но в одном файле (`hkxScene`) строки
упакованы сразу за блоком, который на них указывает, — граф хранит
выравнивание узла. Общие объекты (одна форма у нескольких родителей)
пишутся один раз.

### 1.3 Пространство

Формы лежат в пространстве модели, как меши: у светильника `405ae276`
(`gf2/cuba/local/vic/high/venue_127`) коллизия `dd5056e8` совпадает с
мешем до миллиметра; у тела в файлах почти всегда единичное преобразование
(у 23 988 из 27 423). Новые коллизии строятся в том же пространстве.

**Открыто:** у 1 732 из 2 252 metamodel, чьи меш и коллизия лежат в одном
потоке, границы коллизии не совпадают с первым мешем. Это зоны террейна
(коллизия покрывает другую область) и часть реквизита заведений: например,
пепельница размером 0,97 м в трёх заведениях имеет три коллизии с
разными смещениями (28,8; 12,2; −27,5), (40,9; 9,5; 1,9) — похоже на
координаты заведения. Свойство `CollisionHavok4Part.ClientSpace` у всех
`true`, преобразований частей нет; как игра сдвигает такие коллизии, не
установлено.

## 2. MOPP

`hkpMoppBvTreeShape` отвечает на вопрос «какие треугольники могут касаться
этого ящика», исполняя байт-код. Машина запроса в игре — `0x00C61BA0`
(подготовка) и `0x00C61050` (интерпретатор); `hkpMoppBvTreeShape::queryAabb`
(`0x00C31810`) сначала обрезает ящик запроса пространством кода. Порт —
`MoppCode::query` в `hkx/mopp.rs`.

**Пространство кода:** точка `p` → `(p − смещение) × масштаб`, 24 бита на
ось. Ящик запроса переводится с запасом: `min − 1`, `max + 1`, затем в ячейки
`>> 16` (8 бит), к верхней границе ещё `+1`. Havok выбирает смещение = угол
AABB меша, масштаб = 254·2¹⁶ / наибольший размер (верхняя ячейка — 254).

| Код | Байт | Действие |
|---|---|---|
| `00` | 1 | конец ветви |
| `01`–`04` | 4 | масштаб ×2ⁿ: `смещение = (смещение + xyz) << n`, ячейки мельче |
| `05`, `06`, `07` | 2, 3, 4 | переход вперёд на 8/16/24-битное расстояние |
| `09`, `0A` | 2, 3 | прибавить к смещению ключа; `0B` (5) — задать его |
| `0C` | 3 | продолжить с куска `n` (`n × 512` байт от начала кода; код «с разбиением на куски» добит `0xCD`) |
| `0D` | 5 | ничего (в начале кода включает свойства в ключ) |
| `10`–`12` | 4 | деление по x, y, z: `lo hi jump`; первая ветвь (следующий байт) — если `min < lo`, вторая (через `jump`) — если `hi < max+1` |
| `13`–`1C` | 4 | то же по диагоналям `y+z`, `y−z`, `x+z`, `x−z`, `x+y`, `x−y` (значения ×2, со сдвигом −255 у разностей), `x+y+z`, `x+y−z`, `x+z−y`, `x−y−z` (×3) |
| `20`–`22` | 3 | деление одной плоскостью `v jump` |
| `23`–`25` | 7 | деление с 16-битными переходами для обеих ветвей |
| `26`–`28` | 3 | отсечение: дальше, только если ящик пересекает `[lo, hi)` по оси |
| `29`–`2B` | 7 | отсечение по 24-битным границам в исходном пространстве |
| `30`–`4F` | 1 | ключ `код − 0x30` (+ смещение ключа) |
| `50`–`53` | 2–5 | ключ с 8/16/24/32-битным аргументом |
| `60`–`6B` | 2, 3, 5 | свойства (на ключ не влияют) |

Проверка на корпусе (23 772 кода, 1 715 684 треугольника): полный обход
кода даёт ключи всех треугольников, кроме 164 (их Havok в код не включил);
запрос по собственному ящику треугольника находит его во всех случаях,
кроме трёх плоских треугольников на верхней границе пространства кода.

**Новый код** (`mopp::build`): дерево делений `10`–`12` по медиане самой
длинной оси центров (`23`–`25` + переход `07`, если ветвь длиннее 255 байт),
в каждом листе — три отсечения `26`–`28` и ключ. Границы ячеек округляются
наружу, ящики треугольников расширены на 1 см. Проверка: для каждого
треугольника каждого меша игры новый код находит его по его ящику; на
случайных запросах находятся все пересекающие треугольники, отсечение
работает. Код в ~1,5 раза больше кода Havok (26,2 против 17,5 МБ на корпусе).

## 3. Коллизия для новых объектов

`collision-build ИГРА ПОТОК METAMODEL [--from файл.glb] [--kind mesh|hull|box]`:

| Вид | Форма | Когда |
|---|---|---|
| `mesh` (по умолчанию) | неподвижное тело, MOPP над `hkpSimpleMeshShape` (тип сварки «нет», вершины `w = 0`), новый MOPP-код | статические объекты; форма 8 430 мешей игры |
| `hull` | неподвижное тело, `hkpConvexVerticesShape`: выпуклая оболочка, плоскости отодвинуты на радиус 0,05; у модели больше чем с 256 разными вершинами оболочка строится по её крайним точкам в 266 направлениях (оси, диагонали и 252 направления равномерно по сфере): каждая — вершина настоящей оболочки, так что форма лежит внутри неё и касается её в этих направлениях | простые предметы |
| `box` | неподвижное тело, `hkpBoxShape` (в `hkpConvexTranslateShape`, если ящик не в начале координат) | грубая коллизия |

Тело — по образцу неподвижных тел игры (единичное преобразование, трение
0,5, упругость 0,4, радиус объекта по форме), свойство материала 1 и один
EA-материал — первый материал прежней коллизии metamodel (звуки и эффекты
поверхности остаются). Имена классов и подписи — как в файлах игры.
Новый `hkx` получает новые ids и встаёт перед metamodel; все ссылки
`CollisionHavok4Part.CollisionModel` metamodel (тип `hka`, `0x33A1671E`,
или `hkx`, `0x33A16735`) переводятся на него. Metamodel без части коллизии получить её
не может (добавление части не поддерживается).

Геометрия: glTF (`--from`, все треугольные примитивы с преобразованиями
узлов) или первый меш metamodel так, как он есть в рабочем пространстве
(например, после `model-import`).

API для других этапов (`import/collision.rs`):

- `attach(metamodel, mesh, kind, material, used, seed)` — новый `hkx` и
  данные metamodel со ссылками на него (без записи);
- `plan(...)` / `CollisionPlan::commit` — то же одной операцией рабочего
  пространства;
- этап 10: `ImportOptions::collision` (`model-import --collision KIND`) —
  коллизия из импортируемого glTF в той же операции, и для замены, и для
  нового набора;
- этап 11: `ModelChoice::CloneWithCollision` (`level add --clone-model …
  --collision KIND`, флажок «Own collision» в редакторе уровня) — клон
  metamodel получает свою коллизию из своих мешей.

Корпусный тест `new_collision_is_recorded_and_applied_on_copies`: все три
вида на копии `venue_127`, после `apply` поток читается, новый `hkx` стоит
перед metamodel и разбирается, его границы совпадают с мешем, новых
неразрешённых ссылок нет, отмена возвращает файлы побайтно.

## 4. Просмотр и экспорт

- `collision-export ИГРА -o КАТАЛОГ [--stream S] [--format obj|glb]`:
  треугольники всех тел в пространстве модели и JSON с телами, формами и
  материалами. Сферы, капсулы и цилиндры разбиваются на треугольники,
  выпуклые оболочки собираются по плоскостям.
- Редактор: ресурс `hkx` — список тел и каркас; в просмотре модели —
  флажок «Collision» (коллизия metamodel того же потока, показывающего
  меш); в редакторе уровня — «Collision» для выбранного объекта (части
  `CollisionHavok4Part` развёрнутой модели с их размещением). Корпусный тест
  уровней: у 23 985 объектов есть коллизия, все 2 806 `hkx` читаются и дают
  треугольники.

## 5. Открытые вопросы

1. Смещённые коллизии реквизита заведений и террейна (§1.3).
2. Новая коллизия всегда неподвижна; динамические тела (масса, инерция,
   разрушаемые предметы) не создаются.
3. Значение слов `EAMaterial` (кроме номера поверхности) и полей тела
   0x34–0x4C (кэш широкой фазы во время выполнения; у новых тел нули).
4. Проверка в игре: см. `docs/analysis/game-bench.md`.
