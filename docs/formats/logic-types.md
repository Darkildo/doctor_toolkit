# Форматы: variabledictionary, partsdb, graph и два безымянных типа

Типы, связанные с игровой логикой и SimGroup. Покрытие разное: от полного
(`variabledictionary`, `partsdb`) до заголовка (безымянные типы). Код —
`crates/doctor-toolkit/src/resource/{variabledictionary,partsdb,graph}.rs`,
экспорт — `doctor-toolkit logic-export`.

## 1. variabledictionary

Type id `0x23FB1032`, 26 ресурсов: именованные глобальные переменные
скриптов уровня (`Five_minute_timer`, `poi_p05_polch_var_active`).

**Проверено на GF2 PC**: все 26 ресурсов (98 переменных) разбираются, и
`encode(parse(x)) == x` побайтно.

| Смещение | Тип | Поле |
|---|---|---|
| 0x00 | u32 | версия, 4 |
| 0x04 | u32 | число записей N |
| 0x08 | N × 16 байт | записи, отсортированы по хэшу |
| | | область строк: NUL, затем имена с NUL; без выравнивания в конце |

Запись: `u32 хэш записи, u32 вид (0 или 1), u32 начальное значение, u32
абсолютное смещение имени`. У вида 0 значение всегда 0, у вида 1 — 0 или 1
(флаг). «Вид» — флаги записи: загрузчик игры (`0x004423F0`, издание
1.0.789.0) кладёт младшие 16 бит в запись менеджера переменных, и бит 0
означает «переменная попадает в сохранение» (63 переменные из 98). Хэш
записи — ключ переменной в сохранении; по имени игра считает второй хэш,
`sdbm` имени в нижнем регистре, для поиска из Lua (`save.md` §4).

Имена лежат не в порядке записей и не по алфавиту — вероятно, в
порядке исходного файла; кодировщик сохраняет этот порядок.

Неизвестно: хэш-функция записи (не SDBM, FNV-1a, FNV-1, djb2 и CRC-32 ни в
каком регистре).

`logic-import` меняет «вид» и значение записей и добавляет новые записи
(элементы JSON после существующих; хэш записи — любое число, не занятое
другой переменной игры); записи ресурса пересортировываются по хэшу.

## 2. partsdb

Type id `0xA6F7263E`, 68 ресурсов: базы частей персонажей
(`globalfolder/characters/allcharacters`: `player`, `wrk_male`,
`fam_granados`; `temp_male`, `temp_female`; `igc_*` в роликах) и машин
(`globalfolder/vehicles/assembly/vehicle_shared/*`: `sedan60_03`,
`jeep60_01`). Магия `0x50744442` (на диске `BDtP`). Как из базы собирается
персонаж — `characters.md`.

**Проверено на GF2 PC**: все 68 ресурсов разбираются полностью, 2 599
частей, 2 291 вариант, 1 251 набор, и собираются обратно **побайтно**
(`PartsDb::encode`, корпусный тест
`every_parts_database_parses_and_reencodes_byte_for_byte`); JSON
(`logic-export`) читается обратно без потерь.

Образ памяти без релокаций: указатели абсолютные, выравнивания нет нигде
(списки `u16` сдвигают всё, что после них, на нечётные адреса).

| Смещение | Тип | Поле |
|---|---|---|
| 0x00 | u32 | магия |
| 0x04 | u16, u16 | 0x20; версия 1 |
| 0x08 | u32 | 0 |
| 0x0C | u32 | размер ресурса |
| 0x10 | 9 × (u32 число, u32 указатель) | таблицы T0..T8 |
| 0x58 | u32 | указатель на имя базы |
| 0x5C | u32 | 0 |

| Таблица | Шаг | Запись |
|---|---|---|
| T0 части | 0x3C | `*имя, *слот (T2) или 0, 5 × u32 id меша, 5 × u32 0, *метка, u32 число, *список *тегов` |
| T1 варианты | 0x10 | `*имя, u32 0, u32 число, *список u16 — индексы частей` |
| T2 слоты | 4 | `*имя` (`head`, `upper_body`, `a_hat`; у машин — по слоту на деталь) |
| T3 пресеты | 0x0C | `*имя, u32 число, *элементы` |
| T4 блендеры | 0x0C | `*имя, u32 число, *веса` |
| T5 наборы | 0x20 | `*имя, *T8, u32 число, *первая запись T7, u32 число, *цвета частей, u32 число, *выбор пресетов` |
| T6 группы | 0x0C | `*имя, u32 число, *список *T5` |
| T7 выбор в слоте | 0x0C | `*слот T2, u32 число, *список *T1` |
| T8 описание базы | 0x48 | `u32 0, u32 вид, *имя базы, 7 × (число, указатель) таблиц T0..T6, u32 0` |

Вложенные записи:

| Запись | Размер | Поля |
|---|---|---|
| элемент пресета | 0x10 | `*имя (a_default, pattern1), *T4 или 0, u32 число, *замены` |
| замена материала | 0x0C | `u32 материал меша, u32 материал вместо него, u32 материал повреждённой машины или 0` |
| вес блендера | 0x0C | `*имя морф-цели (fat, headnawd), f32 мин, f32 макс` |
| цвета части (T5) | 0x0C | `*T0, u32 число, *{u32 материал, u32 число, *список u32 кандидатов}` |
| выбор пресета (T5) | 0x0C | `*T3, u32 число, *список *элементов этого пресета` |

**Хэши частей — идентификаторы ресурсов мешей.** Пять слов T0 с 0x08 —
последний id (`ids[3]`) ресурсов `mesh`: у персонажей `<часть>_lod1` и
`<часть>_lod2` (у 308 частей оба — `_lod1`, у 77 второго нет), у машин
`_dmg0`, `_dmg1`, `_dmg2`, `_dmg3`, `_lod2`. Совпадений 2 585 из 2 585
ненулевых. Функция, которой инструмент игры получал id мешей из имён, не
найдена: id `name_lod1` и `name_lod2` отличаются ровно на `65599⁴`, то есть
это SDBM строки, у которой после цифры LOD стоят ещё четыре символа, а перед
именем — неизвестный префикс (у одинаковых имён в разных потоках id разные).
Для игры функция не нужна: база хранит id, и новые части ссылаются на id
новых мешей.

**Материалы — CRC-32 имени** (как в `geometry.md` §6): замены пресетов,
кандидаты цветов частей.

**Вид** (T8 + 4): 2 — персонажи (два уровня детализации), 4 — машины (пять
моделей на деталь). **Метка** части — у машин кусок коллизии
(`pcollision_door`, `pcollision_wheel`), у персонажей пусто. **Теги**
(`hatCulled`, `longSleeveCulled`, `untuckedShirtCulled`, `gloveCulled`, …,
12 разных) — часть скрывается, когда надето что-то, что ставит этот флаг.

Набор владеет последовательным отрезком T7 — по одной записи на слот
(48 × 14 = 672 записи T7 в базе `player`), отрезки идут в порядке наборов.

### 2.1 Раскладка для записи

Порядок разделов: заголовок, T0, T1, T2, T5, T6, T7, T8; цвета частей всех
наборов (записи, затем списки материалов, затем кандидаты); T3, элементы
всех пресетов, их замены; выбор пресетов всех наборов; T4 и веса; списки
частей вариантов; списки вариантов T7; списки элементов выбора пресетов;
списки наборов групп; списки тегов частей; строки.

Строки уникальны и идут в порядке первого использования: имя базы; у
каждой части имя, метка (пустая строка — тоже строка), теги; варианты;
слоты; пресеты с именами элементов; блендеры с именами весов; наборы;
группы.

Пустой список указывает туда, где он был бы записан. Исключение — списки
тегов частей: пустой повторяет указатель последнего непустого списка тегов
перед ним (0 до первого). Так раскладывает исходный инструмент; игре это
безразлично, но иначе не получить побайтного совпадения.

### 2.2 Правка

- `logic-export` → правка JSON (индексы таблиц — числа, хэши — шестнадцать
  цифр) → `logic-import`: база пишется целиком, проверяются индексы.
- `doctor-toolkit partsdb add-part GAME STREAM DB --name … --slot a_hat
  --mesh <id или имя меша> [--mesh …] [--set …|--all-sets] [--only]` —
  новая часть, вариант из неё и выбор в наборах; `partsdb allow` — разрешить
  существующий вариант; обе команды пишут в рабочее пространство.
- Библиотека: `PartsDb::add_part`, `add_variant`, `allow_variant`,
  `clone_set`, `encode`.

## 3. graph

Разобран полностью на этапе 42: `navigation-graph.md` (заголовок, узлы,
рёбра, соседние графы, свойства, R-дерево, таблица путей, видимость, флаги,
раскладка; все 2 178 графов пишутся обратно побайтно).

SimGroup ссылается на GUID графа (атрибут 0 класса `PatrolRelay`, 77 раз)
и на GUID не из заголовков графов (атрибут 0 класса `0xC640736F`, 216 раз;
`0x2F92FD66` 2, `0xBB2DA0F9` 1) — не проверено, указывают ли они на значения
свойств графов (тип GUID, `navigation-graph.md` §4).

## 4. `covernodetable` (`0xDF14DA75`) — таблицы точек

682 ресурса, 52 162 записи. Тег `covernodetable` найден на этапе 40
(SDBM тега равен id типа): это, вероятно, точки укрытий. Разбор —
`crates/doctor-toolkit/src/resource/points.rs`, проверки —
`research/level_survey.py points`, корпусный тест `every_point_table_parses`.

**Проверено на GF2 PC**: обход ниже находит в каждом ресурсе ровно N записей
и заканчивается на конце данных; GUID каждой записи кончается логином автора.

| Смещение | Тип | Поле |
|---|---|---|
| 0x00 | u32 | 2 |
| 0x04 | u32 | число записей N |
| 0x08 | u32 | небольшое число (смысл неизвестен) |
| 0x14, 0x18 | u32 | небольшое число и хэш (смысл неизвестен) |
| 0x28 | | N записей |

Запись: 16 байт префикса (`u32 0, u32 0, u32 k, u32`; при `k ≠ 0` за ним ещё
28 байт — вероятно, связи, не разобраны), затем 0x7C байт:

| Смещение | Тип | Поле |
|---|---|---|
| 0x00 | 16 байт | GUID (по виду NeoGuid, `simgroup.md` §5: имя машины `XANDAYA680` и два ключа; здесь не проверялось) |
| 0x10 | 9 × f32 | поворот, строки right, up, at (обычно вокруг Y) |
| 0x34 | 3 × f32 | позиция в мировых координатах |
| 0x40 | 2 × f32 | косинусы (0,819 = cos 35°; 0,94…0,985) |
| 0x48 | 2 × f32 | радиус 25 и квадрат расстояния (40², 60², 90²) |
| 0x50 | 8 байт | |
| 0x58 | 2 × 3 × f32 | позиция на 1,3 м выше и сама позиция |
| 0x70 | 2 × f32 | |
| 0x78 | u16, u16 | вид (1, 2, 4, 8; у 21 записи ещё бит 0x2000), 10 |

Ни один GUID не совпадает с GUID объектов SimGroup, частей и состояний
metamodel; ссылок на модели нет. Значит, это не размещение моделей, а,
вероятно, точки ИИ (укрытия или позиции с конусом обзора на высоте глаз).
Редактор уровней показывает их маркерами (`docs/levels.md` §4).

## 5. `treemodel` (`0xCDB9D42B`) — модели деревьев

Тег найден на этапе 40 (SDBM тега равен id типа).


432 ресурса. Формат разобран на этапе 68 — см. `treemodel.md`: части
(ствол полосами, листья к камере, листья и ветви пальм), материалы,
вершины, как игра их рисует. На эти ресурсы ссылается
`TreeModelPart.TreeModel` в metamodel (2 351 ссылка).
