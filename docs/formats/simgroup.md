# Формат: SimGroup

`simgroup` (type id `0xCCB51828`) — размещённые игровые объекты уровня и
значения их атрибутов: здания, двери, точки появления, триггеры, логика
миссий. Магия `0x53696D47` (на диске `GmiS`).

**Проверено на GF2 PC**: все 2006 ресурсов корпуса (111 518 объектов)
разбираются, и `encode(parse(x)) == x` побайтно для каждого.
Код: `crates/doctor-toolkit/src/resource/simgroup.rs`; проверки —
`research/simgroup_survey.py`, `tests/corpus.rs`
(`every_simgroup_parses_and_names_its_objects`).

Прежняя версия этого документа описывала формат без образцов данных и
неверна почти во всём (пакеты «с размерами», FNV-1a, сентинелы). Ниже —
формат, восстановленный по файлам игры.

## 1. Общее устройство

Все значения little-endian. **Каждый указатель внутри ресурса относительный**:
цель = позиция поля + значение поля (знаковое `i32`).

| Смещение | Тип | Поле |
|---|---|---|
| 0x00 | 8 байт | нули |
| 0x08 | u32 | магия `0x53696D47` |
| 0x0C | u32 | версия, всегда 1 |
| 0x10 | u32 | хэш группы: хэш потока группы в TOC (свёртка GUID потока, `toc.md` §3) — у 1 999 групп из 2 006; 0 в семи корневых потоках `*_global`. См. §1.1 |
| 0x14 | u32 | флаги, всегда 1 |
| 0x18 | u32 | число объектов N |
| 0x1C | u32 | 0 |
| 0x20 | u32 | размер области aux |
| 0x24 | u32 | размер области строк |
| 0x28 | u32 | смещение таблицы объектов, всегда 0x30 |
| 0x2C | u32 | 0 |
| 0x30 | N × u32 | абсолютные смещения объектов, по возрастанию |

### 1.1 Хэш группы

Проверено на всех 2 006 SimGroup игры (корпусный тест
`simgroup_group_hash_is_the_stream_hash`): поле равно хэшу записи потока в
TOC. В exe 1.0.789.0 это ключ группы у менеджера SimGroup:

- загрузчик ресурса `0x00448140` ищет хэш в таблице менеджера (`+0xB0`,
  число `+0xB4`, записи «хэш, флаги», поиск `0x00447890`): флаг 4 —
  создание объектов группы откладывается;
- `0x00447070` решает, активна ли группа: по умолчанию — бит 0 флагов
  заголовка (0x14), запись таблицы с флагом 1 включает группу, с флагом 2
  выключает;
- записи в таблицу добавляет `0x00447AB0(хэш, вкл, сразу)`, а его зовёт
  действие `EnableDisableStreams` (`0x008142F0`), когда его хэша **нет** в
  загруженных TOC: тогда оно включает и выключает не поток, а группу с
  таким хэшем. Если хэш есть в TOC, действие ставит биты потока
  (`new-resources.md` §3.1), а группа приходит и уходит вместе с потоком.

Новым группам тулкит ставит хэш их потока (`level::edit::add_group`). До
этапа 84 новые группы получали хэш 0 и работали (новая зона этапа 57,
`game-bench.md` §25) — для обычной загрузки вместе с потоком поле не важно.

Затем подряд, без промежутков:

1. **aux** — 16-байтовые GUID, 12-байтовые векторы, 64-байтовые матрицы.
   Одинаковые блоки хранятся один раз и могут перекрываться.
2. **строки** — байт NUL, затем строки с завершающим NUL, выравнивание до 4.
   На каждую строку есть ссылка.
3. **пакеты атрибутов** — вплотную друг к другу.
4. **объекты** — вплотную до конца ресурса.

## 2. Пакет атрибутов

Пакет хранит атрибуты, которые добавляет один класс иерархии.

| Поле | Тип |
|---|---|
| хэш класса: SDBM имени в нижнем регистре (`sdbm("entity") = 0x38523FC3`) | u32 |
| число атрибутов класса A | u16 |
| маска умолчаний: бит i = 1 — атрибут i равен нулю и не хранится | ⌈A/8⌉ байт |
| нули до кратного 4 от начала пакета | |
| по одному u32 на каждый хранимый атрибут | |

Хранимое значение — скаляр (int, float, хэш) или относительный указатель в
область строк либо aux. Тип атрибута в файле **не записан**.

Пакеты общие: объекты с одинаковыми значениями атрибута класса ссылаются на
один пакет (12 902 пакета на 10 188 объектов в `globals_global`).

## 3. Объект

| Смещение | Тип | Поле |
|---|---|---|
| 0x00 | 28 байт | нули (место под состояние в памяти) |
| 0x1C | u8 | флаги: бит 0 всегда 1, бит 1 и бит 3 (= есть компоненты); встречаются 1, 3, 11 |
| 0x1D | u8 | 0 или 1, смысл неизвестен |
| 0x1E | u8 | число ссылок L |
| 0x1F | u8 | число пакетов P |
| 0x20 | i32 | указатель на пакет компонентов, 0 если компонентов нет |
| 0x24 | i32 | указатель на GUID объекта в aux |
| 0x28 | u32 | хэш класса объекта |
| 0x2C | L × i32 | указатели на GUID в aux: ресурсы, нужные объекту |
| | P × i32 | указатели на пакеты, от базового класса к производному |

Последний пакет — пакет класса самого объекта (110 152 объекта; у
остальных последний класс не хранит атрибутов). Первый пакет почти всегда
`CAttributeHandler` (108 938) или `CSystemCommands` (2 574).

Пакет компонентов (24 584 объекта) — обычный пакет, его значения — хэши
классов компонентов (20 классов, например `ChatterComponent`).

## 4. Типы значений и схема

Тип каждого атрибута выведен по корпусу (`research/simgroup_schema.py`) и
записан в `data/gf2/simgroup_schema.txt`: строки
`<хэш класса> <индекс> <тип> <число значений> [<имя>]`.

| Тип | Признак | Атрибутов |
|---|---|---|
| `string` | указывает в область строк | 499 |
| `guid` | указывает в aux, блок 16 байт | 499 |
| `vec3` | указывает в aux, блок 12 байт | 38 |
| `matrix` | указывает в aux, блок 64 байта | 1 |
| `float` | все значения — правдоподобные float | 1769 |
| `int` | все значения — небольшие целые | 636 |
| `hash` | остальное: хэши, битовые маски | 188 |

Всего 3634 атрибута; все значения корпуса имеют тип из схемы. Деление
int/float/hash эвристическое: булевы хранятся как int 1, а атрибут,
встреченный только с небольшими значениями, может оказаться float.

**Имена атрибутов** в исполняемом файле не хранятся. Известны 40 имён — те,
что задают ресурсы `metamodel` (таблица свойств хранит пару «имя класса,
индекс атрибута» и имя, см. `metamodel.md`): `CMD_LoadMatrix`,
`CMD_SetModel`, `CMD_SetName`, `CMD_SetInitialHealth`, двери (`CMD_DoorSpeed`,
…), `Destructible` (`CMD_SetTargetType`, …).

**Имена классов**: `data/gf2/sim_classes.txt`, 278 из 329 хэшей корпуса
(237 из 253 классов объектов), подобраны `research/sim_class_names.py` по
идентификаторам из `godfather2.exe` и файлов игры.

## 5. GUID и ссылки

GUID бывает двух видов.

- **GUID объекта** — NeoGuid: имя машины автора из 10 букв и цифр,
  первая всегда `X` и не хранится (`XCHRIST427`, `XDUMONT770`,
  `XANDAYA680`, `XDOWD1646X`), и два 28-битных ключа. В словах
  little-endian `w0..w3`: `w0 = имя[9] << 24 | ключ1 >> 4`,
  `w1 = (ключ1 & 0xF) << 28 | ключ2`, байты 8..16 — `имя[1..9]`. Текстовая
  форма — `<имя>_<ключ1>_<ключ2>_v3`, ключи по 7 шестнадцатеричных цифр;
  так устроены имена сообщений вроде
  `XCHAVEZ197_C8A0137_6EDD352_v3_social_started` (но GUID объектов с такими
  ключами в группах нет: 0 из 7 115). Схема взята из сверки с
  другим редактором игр EARS (этап 39) и проверена: у всех 111 518 объектов имя —
  буквы и цифры, машин 127; ключ1 общий у групп объектов, ключ2 у соседних
  часто отличается на 1. Байт 3 — последняя буква имени, а не случайный
  байт (раньше мы считали первые 8 байт случайными). 109 275 различных GUID
  на 111 518 объектов: 434 GUID встречаются больше одного раза (в каких
  группах и почему — не выяснялось). Имя машины — только заглавные буквы и
  цифры: у всех 111 518 объектов, у всех 2 178 `graph` и 188
  `materialswaplistresource` (их ids — тоже NeoGuid).
- **Ссылка на ресурс**: 32-битный id ресурса, повторённый 4 раза
  (`2f4fcbd4 2f4fcbd4 2f4fcbd4 2f4fcbd4`). Id — последний из четырёх id
  заголовка ресурса (`ids[3]`, колонка «ids» команды `list`). В JSON у
  такого атрибута есть поле `resource`.

Атрибуты типа `guid` в корпусе: 58 583 ссылки на объекты (`InterestingObject`
15, `NPC` 13, `FuncSpawn` 2, …), 29 065 ссылок на ресурсы, остальные —
GUID, которых нет среди объектов SimGroup (часть из них — GUID ресурсов
`graph`, см. `logic-types.md`). Типы ресурсов по ссылкам:

| Атрибут | Ресурс |
|---|---|
| `Entity` 1 `CMD_SetModel` | `metamodel` (9 897) |
| `InterestingObject` 9, `Animated` 3 | `bnk` |
| `NPC` 16, `Destructible` 11, `Item` 24, `ExecuteVFX` 7, … | `vfx` |
| `Animated` 2 | `rcb` |
| `Item` 27, `Sentient` 4 | `hkx` |
| `ChatterComponent` 0..3 | `chv` |

**Создание GUID** (`resource::neoguid`, 2026-11-13) — одна функция для
всех новых GUID тулкита:

| API | Что делает |
|---|---|
| `MachineName::new("XNAME12345")`, `MachineName::TOOLKIT` | имя машины: 10 заглавных букв и цифр, первая `X` (строчные приводятся); имя тулкита — `XDOCTORTKX` |
| `neo_guid(&машина, ключ1, ключ2)` | GUID по имени машины и двум ключам (старшие 4 бита ключей отбрасываются) |
| `guid_for_name(&машина, имя, попытка)` | детерминированный GUID из имени объекта или потока: ключ1 = FNV-1a(`имя`), ключ2 = FNV-1a(`имя/b`), по 28 бит; при попытке n > 0 — от `имя#n`. Одно имя — всегда один GUID (так проект этапа 36 получает одинаковые GUID при каждой сборке) |
| `new_guid(&машина, имя, занят)` | первый `guid_for_name` с попытками 0, 1, … , который не занят |
| `parts(&guid)`, `text(&guid)` | обратно: машина и ключи, текст `<имя>_<ключ1>_<ключ2>_v3`; `None`, если GUID не канонический |

Ею пользуются `simgroup_edit::new_object_guid` (новые объекты: уровень,
граф логики, скрипты), `create::new_stream_guid` (новые потоки: ещё и
хэш TOC не занят) и `UsedIds::allocate_guid` (ids новых `graph` и
`materialswaplistresource`: оба слова ключей свободны). До 2026-11-13 первые
8 байт были двумя FNV-1a, а байты 8..16 — `DOCTORTK`, поэтому байт 3 не был
буквой; такие GUID в рабочих пространствах остаются как есть: GUID только
сравниваются и нигде не вычисляются заново.

**Ссылки объекта** (поле L, 1 038 штук) — всегда ссылки на ресурсы, которые
объект подгружает: `Gun`, `Item`, `ThrowableItem` → `mesh`;
`TrinityGameSequence` → `trinity_seq_master`; `AICarBehavior` → `hkx`;
`Player` → `shk`; `WorldGraphPartition` → `wgi`.

## 6. Положение объекта

Трансформ — атрибут 1 класса `CSystemCommands` (`0xB390B11A`),
`CMD_LoadMatrix`: указатель на 64-байтовую матрицу в aux.

- Матрица 4×4 построчно (RenderWare `RwMatrix`): строки right, up, at,
  position; четвёртый столбец всегда `(0, 0, 0, 1)` (61 279 из 61 279).
- Ось Y — вверх: по Y уровни занимают десятки метров, по X и Z — тысячи
  (`gf2`: X −2604…1580, Y −221…123, Z −1417…1449).
- У 58 427 матриц длины строк равны 1 (чистый поворот); у остальных есть
  масштаб (триггеры `0.75 × 4 × 0.25` и т. п.).
- Трансформ есть у 61 279 объектов. Пакет `CSystemCommands` без матрицы —
  объект в начале координат или положение задаётся иначе (`Animated`,
  `PartedAnimated`: пакет есть, матрицы нет). Объекты логики
  (`MultiManager`, `TriggerRandom`, `TriggerAuto`, реле) пакета
  `CSystemCommands` не имеют — у них нет положения.

Библиотека: `SimGroup::transform(&object)`, `SimGroup::model(&object)`; в JSON
у объекта поля `position` и `model`.

## 7. Как объект попадает в игру

Сводка для будущего редактора уровней (что известно и насколько уверенно):

1. Хэш класса объекта выбирает класс движка; пакеты — атрибуты по уровням
   иерархии, базовый первым (проверено).
2. Видимая модель: `Entity.CMD_SetModel` → id ресурса `metamodel`;
   metamodel перечисляет части (`ModelPart.Model` → `mesh`,
   `CollisionHavok4Part.CollisionModel` → `hkx`, `VFXPart.Vfx` → `vfx`) с
   собственными матрицами относительно объекта (проверено по данным).
3. Мировая матрица объекта — `CSystemCommands.CMD_LoadMatrix` (проверено
   по данным; что движок умножает матрицы частей на неё — предположение).
4. Ссылки объекта (L) — ресурсы, которые надо загрузить вместе с ним.
5. Ресурс, на который ссылаются, ищется по id среди ресурсов загруженных
   потоков; как поток с нужным ресурсом попадает в загрузку — предмет
   этапа 5 (`SHDR` ids и GUID в TOC).

Чтобы добавить объект, нужно: новый GUID (ключи и имя машины),
блок GUID в aux, новые или общие пакеты, запись объекта и смещение в
таблице. Правка существующих объектов и пересчёт указателей описаны в §9,
добавление и удаление объектов — там же; как объект показывается в 3D и
правится в редакторе уровней — `docs/levels.md`.

## 8. Неизвестное

- Смысл байта 0x1D объекта и бита 1 флагов.
- Имена 3594 из 3634 атрибутов и 51 из 329 классов (`CommonNPC` и
  др. названы, `0x82222D2E`, `0x84F8C155` — нет).
- Точное деление int / float / hash / bool (см. §4).
- Что задают атрибуты 2 и 3 `CSystemCommands` (int, почти у всех объектов 1).

## 9. Запись и правка

Код: `crates/doctor-toolkit/src/resource/simgroup_edit.rs`, запись —
`SimGroup::encode`.

**Модель.** Разбор запоминает у каждого атрибута-указателя не сырое `u32`, а
цель: смещение в области aux или строк (`Attr::target`). Объект хранит
смещения своего GUID и ссылок в aux. `encode` вычисляет все относительные
указатели заново по месту поля, поэтому пакеты могут менять размер, порядок и
общих владельцев.

**Что меняется.**

| Метод | Что делает |
|---|---|
| `set_attr(объект, слот, индекс, значение)` | значение атрибута пакета `objects[объект].packets[слот]`; `None` или ноль — умолчание |
| `set_class_attr` | то же по хэшу класса |
| `set_transform`, `set_position` | `CSystemCommands.CMD_LoadMatrix`; `Transform` раскладывает матрицу на положение, поворот (градусы вокруг X, затем Y, затем Z, оси неподвижны) и масштаб |
| `set_model` | `Entity.CMD_SetModel` — GUID-ссылка на `metamodel` |
| `set_link` | ссылка объекта (поле L) |
| `duplicate_object(объект, GUID)` | копия записи объекта в конце таблицы с новым GUID; пакеты, список компонентов и ссылки **общие** с исходным |
| `copy_object_from(группа, объект, GUID)` | копия объекта другой группы: пакеты переносятся (строки и блоки aux — в свои области) и делятся с равными пакетами этой группы |
| `remove_object` | удаляет запись и пакеты, которыми пользовался только этот объект; индексы следующих объектов уменьшаются |
| `references_to(GUID)` | атрибуты, где хранится GUID объекта (что останется висеть после удаления) |

**Новые объекты.** Запись объекта дописывается в конец (порядок остальных
не меняется), GUID — `new_object_guid`: канонический NeoGuid машины
`XDOCTORTKX` с ключами из «зерна» (§5, `resource::neoguid`); GUID-ссылки на
ресурсы и уже занятые GUID группы отвергаются.
Блок GUID добавляется в aux, и при записи aux и строки раскладываются
заново (§ выше), поэтому удаление добавленных объектов возвращает исходные
байты. Корпусный тест `objects_insert_and_remove_in_every_simgroup`: во всех
2 006 группах три дубликата (один перемещён) — разбор совпадает, прежние
объекты не изменились, запись стабильна, удаление дубликатов даёт исходные
байты; копия объекта «из другой группы» и удаление случайного объекта —
разбор совпадает с ожидаемым. Ссылки других объектов на удалённый GUID не
меняются; что с ними делает игра, не проверялось.

Значение проверяется по виду атрибута: хранимое значение сохраняет способ
хранения (int, float и hash взаимозаменяемы — это одно слово; строка, GUID,
вектор и матрица — нет), неустановленный атрибут проверяется по схеме.
Пустая строка и нулевой скаляр означают умолчание: бит маски ставится,
значение не хранится (в корпусе нет ни одного хранимого нуля и ни одной
пустой строки).

**Общие пакеты — копия при записи.** Объекты с одинаковыми значениями класса
делят пакет (31 141 общий пакет в корпусе). Правка значения одного объекта
даёт этому объекту копию пакета в конце списка; если результат совпал с
другим пакетом того же класса, объект переходит на него, а пакет, которым
никто не пользуется, удаляется. Вернув значение, получаем исходные байты.

**Строки и aux.** Новая строка или блок aux берутся из области, если там уже
есть такие же байты (для aux — на границе 4 байт), иначе дописываются в
конец. Блоки aux общие и перекрываются (4 880 перекрытий в корпусе), поэтому
на месте ничего не меняется. После правки, которая добавила данные, `encode`
раскладывает области заново:

- aux: остаются только байты, на которые кто-то ссылается (в корпусе в aux
  нет ни одного байта без ссылки, так что удаляются только блоки, брошенные
  правками); выравнивание 4 сохраняется. Если в группе есть атрибут
  неизвестного вида (`Value::Bytes`, в GF2 таких нет), aux не сжимается;
- строки: NUL, затем каждая строка один раз в порядке первой ссылки из
  пакетов, дополнение до 4. Так устроены все 2006 групп игры (проверено
  `research`-скриптом: все ссылки на начало строки, ни одной строки без
  ссылки, порядок — порядок первой ссылки).

Неизменённая группа пишется побайтно как была; после скалярных правок
области пишутся как были.

**Проверка.** Тест корпуса `random_simgroup_edits_reparse_with_the_edited_values_only`:
во всех 2006 группах 26 637 случайных правок (все виды значений, умолчания,
перемещения), запись, разбор: правленые значения на месте, все остальные
значения, классы, GUID, ссылки и компоненты как в оригинале, повторная запись
стабильна. Тест `exported_logic_json_imports_back_without_changes`: JSON
каждой группы возвращается без изменений, а перемещение объекта через JSON
даёт ровно одну правку (1510 групп).

**В игре** (стенд `tools/game-bench.sh`, теневая копия): группа
`gf2/frontend` #46 с изменёнными `RenderingParams` (скаляры) и строкой
`TextBox` (область строк разложена заново, ресурс +44 байта) загружается,
игра доходит до меню «Select Profile». Видимого эффекта эти атрибуты на
титульном экране не дают; проверка видимой правки в игровом уровне — в
списке открытых проверок (`docs/analysis/game-bench.md`).

**JSON.** `logic-export` пишет в документ `stream`, `resource`, `type`, `id`;
`logic-import` сравнивает документ с ресурсом и пишет только отличия
(`logic_import::apply_json`): значения атрибутов (удалённый из документа
атрибут становится умолчанием), поля объекта `position` и `model` (они
важнее матрицы и GUID, если изменены оба). Объекты и пакеты сопоставляются
по порядку и сверяются по классу и GUID. Значение `null` у float (так JSON
пишет NaN) не меняется.
