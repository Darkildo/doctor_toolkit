# Формат: дельта ресурса

Дельта — разница между двумя версиями одного ресурса, записанная как список
операций над элементами с устойчивыми адресами: «добавить эти объекты, задать
эти атрибуты». Её можно наложить не только на ту версию, с которой она снята,
но и на изменённую: мод, собранный поверх чужого мода, переживает его
обновление, а два мода, добавившие по объекту в одну SimGroup или по зоне в
один город, работают вместе.

Ядро библиотеки — этап 109. С этапа 110 дельты
— часть формата мода (версия 6): сборка мода кладёт дельту вместо ресурса,
менеджер модов сворачивает дельты включённых модов (§12, `docs/mods.md`
§1.7, §2, §3.4).

Код: `crates/doctor-toolkit/src/resource/delta/` (`mod.rs` — общее,
`simgroup.rs`, `lh2.rs`, `partsdb.rs`, `wgi.rs`). Тесты: модульные на
миниатюрной игре (`delta/game_tests.rs`), корпусные
(`tests/corpus/delta.rs`), фаззинг (`fuzz/fuzz_targets/delta.rs`).

## 1. Типы и адреса

| Тип | Адрес элемента | Операции |
|---|---|---|
| `simgroup` | GUID объекта | добавить объект с его пакетами, убрать объект, задать атрибут `класс.индекс`, матрицу, модель |
| `lh2` | хэш строки и столбец языка | задать текст, добавить строку |
| `partsdb` | имя части, варианта, набора, слота | добавить часть, добавить вариант, разрешить вариант в наборе |
| `wgi` | GUID потока ячейки | добавить ячейку, убрать ячейку |

У остальных типов дельт нет: `delta::kind_of(type_id)` возвращает `None`, и
ресурс хранится целиком.

## 2. Документ

Дельта — документ JSON в UTF-8:

```json
{"format":1,"kind":"lh2","ops":[
  {"op":"set","hash":"00000002","language":"0","old":"World","text":"Mondo"},
  {"op":"add","hash":"00000007","texts":[{"language":"0","text":"Seven"}]}
]}
```

- `format` — версия формата документа, сейчас 1 (`delta::FORMAT`). Документ
  с большей версией отвергается: в нём могут быть операции, которые эта
  версия программы молча пропустила бы.
- `kind` — `simgroup`, `lh2`, `partsdb` или `wgi` (тег типа ресурса).
- `ops` — операции в порядке наложения; у каждой поле `op`.
- Неизвестные поля и операции — ошибка разбора, а не пропуск.

**Канонический вид.** `Delta::to_bytes` пишет документ без пробелов, ключи —
в порядке полей структур, списки — в порядке операций; необязательные поля со
значением по умолчанию не пишутся. В документе нет ни одного словаря с
произвольными ключами, поэтому порядок не зависит от хэш-таблиц: одна и та же
дельта всегда даёт одни и те же байты (и один SHA-256). Тесты:
`Delta::parse(b).to_bytes() == b` для каждой дельты, которую выдал `diff`
(модульные и корпусные), и побайтно закреплённые документы `lh2`, `partsdb`,
`wgi` в `game_tests.rs`.

**Числа.** Хэши и id ресурсов — восемь шестнадцатеричных цифр в строке, GUID
— 32 цифры (как в JSON SimGroup). `f32` пишется числом, а не конечное
значение (NaN, бесконечность) — строкой из восьми шестнадцатеричных цифр его
битов: JSON таких чисел не знает, а дельта обязана вернуть те же биты.

## 3. Правило точности

Сборка мода кладёт дельту вместо ресурса, только если

```text
apply(diff(база, моё), база) == моё      — побайтно
```

и документ занимает в файле мода меньше места, чем ресурс (правило размера,
§12).

Это проверяет сам `diff`: он накладывает документ, **прочитанный обратно из
своих байт**, на базу и сравнивает с «моим». Не совпало или изменение не
выражается операциями — `diff` возвращает `None`, и ресурс остаётся целым.
Неверной дельты он не возвращает. `delta::exact(type_id, база, моё)` даёт
байты документа и повторяет проверку уже на них.

Что не выражается и потому даёт `None`:

| Тип | Изменение |
|---|---|
| `simgroup` | заголовок группы (версия, хэш, флаги); класс, флаги, ссылки (`links`), набор классов пакетов или компоненты существующего объекта; порядок объектов; новый объект не в конце; правка объекта, GUID которого в группе не один |
| `lh2` | удалённая строка; версия, флаги, список языков таблицы |
| `partsdb` | всё, кроме частей и вариантов, добавленных в конец, и вариантов, добавленных в выбор слота набора (или ставших единственным выбором): правка части, новый слот, пресет, блендер, набор (в том числе `clone_set`), группа |
| `wgi` | изменённая таблица потоков; изменённая существующая ячейка; новая ячейка в кольце с другой |

## 4. Наложение на изменённую базу

`apply` накладывает то, что есть к чему приложить, и
возвращает `Applied`:

| Поле | Что в нём |
|---|---|
| `data` | новые данные ресурса; если не применилась ни одна операция — сама база, байт в байт |
| `applied` | число применённых операций |
| `skipped` | пропущенные операции: номер, адрес, причина (`operation 1 (object …): the object is not in the group`) |
| `conflicts` | операции, применённые поверх значения, которого автор не видел: в базе было ни «старое», ни «новое» значение. Операция побеждает, запись называет объект и атрибут (или строку и язык) |

| Случай | Что происходит |
|---|---|
| цели операции нет (объект, строка, язык, набор, слот, часть, ячейка, нужный ячейке поток) | операция пропускается, в `skipped` — причина; остальное применяется |
| у объекта нет пакета класса, у класса меньше атрибутов, атрибут хранит значение другого вида | пропуск с причиной |
| добавляется элемент с занятым адресом: GUID объекта, хэш строки, имя части или варианта, поток ячейки | **ошибка**, ресурс не меняется: адреса уникальны, и две дельты, добавляющие один адрес, не могут быть правы обе |
| атрибут или текст уже равен новому значению | операция считается применённой, конфликта нет |

Операции «задать» несут значение, которое автор менял (`old`), — по нему и
находится конфликт двух дельт, задающих один атрибут.

## 5. `simgroup`

```json
{"format":1,"kind":"simgroup","ops":[
  {"op":"remove","object":"<GUID>"},
  {"op":"set","object":"<GUID>","attribute":"38523fc3.3","old":{"int":1},"new":{"int":2}},
  {"op":"transform","object":"<GUID>","old":[[…],[…],[…],[…]],"matrix":[[…],[…],[…],[…]]},
  {"op":"model","object":"<GUID>","old":"70010001","model":"12345678"},
  {"op":"add","object":"<GUID>","class":"38523fc3","flags":3,"flags2":1,
   "links":["<GUID ресурса>"],
   "components":{"class":"…","count":2,"attrs":[…]},
   "packets":[{"class":"b390b11a","count":4,"attrs":[
     {"index":1,"value":{"matrix":[[…],[…],[…],[…]]}}]}]}
],"layout":{…}}
```

| Операция | Смысл |
|---|---|
| `remove` | убрать объект и пакеты, которыми пользовался только он (`SimGroup::remove_object`) |
| `set` | атрибут `attribute` = `<хэш класса>.<индекс>` (`b390b11a.1`); `new` нет — умолчание; `old` нет — было умолчание |
| `transform` | мировая матрица, `CSystemCommands.CMD_LoadMatrix` (4×4 построчно: right, up, at, position) |
| `model` | `Entity.CMD_SetModel` — id ресурса `metamodel`; без `model` — модель снята |
| `add` | новый объект в конец группы со всеми пакетами. Пакет, равный пакету группы, делится с ним, строки и блоки aux вносятся в свои области — это `SimGroup::copy_object_from` |

`transform` и `model` — те же правки атрибута, названные отдельно, чтобы
отчёт о конфликте и просмотр мода говорили «матрица» и «модель»; `diff`
пишет их, когда оба значения — матрицы (или умолчание и матрица) и id
ресурса (или умолчание).

**Значения**: `{"int":-7}`, `{"float":0.5}`, `{"hash":"0000abcd"}`,
`{"string":"door_01"}`, `{"guid":"<32 цифры>"}`, `{"vec3":[x,y,z]}`,
`{"matrix":[[…],[…],[…],[…]]}`, `{"bytes":"<hex>"}` (блок aux атрибута
неизвестного вида). Int, float и hash — одно слово в файле; два скаляра
равны, когда равны их слова.

**Объект находится по GUID** (первый с таким GUID). Если GUID правленого или
удалённого объекта встречается в группе больше одного раза, `diff` дельту не
делает.

Имён классов и атрибутов в документе нет: они берутся из таблиц программы и
от версии к версии пополняются, а байты дельты должны оставаться теми же.
Имена пишутся только в сообщениях (`Entity.CMD_SetInteriorLit`).

### 5.1 Раскладка (`layout`)

Это ответ на главный риск этапа: **воспроизводит ли запись SimGroup после
`apply` байты автора? Одними операциями — нет.** Операции говорят, что лежит
в группе, но не где: `SimGroup::encode` пишет пакеты в порядке списка,
новые блоки aux — в порядке появления, строки — в порядке первой ссылки, а
всё это зависит от истории правок:

- объект A перемещён, затем B, затем снова A — матрица A оказывается после
  матрицы B; переместить каждый по разу — наоборот;
- дубликат (`duplicate_object`, затем перемещение) сначала получает блок
  GUID, потом матрицу; `add` вносит пакеты, потом GUID;
- правка общего пакета даёт копию в конце списка, правка пакета с одним
  владельцем меняет его на месте; что из двух случится, зависит от того,
  удалён ли к этому моменту второй владелец;
- в файлах игры равные пакеты не всегда общие: дубликат объекта делит пакет
  своего образца, а `add` берёт первый равный.

Замер (§9): одни операции дают байты автора в 100 % случаев только для одной
правки атрибута, одного перемещения и удаления; для дубликата — в 53 %, для
двенадцати смешанных правок — в 11–13 %.

Поэтому, когда операции дают ту же группу в другой раскладке, `diff`
добавляет в документ `layout` — куда писатель кладёт данные **на той базе, с
которой снята дельта**:

```json
"layout":{"base":"<SHA-256 базы>",
  "packets":[[0,82],[83,1],[82,1]],
  "users":[[4,1,37]],
  "aux":[[0,2352],[2416,64],[2352,64],"00ff"],
  "aux_pointers":[[12,2400]],
  "strings":[[0,5],"забытая строка",[5,2]],
  "string_pointers":[[3,17]]}
```

| Поле | Смысл |
|---|---|
| `base` | SHA-256 базы. На любой другой базе `layout` не используется |
| `packets` | порядок пакетов: отрезки `[первый, число]` номеров пакетов того, что дали операции |
| `users` | `[объект, слот, пакет]`: объект пользуется другим из двух равных пакетов (слот после последнего пакета — список компонентов) |
| `aux` | область aux: отрезки `[смещение, размер]` области, которую дали операции, и байты без ссылок (hex) — их оставляет правка, которую потом отменили |
| `aux_pointers` | `[номер указателя, смещение]`: указатель, который смотрит не туда, куда ведёт его отрезок (в области бывают одинаковые блоки) |
| `strings` | область строк: отрезки `[первая, число]` номеров строк и строки без ссылок |
| `string_pointers` | то же для указателей на строки |

Пустой список — «оставить как дали операции». Номер указателя — его место в
обходе: GUID и ссылки каждого объекта по порядку, затем значения пакетов.

**Раскладка только переставляет данные и не меняет ни одного значения.**
Указатель переходит за своим блоком, а `apply` перед записью сверяет: байты
блока (или строка) по новому адресу равны прежним, пакет, отданный объекту
через `users`, равен его пакету. Иначе — ошибка «the layout of the delta
does not fit», группа не пишется. То есть содержимое группы всегда задают
операции, и раскладка не может протащить в игру правку, которой в них нет.

На изменённой базе результат пишется обычной записью `SimGroup::encode` —
как после тех же правок, сделанных руками.

## 6. `lh2`

```json
{"op":"set","hash":"0266681f","language":"en","old":"Fredo","text":"Alfredo"}
{"op":"add","hash":"5d0c7e11","texts":[{"language":"en","text":"New"},{"language":"cs","text":"Nový"}]}
```

- Столбец называется кодом языка; у таблицы без списка языков (текстовые
  потоки игры держат по одному языку) столбцы — `0`, `1`, …
  (`StringTable::column_names`).
- `add` на таблице с другим набором языков: столбец, для которого в операции
  нет текста, получает первый текст операции — строка видна на любом языке.
- Запись `lh2` каноническая (`to_bytes(parse(x)) == x`), раскладки нет.

Попутно: `navigation::unpack::apply_strings_adding` — импорт документа
`text-export`, который добавляет записи с неизвестным хэшем (нужен текст в
каждом столбце). `apply_strings` для прежних вызывающих не изменился:
неизвестный хэш — ошибка.

## 7. `partsdb`

```json
{"op":"add_part","name":"cap","slot":"a_hat","models":["00000077","00000000","00000000","00000000","00000000"],"tags":["hatCulled"]}
{"op":"add_variant","name":"cap","parts":["cap"]}
{"op":"allow","set":"fam_granados","slot":"a_hat","variant":"cap"}
```

Индексы частей и вариантов в разных версиях базы разные (мод ниже добавил
свои), имена — одни. `allow` с `"only":true` делает вариант единственным
выбором слота. Имена сравниваются без учёта регистра, как в
`PartsDb::part_index`. Запись каноническая.

## 8. `wgi`

```json
{"op":"remove","stream":"<GUID>"}
{"op":"add","stream":"<GUID>","centre":[20.0,3.0,0.0],"radius":11.4,
 "box_min":[10.0,0.0,-4.0,1.0],"box_max":[30.0,6.0,4.0,1.0],
 "kind":0,"flags":0,"lod_mask":1,"name_hash":"…","needs":["<GUID потока-родителя>"]}
```

- `add` несёт все поля ячейки (`resource::wgi::Cell`); хэш потока — свёртка
  GUID. Поля с обычным значением не пишутся: `min_distance`, `max_distance`
  (0), `name_hash` (0), `linked_stream` (`fe16702f`), три поля, которые игра
  не читает.
- Нужные потоки (`needs`) названы GUID: место потока в таблице в разных
  версиях сетки разное. Список кладётся в пул туда, где такие слова уже
  есть, иначе дописывается (`WorldGrid::intern_list`).
- Новая ячейка стоит в своём кольце.
- `remove` чинит кольцо и убирает слова в конце пула, на которые никто не
  ссылается (`WorldGrid::trim_pool` — то же делает
  `level::world_grid::remove_zone_cell`).

## 9. Замеры на корпусе

The Godfather II PC 1.0.789.0, `EARS_GF2_DIR=… cargo test --release --test
corpus delta::`, 2026-11-18. Файлы игры только читаются.

**SimGroup**, тест `simgroup_deltas_give_the_authors_bytes_back`: все 2 006
групп, 10 сценариев по 4 раза с разными объектами и значениями. Правки
делаются так, как их делают программы: каждая записывается и группа читается
заново (редактор) либо все на одной разобранной группе (сборка проекта).
«Случаев» меньше там, где в группе нет объекта с матрицей.

| Сценарий | Случаев | `exact` дал дельту | Из них хватило одних операций | Дельта / ресурс, байт в среднем |
|---|---|---|---|---|
| перемещён один объект | 6 040 | 6 040 (100 %) | 100,0 % | 336 / 13 475 |
| перемещён A, перемещён B, снова A | 6 040 | 6 040 (100 %) | 67,8 % | 564 / 13 482 |
| задан один атрибут | 8 024 | 8 024 (100 %) | 100,0 % | 147 / 10 357 |
| заданы четыре атрибута | 8 024 | 8 024 (100 %) | 94,3 % | 457 / 10 386 |
| дубликат объекта | 8 024 | 8 024 (100 %) | 53,7 % | 809 / 10 468 |
| дубликат и ещё одно перемещение копии | 8 024 | 8 024 (100 %) | 53,1 % | 809 / 10 468 |
| копия объекта другой группы | 8 024 | 8 024 (100 %) | 52,3 % | 813 / 10 469 |
| удалён объект | 8 024 | 8 024 (100 %) | 100,0 % | 98 / 10 192 |
| 12 смешанных правок, каждая записана | 8 024 | 8 024 (100 %) | 11,1 % | 2 726 / 10 523 |
| 12 смешанных правок, одна запись | 8 024 | 8 024 (100 %) | 12,8 % | 2 687 / 10 518 |

Итого 76 272 набора правок, все возвращаются побайтно. Без `layout` цель
этапа («на всех 2 006 SimGroup случайные правки, `apply(diff)` даёт те же
байты») не достигалась: смешанные правки сходились в каждом восьмом случае.

**Изменённая база**, тест
`simgroup_deltas_apply_to_a_changed_base_as_the_edits_by_hand`: 2 006 групп
из 2 006. Автор делает шесть смешанных правок; «другой мод» добавляет в базу
объект, копирует, удаляет (в 1 369 группах — где есть второй нетронутый
объект) и перемещает объекты, которых автор не трогал. Дельта, наложенная на
такую базу, разбирается, записывается как читается и по объектам, классам,
GUID, ссылкам, компонентам и значениям равна тем же правкам, сделанным
руками на этой базе; пропусков и конфликтов нет.

**Остальные типы** — все ресурсы корпуса:

| Тип | Ресурсов | Правки | `exact` | На изменённой базе = правкам руками (побайтно) |
|---|---|---|---|---|
| `lh2` | 21 | три текста, две новые строки | 21 | 21 |
| `partsdb` | 68 | часть, вариант из неё и старой части, разрешение в наборе | 68 | 68 |
| `wgi` | 28 | две новые ячейки с родителем из таблицы, удалена ячейка игры | 28 | 28 |

**Состояние файлов игры при замере.** `applied.json` рабочего пространства и
менеджера модов пусты (в игру ничего не записано), и все 2 325 файлов
эталона `_doctor_toolkit/reference.json` совпадают с ним по SHA-256. Сам
эталон снят с этой же копии игры; её известное отличие от дисков —
`gf2/globals_global.str`, переписанный старым тулкитом (`tests/corpus.rs`,
`every_stream_parses_and_rewrites_identically`).

**Фаззинг**: цель `delta` (`fuzz/fuzz_targets/delta.rs`, зёрна
`fuzz/seeds/delta/`) — разбор, запись, повторный разбор и наложение на
маленький ресурс своего вида; у дельты SimGroup `layout.base` подставляется
под эту базу, чтобы фаззер доходил до кода раскладки. Прогон 2026-11-18:
878 840 запусков за 151 с, ошибок нет.

**Правило сборки мода** (этап 110), тест
`the_rule_of_the_build_on_every_simgroup` (`tests/corpus/mod_deltas.rs`):
все 2 006 групп, правки автора записаны по одной; сколько ресурсов идёт в
мод дельтой (`mods::delta_for`: точная **и** меньше ресурса в файле мода,
оба размера — после deflate). Точны все; целым ресурс остаётся только из-за
размера.

| Правки | Случаев | Дельтой | Целым (не меньше) | Дельта / ресурс, байт в среднем (несжатые) |
|---|---|---|---|---|
| задан один атрибут | 1 907 | 1 874 (98,3 %) | 33 | 156 / 10 557 |
| один новый объект, перемещён | 2 006 | 1 646 (82,1 %) | 360 | 856 / 12 663 |
| три новых объекта | 2 006 | 1 620 (80,8 %) | 386 | 2 367 / 13 085 |
| шесть смешанных правок | 2 005 | 1 511 (75,4 %) | 494 | 1 514 / 13 684 |
| двенадцать смешанных правок | 2 006 | 1 302 (64,9 %) | 704 | 3 144 / 15 860 |

Для сравнения — то же правило по несжатым размерам (документ короче ресурса
в байтах), замер при выборе правила: 98,3 %, 77,8 %, 49,9 %, 62,6 % и
48,6 %. Документ — текст, объект в нём в 2–3 раза длиннее, чем в группе,
поэтому сравнение «как есть» оставляло целыми половину зон уже при трёх
новых объектах; сжатые размеры ближе к тому, сколько мод действительно
занимает. Остаток (каждая пятая зона при одном новом объекте) — маленькие
группы, где новый объект сравним со всей группой.

**Свёртка в менеджере** (этап 110), тест
`two_mods_of_random_edits_fold_on_copies_of_real_zones`: два мода, каждый —
четыре смешанные правки и два новых объекта в одних и тех же зонах
(первые по имени потоки с одной SimGroup от восьми объектов, файл до
8 МиБ), каждый сделан на оригинале игры. Моды ставятся в менеджер копии
(ссылки на файлы игры, запись заменяет ссылку) и записываются.

| Зон | Дельт (мод 1 + мод 2) | Свёртка | По индексу | Запись потоков | Пропущенные операции | Конфликты по элементам |
|---|---|---|---|---|---|---|
| 24 | 24 + 24 | 9 мс | 2 мс | 1,0 с | 2 ресурса | 6 |
| 172 | 172 + 172 | 112 мс | 23 мс | 6,2 с | 9 | 21 |
| 600 | 599 + 600 | 403 мс | 64 мс | 21,7 с | 19 | 82 |

Во всех зонах поток разбирается, группа пишется как читается и держит
объекты, добавленные **обоими** модами; объекты, которых не трогал ни
один, — как в игре; после «Вернуть оригиналы» файлы копии побайтно равны
файлам игры. «По индексу» — новый менеджер после записи: дельты не
читаются, считаются только хэши оригиналов.

## 10. Библиотека

| Функция | Что делает |
|---|---|
| `delta::kind_of(type_id)` | вид дельты типа ресурса или `None` |
| `delta::diff_resource(type_id, база, моё)` | `Ok(Some(Delta))` — проверенная дельта; `Ok(None)` — хранить целиком; `Err` — ресурс не разбирается |
| `delta::apply_resource(type_id, документ, база)` | `Applied` (§4) |
| `delta::exact(type_id, база, моё)` | байты документа, только если наложение на базу даёт «моё» побайтно |
| `Delta::parse`, `Delta::to_bytes`, `Delta::apply`, `kind`, `len`, `is_empty` | документ любого вида |
| `delta::simgroup::{diff, apply, operations}`, `lh2::{diff, apply}`, `partsdb::{diff, apply}`, `wgi::{diff, apply}` | то же по типам; `simgroup::operations` — операции без проверки байт (что изменилось в группе при любой раскладке) |
| `delta::operations(type_id, база, моё)` | операции для переноса на **другую** версию ресурса — перебазирования (этап 111): у SimGroup по содержимому, без побайтной проверки и без `layout` (она привязана к прежней базе); у остальных видов — как `diff_resource` |
| `simgroup_edit::compare_by_guid(old, new)` | сравнение двух версий группы с сопоставлением объектов по GUID: пары, изменённые атрибуты, добавленные, удалённые (`compare` по номеру остался как был) |
| `Delta::targets()` | адрес каждой операции словами заметок `apply` (`object <GUID>, Entity.CMD_SetModel`, `string <хэш>, language en`): по нему менеджер находит мод, чьё значение перезаписано |
| `mods::delta_for(type_id, база, моё)` | правило сборки мода: документ, либо причина, по которой ресурс остаётся целым (`KeptWhole`) |

## 11. Не сделано и открыто

- `simgroup`: нет операций для ссылок объекта (`links`), флагов, компонентов
  и для вставки объекта не в конец; такие правки хранят группу целиком.
- `partsdb`: нет операции «добавить набор» (`clone_set`) и правок пресетов.
- `wgi`: нет правки существующей ячейки.
- `lh2`: нет удаления строки.
- Раскладка действует только на базе, с которой снята дельта. Если у игрока
  ниже стоит ещё одна дельта того же ресурса, результат верен по содержимому,
  но его байты не те, что были у автора, — сравнивать его можно только с
  результатом той же свёртки. Менеджер так и делает: в план идёт хэш
  свёртки (`docs/mods.md` §3.4).
- Правило размера оставляет целыми маленькие ресурсы (§9): такой мод с
  правками других модов того же ресурса не объединяется.

## 12. Где дельты используются (этап 110)

| Где | Что |
|---|---|
| формат мода, версия 6 | у записи ресурса поле `delta` (`kind`, `format`); данные — документ; `original` необязателен (`docs/mods.md` §1.7) |
| сборка мода | `mods::mod_from_workspace` → `delta_for`: дельта от базы правки (данные зависимости или оригинал игры), если она точна и меньше ресурса; иначе ресурс целиком. Отказ от дельт — `--no-deltas`, флажок, `deltas: false` (`docs/mods.md` §2) |
| менеджер модов | `mods::fold`: оригинал игры или последний целый ресурс, поверх — дельты включённых модов по порядку; результат в `.folded/`, хэш результата в плане; кэш по (тип, хэш данных, хэш документа) (`docs/mods.md` §3.4) |
| проверки | `Applied::skipped` → сообщение `OperationsSkipped`; `Applied::conflicts` → конфликт по элементам между модами или сообщение `ValuesDiffer`, если отличается сама игра; ошибка `apply` (занятый адрес) → роковая проблема `DeltaRefused` |
| запуск без записи | менеджер подготовленной копии сворачивает так же (`Source::Mods`, `Source::Project`) |
| перебазирование (этап 111) | `Workspace::rebase`: `operations(данные, на которых правка сделана, правка)` накладываются на данные, которые игра даёт сейчас; `Applied::skipped` и `conflicts` идут в отчёт по объекту или строке; ошибка `apply` (занятый адрес) — правка ждёт решения автора (`docs/project.md` §0.3). На корпусе: шесть случайных правок каждой из 2 006 SimGroup, записанные одним проходом (раскладка, на которой дельты не проверялись), на изменённой базе дают то же, что правки руками (`tests/corpus/rebase.rs`) |

В игре (стенд, `docs/analysis/game-bench.md` §52): два мода с дельтой
`simgroup` одной зоны и дельтой `wgi` одной сетки города — оба объекта в
зоне и обе новые зоны загружены, с подменами и после записи менеджером.

**Правило размера.** Точной дельты мало: она идёт в мод, только если
занимает в файле мода меньше, чем ресурс, — сравниваются документ и ресурс
после deflate, как их хранит ZIP мода (`mods::delta_for`, `stored_size`).
Документ не меньше ресурса значит, что автор переписал ресурс почти весь;
объединять там нечего, а файл мода вырос бы. Причина в отчёте сборки —
`KeptWhole::NotSmaller` с обоими размерами.
