# Моды

Мод — это один файл ZIP с манифестом и новыми данными ресурсов, которые он
заменяет или добавляет (с версии 2 формата — и новые потоки; с версии 3 —
зависимости от других модов, проверенные издания игры и правила порядка
загрузки, §1.3; с версии 5 — исполняемый код, который ставится только с
согласия игрока, §1.6; с версии 6 — дельты: правки ресурса вместо целого
ресурса, которые менеджер объединяет с правками других модов, §1.7). По сути это
экспортированное рабочее пространство
(`docs/workspace.md`): те же ключи ресурсов, те же хэши данных и оригиналов.
Моды ставит менеджер модов: он хранит установленные моды, их порядок и
записывает в игру общий результат включённых модов теми же средствами, что и
рабочее пространство (резервные копии, атомарная запись, размеры в TOC).
С этапа 46 включённые моды можно и не записывать: `doctor-toolkit play ИГРА
--mods` собирает их результат вне папки игры, а модуль живой связи
подставляет игре эти файлы на время запуска (`docs/guide/11-play.md` §11.11,
`docs/analysis/live-link.md` §14).

Код: `crates/doctor-toolkit/src/mods/` (библиотека), команды
`doctor-toolkit mods …` и `doctor-toolkit integrity` (CLI), окно **Mods**
редактора и отдельная программа для игроков Open Mod Manager — файл
`open-mod-manager` (`crates/doctor-toolkit-mods`, общая панель для обоих).

## 1. Формат мода

```text
example.zip
├── mod.json                 манифест
├── preview.png              картинка (необязательно; .png или .jpg)
└── payloads/<sha256>        новые данные ресурсов, по одному файлу на разное содержимое
```

Данные лежат в распакованном виде, сжаты deflate внутри ZIP. Имя файла данных —
SHA-256 его содержимого; одинаковые данные хранятся один раз.

Ресурс лежит в моде целиком, а изменённые `simgroup`, `lh2`, `partsdb` и
`wgi` — с версии 6 — как дельта: список операций («добавить эти объекты,
задать эти атрибуты»), §1.7.

### 1.1 `mod.json`

```json
{
  "format": "doctor-toolkit-mod",
  "format_version": 1,
  "id": "restored-hq-billboards",
  "name": "Restored HQ Billboards",
  "version": "1",
  "author": "cha1r",
  "description": "…",
  "url": "https://…",
  "preview": "preview.png",
  "game": {
    "profile": "The Godfather II (PC)",
    "executable_size": 13840384,
    "executable_sha256": "…"
  },
  "resources": [
    {
      "key": "gf2/queens/local:tg4d:00000000.4802e0a3.3935459f.1848baba",
      "payload": { "sha256": "…", "size": 786464 },
      "original": { "sha256": "…", "size": 786464 },
      "storage": "raw",
      "label": "Import texture billboard"
    }
  ],
  "converted_from": "vpat"
}
```

| Поле | Смысл |
|---|---|
| `format`, `format_version` | `doctor-toolkit-mod`; 1 — только замены, 2 — ещё добавленные ресурсы и новые потоки (§1.2), 3 — зависимости, издания, порядок (§1.3), 4 — файлы архивов `.viv` и дочерние потоки, открываемые вместе с родителем (§1.5), 5 — исполняемый код (§1.6), 6 — дельты (§1.7). Мод более новой версии формата не открывается, сообщение предлагает обновить программу («Update Open Mod Manager (doctor_toolkit) to install it»; программы до этапа 71 пишут «Update doctor_toolkit») |
| `id` | идентификатор: 1–64 символа `a-z`, `0-9`, `-`, `_`. Установка мода с тем же `id` — обновление: место в порядке загрузки и включённость сохраняются |
| `name`, `version`, `author`, `description`, `url` | метаданные для игрока; `url` только `http://` или `https://`. `version` в версиях 1–2 — свободный текст, в версии 3 — семантическая версия (§1.3) |
| `preview` | имя картинки в архиве: простое имя файла, `.png`, `.jpg` или `.jpeg` |
| `game.profile` | профиль игры; мод для другого профиля не устанавливается |
| `game.executable_*` | исполняемый файл игры, на которой мод сделан. Несовпадение только сообщается: пригодность проверяется по ресурсам |
| `resources[].key` | ключ ресурса `поток:тип:ids` (`docs/workspace.md`, §1) |
| `resources[].payload` | новые данные: SHA-256 и размер |
| `resources[].original` | данные ресурса в игре, для которой сделан мод. По ним проверяется совместимость |
| `resources[].storage` | `raw` или `refpack`; поля нет — как у оригинала |
| `resources[].added` | есть у **добавленного** ресурса (версия 2), §1.2 |
| `resources[].delta` | есть у ресурса, который хранится как **дельта** (версия 6), §1.7; `original` у него необязателен |
| `streams` | новые потоки (версия 2), §1.2 |
| `converted_from` | откуда мод получен, если не собран из рабочего пространства (`vpat`) |
| `messages` | **новые сообщения мода** (этап 73): имена, которые шлют или слушают его SimGroup и которых нет в игре, по алфавиту. Сборка из рабочего пространства заполняет поле сама. На шине сообщение — `sdbm(lower(имя))`, поэтому имя из списка не может быть именем сообщения игры и не может совпадать с ним по хэшу: такой мод не собирается и не ставится (`mod.json: \`messages\`: … has the hash … of the game message …`). Поле необязательное и годится для любой версии формата; программы до этапа 73 его не читают. Схема — `#/$defs/mod_messages` в `data/gf2/schema/gf2-types.schema.json` (`docs/logic-graph.md` §2.1) |

### 1.2 Добавленные ресурсы и новые потоки (версия 2)

Версия 2 переносит то, что рабочее пространство умеет добавлять
(`docs/workspace.md`, §3.4; `docs/analysis/new-resources.md`): новые ресурсы
в существующих потоках и новые потоки с записями в TOC. Поля те же, что в
манифесте рабочего пространства версии 2:

```json
{
  "format_version": 2,
  "resources": [
    {
      "key": "gf2/level:metamodel:5c7e0a11",
      "payload": { "sha256": "…", "size": 4096 },
      "original": { "sha256": "e3b0c442…", "size": 0 },
      "added": { "mem_policy": 1402186753, "alignment": 16,
                 "before": "gf2/level:mesh:00000003", "order": 3000000 }
    },
    {
      "key": "gf2/doctor/props:mesh:7a3d11c2",
      "payload": { "sha256": "…", "size": 52000 },
      "original": { "sha256": "e3b0c442…", "size": 0 },
      "added": { "mem_policy": 951236818, "alignment": 128, "order": 4000000 }
    }
  ],
  "streams": [
    {
      "name": "gf2/doctor/props",
      "guid": "1f2e3d4c5b6a7988444f43544f52544b",
      "hash": 2271560481,
      "parent": "gf2/level",
      "with_parent": true,
      "tocs": ["gf2/level.toc"]
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `added.mem_policy`, `added.alignment` | политика памяти и выравнивание из заголовка `SHDR`; выравнивание — степень двойки до 0x10000 |
| `added.before` | ключ ресурса того же исходного потока, перед которым встаёт новый; нет — в конец. Для ресурса нового потока не задаётся |
| `added.order` | порядок среди добавленных в одно место |
| `original` добавленного | пустые данные (SHA-256 пустой строки, размер 0) |
| `streams[]` | имя, GUID (32 шестнадцатеричные цифры) и его свёртка `hash`, родитель, `with_parent` (дочерний поток, флаги TOC `0,0,5,0`; иначе `0,0,1,0`), список TOC и другой родитель в отдельных TOC (`toc_parents`) |

В новом потоке могут быть только добавленные ресурсы. Добавлять можно и в
поток, который создаёт другой мод (дополнение к моду): тогда этот мод должен
быть включён.

**Совместимость версий.** Мод, который только заменяет ресурсы, собирается
как версия 1 и читается прежними программами. Версия 1 с полями `added` или
`streams` отвергается (старая программа приняла бы добавленный ресурс за
замену). Неизвестные поля, как и раньше, пропускаются.

### 1.3 Версия 3: зависимости, издания, порядок загрузки

По образцу Fabric/Forge (зависимости с условиями на версии) и LOOT (мягкие
правила порядка). Пример — патч поверх мода «New New York»:

```json
{
  "format": "doctor-toolkit-mod",
  "format_version": 3,
  "id": "nny-night",
  "name": "New New York: ночь",
  "version": "1.2.0-beta",
  "author": "…",
  "description": "Ночные фонари для New New York.",
  "game": {
    "profile": "The Godfather II (PC)",
    "executable_size": 13840384,
    "executable_sha256": "31f579a8…",
    "editions": ["1.0.789.0"]
  },
  "requires_manager": ">=1.0.0",
  "depends": { "new-new-york": ">=1.1 <2" },
  "recommends": { "hd-textures": "*" },
  "incompatible": {
    "old-nights": { "versions": "<3", "reason": "меняет те же фонари" },
    "dark-city": "^1.0"
  },
  "load_after": ["hd-textures"],
  "load_before": ["final-touches"],
  "resources": [ … ]
}
```

| Поле | Смысл |
|---|---|
| `version` | обязательна семантическая версия: `1`, `1.2`, `1.2.3`, с суффиксом пред-выпуска `-beta`, `-rc.1` (и сборки `+…`, в сравнениях не участвует). Недостающие числа — нули: `1.2` = `1.2.0`. Порядок как в semver: `1.2.0-beta` < `1.2.0-rc.1` < `1.2.0` |
| `game.editions` | издания, на которых мод проверен: версия известной сборки (`1.0.789.0`, `1.0.764.0`; `doctor_toolkit::edition`, `KnownEdition::version`) или полный id сборки (`1.0.789.0-2009-10-05`). Пусто или нет поля — любое издание (как в версии 2); при сборке по умолчанию пусто: мод данных подходит любому изданию, где совпадают ресурсы, — это решает побайтная сверка оригиналов |
| `requires_manager` | условие на версию менеджера модов (`>=1.0.0`): версия Open Mod Manager и `doctor-toolkit` общая |
| `depends` | `id → условие`: моды, без которых этот не работает (жёсткие зависимости) |
| `recommends` | `id → условие`: подсказка, с чем мод лучше |
| `incompatible` | `id → {"versions": условие, "reason": текст}` или кратко `id → условие`; `versions` по умолчанию `*` |
| `load_after`, `load_before` | id модов: мягкие правила порядка; мод, которого нет, правило не включает |

Все поля необязательны и пишутся только непустыми. Мод без них записывается
прежней версией формата (1 или 2) и побайтно так же, как раньше (тест
`version_2_manifests_are_written_back_byte_for_byte`); версия 1–2 с полями
версии 3 отвергается («version 3 is needed»).

**Условия на версии** (`mods::version`, разбор версий — крейт `semver`,
короткие версии дополняются нулями до него):

| Запись | Подходит |
|---|---|
| `*` (или пусто) | любая версия |
| `1.2`, `=1.2` | ровно 1.2.0 |
| `>1.2`, `>=1.2`, `<2`, `<=1.4` | как написано; `<2` не пускает и пред-выпуски 2.0.0 (`2.0.0-beta`) |
| `^1.2` | от 1.2.0 до 2.0.0 (не включая); `^0.3` — до 0.4.0, `^0.0.3` — до 0.0.4 |
| `~1.2` | от 1.2.0 до 1.3.0; `~1` — до 2.0.0 |
| `>=1.1 <2` | пробел — «и»: должны выполняться все сравнения (не больше 8) |

В отличие от Cargo, пред-выпуск в диапазоне подходит как любая версия
(`>=1.1` пускает `1.2.0-beta`). Версия мода формата 1–2, которая не читается
как semver (`beta two`), подходит только под `*`.

**Проверки при чтении** (`ModManifest::validate`): `version` — semver;
условия разбираются (`>=1,<2`, `=>1`, `1.2 || 2` — ошибка); id в списках —
правильные id, не сам мод, без повторов, не больше 256 в списке; мод не
может быть одновременно в `depends` и `incompatible`, в `load_after` и
`load_before`, зависимость не может стоять в `load_before`; причина — до
1 000 байт без управляющих символов, кроме перевода строки; издания — до
32, без пробелов и повторов. Неизвестное издание — только предупреждение
(`ModManifest::warnings`, `mods info`, проверка в мастере сборки).

### 1.5 Версия 4: файлы архивов (этап 83)

Мод может нести записи архивов `.viv` — потоковый звук: новую голосовую
реплику (`docs/formats/audio.md` §15), заменённую музыку или речь, файл речи
с правленым субтитром.

```json
"files": [
  { "key": "viv:audiostreams\\c1_xxx_0\\d_doc1_xxx_0000001.exa.snu",
    "payload": { "sha256": "…", "size": 57648 },
    "label": "New voice line doc1_xxx_0000001 (DOCTOR_TEST)" }
]
```

В версии 4 пишется и мод с дочерним потоком, который игра открывает вместе
с родителем (поле `auto_load` потока, этап 84, `docs/workspace.md`):
менеджер старше этого поля поставил бы такой поток выключенным и ничего не
сказал, а мод версии 4 он не откроет и предложит обновиться.

- Ключ — запись архива (`viv:` и имя в нижнем регистре через `\`); свободные
  файлы (ролики `movies/…`) моды не несут. Имя проверяется: печатные символы
  ASCII, без `/`, `..` и пустых частей, не в `_doctor_toolkit\`.
- Данные — в `payloads/`, как у ресурсов; оригинал не хранится и не
  сверяется: архивы игры не переписываются.
- `mods build` кладёт в мод все записи архивов рабочего пространства; при
  сборке по выбранным ключам — записи тех операций, чьи ресурсы выбраны
  (реплика едет вместе со своими `chv`, `smb`, `get`).
- Менеджер пишет записи включённых модов в свой накладной архив
  `GODFATH0.viv` (владелец `mods`), а архивы игры сдвигает на номер выше — тот
  же механизм, что у рабочего пространства (`docs/formats/audio.md` §9). Одну
  запись у двух модов берёт последний по порядку загрузки. Выключение мода и
  `mods unapply` убирают накладной архив и возвращают имена.
- Ограничения: `mods status`, `mods check` и список конфликтов говорят только о
  ресурсах потоков; записи архивов они не показывают (запись пишется при
  `mods apply` и убирается при `mods unapply` всегда).
- Мод без `files` по-прежнему пишется версией 1–3 и читается старыми
  программами; с `files` старая программа отказывает и предлагает обновиться.
- Мод может состоять из одних файлов архивов, без ресурсов потоков
  (заменённый звук, время субтитра ролика): с этапа 104 проверка манифеста
  считает и их (раньше — «the mod replaces no resources»).
- **Файл архива идёт в мод целиком.** Частичной замены файла в формате нет.
  Это заметно на времени субтитров ролика: таблица `TOB1` лежит в заголовке
  потокового звука (`docs/formats/cutscenes.md` §4), и правка одного времени
  (`cutscene subtitle`, `edit_subtitle` в MCP, дорожка Subtitles редактора)
  делает изменением весь звуковой файл — у `igc16` 10,5 МБ. Сборка мода
  говорит об этом: `BuildReport::notes` (функция `mods::whole_sound_notes`)
  называет каждый звук от 1 МиБ с таблицей субтитров, который мод несёт
  целиком; `mods build` печатает строки `note: …`, `mod_build` возвращает их
  в `notes`. Текст субтитра — строка таблицы `lh2` и едет в мод одной
  строкой. Замена части файла потребовала бы новой версии формата и
  поддержки в менеджере (накладной архив собирался бы из оригинала и
  заплатки); не сделано.

### 1.4 Чтение недоверенного файла

Мод присылают незнакомые люди, поэтому чтение (`mods::package`) проверяет всё:

| Проверка | Предел или правило |
|---|---|
| Число записей в ZIP | не больше 250 016 |
| Повторяющиеся имена записей | отказ |
| Расхождение локальных заголовков и центрального каталога | отказ |
| Имена записей | отказ для `..`, `.`, пустых частей, абсолютных путей, `\`, `:`, управляющих символов |
| Символические ссылки, шифрование | отказ |
| Сжатие | только stored и deflate |
| `mod.json` | не больше 32 МиБ, проверка всех полей и длин строк |
| Один ресурс | не больше 512 МиБ (самый большой ресурс GF2 — около 26 МиБ) |
| Все данные мода | не больше 8 ГиБ, не больше 250 000 ресурсов |
| Картинка | не больше 8 МиБ |
| Имя нового потока (по нему создаётся файл `<имя>.str`) | части из `a-z`, `0-9`, `_`, `-`, `.` через `/`; отказ для пустых частей, `.` и `..`, `\`, `:`, абсолютных путей, заглавных букв, пробелов, имён внутри `_doctor_toolkit` и `_toolkit`, имён устройств Windows (`con`, `aux`, `com1`…) и частей, кончающихся точкой |
| TOC нового потока | 1–64 разных пути вида `поток.toc` по тем же правилам; другой родитель — только для своих TOC |
| Новые потоки | не больше 10 000; имена и хэши не повторяются, хэш не 0, GUID — 32 шестнадцатеричные цифры, родитель — не сам поток и не другой новый поток мода |
| Добавленный ресурс | `original` — пустые данные; выравнивание — степень двойки до 0x10000; `before` — ресурс того же потока, не сам ресурс; в новом потоке — без `before` |
| Замена в новом потоке своего же мода | отказ: в новом потоке нет оригиналов |
| Один GUID у двух добавленных ресурсов мода с разными данными | отказ (игра загрузит только один) |
| Версия 1 с `added` или `streams` | отказ |
| Версия 1–2 с полями версии 3, версия 3 с версией мода не semver, неразборчивое условие, самоссылка, повтор, противоречие списков (§1.3) | отказ |
| Неизвестное издание в `game.editions` | предупреждение |
| Поле `delta` ресурса в версии 1–5 | отказ («version 6 is needed») |
| Дельта не того вида, что тип ресурса; версия документа новее известной; дельта у добавленного ресурса | отказ |
| Данные дельты — не документ дельты или документ другого вида (проверяется при `mods info` и установке) | отказ |
| Раздел `native` в версии 1–4 | отказ («version 5 is needed») |
| `native.edition` не `1.0.789.0`; `platform_abi` 0; модулей нет или больше 16 | отказ |
| Имя модуля: путь (`/`, `\`, `..`, `:`), заглавные буквы, не `.asi`, имя устройства Windows, имя модуля тулкита, повтор | отказ |
| Модуль пустой, больше 64 МиБ, хэш не SHA-256 | отказ |
| Модуль — не 32-битная DLL Windows (проверяется при `mods info`, установке и перед записью в игру) | отказ |

Файлы никогда не извлекаются по имени из архива: читаются только `mod.json`,
картинка, названная в нём, и `payloads/<sha256>` для хэшей из манифеста. Размер
записи сверяется с манифестом до чтения, а чтение ограничено этим размером:
ZIP-бомба, у которой в заголовке написано 300 байт, а внутри 64 МиБ нулей,
останавливается на пределе. Каждые данные сверяются с SHA-256. Лишние записи
игнорируются и показываются как предупреждения. Всё это проверено тестами
`malicious_packages_are_refused`, `malicious_version_2_manifests_are_refused`
и `malformed_vpat_patches_are_refused`.

### 1.6 Версия 5: исполняемый код (этап 81)

Мод может нести **код** — модули `.asi` для папки `scripts` игры: нативные
моды платформы `doctor_platform.asi` (новые классы объектов, функции Lua,
сообщения — `docs/analysis/asi-platform.md`) или обычные ASI-плагины.
Пример — `examples/native-class` (сборка `build.sh`: данные и два модуля в
одном моде).

```json
"format_version": 5,
"native": {
  "edition": "1.0.789.0",
  "platform_abi": 1,
  "required": true,
  "modules": [
    { "file": "doctor_example.asi",
      "payload": { "sha256": "d7283c46…", "size": 284160 } },
    { "file": "doctor_example_c.asi",
      "payload": { "sha256": "9992c50b…", "size": 85932 } }
  ]
}
```

| Поле | Смысл |
|---|---|
| `edition` | издание игры, для которого собран код. Сейчас принимается только `1.0.789.0` — единственное, где работает платформа; другое значение — отказ при чтении |
| `platform_abi` | версия ABI платформы, с которой собраны модули (`DOCTOR_ABI_VERSION` из `doctor_sdk.h`, `doctor_sdk::ABI_VERSION`). Нет поля — модули платформой не пользуются (обычные ASI-плагины), и `doctor_platform.asi` для них не ставится. Мод, которому нужна версия новее, чем умеет эта программа, не записывается: «обновите Open Mod Manager» |
| `required` | `true` — без кода мод не имеет смысла: пока код поставить нельзя (нет согласия, другое издание, нет загрузчика), мод не записывается **совсем**. Нет поля — данные мода полезны и сами: без кода ставятся только они |
| `modules[].file` | простое имя файла в `scripts/`: строчные латинские буквы, цифры, `_`, `-` и расширение `.asi`, до 52 символов. Никаких путей, заглавных букв, имён устройств Windows и имён модулей тулкита (`doctor_live.asi`, `doctor_render.asi`, `doctor_crash.asi`, `doctor_platform.asi`, `doctor_loader.asi`) |
| `modules[].payload` | DLL: SHA-256 и размер; данные лежат в `payloads/<sha256>`, как данные ресурсов. От 1 до 16 модулей, каждый до 64 МиБ |
| `modules[].label` | что это за модуль, для игрока (необязательно) |

Мод только с кодом, без ресурсов, допустим.

**Почему версия 5, а не поле версии 3 или 4.** Менеджеры 0.0.5–0.0.7
читают форматы 3 и 4 и неизвестные поля пропускают: мод с разделом `native`
в такой версии они поставили бы без кода и ничего не сказали. Правило
формата — «новое поле, которое старая программа молча поставила бы
неправильно, требует версии, которую она не откроет» — поэтому мод с кодом
пишется версией 5 (`ModManifest::required_version`), а раздел `native` в
версии 1–4 — ошибка чтения («version 5 is needed»). Старая программа
отвечает «the mod uses format version 5 … Update Open Mod Manager» (тест
`the_section_is_validated_and_needs_format_version_5`; на стенде —
`doctor-toolkit` 0.0.4, `game-bench.md` §45). Мод без кода по-прежнему
пишется наименьшей подходящей версией.

**Правила установки кода** (`mods::native`). Данные мода компьютеру игрока
навредить не могут, код — может, поэтому правила здесь строже, чем
где-либо в менеджере:

- **Без ответа игрока ничего исполняемого в папку игры не кладётся.**
  Вопрос задаётся на каждый мод и показывает, что это код, а не данные,
  какие файлы и с какими SHA-256 лягут в папку игры (модули мода, а с ними
  файлы тулкита — платформа и, если в игре нет загрузчика, загрузчик).
  Ответы: **разрешить код**, **только данные** (если мод не `required`) или
  выключить мод.
- **Ответ запоминается для мода** и действует для его следующих версий
  (`_doctor_toolkit/mods/native.json`, раздел `consent`: id мода → SHA-256
  показанных модулей → `code` или `data`; хэши — запись того, что игрок
  видел). Обновление мода с другой DLL ставится без нового вопроса: новая
  DLL заменяет прежнюю при следующей записи в игру, как и данные мода. Удаление мода ответ забывает.
- **Только на издание 1.0.789.0.** Исполняемый файл игры сверяется так же,
  как это делает сама платформа (заголовок PE и места, которые она правит:
  `doctor_toolkit_live::platform::CHECKS`). На другом издании мод с
  `required` не записывается, у остальных ставятся только данные.
- **Хэш сверяется дважды**: при установке мода (чтение архива) и перед
  записью в игру (чтение из папки установленного мода); оба раза файл
  должен быть 32-битной DLL Windows (`native::check_module`: `MZ`, `PE`,
  машина `0x014C`, признак DLL). Подменённый после установки файл не
  ставится.
- **Чужие файлы не трогаются.** Если в `scripts/` уже лежит файл с именем
  модуля (без учёта регистра букв), который менеджер не писал, код мода не
  ставится («…is already in the game»). Модуль, изменённый другой
  программой после установки, менеджер своим больше не считает: не
  обновляет и не удаляет, а сообщает. `doctor_platform.asi`, положенный
  автором руками, используется как есть. Два включённых мода с модулем
  одного имени и разным содержимым — код второго по порядку не ставится.

**Загрузчик.** Модули `.asi` грузит ASI-загрузчик — DLL в папке игры,
которая занимает место системной (`dinput8.dll`). У игроков этой игры это
Ultimate ASI Loader; он чужой, в поставку тулкита не входит и тулкитом не
скачивается. Если загрузчик в папке игры есть (любой `dinput8.dll` или
другой прокси с метками Ultimate ASI Loader, `live::loader::find`), он
используется как есть. Если нет — менеджер вместе с первым модулем кладёт
**свой** загрузчик: `doctor_loader.dll` (крейт
`crates/doctor-toolkit-loader`, сборка `tools/build-loader.sh`, лицензия
проекта) под именем `dinput8.dll`. Он загружает все `*.asi` из папки игры,
`scripts\` и `plugins\` по алфавиту и передаёт единственную функцию,
которую игра берёт из `DINPUT8.dll`, — `DirectInput8Create` — системной
DLL; ничего не патчит, настроек не читает, файлов не пишет. Под Wine и
Proton любому загрузчику нужна переменная `WINEDLLOVERRIDES=dinput8=n,b`
(для Steam — строка запуска `WINEDLLOVERRIDES="dinput8=n,b" %command%`);
без неё Wine берёт свою `dinput8.dll` и модули не грузятся. Если
загрузчика нет и файла `doctor_loader.dll` рядом с программой нет, код не
ставится, а менеджер объясняет, что положить в папку игры.

**Файлы тулкита** менеджер ищет рядом с программой (файлы выпуска
`doctor_platform.asi` и `doctor_loader.dll`), в `../share/doctor_toolkit`,
в `target/live` репозитория; переменные `DOCTOR_PLATFORM_MODULE` и
`DOCTOR_LOADER_MODULE` называют их явно.

**Когда код попадает в игру и уходит из неё.**

| Действие | Код |
|---|---|
| установка мода | ничего не кладётся; CLI печатает вопрос, окно открывает его |
| «Записать в игру» (`mods apply`) | после данных ставятся модули модов, на которые есть согласие, платформа и (если нужен) загрузчик; что написано — в `native.json`, раздел `written`, с хэшем каждого файла |
| «Играть с модами» (данные вне папки игры) | код ставится так же, как при записи: он должен лежать в `scripts/` |
| выключение мода, удаление, обновление на другую DLL, ответ «только данные», «спросить снова» | модули мода убираются **сразу**, не дожидаясь записи; с последним модулем уходят платформа (и её журнал `doctor_platform.log`) и загрузчик, если их клал менеджер |
| «Вернуть оригиналы» (`mods unapply`) | убирается всё, что клал менеджер; согласие остаётся, следующая запись вернёт код |

Загрузчик тулкита остаётся, пока в папке игры или `scripts/` есть хоть
один `.asi` (например, модуль отчётов о падениях), и уходит при следующем
изменении списка модов после того, как их не осталось. Пустая папка
`scripts/` удаляется; файл `native.json` удаляется, когда в нём не осталось
ни ответов, ни записей. Файл, который нельзя удалить сейчас (игра
запущена), остаётся записанным и удаляется при следующем случае.

**Сборка.** `mods build` и `mods install-workspace`:

```sh
doctor-toolkit mods build "$GAME" -o my-mod.zip --name "My mod" \
    --native target/i686-pc-windows-gnu/release/my_mod.dll \
    --native extra.asi=build/extra.dll --native-required
```

| Ключ | Смысл |
|---|---|
| `--native [ИМЯ.asi=]ФАЙЛ` | модуль; без имени — имя файла строчными буквами с расширением `.asi`. Повторяется |
| `--native-required` | поле `required` |
| `--native-plain` | модули не пользуются платформой (нет `platform_abi`) |
| `--platform-abi N` | версия ABI, если не та, что у этой программы |

Сборка проверяет, что каждый файл — 32-битная DLL, и предупреждает, если в
модуле нет имени `doctor_mod_init` (платформа такой модуль не запустит).
В редакторе — поле **Executable code (.asi)** раздела «Dependencies,
editions and load order» окна Mods и мастера «Собрать мод…» (путь или
`имя.asi=путь` на строку) и флажок «без кода мод не работает». В MCP — параметры
`native`, `native_required`, `native_plain` инструмента `mod_build` (этап
104; пути абсолютные). Разбор строки модуля и чтение DLL — одна функция
библиотеки для всех трёх поверхностей (`mods::native::NativeSpec`,
`module_spec`). В Python сборки мода с кодом нет.

**MCP и согласие.** Сервер MCP собирает мод с кодом, ставит его и
показывает состояние (`mods` с `action: native`: ответ игрока, состояние
кода, файлы в игре, а с `id` — что мод поставил бы в игру; поле `code` в
списке модов), но **ответить на вопрос о коде не может**: ни у одного
инструмента нет параметра или действия, которое вызвало бы
`native::set_consent`; ответ даёт игрок в окне менеджера или командой
`mods native`. Так как ответ действует и для следующих версий мода, сервер
не ставит мод, чьи модули отличаются от тех, на которые игрок согласился
(`native::replaces_agreed_code`: `mods_manage` `install` и
`install_workspace` отказывают и отсылают к менеджеру) — иначе агент мог бы
подменить согласованный код своим. Человек, обновляющий мод в окне или
командой `mods install`, по-прежнему не переспрашивается.

**Команды.**

```sh
doctor-toolkit mods native "$GAME"                 # состояние кода всех модов, файлы менеджера в игре, загрузчик
doctor-toolkit mods native "$GAME" my-mod          # вопрос: файлы и хэши; текущий ответ
doctor-toolkit mods native "$GAME" my-mod --allow  # согласие (по хэшам); затем mods apply
doctor-toolkit mods native "$GAME" my-mod --data-only
doctor-toolkit mods native "$GAME" my-mod --forget # забыть ответ: код убирается и ждёт
```

`mods info` показывает раздел кода мода; `mods install` печатает вопрос и
команду ответа; `mods check` и `mods apply` называют моды, код которых не
поставлен, и причину.

**Проверки при чтении** — в таблице §1.4. Тесты:
`crates/doctor-toolkit/src/mods/native/tests.rs` (имена и DLL, версия 5 и
отказ старых программ, вопрос и три ответа, обновление мода с новой сборкой без нового вопроса,
`required`, другое издание, новее ABI, чужие файлы, загрузчик, подменённый
модуль, два мода с одним именем модуля), в Open Mod Manager —
`a_mod_with_code_asks_before_anything_executable`. В игре —
`game-bench.md` §45.

### 1.7 Версия 6: дельты (этап 110)

Мод может не заменять ресурс целиком, а нести **дельту** — операции,
которые превращают данные, на которых работал автор, в его данные:
«добавить эти объекты, задать эти атрибуты» (`resource::delta`, документ и
правила — `docs/formats/delta.md`). Дельты есть у четырёх типов: `simgroup`
(объекты зоны), `lh2` (таблица строк), `partsdb` (база частей персонажей),
`wgi` (мировая сетка: ячейка новой зоны — правка общей сетки города).
Менеджер накладывает дельты включённых модов на то, что есть у игрока
(§3.4), поэтому:

- два мода, добавившие объекты в одну зону, — оба в игре;
- два мода, добавившие по новой зоне в один город, — обе ячейки в сетке;
- расширение чужого мода переживает его обновление: оно хранит свои
  правки, а не копию его данных.

```json
"format_version": 6,
"resources": [
  {
    "key": "gf2/cuba/local/yuri/high/terrain3:simgroup:00000000",
    "payload": { "sha256": "2c26b46b…", "size": 812 },
    "original": { "sha256": "5fa303d0…", "size": 10468 },
    "label": "Add a crate",
    "delta": { "kind": "simgroup", "format": 1 }
  }
]
```

| Поле | Смысл |
|---|---|
| `resources[].delta` | есть у ресурса, данные которого — документ дельты: `kind` — вид (`simgroup`, `lh2`, `partsdb`, `wgi`; должен быть видом типа ресурса из ключа), `format` — версия документа (сейчас 1, `delta::FORMAT`) |
| `resources[].payload` у дельты | документ дельты (JSON), `payloads/<sha256>` как у любых данных |
| `resources[].original` у дельты | данные, на которых дельта снята. **Необязательно** и ни с чем не сверяется: дельта накладывается на то, что есть. Сборка его пишет (по нему видно, на чём сделан мод); у мода без поля это пустые данные |
| `resources[].added` у дельты | запрещено: дельту добавленного ресурса не на что накладывать |

Остальные ресурсы того же мода — целые, как раньше.

**Почему версия 6.** То же правило, что у версии 5 (§1.6): менеджеры,
читающие версии 3–5, неизвестное поле `delta` пропустили бы и записали в
игру **документ JSON вместо ресурса**. Поэтому мод с дельтой пишется
версией 6 (`DELTA_VERSION`, `ModManifest::required_version`), поле `delta`
в версии 1–5 — ошибка чтения («version 6 is needed»), а прежняя программа
отвечает «the mod uses format version 6; this program reads up to 5. Update
Open Mod Manager (doctor_toolkit) to install it» (`ModManifest::parse_up_to`,
тест `version_6_manifests_round_trip_and_older_managers_refuse_them`). Мод
без дельт пишется наименьшей подходящей версией и побайтно так же, как
раньше (`version_2_manifests_are_written_back_byte_for_byte`,
`the_build_keeps_a_resource_whole_when_a_delta_is_not_exact_or_not_smaller`).

**Проверки при чтении** — в таблице §1.4: вид дельты подходит типу ресурса,
версия документа не новее известной, ресурс не добавленный; при чтении
файла мода (`mods info`, установка) каждый документ разбирается и его вид
сверяется с манифестом (`mods::read_delta`) — мод с документом другого вида
или с мусором вместо документа не устанавливается.

## 2. Сборка мода

Мод собирается из изменений рабочего пространства: из всех или из выбранных.

```sh
doctor-toolkit mods build "$GAME" -o billboards.zip --name "HQ Billboards" \
    --mod-version 1.2 --author me --url https://example.org --preview shot.png
doctor-toolkit mods build "$GAME" -o text.zip --name "Text fix" gf2/text/dd7d7050
```

Без `--id` идентификатор получается из названия (`HQ Billboards` →
`hq-billboards`). Ключи в конце команды выбирают изменения (ключ или часть
ключа). Добавленные ресурсы и новые потоки рабочего пространства попадают в
мод (версия 2); при выборе ключей новый поток берётся, если выбран ресурс в
нём. `doctor-toolkit mods info FILE` показывает содержимое мода, версию
формата, новые потоки и поля версии 3 и проверяет все данные; с
`--resources` — список ресурсов (добавленные помечены `added`, с местом
`before`).

**Поля версии 3** при сборке:

```sh
doctor-toolkit mods build "$GAME" -o night.zip --name "NNY night" --mod-version 1.2-beta \
    --depends "new-new-york=>=1.1 <2" --recommends hd-textures \
    --incompatible "old-nights=<3:меняет те же фонари" \
    --load-after hd-textures --load-before final-touches \
    --edition 1.0.789.0 --requires-manager ">=1.0.0"
```

| Ключ | Поле |
|---|---|
| `--depends ID[=УСЛОВИЕ]`, `--recommends ID[=УСЛОВИЕ]` | `depends`, `recommends`; без условия — `*` |
| `--incompatible ID[=УСЛОВИЕ][:ПРИЧИНА]` | `incompatible` |
| `--load-after ID`, `--load-before ID` | правила порядка |
| `--edition ИЗДАНИЕ` | `game.editions`; `this` — издание этой игры (ошибка, если сборка неизвестна); по умолчанию — пусто, любое издание (`any` — то же) |
| `--requires-manager УСЛОВИЕ` | по умолчанию `>=` версии этой программы (первой, что читает версию 3); `none` — без условия |

Ключи повторяются. Так собранный мод — всегда версии 3 (в нём
`requires_manager`); мод прежней версии получается с `--requires-manager
none` без остальных ключей. В Python и MCP
(`Workspace.build_mod`, `mod_build`) — то же через `mods::Relations`.

**Зависимости подставляются сами** (`mods::suggested_dependencies`,
`add_suggested_dependencies`): если изменение рабочего пространства
заменяет ресурс, который меняет мод, записанный менеджером в игру (по
`applied.json` и плану включённых модов), или ложится в поток, который этот
мод создал, мод становится зависимостью с условием `>=<его версия>` (`*` для
версии не semver); сам собираемый мод (тот же `id`) не считается. Для
заменённых ресурсов такого мода в манифест пишется `original` — данные
зависимости (`Relations::made_on`): рабочее пространство хранит оригинал
игры из резервной копии, а редактор показывал и правил игру с модом.
Явно названная зависимость или несовместимый мод не переписываются. CLI
пишет добавленные строкой `depends on ID >=…`.

**У проекта с базой зависимости не угадываются** (этап 108,
`docs/project.md` §0.2). База — раздел `[base]` в `project.toml`: моды, на
которых сделан проект, с условиями на версии. Мод такого проекта
(`Project::mod_of`: установка в менеджер, «Играть», `project mod`) зависит
от модов базы с этими условиями (по умолчанию `^<версия, на которой
сделан>`) и ни от каких других — в том числе от мода базы, который включён,
но не записан в игру. Данные для `original` берёт `mods::add_made_on`: для
каждого заменяемого ресурса — данные последнего по порядку загрузки
включённого мода-зависимости (и его зависимостей), который этот ресурс
меняет или добавляет, записан он в игру или нет. Это ровно то, с чем
менеджер сверяет патч поверх модов (§3.3), поэтому мод проекта проходит
сверку и тогда, когда база только включена.

**Дельты при сборке (версия 6).** Заменённый ресурс вида `simgroup`,
`lh2`, `partsdb`, `wgi` идёт в мод дельтой, когда выполняются оба условия
(`mods::delta_for`):

1. **точность** — `delta::exact(тип, база, моё)` дал документ, то есть
   наложение документа на базу возвращает «моё» побайтно
   (`docs/formats/delta.md` §3); изменение, которое операциями не
   выражается, оставляет ресурс целым;
2. **размер** — документ занимает в файле мода меньше места, чем сам
   ресурс: сравниваются оба, сжатые deflate, как данные мода в ZIP.
   Документ не меньше ресурса значит, что мод переписал ресурс почти весь:
   объединять с чужими правками там уже нечего, а файл мода только вырос
   бы. Сравнение идёт по сжатым размерам, потому что документ — текст:
   новый объект в нём в 2–3 раза длиннее, чем в группе.

**База** — данные, на которых сделана правка: данные зависимости, если
ресурс меняют моды, записанные в игру (`Relations::made_on` и
`made_on_data`; складываются все их дельты — зависимостями становятся все
моды в свёртке), иначе оригинал игры из рабочего пространства. Состояние
самого собираемого мода, если он уже установлен, в базу не входит.
Добавленный ресурс всегда целый.

Дельты включены по умолчанию. Отказ — на одну сборку:

| Где | Как |
|---|---|
| CLI | `mods build … --no-deltas`, `mods install-workspace … --no-deltas` |
| Редактор | флажок **Keep whole resources (no merging)** раздела «Dependencies, editions and load order» окна Mods и мастера «Собрать мод…» |
| MCP | `mod_build` с `deltas: false` |
| Python | `ws.build_mod(…, deltas=False)`, `mods.install_workspace(…, deltas=False)` |
| Проект | `[build] deltas = false` в `project.toml` (`project mod`, `project install`, Play) |

С отказом каждый ресурс целый и мод пишется прежней версией — его поставит
и менеджер, который версию 6 не читает; но такой мод заменяет то, что с
теми же ресурсами делают другие моды. Отчёт сборки называет число дельт:
`BuildReport::deltas` из `delta_kinds` ресурсов таких типов; CLI пишет
«3 of 4 resource(s) that have deltas are stored as deltas», ресурсы,
оставшиеся целыми, названы строками `note:` с причиной (`KeptWhole`:
изменение не выражается операциями; документ не меньше ресурса; данные
базы неизвестны). Замеры правила на игре — `docs/formats/delta.md` §9.

В редакторе: окно **Mods** → раздел **Build a mod from the workspace**:
название, версия, автор, описание, адрес, картинка и свёрнутый раздел
**Dependencies, editions and load order** (по моду на строку: `id
условие`, у несовместимых `id условие: причина`; правила порядка — id через
запятую; издания — пусто: любое, кнопка **Only this edition** вписывает
издание этой игры; менеджер — пусто: эта
версия или новее, `none`: без условия) с кнопкой **Find mods it is made
on**, которая вписывает подставленные зависимости в поле. **Save mod
file…** записывает ZIP, **Install as mod** ставит рабочее пространство в
менеджер этой игры (см. §4). Мастер **Собрать мод…** (руководство §15) — те
же поля на шаге сведений; проверка на последнем шаге называет добавленные
сами зависимости и неизвестные издания.

## 3. Менеджер модов

**Отчёты о падениях (этап 99).** Менеджер один раз спрашивает, держать ли в
`scripts/` игры модуль `doctor_crash.asi`; до ответа модуль не ставится.
После согласия — после «Записать в игру» и перед «Играть» —
менеджер кладёт модуль и пишет список
включённых модов с версиями в `_doctor_toolkit/crashes/context.txt`; когда
игра падает, модуль пишет отчёт и минидамп в `_doctor_toolkit/crashes/`, а
менеджер показывает строку «Последнее падение» с кнопками «Открыть отчёт» и
«Папка». Выключатель — «Отчёты о падениях» в меню «Ещё». Подробно —
`docs/analysis/crash-reports.md`.

**Исполняемый код (этап 81).** Мод формата 5 несёт модули `.asi`. Менеджер
кладёт их в `scripts/` игры только после согласия игрока на этот мод (по
хэшу каждого файла), только на издании 1.0.789.0, и убирает при выключении
мода и «Вернуть оригиналы» — §1.6.

```text
<игра>/_doctor_toolkit/mods/
├── registry.json     установленные моды в порядке загрузки, включён или нет; у мода, поставленного из рабочего
│                     пространства, — его папка (`workspace`, этап 111: `docs/project.md` §0.3)
├── sets.json         сохранённые наборы модов: кто включён и в каком порядке
├── applied.json      что менеджер записал в игру (формат как у рабочего пространства)
├── native.json       ответы игрока про код модов и какие файлы кода положил менеджер (§1.6)
├── .folded/          свёртки дельт (§3.4): index.json и payloads/ со сложенными ресурсами
├── lock              блокировка изменений (пустой файл, этап 107)
├── lock.holder       кто её держит: номер процесса и программа
└── <id>/             установленный мод
    ├── mod.json
    ├── preview.png
    └── payloads/ab/ab12…
```

Установка распаковывает мод во временный каталог `.staging-<pid>`, проверяет
каждый ресурс и только потом переименовывает его в `<id>/`; прерванная
установка не оставляет полумода. При установке мод сразу сверяется с игрой, и
несовпадения показываются. Игра при установке не меняется.

**Один писатель** (`mods::RegistryLock`, этап 107). Моды одной игры
показывают сразу несколько программ — Open Mod Manager, окно Mods
редактора, командная строка; редактор ещё и сам ставит проект как мод
(«Install project into Mods») и читает моды при каждом «Играть». Каждая
держит список модов в памяти и записывает его целиком, поэтому раньше
вторая запись могла потерять мод, поставленный первой. Теперь:

- Изменение — установка, удаление, включение, порядок, набор, запись в игру
  и возврат оригиналов — делается под блокировкой ОС на файле `lock`
  (`File::try_lock`, как у рабочего пространства, `docs/workspace.md` §2;
  общий код — `workspace::lock::FolderLock`). Блокировка берётся на время
  одного изменения, а не на всё время, пока открыто окно. Кто её не получил,
  получает ошибку с именем держателя («the mods in … are being changed by
  open-mod-manager (process N); wait until it has finished and try again»)
  и ничего не меняет. Держатель называется именем исполняемого файла.
- Перед изменением менеджер сверяет `registry.json` и `applied.json` с тем,
  что он читал или писал последним (SHA-256), и, если их поменяла другая
  программа, **читает моды заново** — изменение делается с тем, что есть
  сейчас. Окно делает то же перед каждой своей задачей
  (`ModManager::reload_if_changed`), так что «Обновить» показывает чужие
  изменения.
- Запуск без записи в игру (`play::overlay`, источники `Mods` и `Project`)
  держит блокировку, пока строит подготовленную копию: моды в это время
  никто не ставит и не удаляет. В копию файлы `lock` и `lock.holder` не
  отражаются — менеджер копии блокирует свой файл.
- Блокировка, которая сама создала папку `mods/` (изменение не удалось и
  ничего не записало), убирает её за собой; файл `lock` в папке с реестром
  остаётся.

Чтение (список, проверка, состояние) блокировку не берёт: файлы заменяются
атомарно. Тесты: `two_programs_change_the_mods_without_losing_each_others_changes`,
`one_program_changes_the_mods_at_a_time`.

| Действие | CLI | Окно |
|---|---|---|
| Список | `mods list GAME` | таблица |
| Установить `.zip` или `.vpat` | `mods install GAME FILE… [--disabled]` | **Install mod…** |
| Включить, выключить | `mods enable GAME ID… [--with-deps]`, `mods disable GAME ID… [--force]` | переключатель |
| Порядок загрузки | `mods move GAME ID POSITION` (с 1) | перетаскивание, **Выше**, **Ниже** |
| Упорядочить по правилам | `mods sort GAME [--dry-run]` | **Упорядочить** (Sort) |
| Конфликты | `mods conflicts GAME [--all]` | раздел **Conflicts** |
| Совместимость | `mods check GAME` | столбец State, подробности мода |
| Сравнение с игрой | `mods status GAME` | строка состояния |
| Записать в игру | `mods apply GAME [--force] [--ignore-compatibility]` | **Apply to game** |
| Вернуть оригиналы | `mods unapply GAME [--force]` | **Restore originals** (два щелчка) |
| Удалить | `mods uninstall GAME ID… \| --all [--force]` | **Удалить…** (после вопроса) |

| Код мода: состояние, вопрос, ответ | `mods native GAME [ID] [--allow \| --data-only \| --forget]` | вопрос после установки; раздел «Исполняемый код» выбранного мода |
| Наборы модов: сохранить, выбрать, удалить | — (инструмент `mods_manage`: `save_set`, `use_set`, `delete_set`) | список **Set**: набор, **Save as a set…**, **Delete set …** |
| Привести моды к базе проекта (этап 108) | `project base ПРОЕКТ --apply` | в редакторе: полоса вверху окна и **File → Bring the mods to the project's base** — делает окно Mods |

**Наборы модов** (`sets.json`, формат `doctor-toolkit-mod-sets`) — названная
расстановка: какие моды включены и в каком порядке (`ModManager::save_set`,
`use_set`, `delete_set`, `current_set`, `arrange`; в окне — список **Set**,
§7). Выбор набора меняет только реестр; в игру моды попадают следующей
записью. Мод набора, которого уже нет, называется; мод, установленный позже
набора, выключается и встаёт в конец. Набор — путь назад после «привести
моды к базе проекта» (`docs/project.md` §0.2): `Base::bring` сохраняет
расстановку как `Before <имя проекта>` (`ModManager::free_set_name` даёт
имя, которого ещё нет: `… (2)`), расставляет моды базы и записывает их
одной операцией (`ModManager::arrange_and_apply`: при отказе записи
расстановка возвращается).

**Какие моды стоят в игре** (`ModManager::in_game` → `GameMods`): для
каждого установленного мода — включён ли он и **записан ли в игру**
(`ModInGame::written`), его версия и SHA-256 манифеста
(`ModManifest::sha256`), и сколько ресурсов выключенных и удалённых модов
ещё лежит в файлах игры (`leftover`). «Включён» и «записан» — разное: мод,
включённый после последней записи, в файлах игры отсутствует, а
выключенный — ещё присутствует. С этим списком проект сверяет свою базу.

**Порядок загрузки.** Моды применяются по порядку списка: если два включённых
мода **заменяют** один ресурс целиком, используются данные того, что ниже;
дельты (версия 6) накладываются по очереди и объединяются (§3.4). Конфликт —
ключ ресурса, который целиком меняют или добавляют несколько модов (или
целый ресурс стоит ниже чужих дельт и стирает их); показываются все
такие моды и победитель, а одинаковые данные помечаются как безвредное
пересечение. У модов с дельтами конфликт — только значения, которые задали
оба (`Conflict::elements`), §3.4. Конфликт, в котором победитель зависит (прямо или через
другие моды) от всех остальных, — **патч** (`Conflict::patch`): он
выигрывает намеренно, карточка не предупреждает, `mods conflicts` пишет
«(a patch on top of the others)». Правила порядка версии 3 и их проверка —
§3.2, патчи поверх модов — §3.3.

**Столкновения** (`Clash`; `mods conflicts`, `mods check`, раздел
**Conflicts**) — то, что порядком загрузки не решается:

| Столкновение | Что делается |
|---|---|
| два мода создают поток с одним именем по-разному (хэш, родитель, TOC, флаги) | `apply` отказывает, пока оба включены |
| то же, но одинаково (название операции не в счёт) | безвредно: ресурсы обоих модов ложатся в один поток |
| два мода создают разные потоки с одним хэшем | `apply` отказывает |
| два мода добавляют ресурсы с одним GUID под разными ключами и с разными данными | `apply` отказывает (игра загрузит один); с одинаковыми данными — безвредно, игра делит ресурс |
| мод добавляет ресурсы в поток игры, ресурсы которого заменяет другой мод | только сообщение: записываются оба, автору стоит проверить, что добавленное подходит к заменённому; моды, связанные зависимостью, не сообщаются |
| мод объявил другой мод несовместимым (`incompatible`), оба включены, версия другого подходит под условие | `apply` отказывает (`Clash::Incompatible`), причина автора видна в сообщении, карточке («Несовместим с …») и `mods conflicts` |

**Совместимость.** Перед записью каждый ресурс каждого включённого мода
сверяется с оригиналом игры — с тем файлом, из которого поток будет
пересобран (резервная копия или сам файл):

| Результат | Что делается |
|---|---|
| потока нет в игре, ресурса нет в потоке | запись невозможна, мод нужно выключить |
| данные оригинала отличаются от `original` мода (для целых ресурсов; у дельты оригинал не сверяется) | отказ; `--ignore-compatibility` (флажок в окне) записывает всё равно |
| дельта добавляет то, что уже есть: объект с таким GUID, строку с таким хэшем, часть или вариант с таким именем, ячейку того же потока (`Problem::DeltaRefused`); документ или ресурс под ним не разбирается | запись невозможна: выключить этот мод или тот, что добавил то же самое раньше |
| операции дельты не к чему приложить: объекта, строки, набора, ячейки нет — мод ниже убрал их или игра другого издания (`Problem::OperationsSkipped`) | только сообщение: операция пропускается, остальные пишутся; `mods check`, карточка мода и итог `mods apply` называют мод, объект (или строку) и причину |
| операция дельты задаёт значение, которое в игре не то, что видел автор, и ни один мод ниже его не задавал (`Problem::ValuesDiffer`) | только сообщение: берётся значение мода |
| дельте не на что наложиться: ресурса нет в игре и ни один включённый мод ниже не даёт его целиком | запись невозможна, как для замены |
| исполняемый файл не тот, на котором сделан мод | только предупреждение при установке; известные издания называются по имени (`doctor_toolkit::edition`, «the mod was made for another edition of the game (PC 1.0.764.0, retail DVD …; this game is PC 1.0.789.0 …)») |
| издание игры не в `game.editions` (версия 3; издание игры — `edition::game_edition`: версия известной сборки или версия из исполняемого файла неизвестной, иначе «неизвестное») | «Не подходит к этой версии игры»; запись — только с `--ignore-compatibility` (флажок в окне) |
| `requires_manager` не пускает эту версию программы | «Обновите Open Mod Manager»; запись невозможна |
| зависимость не установлена или выключена (повреждена) | «Нужен мод X ≥1.1»; запись невозможна, обхода нет: без зависимости ресурсы мода сверять не с чем |
| у зависимости не та версия | «Нужна версия X ≥1.1»; запись — только с `--ignore-compatibility` (ресурсы всё равно сверяются с её данными) |
| зависимость ниже мода в порядке | запись невозможна; **Упорядочить** / `mods sort` |
| рекомендованный мод не включён или не той версии | только замечание (`Problem::Recommended`) |
| код мода не может быть поставлен (`Problem::Native`: нет ответа игрока, выбрано «только данные», другое издание, нет загрузчика или платформы, имя модуля занято чужим файлом) | у мода с `native.required` — запись невозможна, обхода нет; у остальных — замечание, пишутся только данные |
| моду нужен ABI платформы новее, чем у программы; модуль установленного мода повреждён | запись невозможна |
| добавленный ресурс уже есть в потоке | запись невозможна |
| GUID добавленного ресурса занят ресурсом игры с другими данными (проверяется по всей игре, по оригиналам; ~2 с на GF2) | запись невозможна; с теми же данными — можно (общий ресурс) |
| добавленный ресурс — в потоке, которого нет ни в игре, ни среди новых потоков включённых модов | запись невозможна |
| замена ресурса в потоке, который создаёт другой мод | запись невозможна: в новом потоке только добавленные ресурсы |
| ресурса `before` нет в потоке | только сообщение: ресурс встаёт в конец |
| новый поток уже есть в игре (файл или запись TOC) | запись невозможна |
| хэш нового потока занят в TOC, TOC нет в игре, родителя нет в TOC | запись невозможна |

Потоки и TOC, которые создал или дописал сам менеджер, сверяются по
оригиналам (резервным копиям), поэтому повторная проверка после `apply` не
находит «занятых» имён и хэшей.

**Запись** (`apply`) пересобирает каждый затронутый поток из оригинала со
всеми выигравшими данными включённых модов — той же функцией, что и
рабочее пространство (`workspace::deploy`): проверки до первой записи,
резервные копии в `_doctor_toolkit/backups/`, атомарная замена файлов, размеры
потоков во всех TOC. Поток, который больше ни один включённый мод не меняет,
возвращается к оригиналу побайтно. Поток, изменённый другой программой,
перезаписывается только с `--force`. Выключение или удаление мода вступает в
силу при следующем `apply`.

Добавленные ресурсы вставляются при той же пересборке (`ustream::rebuild_with`).
Новый поток пишется с нуля, в его TOC добавляются запись имени, файловая
запись и, для дочернего потока, ссылка у родителя; TOC пересчитывается от
оригинала. Поток, который не создаёт больше ни один включённый мод, удаляется,
и его TOC возвращаются к оригиналу побайтно. Проверка целостности называет
файл созданного потока «changed by the mod manager».

**Возврат оригиналов** (`unapply`) возвращает каждый поток, записанный
менеджером, и его размеры в TOC, удаляет созданные потоки; моды остаются
установленными. Тест `adding_mods_install_apply_and_restore_byte_for_byte`
проверяет побайтный возврат после `unapply`, выключения и удаления мода,
`clashes_between_adding_mods_are_found_and_stop_applying` и
`adding_mods_that_do_not_fit_the_game_are_refused` — таблицы выше; корпусный
`cloned_models_and_new_streams_round_trip_on_copies` — что мод из рабочего
пространства с клонами модели и новым дочерним потоком даёт на копиях
настоящих потоков те же файлы, что и само рабочее пространство. Команда
`doctor-toolkit restore` по-прежнему возвращает из резервных копий все файлы,
которые менял тулкит.

### 3.1 Чужие файлы, атомарная запись, незавершённая запись

**Что не считается файлами игры.** Поток — файл `*.str`, который начинается
с магии `3slo`; оглавление — файл `*.toc` с магией StreamTOC (`287bba9c`).
Остальные файлы с такими расширениями пропускаются (`GameInstance::skipped`,
их число пишут отчёт об ошибке и `validate`), их никто не читает и не пишет.
Пример — кэш шейдеров драйвера NVIDIA `GLCache/<hash>/<hash>/*.toc` (магия
`CDVN`) в папке игры: без проверки магии запись мода падала на нём с «bad
StreamTOC magic 0x4e564443». Кроме того, по имени (без учёта регистра)
пропускаются каталоги кэшей драйверов и программ: `GLCache`, `DXCache`,
`NV_Cache`, `ShaderCache`, `shader_cache`, `DxcCache` — и каталоги тулкитов
`_toolkit`, `_doctor_toolkit`.

**Запись — одна операция** (`game::GameWrite`, ею пишут менеджер модов,
рабочее пространство и прямые замены ресурсов). Сначала делается всё, что
может упасть: разбор оригиналов и всех затронутых TOC, сборка каждого нового
потока и TOC; новые файлы пишутся рядом с целевыми во временные файлы
(`.<имя>.<pid>.doctor-toolkit-tmp`) и сбрасываются на диск. Затем
делаются недостающие резервные копии, в `applied.json` отмечаются
записываемые файлы (`in_flight`), и только после этого файлы встают на места
переименованием, а заменённые сохраняются в `_doctor_toolkit/undo/` (жёсткой
ссылкой, где ФС не умеет — копией). Ошибка на этом шаге возвращает уже
поставленные файлы из `undo/` (то есть к состоянию до операции, а не к
оригиналам), удаляет сделанные этой операцией резервные копии и запись
`in_flight`; сообщение кончается словами «nothing is changed in the game».
Ошибка до первой замены ничего не меняет вовсе. Файлы вне потоков (архив-
наложение, ролики рабочего пространства) пишутся после потоков своим путём,
каждый атомарно.

**Незавершённая запись.** Если `applied.json` помнит файл `in_flight`, а файл
игры не равен ни оригиналу, ни записанному ранее (`Deployment::interrupted`,
`ModManager::interrupted`, `mods::interrupted_writes`), запись прервалась
посередине — отключение питания или сбой отката: поток уже другой, а TOC,
возможно, нет. Такой поток никогда не считается «актуальным». Open Mod
Manager показывает это красной строкой с кнопкой «Вернуть оригиналы»,
редактор — ошибкой при открытии игры («Инструменты → Восстановить
оригиналы» возвращает все файлы из резервных копий), CLI `mods` —
предупреждением перед каждой командой. «Вернуть оригиналы» (`unapply`) в
таком состоянии берёт поток из резервной копии побайтно; если при этом
какой-то TOC или оригинал не разбирается, файл всё равно возвращается, а
отчёт предупреждает, что размер в этом TOC оставлен как есть. «Записать в
игру» пересобирает такой поток заново от оригинала. Тесты:
`foreign_toc_files_do_not_stop_writing_mods`,
`a_failed_write_puts_every_file_back` (сбой до и между заменами — игра,
`applied.json` и резервные копии как были),
`restore_originals_mends_an_interrupted_write`,
`restore_originals_does_not_need_the_tables_of_contents`, в Open Mod Manager —
`an_interrupted_write_is_told_and_restored`.

### 3.2 Правила порядка (версия 3)

`mods::order`: **жёсткое** правило — зависимость (`depends`) стоит выше
зависящего мода; **мягкие** — `load_after`, `load_before`. Правило между
модами, один из которых не установлен, не действует. Правила берутся у всех
установленных модов, включённых и нет (порядок не прыгает при
переключении).

- **Установка и включение** ставят мод в ближайшее к его месту допустимое
  (`order::place`): после модов, которые ему нужны, и `load_after`, до
  `load_before` и модов, которым нужен он. Новый мод ставится последним и
  поднимается только при необходимости (зависимость, установленная после
  зависящего мода, встаёт прямо над ним). Если мягкие правила вместе с
  жёсткими не выполнить, учитываются только жёсткие; если и их нельзя — мод
  остаётся на месте, а проверка и **Упорядочить** объясняют почему.
  Обновление мода (тот же `id`) сохраняет место, если новые правила его
  позволяют.
- **Упорядочить** (`ModManager::sort`, `mods sort`, MCP `mods_manage`
  `sort`, Python `ModManager.sort`) — устойчивая топологическая сортировка:
  из модов, которые правила уже разрешают, первым идёт тот, что выше сейчас,
  поэтому ручной порядок сохраняется везде, где правила молчат; повторная
  сортировка ничего не двигает. Цикл из жёстких правил — ошибка с перечнем
  модов («the mods a → b need each other in a circle»); мягкое правило,
  которое замкнуло бы цикл (с жёсткими или с другими мягкими, в порядке
  модов в списке), отбрасывается, и сортировка его называет.
- **Перетаскивание и `mods move`** против жёсткого правила не выполняются:
  «Сюда нельзя: X нужен моду Y, он должен быть выше» (`cannot move …:
  `Y` needs `X``). Против мягкого — выполняются с предупреждением, какое
  правило нарушено. Ход, который не нарушает новых правил (например,
  исправляет уже нарушенное), разрешён.
- **Выключение и удаление** мода, который нужен включённым модам: в окне —
  вопрос со списком, в CLI и MCP — отказ без `--force` (`force`).
- **Включение** мода с установленными, но выключенными зависимостями: в
  окне — вопрос «Включить все / Только этот»; `mods enable --with-deps`
  (MCP `with_deps`) включает и их, без ключа мод включается и сообщение
  называет выключенные зависимости.

Проверено тестами `mods::order` (устойчивость, повторная сортировка,
жёсткий и мягкие циклы, ближайшее место), `mods::version` (условия),
`the_load_order_follows_the_rules`,
`dependencies_versions_and_recommendations_are_checked`,
`editions_the_mod_manager_and_incompatible_mods_are_checked`, CLI —
`mods_of_format_3_build_install_order_and_switch`.

### 3.3 Патчи поверх модов

Мод с `depends` сверяется не с чистой игрой, а с игрой плюс его
**включёнными** зависимостями (и их зависимостями), применёнными по порядку
загрузки (`ModManager::check_mods`): если зависимость меняет или добавляет
ресурс, `original` мода у этого ресурса должен быть данными зависимости;
добавлять ресурсы в поток, созданный зависимостью, и заменять ресурсы в нём
можно. При записи замена ресурса, добавленного зависимостью, остаётся
добавлением (`ModManager::plan`), а оригиналом в плане остаётся оригинал
игры. Тест `a_patch_on_top_of_a_mod_installs_applies_and_restores_byte_for_byte`:
базовый мод меняет меш и создаёт поток; патч, собранный в рабочем
пространстве на игре с записанным базовым модом, меняет меш ещё раз,
заменяет ресурс созданного потока и добавляет в него свой; зависимость
подставлена сама, проверка чистая; запись, выключение патча (игра — как с
одним базовым модом), «Вернуть оригиналы» и удаление обоих дают игру
побайтно.

**С дельтами (версия 6)** патч поверх мода перестаёт быть копией его
данных. Сборка снимает дельту с данных основы (`made_on_data`), в мод идут
только правки автора, и у игрока они накладываются на ту версию основы,
которая у него стоит: основа обновилась — расширение применяется к новой;
операция, чья цель в новой версии исчезла, пропускается с сообщением
(`an_extension_survives_the_update_of_the_mod_it_is_made_on`). `original`
дельты не сверяется, поэтому «не тот оригинал» при обновлении основы
больше не возникает. Зависимость остаётся: без основы объектов, которые
правит расширение, нет. Целый ресурс поверх мода с дельтой (изменение не
выразилось операциями) сверяется со свёрткой зависимостей — у игрока она
должна дать те же данные, что были у автора
(`a_whole_resource_made_on_a_mod_with_a_delta_is_checked_against_the_fold`).

**Основа обновилась у автора (этап 111).** У игрока дельта переживает
обновление основы сама; у автора — нет: его рабочее пространство хранит
«данные прежней основы плюс правка», и следующая сборка сняла бы дельту с
**новой** основы — в мод попали бы операции, которые убирают добавленное
обновлением и возвращают убранное им. Поэтому правка помнит, на каких
данных она сделана (`Change::made_on`, `docs/workspace.md` §3.1), а сборка
сверяет это с тем, на чём мод собирается (`Relations::made_on`, без него —
оригинал игры). Не совпало — ресурс попадает в `BuiltMod::stale`, и отчёт
сборки и установки начинается с предупреждения:

```text
warning: 1 change(s) were made on other data than the mod is built on
(gf2/town/yard:simgroup:…): the mods below were updated or are others since
the edits, and the mod takes back what they changed since. Rebase the changes
first (`doctor-toolkit project rebase`, `workspace rebase`, Rebase in the
Changes panel of the editor)
```

Сборку оно не останавливает (решение и причины — `docs/project.md` §0.3).
Перебазирование переносит правку на нынешние данные основы: операции между
прежней основой и правкой накладываются на новую, и мод снова несёт только
сделанное автором (`a_project_is_rebased_onto_the_update_of_its_base`:
после обновления основы и перебазирования дельта расширения — одна операция
«добавить объект», а не «убрать объект основы, вернуть убранный ею»).

### 3.4 Свёртка дельт (версия 6)

`mods::fold`, `ModManager::plan`. Данные ресурса, который меняют включённые
моды:

1. **основа** — данные последнего включённого мода, который заменяет или
   добавляет ресурс **целиком**; если такого нет — оригинал игры (резервная
   копия или сам файл, как при любой записи);
2. поверх основы — **дельты включённых модов, стоящих ниже неё по списку**,
   по порядку загрузки (`delta::apply_resource`). Дельты модов выше целого
   ресурса им стёрты — это прежний конфликт целых ресурсов.

Результат — новые данные, которых нет ни в одном моде. Менеджер кладёт их в
своё хранилище `.folded/payloads/` **до записи** и называет в плане их
SHA-256 (`Change::payload`), поэтому сравнение с игрой (`up_to_date`),
`applied.json`, возврат оригиналов, резервные копии и запуск без записи
работают без изменений: для них это обычные данные ресурса. Ресурс, чьи
дельты ничего не изменили (все операции пропущены), в план не входит.

**Раскладка.** Дельта SimGroup возвращает байты автора только на той базе,
с которой снята (раздел `layout`, `docs/formats/delta.md` §5.1). На другой
базе — ниже стоит ещё чей-то мод — результат верен по содержимому, но байты
другие. Поэтому свёртка **никогда не сравнивается с хэшем данных автора**
(его в моде с дельтой и нет): в план и в `applied.json` идёт хэш того, что
получилось у игрока.

**Детерминированность и кэш.** Наложение — функция байт данных и байт
документа, поэтому шаг свёртки определяют тип ресурса, SHA-256 данных, на
которые накладывают, и SHA-256 документа. `.folded/index.json` помнит для
каждого шага хэш результата, число применённых операций, пропущенные
операции и конфликты (или причину отказа). Свёртка, все шаги которой
известны, не читает ни одной дельты и ничего не накладывает; включение,
выключение и перестановка модов меняют цепочку ресурса, и считаются только
новые шаги. Данные из кэша читаются по хэшу и сверяются с ним; если данные
дают не тот хэш, что помнит индекс, цепочка считается заново. Папку пишет
только `apply` (проверки и сравнение держат посчитанное в памяти), после
записи в ней остаётся то, на чём стоит записанный план; без модов папка
удаляется. Версия «движка» наложения (`ENGINE` в `fold.rs`) — в индексе:
при её смене шаги считаются заново.

**Конфликты по операциям** (`ModManager::conflicts`, `mods conflicts`,
раздел **Conflicts** окна):

| Случай | Что делается |
|---|---|
| два мода добавляют разное в один ресурс (объекты, строки, части, ячейки) | не конфликт: в игре оба |
| две дельты задают одно значение — атрибут одного объекта, текст одной строки в одном языке | конфликт: побеждает нижний мод; запись называет ресурс, оба мода и элементы (`object <GUID>, Entity.CMD_SetInteriorLit: the value was 5, not default as when the delta was made`). Одинаковое значение у обоих — не конфликт |
| дельта задаёт значение, которое дал целый ресурс мода ниже | тот же конфликт по элементам с этим модом |
| две дельты добавляют один адрес (GUID объекта, хэш строки, имя части или варианта, поток ячейки) | роковая проблема нижнего мода (`DeltaRefused`), §3 «Совместимость» |
| целый ресурс ниже чужой дельты | прежний конфликт целых ресурсов: побеждает целый, список элементов пуст |
| операция, цель которой исчезла | не конфликт: пропуск с сообщением (`OperationsSkipped`) |

Кто задал значение до победителя, менеджер находит по адресам операций
дельт ниже (`Delta::targets`); если не задавал никто — отличается сама
игра, и это сообщение проверки (`ValuesDiffer`), а не конфликт модов.

**Время** (корпусный тест `two_mods_of_random_edits_fold_on_copies_of_real_zones`,
2026-11-18, сборка release): два мода по 172 зоны, по шесть правок в
каждой, — свёртка 344 дельт 0,11 с, повторно по индексу 0,02 с, сама запись
172 потоков 6,2 с; два мода по 600 зон — 0,40 с, 0,06 с и 21,7 с. Свёртка
— доли процента времени записи.

`game-bench.md` §52: два мода, добавившие по объекту в одну SimGroup и по
новой зоне в один город; все четыре объекта и обе зоны в игре — с
подменами (пересборка потоков и ресурсы в памяти) и после `mods apply`.

## 4. Моды и рабочее пространство

Рабочее пространство редактора и менеджер модов **не пишут в игру
одновременно**:

- `mods apply` отказывает, пока рабочее пространство игры
  (`_doctor_toolkit/workspace`) держит свои изменения в файлах игры, — даже с
  `--force`. Сообщение предлагает вернуть оригиналы (`workspace revert --game`
  или **Revert game** в окне Changes).
- `workspace apply` (и прямой режим) отказывает, пока менеджер держит моды в
  игре, и предлагает `mods unapply` или установку рабочего пространства как мода.
- Рабочее пространство в другом каталоге (`--dir`) так не проверяется, но его
  запись менеджер видит как изменение другой программой (поток отличается от
  резервной копии) и без `--force` не трогает; то же в обратную сторону.
- **Рабочее пространство проекта** (этап 107, `workspace::Owner::Project`,
  `docs/workspace.md` §4) в игру само не пишет вовсе: `workspace apply`,
  прямой режим и `project build --apply` отказывают и называют путь через
  менеджер. У файлов игры поэтому один владелец, кроме рабочего
  пространства самой игры, — менеджер модов.

Почему так: у каждого владельца своя запись `applied.json`, и общий файл,
который пишут двое, превращается в конфликт при каждой записи. Чтобы
проверить свою работу вместе с другими модами, автор ставит рабочее
пространство как мод: `doctor-toolkit mods install-workspace GAME --name …`
или **Install as mod** в окне Mods. Мод встаёт последним в порядке загрузки
(выигрывает конфликты) и включается; повторная установка с тем же `id`
обновляет его. Проверено тестом
`the_workspace_and_the_mods_do_not_write_at_the_same_time`.

**Проект — мод менеджера** (этап 107, `docs/project.md` §0.1). Проект со
своим рабочим пространством попадает в игру только так:

| Как | Что происходит |
|---|---|
| **File → Install project into Mods** в редакторе, `doctor-toolkit project install ПРОЕКТ` | `Project::install_into`: рабочее пространство проекта ставится модом с id, именем и версией из `project.toml`, включённым и последним; зависимости — моды базы проекта с её условиями (§2), а у проекта без базы — моды, записанные в игру, на данных которых сделаны правки (`add_suggested_dependencies`). В файлы игры он попадает при следующем `apply` менеджера |
| **Play** в редакторе, `play --workspace-dir ПРОЕКТ/workspace`, `live install --apply --workspace-dir …`, инструмент `play` сервера MCP | источник оверлея `Source::Project`: в подготовленной копии игры (`play::overlay`) открывается менеджер модов **копии** — те же моды, тот же порядок, — в него ставится проект, и `apply` менеджера пишет в копию. Игра видит «включённые моды и проект поверх», в том числе когда моды записаны в файлы игры. Папка игры, `registry.json` и `applied.json` настоящего менеджера не меняются: в копии это ссылки, а запись заменяет ссылку файлом копии |

Проект ставится модом с дельтами (если в `project.toml` нет `[build]
deltas = false`), и менеджер копии сворачивает их так же, как менеджер
игры: проект поверх модов с дельтами в игре виден вместе с ними
(`the_staged_mods_and_a_project_are_folded`). Папка `.folded` копии — своя;
индекс игры в ней — ссылка, пока свёртка копии не узнала нового.

Проект без правок модом не становится; мод с его id, уже стоящий в
менеджере (проект, установленный раньше), в копии заменяется нынешним
состоянием проекта, а у проекта без правок — выключается. Заменённые
ролики (`file:…`), которых формат мода не несёт (§1.5), кладутся в копию
как файлы, поэтому «Играть» их показывает, а установленный мод — нет.
Тесты: `a_project_is_staged_on_top_of_the_mods_written_into_the_game`,
`the_installed_state_of_a_project_is_replaced_for_the_launch`
(`play/overlay/tests.rs`), `a_project_is_installed_into_the_mods`
(`project/tests.rs`).

## 5. Патчи старого тулкита (`.vpat`)

Формат восстановлен по пяти патчам, которые старый тулкит поставил в игру
(`_toolkit/installed_patches/`), сравнением с изменёнными файлами игры и с
оригиналами в `_toolkit/backups/`. Код старого тулкита не использовался.
Смысл флагов, операций и блока ресурсов, адресуемых по типу, взят из сверки
с другим редактором игр EARS (этап 39) и
не противоречит пяти патчам: у всех флаги патча 0, версия потока 0, флаги
файла 0 или 1, операция 1 у всех 177 ресурсов. Числа little-endian, строки
оканчиваются нулём (Latin-1).

| Поле | Тип | Значение |
|---|---|---|
| магия | 4 байта | `VPAT` |
| версия формата | u32 | 1 |
| название | строка | `Restored HQ Billboards` |
| автор | строка | `cha1r` |
| версия патча | u32 | 1, 3, 4, 8 |
| игра | u32 | 2 — The Godfather II (как `type="2"` в `_toolkit/game_instance.xml`) |
| идентификатор патча | u32 | случайное число, выбранное при создании патча |
| флаги патча | u32 | 1 — поднимать версию при каждой правке; во всех пяти 0. На установку не влияют |
| число файлов | u32 | |
| **файл:** путь | строка | относительно каталога игры, с `\`: `gf2\queens\local.str` |
| версия потока | u32 | 0 |
| флаги файла | u32 | 1 — ничего особого, 2 — после списка идёт блок ресурсов по типу; в старых патчах 0. Другие биты — ошибка разбора |
| число ресурсов | u32 | |
| **ресурс:** ids | 4 × u32 | четыре идентификатора из `SHDR` |
| тип | u32 | `type_id` из `SHDR` |
| операция | u32 | 1 — заменить, 2 — удалить, 3 — добавить; 0 — ничего (пропускается). Другое — ошибка разбора |
| размер | u32 | |
| данные | байты | распакованные данные ресурса |
| **при флаге 2:** число | u8 | ресурсы, адресуемые по типу |
| **ресурс по типу:** тип, операция, размер | 3 × u32 | как выше, без ids |
| данные | байты | |

Ресурс по типу — единственный ресурс этого типа с нулевыми ids в потоке. В
игре нулевые ids только у таких типов, и каждый встречается не больше одного
раза на поток: `simgroup` (1 856 потоков), `covernodetable` (`0xDF14DA75`,
682), `lighttoc` (30), `variabledictionary` (26), `bricknmortarres` (3).
Если в потоке два таких ресурса одного типа, установка отказывает.

Ресурс указывается так же, как ключ ресурса: поток, тип и четыре ids, поэтому
патч переводится в мод без догадок. Файл читается целиком структурно с
проверкой границ (размеры не выходят за файл, после последнего ресурса нет
данных, не больше 10 000 файлов и 250 000 ресурсов).

**Сверка с игрой.** Для каждого из четырёх изменённых потоков каждый ресурс
текущего файла сравнён с оригиналом и с данными патчей в порядке установки
из `game_instance.xml`:

| Патч | Ресурсов | Найдено в игре | Результат |
|---|---|---|---|
| Beta Weapon Icons | 1 (`apx`) | 1 | данные в игре равны данным патча |
| Improved Effects | 42 (текстуры) | 42 | равны |
| Restored HQ Billboards | 6 + 2 (текстуры) | 8 | равны |
| US Font Mod | 6 + 6 (текстуры, шрифт) | 0 | ресурсов с такими ids в этой копии игры нет нигде (шрифты здесь — с другими ids); видимо, патч для другого издания |
| Improved Weapons | 114 (текстуры) | 114 | равны |

Остальные ресурсы потоков не изменены. Старый тулкит переписывал поток
целиком, сохраняя **все** ресурсы несжатыми (`globals_global.str` вырос с
42 до 139 МБ, у `frontend.str` нет ни одной замены, но он тоже распакован), и
**не обновлял размеры в TOC**. Наша запись сохраняет сжатие оригинала и
обновляет TOC (тот же `globals_global.str` после установки тех же патчей —
81 МБ).

**Установка `.vpat`** (`mods install GAME patch.vpat`, **Install mod…**)
превращает патч в мод: `id` из названия, версия — номер версии патча,
`converted_from: "vpat"`. Полей версии 3 у такого мода нет, поэтому он, как
и раньше, пишется наименьшей подходящей версией формата — 1 или 2 (то же
правило, что для любого мода без зависимостей); версия патча — целое число,
поэтому как semver она читается (`8` = `8.0.0`) и в условиях других модов
работает. Оригинал каждого ресурса берётся из резервной копии
тулкита, иначе из резервной копии старого тулкита, иначе из файла игры.
Заменяемые ресурсы, которых нет в игре, пропускаются с предупреждением (как
это делал старый тулкит); если не подошёл ни один, установка отказывает.
Добавляемый ресурс становится добавленным ресурсом мода (версия 2, §1.2): в
конец потока, с политикой памяти и выравниванием первого ресурса того же типа
в потоке, а если такого нет — обычными для типа; добавляемый ресурс, который
в игре уже есть, заменяется с предупреждением. Удалять ресурсы игры мод не
умеет, поэтому патч с операцией «удалить» не устанавливается — сообщение
называет число таких ресурсов и первый из них. `mods info --resources`
показывает операцию каждого ресурса и пометку «by type». Установленный патч
можно сохранить как обычный мод (`mods export`).

**Переход со старого тулкита** (`mods import-old GAME`, кнопка **Import from
old toolkit**):

1. резервные копии старого тулкита копируются в `_doctor_toolkit/backups/`
   там, где у тулкита своей копии нет, и становятся оригиналами;
2. установленные патчи ставятся как моды в порядке `game_instance.xml`;
3. файлы игры не меняются. Изменённые старым тулкитом потоки теперь
   отличаются от оригинала, поэтому первая запись — `mods apply --force`
   (флажок **Overwrite files changed by other programs**). Она пересобирает
   потоки из настоящих оригиналов с теми же данными и правильными TOC.

На копии игры из символических ссылок (настоящая игра не менялась): 4 патча
стали модами (US Font Mod не подошёл), `apply --force` переписал 3 потока и
5 TOC за 2 с, `unapply` вернул оригиналы. Корпусный тест
`old_toolkit_patches_install_as_mods_on_copies` делает то же на копиях
оригиналов и проверяет каждый ресурс, размеры в TOC, экспорт мода и возврат
к оригиналам побайтно.

## 6. Проверка целостности

`doctor-toolkit integrity GAME` (кнопка **Check integrity**) проверяет каждый
поток и TOC и называет, кто его изменил:

| Состояние | Когда |
|---|---|
| original | равен резервной копии тулкита, старого тулкита или эталонному хэшу |
| changed by the mod manager | отличается от копии, и `mods/applied.json` говорит, что его записал менеджер |
| changed by the editor's workspace | то же для рабочего пространства игры |
| changed by the old toolkit | отличается от копии старого тулкита (или наша копия совпадает с ней) |
| changed by another program | отличается от копии тулкита, но никто из своих его не писал |
| differs from the reference list | отличается от эталонного хэша |
| not verified | ни копии, ни эталона: проверить не с чем |

Эталон — `_doctor_toolkit/reference.json`, размеры и SHA-256 оригиналов всех
потоков и TOC. Его записывает `integrity --save-reference` на заведомо
неизменённой игре (оригиналы берутся из резервных копий, где они есть).
Без `--full` файлы без копий сравниваются с эталоном только по размеру,
с `--full` — по хэшу (читается вся игра, ~9 ГБ). Готовый эталон для GF2 PC в
поставку не входит: изданий несколько, а копия на этой машине уже менялась.

Ещё проверка показывает установленные патчи старого тулкита и остатки
прерванной записи (`*.doctor-toolkit-tmp`, игра их не читает).
`integrity --adopt-old-backups` делает только шаг 1 перехода со старого тулкита.

## 7. Open Mod Manager (`open-mod-manager`)

```sh
cargo run --release -p doctor-toolkit-mods --bin open-mod-manager -- "$GAME"
```

Отдельная программа для игроков, часть doctor_toolkit («Powered by Doctor»
в правом верхнем углу окна; файл `open-mod-manager`, на Windows
`open-mod-manager.exe`). Руководство — `docs/guide/07-mods-players.md`.
Это та же панель, что окно **Mods** в редакторе (крейт
`doctor-toolkit-mods`, библиотека и программа); в редакторе к ней добавлен
раздел сборки мода из рабочего пространства, а кнопка «Играть с модами»,
перетаскивание файлов и клавиши — только в программе
(`ModsPanel::standalone`). Чтение и запись игры идут в фоновом потоке.

**Этап 64 — удобство для игроков.**

- Игра (`games.rs`): папка из командной строки, иначе запомненная (`game`
  в `mods.toml`), иначе поиск `install::detect` (плюс папки
  `$DOCTOR_TOOLKIT_MODS_SEARCH`; с `DOCTOR_TOOLKIT_MODS_SEARCH_ONLY=1` —
  только они). Одна найденная копия открывается сразу, несколько — выбор
  (путь, издание `Edition::name`, где найдена), ни одной — подсказка и
  «Указать папку игры…».
- Аргументы: папка — игра, файлы `.zip`/`.vpat` — моды; они ставятся после
  вопроса, когда игра открыта. Файлы, брошенные на окно (`dropped_files`),
  ставятся сразу, прочие отклоняются словами. Ярлык
  `tools/desktop/open-mod-manager.desktop` объявляет `MimeType`
  `application/zip` и `application/x-godfather2-vpat` (тип описан в
  `open-mod-manager.xml`, `install-desktop.sh` кладёт его в
  `$XDG_DATA_HOME/mime`): программа появляется в «Открыть с помощью», не
  становясь обработчиком `.zip` по умолчанию. На Windows — «Открыть с
  помощью» → `open-mod-manager.exe`, реестр не трогается.
- Карточки (`cards.rs`): картинка мода, имя, версия, автор, первый абзац
  описания, переключатель, состояние (`state.rs`, `ModState`): Готов,
  Выключен, Не подходит к этой версии игры (несовпадения `check`, кроме
  замечаний), Не работает вместе с … (роковые `Clash`), Конфликт с … (общие
  ресурсы с другими данными; подсказка — чей вариант берётся), Ещё не
  записан в игру (поток мода не `up_to_date`), Повреждён. Порядок —
  перетаскиванием (`DragAndDrop`, линия вставки между карточками),
  контекстное меню и клавиши (Alt+↑/↓) — запасные пути.
- Этап 71 (версия 3): состояния «Обновите Open Mod Manager», «Нужен мод X
  ≥1.1» / «Нужна версия X ≥1.1» / «X должен быть выше» (подсказка — что
  сделать с каждой зависимостью), «Не подходит к этой версии игры» с
  подсказкой про издания и флажок совместимости, «Несовместим с …» с
  причиной автора; кнопка **Упорядочить** (Sort); перетаскивание против
  зависимости не выполняется и объясняется в строке сообщения, против
  мягкого правила — выполняется с предупреждением; вопросы перед
  выключением и удалением нужного другим мода и при включении мода с
  выключенными зависимостями («Включить все / Только этот»); в карточке
  выбранного мода — раздел «Зависимости»: что нужно, рекомендовано,
  несовместимо, правила порядка, кому нужен этот мод, с состоянием цветом,
  проверенные издания, нужная версия менеджера и кнопка «Включить нужные
  моды». Тест `cards_tell_what_a_mod_needs_and_the_order_keeps_it`.
- Главные кнопки: «Играть с модами» (`play.rs`: `overlay::availability`;
  копия `Overlay::build(Source::Mods)`, модуль с перенаправлениями, без
  записи в игру; после выхода игры модуль и копия убираются; без модуля
  или загрузчика ASI — окно с объяснением и «Записать в игру и играть»;
  с флажком «Ресурсы в памяти» вверху окна (`resources_in_memory` в
  `mods.toml`, выключен по умолчанию; этап 100) копия строится
  `Overlay::build_with(…, Streams::Patched)`: вместо пересобранных потоков
  в ней заплатки ресурсов, а модуль собирает потоки при загрузке —
  `docs/analysis/resources-in-memory.md`; файлы архивов формата 4, TOC и
  новые потоки идут прежним путём),
  «Записать в игру», «Вернуть оригиналы» — после вопроса, с окном хода
  (`ModManager::apply_with_progress`, `Deployment::sync_with_progress`:
  поток за потоком) и итогом словами.
- Наборы модов: список **Set** в строке кнопок (виден, когда есть моды
  или наборы) показывает набор, с которым совпадает нынешняя расстановка,
  или «Not saved»; в списке — сохранённые наборы (щелчок переключает),
  **Save as a set…** (вопрос об имени; набор с таким именем заменяется) и
  **Delete set …** для выбранного (после вопроса). `ModManager::save_set`,
  `use_set`, `delete_set`, `current_set`, `arrange` (файл `sets.json` рядом
  с `registry.json`, формат `doctor-toolkit-mod-sets`). Мод набора,
  которого уже нет, называется; установленный позже набора — выключается и
  идёт в конец. Тот же список — в окне Mods редактора, где им пользуется
  и «Привести моды к базе проекта» (этап 108, §3):
  `ModsPanel::bring_to_base` показывает ход записи и итог с именем набора,
  в котором сохранена прежняя расстановка; тест
  `the_mods_are_brought_to_the_base_of_a_project`.
- Отмена последнего изменения (вкл/выкл, порядок, набор — прежний
  `arrangement`; удаление — `remove_undoable`: файлы мода переносятся в
  `.removed-*` и возвращаются `restore_removed` на прежнее место;
  `discard_removed`/`purge_removed` удаляют их, когда отмена уже не нужна).
- Свёрнутый раздел «Подробности»: id, источник, потоки и ресурсы мода,
  создаваемые потоки, несовпадения, конфликты по ключам ресурсов,
  проверенные файлы игры. Проверка целостности — в меню «Ещё», итог —
  словами (`integrity_words`).
- Тема — общая с редактором (`doctor_toolkit_mods::theme`, редактор
  реэкспортирует её как `app::theme`).
- Этап 63 (проверка на игре): картинка карточки кэшируется по id, времени
  установки и версии мода — обновлённый мод показывает свою картинку сразу;
  в шапке папка игры идёт последней и обрезается по ширине (полная — в
  подсказке). Выбор файла «Установить мод…» (`rfd`) на Linux идёт через
  портал `xdg-desktop-portal` шины сеанса: на стенде менеджер запускается
  через `dbus-run-session` (`game-bench.md` §30).

- Этап 81 (версия 5, `native.rs`): у мода с кодом на карточке метка
  **«Исполняемый код»** (подсказка — состояние кода). После установки
  такого мода (и при открытии игры, где он включён и ответа нет) один раз
  сам открывается вопрос: что в моде программа, а не только данные, файлы
  мода и файлы менеджера с размерами и SHA-256, что мешает установке
  помимо ответа, и кнопки **«Разрешить код»**, **«Только данные»** (нет у
  мода с `required`), **«Выключить мод»**, **«Решу позже»**. Состояния
  карточки: **«Ждёт вашего согласия»** (ответа нет; у мода с `required` до
  ответа не пишется ничего), **«Код мода поставить нельзя»** (мод с
  `required`: другое издание, нет загрузчика, нет платформы, имя занято —
  причина в подсказке), «Ещё не записан в игру» (код разрешён, но ещё не
  в игре), «Готов». В разделе выбранного мода — блок «Исполняемый код»:
  состояние словами (поставлен / разрешён, ждёт записи / без кода по

- Этап 110 (версия 6): в разделе выбранного мода — строка **«Объединяется

## 8. Открытые вопросы

- Дельты (§1.7, §3.4). Правило размера оставляет целыми маленькие ресурсы:
  на игре новый объект в SimGroup идёт дельтой в 82 % зон, шесть смешанных
  правок — в 75 % (`docs/formats/delta.md` §9); такой мод с чужими правками
  той же зоны не объединяется. Способа потребовать дельту вопреки размеру
  нет. Конфликт по элементам находится только там, где операция несёт
  прежнее значение (`simgroup`, `lh2`); у `partsdb` и `wgi` операций,
  задающих значение, нет. Файлы архивов и новые потоки не сворачиваются:
  там по-прежнему побеждает последний мод. Свёртку `--ignore-compatibility`
  не затрагивает: отказ дельты (`DeltaRefused`) им не обходится.
  `mods status` и `mods check` читают оригиналы ресурсов с дельтами при
  каждом вызове (хэш); при тысячах таких ресурсов это десятки миллисекунд.

- Код модов (§1.6): согласие хранится в папке игры, поэтому копия игры или
  переустановка спрашивает заново; подписи авторов и списка доверенных
  авторов нет — игрок судит по имени автора и хэшу. Загрузчик тулкита не
  проверен на Windows (только Wine) и не умеет того, что умеет Ultimate ASI
  Loader сверх загрузки модулей (подмена файлов из `update`, настройки).
  Сборки мода с кодом нет в Python и MCP. Файл классов мода для
  инструментов (`DOCTOR_TOOLKIT_CLASSES`) в мод не кладётся.

- Патч, собранный поверх мода, который не записан в игру (только установлен
  и включён), зависимость сам не получает: подстановка смотрит на то, что
  менеджер записал (`applied.json`). Её можно указать руками (`--depends`).
  **Для проектов закрыто на этапе 108:** зависимости мода проекта берутся
  из его базы (`[base]` в `project.toml`, §2), а не из догадки, и данные
  базы для `original` — из включённых модов базы, записаны они или нет.
  Для мода, собранного из рабочего пространства без проекта (`mods build`,
  раздел сборки окна Mods), вопрос остаётся.
- Наборов модов нет в командной строке (`mods …`): сохранить, выбрать и
  удалить набор можно в окне и инструментом `mods_manage`. После `project
  base --apply` вернуться к сохранённой расстановке из командной строки
  нельзя.
- Издание неизвестной сборки определяется по версии в исполняемом файле;
  две разные неизвестные сборки с одной версией для мода неразличимы.
- Удаление созданного потока оставляет пустые каталоги (`gf2/doctor/`), как и
  рабочее пространство; игра их не замечает.
- Блокировка менеджера (§3, этап 107) закрывает одновременные изменения и
  изменение по устаревшему списку. Вне её остались ответы игрока про код
  (`native.json`: `native::set_consent`) и уборка отложенных удалений
  (`purge_removed`, `discard_removed`) — они пишут свои файлы без
  блокировки; окно не узнаёт о чужом изменении само, пока не выполнит
  задачу или «Обновить».
- Отпечаток игры — только исполняемый файл; эталонных хэшей GF2 PC в поставке нет.
- Патчи `.vpat` с блоком ресурсов по типу и с операциями «удалить» и
  «добавить» в обращении не встречались: читатель проверен на синтетических
  патчах (`mods/tests.rs`) и фаззингом, на настоящих — нет. Удаление ресурсов игры
  модом не поддерживается.
- Окно не сравнивает текстуры мода с оригиналом; для этого есть панель Changes
  рабочего пространства.
- Этап 110: цель `mod_manifest` проверяет и версию 6 (зерно
  `manifest_v6.json`: дельты всех четырёх видов, с `original` и без, рядом
  с целым ресурсом): вид дельты подходит типу ресурса, дельта не у
  добавленного ресурса, манифест с дельтой требует версии 6 и программой,
  читающей до версии 5, отвергается — и как прочитан, и как записан обратно;
  2,9 млн прогонов за 121 с, ошибок нет.
- Этап 71: цель `mod_manifest` проверяет и поля версии 3 (зерно
  `manifest_v3.json`; каждое условие после записи и повторного разбора то же
  и так же судит версию мода): 5,4 млн прогонов за 171 с, ошибок нет.
- Фаззинг разборщиков ZIP, `mod.json` и `.vpat` сделан на этапе 13 (цели `mod_zip`, `mod_manifest`, `vpat` в `fuzz/`); ошибок не найдено. На этапе 39 цель `vpat` проверяет и ресурсы по типу и операции (новое зерно `by_type_and_operations.vpat`): 2,5 млн прогонов за 3 мин, ошибок нет.
