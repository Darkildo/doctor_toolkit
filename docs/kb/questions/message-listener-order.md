# В каком порядке слушатели одного сообщения получают его

По коду: слушатели лежат блоками по приоритету (блоки по убыванию; почти все подписки — с приоритетом `0x8000`), внутри блока новый узел встаёт в голову списка (`0x00409090`) — то есть последний подписавшийся зовётся первым.

На стенде четыре `TestTimeOfDay` одного потока получили `aud_test_tod` в порядке возрастания их номеров в списке объектов модуля связи (5386…5389). Соответствует ли этот список порядку создания объектов (и порядку объектов в SimGroup), не установлено, поэтому вывод «в игре объект, стоящий в файле позже, получает сообщение раньше» не подтверждён и не опровергнут. Прогон логики без игры (`logic-run`) зовёт слушателей в порядке объектов области.

Этап 79: `TriggerAuto` подписывается на `iMsgPostSpawnInitialize` с приоритетом `0x7FFF` (конструктор `0x00477DB0`), а не `0x8000` — то есть попадает в другой блок слушателей, чем остальные объекты; порядок блоков («по убыванию») значит, что `TriggerAuto` получают это сообщение после объектов с приоритетом `0x8000`. На стенде не проверено.

## Следующий шаг

Проверить, в каком порядке модуль обходит объекты (список SimManager: голова — новые или старые), и сравнить порядок получателей сообщения с порядком объектов в SimGroup: сообщение с двумя слушателями в одном файле, `live log --messages` (получатели идут в порядке обхода таблицы). По результату поправить порядок в `logic-run`.
