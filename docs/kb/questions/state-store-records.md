# Хранилище состояния объектов: что попадает в сохранение

Известно по коду: хранилище `*0x01223418` держит записи по GUID объекта; перед сохранением рассылает `iMsgStoreEntity` (`0x0043D260`), после загрузки — `iMsgRestoreEntity` (`0x0043D450`). Записи кладут `MultiManager` (`0x5E1F74A6`, остаток срабатываний), `TriggerBase` (`0x9BC8A380`), `VariableWatcher` (`0x8C207D80`); метка `0x137726B7` («объект отработал») заставляет фильтр `0x0043D650` не создавать объект заново. Метку ставят `TriggerAuto`, `MultiManager`, `MultiRemoveTarget`, `TriggerBase`.

Не известно:

- запись `0x5E1F74A6` создаётся без бита сохранения (`0x0043D5F0` пишет флаги 0): по `0x0043D260` / `0x0043D300` она попадает в файл, только если стоит бит 0 слова `+0x1C` хранилища — кто его ставит, не прочитано;
- удаляет ли `0x0043D1B0` с ключом (GUID, −1, −1) одну запись или все записи объекта;
- когда метка `0x137726B7` снимается (`0x0043CFC0`, по маске категории): при новой игре, смене миссии, перезапуске чекпоинта;
- как эти записи лежат в файле сохранения (блок формата сохранений).

## Следующий шаг

Прочитать вызывающих слотов 1–3 таблиц хранилища (`0x0043CCE0` регистрирует их в менеджере объектов) и `0x0043CFC0`; сопоставить с форматом сохранения ([сохранения](../../formats/save.md)). На стенде: мод с `TriggerAuto` с флагом 1 — срабатывает ли он повторно после загрузки сохранения.
