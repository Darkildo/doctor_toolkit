# Объединение вызовов отрисовки: опыт на стенде (этап 101)

Стенд: свой префикс и тень, модуль связи на порту 47901, старт подменой `cmd.txt`; графический модуль с `draw_trace`, `draw_merge` в `scripts/`. Гавана — DXVK 2.6.2 на NVIDIA, 1280×720; после отказа драйвера видеокарты стенда в 16:53 все три города — wined3d поверх llvmpipe, 640×480 (4–7 с на кадр). Второй замер после перезагрузки — снова DXVK на NVIDIA, 1280×720, три города: время, кадр и устойчивость.

| Что | Результат |
|---|---|
| запись кадра D3D9 в трёх городах | 5 788 / 8 828 / 5 983 вызовов отрисовки (Гавана / Нью-Йорк / Майами); карта теней 22–37 %, глубина и нормали 26–36 %, освещённый проход 32–38 %; серии без смены состояния — 23–33 % вызовов; лишних вызовов состояний 3–6 % |
| `draw_merge=1` (серии от трёх вызовов одним) | до Direct3D доходит на 25–26 % (Гавана), 19,3 % (Нью-Йорк), 16,9 % (Майами) вызовов меньше — как в прогнозе по записи |
| сравнение снимков остановленной игры, включено против выключено, два вида в каждом городе | вне маски того, что движется само, пары разных состояний отличаются не больше пар одного состояния (медианы 0–156 против 48–930 пикселей) |
| сравнение снимков под DXVK в Нью-Йорке и Майами (по две серии с камеры игрока и повтор «игрок / сверху»), ещё раз Гавана | то же: пары разных состояний — медианы 23–413 пикселей с камеры игрока и 42–1 063 сверху, пары одного — 59–526 и 64–660; в повторе в Майами разница больше, но идёт от машин, прохожих и смены освещённости между снимками, а не от состояния |
| время кадра и ЦП, серии «включено — выключено» по 8 с под DXVK: три города, по три сеанса по 280 с, 87 сравнений на город | **выигрыша нет.** Время кадра: −0,0 / +0,1 / +0,1 % (Гавана / Нью-Йорк / Майами; квартили ±1 %) — кадр стенда держит показ в Xvfb. ЦП потока рендера: **+5,2 / +7,9 / +6,5 %** (квартили +2,0…+8,3, +4,8…+10,4, +2,4…+9,1; знак один во всех девяти сеансах). ЦП потока `dxvk-cs`: −1,3 / −0,5 / 0,0 % (внутри разброса) |
| устойчивость итоговой сборки под DXVK: `draw_merge=1`, семь переносов игрока на 150–300 м, три города | по сеансу 6,9 мин, 14,4–14,9 тыс. кадров: без падений, исключений и отказов в журнале модуля; журнал ядра о видеокарте чист |

Найдено:

- Первый вариант (вызов уходил в устройство после `Issue` запроса видимости, созданного до установки перехватов) убирал из кадра дальние здания — [запросы видимости](../questions/occlusion-queries.md). Поймано сравнением снимков, исправлено.
- Буфер индексов, созданный в первом кадре потока рендера, ронял игру внутри DXVK — [вопрос](../questions/dxvk-buffer-allocation-failure.md); модуль создаёт буфер заранее.
- Кэш состояний у игры уже есть; фильтр лишних вызовов сам по себе убирает 3–6 % вызовов состояний.
- Меньше вызовов — не меньше времени: модуль перехватывает 24–43 тыс. вызовов устройства за кадр и сверяет состояния с копией, а экономит 1 000–1 900 вызовов отрисовки, каждый из которых в DXVK на потоке игры — запись команды в очередь (объяснение — догадка по устройству DXVK). Поток рендера с объединением занят больше.
- Отказ видеокарты первого дня не повторился за 26 сеансов второго замера: связи с модулем не видно. Под пиком чужой нагрузки машины драйвер записал в журнал ядра отказ выделения памяти (`NV_ERR_NO_MEMORY`); сеанс прошёл как обычно, на нём замеры остановлены, а строка ещё дважды повторилась без игры этапа (от модуля не зависит) — серии в окне 640×480 сняты не во всех городах (в Гаване то же: поток рендера +8 %, кадр без изменений), серии с одним фильтром не сняты.

Что не сделано и не проверено: [Windows с Direct3D 9 драйвера](../questions/draw-merge-on-native-d3d9.md) — единственное место, где объединение ещё может окупиться; цена самих перехватов против игры без них (сеансы без перехватов попали под чужую нагрузку); полноэкранный режим и `Reset`; долгая игра, езда и бой; [инстансинг реквизита](../questions/draw-instancing.md). `draw_merge` по умолчанию выключен и включать его по умолчанию не нужно.
