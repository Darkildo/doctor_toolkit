# Вся игра как проект

Редакция от 2026-11-20. Издание 1.0.789.0 (данные NTSC). Источник — корпусный
тест `whole_game::the_whole_game_builds_back_from_a_project`
(`crates/doctor-toolkit/tests/corpus/whole_game.rs`): все ресурсы всех потоков
разбираются в исходники проекта (`docs/project.md`), затем каждая запись
собирается заново (`project build --force`) в пустое рабочее пространство.
Файлы игры только читаются.

```sh
EARS_GF2_DIR="/path/to/The Godfather II" DOCTOR_WHOLE_GAME=1 \
DOCTOR_WHOLE_GAME_DIR=/big/disk/whole DOCTOR_WHOLE_GAME_REPORT=whole.txt \
    cargo test --release -p doctor-toolkit --test corpus whole_game -- --nocapture
```

## 3. Что не сошлось

- **Три скрипта Lua** (`gf2/globals_global`: `aud_pc_car`,
  `mus_underscore`, `mus_underscore_content_mia`) после декомпиляции и
  компиляции давали другой байт-код. Остальные 27 — побайтно. Исправлено
  (ниже).
- **Десять теневых мешей в `shared/`** (`*__shadow_dmg0`, `shadowfemale_lod1`)
  не собирались: «meshvolatile … is already in the workspace». Исправлено
  (§3.2).

### 3.1 Три скрипта Lua

Код, константы (и числа `float`), имя чанка, upvalue и области локальных
переменных совпадали; в каждом скрипте отличался один номер строки
отладочной информации (`formats/lua.md` §3):

| Скрипт | Функция, инструкция | Строка: игра / сборка | Причина |
|---|---|---|---|
| `aud_pc_car` | `main.12`, 248-я, `JMP` перед `elseif TESTChaseCars ~= 0` | 463 / 462 | переход через `elseif` имеет строку последнего токена ветки — `end` вложенного `if`, а декомпилятор ставил этот `end` сразу под последним оператором |
| `mus_underscore` | `main.24`, 297-я, `JMP 0` перед пустым `else` | 965 / 963 | то же: `end` вложенного `if … else … end` стоял двумя строками ниже |
| `mus_underscore_content_mia` | `main`, 672-я, `LOADK 110812` | 503 / 502 | 33-й элемент таблицы ставился на строку `SETLIST` — сброса 32 элементов, который кодируется на запятой после 32-го |

Почему проверка при создании проекта их пропустила: она принимала и «тот
же код, другая отладочная информация» (`Comparison::SameCode`), а сборка
сравнивает байты. Теперь декомпилятор ставит `end` вложенного `if` на строку
перехода через `else`/`elseif` и не относит сброс `SETLIST` к следующему
элементу таблицы; все 30 скриптов компилируются обратно побайтно (корпусный
тест `every_lua_script_decompiles_and_compiles_back`; проект
`gf2/globals_global --type lua`, `project build --force` — 30 записей,
0 изменённых ресурсов). Проверка при создании принимает только побайтное
совпадение: скрипт, чьи строки разошлись бы, остаётся `raw`. Тест
`whole_game` больше не допускает изменённых записей `lua`.

### 3.2 Десять теневых мешей

Теневые меши машин (`<машина>__shadow_dmg0`), `shadowfemale_lod1` и
`shadowmale_lod1` — все 50 ресурсов `mesh` игры без `meshvolatile`: все
вершины лежат в самом меше. Общего `meshvolatile` у двух мешей в игре нет
(id `meshvolatile` — `!id` своего меша), и при создании проекта запись
теневого меша — один меш, ключ на поток. 50 ресурсов в 50 потоках дают 21
запись, из них 10 в `shared/` (одинаковые данные в нескольких потоках):
ровно десять ошибок прогона.

Причина — в сборке модели. Запись собирается в каждый свой поток вызовом
`import::model::plan`, а импорт модели по умолчанию заменяет меш и во
**всех копиях** — потоках игры, где лежит меш с теми же ids
(`docs/model-import.md`, «Копии в других потоках»). Общая запись потоков A
и B планировала поток A, который заменял и копию в B, и поток B, который
заменял и копию в A, — каждый ресурс писался дважды. У меша с
`meshvolatile` второй раз просто переписывал те же ресурсы. Меш без
`meshvolatile` построитель мешей так собрать не может — второй поток вершин
он держит в `meshvolatile` и добавляет его, — поэтому план A добавлял
`meshvolatile` в A и в B, план B — снова в B, и рабочее пространство
отказывало. Тот же путь вёл и в ресурсы чужих записей: меш с теми же ids,
но другими данными (своя запись в другом потоке), принудительная сборка
переписывала геометрией соседней записи.

Исправление (`project::cook`, `ImportOptions::keep_copies`): каждый ресурс
пишет одна запись. Копии меша, ключи которых есть в записях проекта (другие
ключи той же общей записи, меши с теми же ids в других записях), импорт
оставляет как есть — их собирают их записи. Копии вне проекта получают меш
от первого потока записи и от первой записи с этими ids, собранной этой
сборкой. Поведение `model-import` без проекта не изменилось. Модель
по-прежнему «другие данные» (меш строится заново); меш без `meshvolatile`
получает при сборке `meshvolatile` в потоке каждого своего ключа.

Проверки: модульный тест `shared_meshes_without_volatile_are_built_once`
(мини-игра: общий теневой меш двух потоков, тот же id с другой геометрией в
третьем, копия вне проекта в четвёртом); корпусный
`shadow_meshes::shared_shadow_meshes_build_each_resource_once` — проект из
всех 50 мешей игры без `meshvolatile`, принудительная сборка 21 записи без
ошибок, каждый ресурс записан одной записью (до исправления — «already in
the workspace» у общих записей, как в прогоне всей игры). Тест
`whole_game` больше не допускает ошибок сборки и проверяет, что ни один
ресурс не записан двумя записями.
