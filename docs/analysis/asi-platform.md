# ASI-платформа: новые классы и функции Lua из DLL (этап 80)

The Godfather II, PC, издание 1.0.789.0 — единственное, в котором платформа
работает. Адреса — виртуальные адреса `godfather2.exe`. Пометки: **[К]** —
прочитано в коде exe (Ghidra, дизассемблер `research/exe_xrefs.py`),
**[Д]** — по файлам игры, **[С]** — проверено в запущенной игре
([стенд](game-bench.md) §43), **[догадка]** — предположение.

Короткая сводка — заметка базы знаний
[платформа нативных модов](../kb/engine/native-mods.md); адреса списком —
[exe: платформа](../kb/exe/native-mods.md).

## 1. Коротко

- `doctor_platform.asi` (крейт `crates/doctor-toolkit-platform-asi`, сборка
  `tools/build-platform-module.sh`) — четвёртый модуль тулкита для
  ASI-загрузчика. Он даёт **нативным модам** — другим `.asi` в папке
  `scripts`, которые экспортируют `doctor_mod_init`, — таблицу функций:
  новые классы SimGroup, новые функции Lua, сообщения, перехваты.
- Класс мода регистрируется той же функцией, что и 299 классов движка
  (`0x004833A0`), поэтому игра создаёт его объекты из SimGroup мода сама,
  как свои: фабрика, конструктор `Base`, читатель атрибутов, слушатель
  сообщений, деструктор. [К][С]
- Функции Lua регистрирует «связка» — объект, который LuaManager хранит в
  списке и зовёт для каждого состояния Lua; так движок регистрирует свои
  функции. [К][С]
- Все места кода игры, которые патчат модули тулкита, собраны в один реестр
  (`doctor_toolkit_live::platform::CLAIMS`); тесты проверяют, что они не
  пересекаются и что ни один модуль не проверяет байты, которые патчит
  другой. Моду платформа отказывает в перехвате, который задевает реестр
  или чужую проверку издания.
- SDK — крейт `crates/doctor-toolkit-sdk` и заголовок C
  `crates/doctor-toolkit-sdk/include/doctor_sdk.h` с одним ABI (версия 1).
  Пример — `examples/native-class` (мод на Rust и мод на C).
- Классы мода описываются для тулкита файлом TOML
  (`DOCTOR_TOOLKIT_CLASSES`): после этого команды, редактор и MCP знают их
  имена, типы атрибутов и входы-выходы сообщений (§6).

## 2. Как движок создаёт объект класса [К]

**Реестр.** `0x004833A0(хэш, имя, фабрика, размер)` (`cdecl`) вставляет
запись `{хэш, фабрика, имя, размер}` в отсортированный массив
`*0x012239BC` (`+4` — число записей); поиск места — `0x00483720`, хэш,
который уже есть, не трогается (возврат 0), массив растёт сам
(`0x004837E0`). Реестр создаётся при первом обращении (флаг `0x01223D14`),
поэтому регистрировать можно и после движка. Движок регистрирует всё из
`0x00688AF0`, которую зовёт старт приложения `0x0068AB50` (вызов по адресу
`0x0068AB55`; сам старт — из `0x0068D010`).

**Создание.** `0x00483410(хэш класса, запись)` (из `0x00446E30`, когда
менеджер объектов решил объект создавать — `0x00446BF0`):

1. ищет класс в реестре (`0x004838C0`); нет — объект не создаётся, игра не
   падает (возврат 0);
2. `объект = фабрика(запись, доп)` — `cdecl`; `доп` — сколько байт нужно
   компонентам объекта после него (`0x00483410` берёт из списка
   компонентов, у логических объектов 0);
3. если есть компоненты, они размещаются по адресу `объект + размер` из
   реестра (`0x004828C0`) — поэтому размер в реестре должен быть честным;
4. зовёт метод `+4` главной таблицы объекта с записью — **читатель
   атрибутов** (`thiscall`, один аргумент).

**Фабрика** класса движка (пример — `TriggerAuto`, `0x00684A50`):
`p = 0x0043B910(0x60, доп)`; если память дали — `конструктор(p, запись)`.
`0x0043B910(размер, доп)` берёт `размер + доп` байт с выравниванием 16 у
аллокатора SimManager (`*0x01223410 + 0x2D4`, метод `+0`); тем же
аллокатором (метод `+4`) память освобождает деструктор.

**`Base`** — общий предок логических классов, 0x50 байт. Конструктор
`0x0046C590(запись)` (`thiscall`) обнуляет поля, ставит флаги слушателя
`1 | 0x12`, регистрирует объект в SimManager (`0x004467C0`) и пишет три
таблицы методов:

| Смещение | Таблица `Base` | Методы |
|---|---|---|
| `+0x00` | `0x00E3280C`, 7 методов | 0 — удаляющий деструктор `0x0046C560(флаги)`; 1 — читатель `0x0046C710` (пустой, `ret 4`); 2 — `0x0043A950` (пустой); 3 — `0x0046C720` (выключить слушатель); 4 — `As` `0x0046C460`; 5, 6 — пустые |
| `+0x3C` | `0x00E32828`, 4 метода — слушатель | 0 — деструктор через переходник `0x0046C780` (`sub ecx, 0x3C`); 1 — обработчик `0x0046C6A0` (передаёт сообщение компонентам); 2 — выключить `0x00461F30`; 3 — включить `0x0046C740` |
| `+0x48` | `0x00E32838`, 1 метод | деструктор через переходник `0x0046C770` (`sub ecx, 0x48`) |

Класс-наследник после конструктора `Base` ставит свои три таблицы
(`TriggerAuto`: `0x00E32F6C`, `0x00E32F88`, `0x00E32F98`) — в них заменены
деструктор, читатель и обработчик, остальное то же. Удаляющий деструктор
(`0x0046C560`) зовёт тело `0x0046C640` (возвращает таблицы `Base`,
обрывает список слабых ссылок `+0x4C`, снимает все подписки слушателя —
`0x004083D0`) и при бите 0 аргумента освобождает память. Деструктор
наследника (`TriggerAuto`, `0x00477E50`) перед этим отписывается от своих
сообщений (`0x004086D0`) и освобождает их переменные (`0x00408310`).

**Запись объекта и пакеты атрибутов.** Читатель получает запись объекта из
SimGroup (формат — `docs/formats/simgroup.md`). Обход пакета — `0x0043AFF0
(запись, хэш класса)` и цикл, который повторён в каждом читателе
(`0x00478040` у `TriggerAuto`):

- упакованная запись (бит 0 байта `+0x1C`): `+0x1F` — число пакетов, их
  смещения (каждое относительно себя) идут с `+0x2C + 4 × байт(+0x1E)`;
  пакет — `{u32 хэш класса, u16 число атрибутов, маска, значения}`:
  поднятый бит маски — «атрибут не записан» (читатель получает 0), значения
  записанных идут подряд с выравниванием 4. Строка, GUID, вектор, матрица
  лежат по адресу «адрес слова значения + слово»;
- неупакованная запись (бит 0 снят): список с `+0x20` из записей
  `{смещение следующей, метка, значение…}`; метка `0x80000000` начинает
  атрибуты класса, имя которого записано текстом с `+8`, метки
  `0x20000000` и `0x40000000` пропускаются (`0x0043B140`), любая другая —
  номер атрибута, значение (или текст строки) — с `+8`.

В файлах игры неупакованных записей нет: все 111 518 объектов упакованы
(`research/record_modes.py`, корпусный тест
`every_object_record_of_the_game_is_packed`) **[Д]**. Второй путь —
наследие инструментов разработчика; платформа его повторяет по коду, на
стенде он не проверялся.

**Что повторяет платформа** (`classes.rs`). Объект класса мода — это `Base`
(создан его конструктором), за ним заголовок платформы и данные мода:

```text
+0x00  Base: таблица методов, …, +0x3C слушатель, +0x48 третья таблица
+0x50  заголовок: метка, номер класса, список подписок
+0x60  данные мода (data_size байт, обнулены)
```

Три таблицы объекта — копии таблиц `Base`, в которых заменены деструктор
(все три входа), читатель и обработчик. Фабрика: память у `0x0043B910`,
конструктор `Base`, таблицы, `create` мода. Читатель обходит пакет класса
(как выше) и отдаёт моду каждый атрибут, записанный и нет, — правило
«незаписанный атрибут читатель получает как 0» (этап 79) сохранено; затем
`loaded`. Обработчик отдаёт моду хэш и слово данных сообщения. Деструктор:
`destroy` мода, отписка и освобождение переменных сообщений, затем
удаляющий деструктор `Base`. В реестр пишется честный размер объекта
(0x60 + данные, кратно 16).

Чего у объекта мода нет: своего `As` (остаётся `Base::As`, который ничего
не сравнивает), компонентов и матрицы (это логический объект, не сущность
мира), записей в хранилище состояния (§9).

Таблицы методов объекта мода лежат в `doctor_platform.asi`, а не в образе
игры. Модуль связи отличал объект от мусора по таблице внутри образа и
объектов мода не видел (стенд §43, прогон 2); теперь он узнаёт их по метке
заголовка платформы (`platform::OBJECT_MARK` по смещению 0x50) — это
единственная правка существующих модулей в этапе (`object_guid` в
`crates/doctor-toolkit-live-asi/src/game.rs`). Адресная отправка
`live send --to` такому объекту по-прежнему не работает: модуль связи
требует, чтобы обработчик слушателя лежал в коде игры.

## 3. Функции Lua: связки [К]

LuaManager (`*0x012233F4`, конструктор `0x0043E140`) держит список
«связок» (`+0x38`). Связка — объект с таблицей из трёх методов: 0 —
деструктор, `+4` — `Register(L)`, `+8` — `Unregister(L)` (`thiscall`, один
аргумент). `0x0043E2E0(связка)` (`thiscall` менеджера) ставит связку в
список и сразу зовёт её `Register` для обоих состояний Lua (`+0x18` —
скрипты игры, `+0x1C`), если они уже есть; создание состояния позже
(`0x0043E790`, `0x0043E5D0`) обходит список и зовёт `Register` у каждой.
`0x0043E380` убирает связку и зовёт `Unregister`. У `0x0043E2E0` 20 мест
вызова; 18 связок — поля игрового объекта: их конструкторы вызываются
подряд в его конструкторе `0x00681840` сразу после конструктора LuaManager
(вызов по адресу `0x00681860`); пример — `0x0046A240` (таблица
`0x00E32490`: `0x0046A260`, `0x0046A2C0`, `0x0046A3D0`).

Регистрация одной функции в `Register` движка (например, `0x007874F0`):
`lua_pushstring(L, имя)` (`0x00625CA0`), `lua_pushcclosure(L, функция, 0)`
(`0x00625D70`), `lua_settable(L, LUA_GLOBALSINDEX)` (`0x00626030`,
индекс −10001). Функция Lua — `cdecl int f(lua_State*)`.

**Что делает платформа** (`lua.rs`). Она подменяет вызов конструктора
LuaManager (`0x00681860`): после конструктора добавляет свою связку через
`0x0043E2E0`. `Register` связки регистрирует функции всех модов тремя
вызовами выше. Так функции попадают в оба состояния и в любое состояние,
созданное позже; новый LuaManager (новый игровой объект) получает связку
заново.

Lua 5.0 в exe собран с нестандартными соглашениями (`docs/analysis/lua-api.md`),
поэтому мод не зовёт функции Lua напрямую, а получает от платформы
обёртки. `cdecl` в exe: `lua_tonumber` (`0x006259B0`, результат — `float` в
`ST0`), `lua_toboolean` (`0x00625A30`), `lua_tostring` (`0x00625A70`),
`lua_pushnil` (`0x00625C20`), `lua_pushnumber` (`0x00625C40`, аргумент —
`float`), `lua_pushboolean` (`0x00625DF0`), `lua_pushlightuserdata`
(`0x00625E10`), `lua_pushstring`. `lua_type` (`0x00625740`) и
`lua_touserdata` (`0x00625B60`) берут аргументы в регистрах — платформа
читает стек сама: `L + 8` — вершина, `L + 0xC` — база текущей функции,
значение — 8 байт `{тип, слово}`; полное userdata — заголовок 0x10 байт и
блок. Числа Lua в игре — `float`. Обёртки обещают только положительные
индексы (аргументы функции).

## 4. Сообщения

Всё, кроме фильтра, идёт через функции шины движка
(`docs/analysis/message-bus.md` §2) без патчей (`bus.rs`):

| Что | Как |
|---|---|
| послать всем | сообщение `{хэш, данные, 0}` на стеке, `0x00408A00(сообщение, force)` |
| послать с объектом в данных | объект данных `{0x00E31E2C, якорь, следующий}` на стеке: конструктор `0x0045CA00(объект)`, отправка, деструктор `0x0045CAC0` — так шлют «себя» объекты игры (`0x00477F40` у `TriggerAuto`) |
| одному объекту | `0x00408BF0(сообщение, слушатель = объект + 0x3C, force)` |
| с задержкой | очередь `*0x01223420`, `0x00440590(переменная, 0, секунды, данные, 0)`; объект данных — 12 байт из `operator new` игры (`0x009C8E50`), очередь удалит его сама (как `0x00477F74`) |
| подписать объект мода | переменная сообщения `{хэш, u16, u16}` — `0x00408260(переменная, хэш)`; подписка — `0x00408900(слушатель, переменная, приоритет)`; в деструкторе объекта — `0x004086D0` и `0x00408310` |
| подписать функцию мода | свой слушатель платформы `{таблица, флаги = 1, подписки}` с четырьмя методами (деструктор, обработчик, выключить, включить) и те же вызовы |
| узнать объект из слова данных | если слово читается и первое слово — `0x00E31E2C`: объект = якорь − 0x48 |

**Фильтр рассылки** — единственное, что требует патча, и ставится он
только когда мод просит фильтр (`add_filter`). Место — 10 байт в
`0x00408A00` после того, как запись таблицы уже в `ESI`: `0x00408A1A`
(`xor al, al; test esi, esi; je 0x00408AE4`). Сообщение — в `EDX`, `force`
— на стеке. Переходник зовёт фильтры модов; если ни один не «проглотил»
сообщение, выполняет заменённые инструкции и продолжает с `0x00408A24`,
иначе возвращает `false` через конец функции `0x00408AE4`. Фильтр может
поменять слово данных. Он видит только рассылку всем: доставка одному
слушателю (`0x00408BF0`) и срабатывание очереди со слушателем мимо него.

Место выбрано так, чтобы не задеть соседей: модуль связи прыгает с первых
пяти байт `0x00408A00` и проверяет 16 байт от него, модуль падений
занимает `0x00408A11` и проверяет 9 байт (до `0x00408A1A`); следующая
проверка модуля связи начинается с `0x00408A70`.

## 5. Перехваты: один реестр на всех

До этапа 80 каждый модуль (`doctor_live`, `doctor_render`, `doctor_crash`)
знал только свои места, а от соседей их защищал один тест модуля падений.
Теперь `crates/doctor-toolkit-live/src/platform.rs` держит:

- `CLAIMS` — **все** места, в которые пишут модули тулкита (52 строки:
  кадр, шина, журнал Lua, чтение и открытие файлов, презентация кадра у
  модуля связи; 9 патчей графического модуля; 2 места модуля падений; 3
  места платформы), с владельцем и длиной;
- `checked(адрес, длина)` — чья проверка издания задевает место;
- `mod_hook_allowed(адрес, длина)` — можно ли моду патчить место: только
  код игры, вне `CLAIMS` и вне проверок издания всех модулей.

Тесты (без игры): никакие два места `CLAIMS` не пересекаются; ни один
модуль не проверяет байты, которые патчит другой; каждое место кода из
`CLAIMS` лежит внутри проверки издания своего владельца; строки реестра
совпадают со списками патчей графического модуля, модуля падений и
платформы. Новый перехват в любом модуле — новая строка в `CLAIMS`. У
графического модуля, модуля падений и платформы тест не даст о ней забыть;
для модуля связи список собран руками по его коду (`journal.rs`,
`profile.rs`, `files.rs`, `lib.rs`) — это слабое место, см. §9.

**Моды.** Мод получает перехват только у платформы (`hooks.rs`):
`hook_check` — проверка без патча; `hook_jump` — прыжок с 5–16 байт целых
инструкций и трамплин, который выполняет заменённые байты и возвращается
(первой инструкцией может быть `call`/`jmp rel32` — смещение
пересчитывается); `hook_call` — подмена цели вызова `call rel32`. Место,
отданное одному моду, второму не отдаётся. Платформа не разбирает
инструкции: что байты — целые инструкции без относительных адресов,
отвечает мод.

**Существующие модули на общий API не переведены** — это сознательное
решение этапа: их перехваты ставятся в `DllMain`, проверены на стенде
(§§21–38), а этап 100 в это же время добавляет в модуль связи новые.
Общим стало то, что можно сделать без правки их кода: реестр и проверки.
План перевода — §9.

**Порядок загрузки.** Платформа патчит в `DllMain` только два вызова
(`0x0068AB55`, `0x00681860`), которых нет ни в чьих проверках; фильтр шины
и перехваты модов ставятся позже, из `doctor_mod_init`, когда все `.asi`
уже загружены и проверили издание. Проверки платформы не включают байты,
которые патчат другие модули, поэтому порядок загрузки `.asi` не важен.

## 6. Схема классов мода для тулкита

Тулкит узнаёт классы мода из файла TOML (`game_types::custom`):

```toml
[class.DoctorCounter]
category = "logic"
summary = "Counts a message and sends another one every limit-th time"
attrs = [
  { i = 0, name = "count_on", pin = "in", kind = "string" },
  { i = 1, name = "send", pin = "out", kind = "string" },
  { i = 2, name = "limit", pin = "param", kind = "int" },
  { i = 3, name = "reset_on", pin = "in", kind = "string" },
]
```

- `category` — как в `data/gf2/logic_schema.toml`: `trigger`, `logic`,
  `ui`, `audio`, `spawn`, `job`, `cinematic`, `relay`, `action`, `object`;
- `pin` — `in` (сообщение, которое объект слушает), `out` (сообщение,
  которое шлёт), `link` (GUID объекта), `asset`, `param`; `kind` — `int`,
  `float`, `hash`, `string`, `guid`, `vec3`, `matrix`; `delay` у выхода —
  номер атрибута-задержки (`float`);
- число атрибутов пакета — наибольший номер плюс один.

Проверки (`doctor-toolkit class-schema ФАЙЛ…`, тесты
`game_types::custom`): имя класса не совпадает по хэшу с классом или
пакетом движка и с другим классом мода; номера и имена атрибутов не
повторяются; сообщение — строка, ссылка — GUID; задержка указывает на
`float` своего класса.

Файлы подключаются переменной окружения `DOCTOR_TOOLKIT_CLASSES` (список
путей, как `PATH`); они читаются один раз, и классы мода попадают в три
таблицы, которыми пользуются все инструменты: схема графа логики
(`LogicSchema::gf2` — категория, входы и выходы, раскладка пакетов нового
объекта: базовые пакеты логического объекта `CAttributeHandler` и `Base`,
как у `TriggerAuto`, и пакет класса), виды значений атрибутов
(`simgroup::Schema::gf2`) и имена классов (`names::sim_classes`). После
этого `simgroup-set` принимает `DoctorCounter.limit=2`, `logic-export`
пишет имена и типы, граф логики показывает входы и выходы объекта, а
`doctor-toolkit simgroup-add ИГРА ПОТОК РЕСУРС КЛАСС` добавляет объект
класса с пустыми пакетами. Файл с ошибкой не используется целиком
(`custom::load_errors`, предупреждение `simgroup-add`).

Имена сообщений мода проверяются тем же правилом, что и раньше (этап 73,
`MessageId::custom`): имя не должно совпадать с сообщением движка или
давать его хэш.

Объекту класса мода нужен атрибут 0 пакета `Base` = 1 (флаги создания):
менеджер объектов читает его копию из байта `+0x1D` записи до создания
(`0x00446BF0`, этап 79). `simgroup-add` ставит байт записи, пример ставит
и атрибут (`--set Base.0=1`), чтобы запись совпадала с правилом файлов
игры.

Не сделано: заметки базы знаний и типы для Python/JSON Schema
(`types-gen`) для классов мода не генерируются; редактор читает переменную
окружения, своего окна «классы модов» у него нет.

## 7. SDK и ABI

Мод — 32-битная DLL с расширением `.asi` в `scripts` рядом с
`doctor_platform.asi`. Она экспортирует
`int doctor_mod_init(const DoctorApi *api)` (`cdecl`). Платформа после
регистрации классов движка обходит загруженные модули процесса (список
загрузчика в PEB), у каждого ищет этот экспорт и зовёт его — в порядке
имён файлов, на главном потоке. Результат каждого мода — в
`scripts/doctor_platform.log`.

Таблица `DoctorApi` (32 функции; Rust — `doctor_sdk::abi::Api`, C —
`doctor_sdk.h`):

| Группа | Функции |
|---|---|
| общее | `edition`, `log`, `hash` |
| классы и объекты | `register_class`, `object_data`, `object_guid`, `object_listen`, `object_unlisten`, `object_enable` |
| сообщения | `send`, `send_object`, `send_to`, `send_later`, `data_object`, `subscribe`, `unsubscribe`, `add_filter` |
| Lua | `register_lua`, `lua_gettop`, `lua_type`, `lua_tonumber`, `lua_toboolean`, `lua_tostring`, `lua_touserdata`, `lua_pushnil`, `lua_pushnumber`, `lua_pushboolean`, `lua_pushstring`, `lua_pushlightuserdata` |
| перехваты | `hook_check`, `hook_jump`, `hook_call` |

Класс описывается структурой `DoctorClass`: имя (оно же имя пакета
атрибутов), размер данных мода в объекте и пять необязательных функций —
`create`, `attribute` (один атрибут пакета), `loaded`, `message`,
`destroy`. Крейт даёт поверх этого типаж `ObjectClass` (значение типа живёт
в объекте) и обёртку `Platform`.

**Что обещано стабильным** (версия ABI 1):

- имя и подпись `doctor_mod_init`; раскладка `DoctorApi`, `DoctorClass`,
  `DoctorAttr`, `DoctorMessage`; значения кодов ошибок и типов Lua;
- таблица `DoctorApi` только растёт: новые функции добавляются в конец,
  поле `size` растёт; мод, собранный со старым заголовком, работает с новой
  платформой, а мод, которому нужна новая функция, проверяет `size`;
- число `DOCTOR_ABI_VERSION` меняется, только когда меняется смысл или
  раскладка существующего; мод обязан отказаться от платформы с другим
  числом (обёртка `Platform::new` это делает);
- на другом издании игры платформа ничего не ставит и ни один мод не
  зовёт (в журнале — причина); `doctor_platform_api()` (экспорт платформы)
  там возвращает `NULL`.

**Что не обещано:**

- раскладка объекта за пределами данных мода (заголовок платформы, поля
  `Base`): к объекту мод обращается только функциями таблицы;
- адреса игры и то, какие места патчит сама платформа;
- порядок вызова `doctor_mod_init` между модами (сейчас — по имени файла);
- вызовы не с главного потока игры (кроме `log`, `hash`, `hook_check`);
- отрицательные индексы и псевдоиндексы в обёртках Lua;
- работа при выгрузке DLL мода: мод живёт до конца процесса.

Ограничения версии 1: до 64 классов на все моды; `register_class` и
`add_filter` — только из `doctor_mod_init`; трамплинов перехватов — 128.

Тест `crates/doctor-toolkit-sdk` сверяет заголовок с крейтом: константы,
порядок функций таблицы и размеры структур для 32 бит; пример на C
собирается из заголовка (`-Wall -Wextra`, `_Static_assert` размеров).

**Распространение (этап 81).** Нативный мод едет в обычном файле мода:
раздел `native` в `mod.json` формата версии 5 называет модули `.asi`, их
SHA-256, издание `1.0.789.0` и версию ABI платформы (`platform_abi` —
`DOCTOR_ABI_VERSION`, с которой собран мод). Менеджер модов кладёт модули в
`scripts/` только после согласия игрока на этот мод, вместе с
`doctor_platform.asi` и — если в папке игры нет ASI-загрузчика — своим
загрузчиком `doctor_loader.dll` под именем `dinput8.dll`; мод, которому
нужен ABI новее, чем у программы, не ставится. Подробно —
`docs/mods.md` §1.6; сборка — `mods build --native ФАЙЛ`
(`examples/native-class/build.sh` собирает данные и оба модуля в один мод).
Класть `.asi` в `scripts` руками по-прежнему можно: платформа их так же
находит.

## 8. Пример и проверка в игре

`examples/native-class/build.sh ВЫХОД [КОПИЯ_ИГРЫ РАБОЧЕЕ_ПРОСТРАНСТВО
[МОД.zip]]` одной командой собирает `doctor_platform.asi`,
`doctor_example.asi` (Rust: класс `DoctorCounter`, функции
`DoctorCounterInfo` и `DoctorSend`, слушатель, фильтр, перехват
`EclipseLog`), `doctor_example_c.asi` (C: класс `DoctorCEcho`, функции
`DoctorCAdd` и `DoctorCUpper`) и данные мода: два объекта новых классов в
SimGroup уровня Гаваны и скрипт, который зовёт новые функции Lua.

Мод на Rust добавляет ещё `DoctorObject`, `DoctorGuid` и `DoctorSelfTest`:
последняя пробует на объекте остальные функции платформы и возвращает
строку результатов — ею на стенде проверены доставка одному объекту,
включение и выключение слушателя, снятие подписок.

Проверено в игре ([стенд](game-bench.md) §43, сценарий —
`research/bench_platform.sh`) **[С]**:

- оба мода вызваны после регистрации классов движка; LuaManager и таблица
  сообщений к этому моменту уже существуют;
- игра создала объекты обоих классов из SimGroup уровня (быстрый старт
  `-stream`, загрузка сохранения через меню, загрузка зоны по запросу);
  читатель получил атрибуты; объекты видны в списке всех объектов модуля
  связи (класс он не называет — у объекта `Base::As`);
- цепочка: два сообщения → `DoctorCounter` шлёт своё с собой в данных →
  `DoctorCEcho` (мод на C) отвечает → слушатель-функция по слову данных
  называет отправителя; отправка с задержкой 2 с доходит;
- фильтр проглатывает сообщение, на которое объект подписан; перехват
  `0x0043E5C0` считает вызовы, функция работает как раньше; перехват входа
  шины моду не дан (место модуля связи);
- скрипт из данных мода при загрузке уровня и по сообщению зовёт функции
  обоих модов, ошибок Lua нет;
- выгрузка зоны вызывает деструктор объекта, загрузка создаёт новый
  (дважды подряд); автосохранение и загрузка сохранения — без падений;
  после загрузки объект начинает с нуля;
- платформа работает и одна, без модуля связи и модуля падений.

Только по коду: неупакованные записи объектов, `hook_call`, отправка с
`force`.

## 9. Что не выяснено и что дальше

- **Состояние объектов мода в сохранениях.** Классы движка с флагом
  «помнить» кладут записи в хранилище состояния (`*0x01223418`,
  `0x0043D0D0`, `0x0043D020`) и восстанавливают их по `iMsgRestoreEntity`
  (этап 79). В API платформы этого нет: объект мода после загрузки
  сохранения создаётся заново из SimGroup со значениями атрибутов.
  [Вопрос](../kb/questions/native-class-saved-state.md).
- **Сущности мира.** Класс мода — только логический объект (`Base`). Класс
  с матрицей, моделью и компонентами (база `Entity`, таблицы `+0x50…+0x58`)
  не делался. [Вопрос](../kb/questions/native-entity-classes.md).
- **Перевод трёх модулей на общий API времени выполнения.**
  [Вопрос](../kb/questions/modules-on-shared-hook-api.md); шаги: (1) дать
  платформе экспорт `doctor_platform_claim(адрес, длина, владелец)`;
  (2) в `install` каждого модуля перед патчем звать его, если платформа
  загружена, и не ставить перехват при отказе; (3) собрать список мест
  модуля связи из одной таблицы в `doctor-toolkit-live`, которой пользуются
  и `CLAIMS`, и его `install` (сейчас список в `CLAIMS` повторяет его код
  руками); (4) прогоны стенда §§21, 22, 27, 29, 37.
- **Неупакованные записи объектов** — путь читателя только по коду (§2).
- **Фильтр** не видит доставку одному слушателю и очередь задержки со
  слушателем; порядок фильтров разных модов — порядок их `add_filter`.
- **`Base` из Lua для объектов мода.** Разбор GUID в `Base(строка)` сломан
  в этой сборке (этап 74); функция мода могла бы отдавать скрипту
  указатель объекта (`lightuserdata`), но готового способа сделать из него
  `Base` для групп нет.
- Потоки: вызывается ли шина не с главного потока, не проверялось; патч
  фильтра ставится при старте приложения.
