# Шина сообщений: разбор по `godfather2.exe` (этап 78)

Издание — только PC 1.0.789.0; все адреса виртуальные. Короткая сводка —
заметка базы [шина сообщений](../kb/engine/message-bus.md), адреса списком —
[exe: шина](../kb/exe/message-bus.md). Здесь — как это прочитано и на чём
держится.

Обозначения: **[К]** — прочитано в коде exe; **[Д]** — по файлам игры;
**[С]** — проверено в запущенной игре ([стенд](game-bench.md) §36).

## 1. Коротко

- Шина одна и синхронная: `0x00408A00` зовёт обработчики слушателей один за
  другим, обработчик может слать дальше — вложенная рассылка проходит целиком
  до возврата. [К][С]
- Кроме рассылки всем есть **доставка одному слушателю** (`0x00408BF0` и две
  обёртки, 127 мест вызова и один переход) и **очередь задержки**
  (`0x00440590`, 62 места и обёртка `0x004760D0`). Так, например, движок шлёт
  `iMsgPostSpawnInitialize` объектам загруженной SimGroup, а сущность —
  сообщения своим компонентам. [К][С]
- Слово данных сообщения — 0 или указатель на объект, который отправитель
  собрал у себя на стеке. Объекты SimGroup кладут туда указатель на объект
  (на себя или на вошедшего в триггер) либо пересылают то, что получили. [К]
- Отправителя у сообщения нет. Его можно назвать по месту вызова шины и по
  слушателю, чей обработчик в этот момент выполнялся: модуль связи делает
  это с протокола 8 (§8). [С]
- Отправитель в коде движка найден у 320 имён сообщений из 645 (было
  известно 9), слушатель в коде — у 262; слово данных — у 310 имён движка и
  у 33 023 из 42 087 сообщений файлов игры (§4, §5).

## 2. Функции и структуры [К]

| Адрес | Что это |
|---|---|

| `0x00408260` | `(переменная*, хэш)`: найти или создать запись таблицы `*0x01162380`, положить хэш в переменную |
| `0x00408240` | `(переменная*, "имя")`: то же по имени; так код движка называет свои сообщения |

| `0x00408900` | `(слушатель*, переменная*, приоритет)`: подписать на готовую переменную; 387 мест, приоритет почти всегда `0x8000` (373) |
| `0x00408680` | `thiscall` слушатель`(переменная*)`: подписать с приоритетом `0x8000`; 236 мест |

| `0x004086D0` | `thiscall` слушатель`(переменная*)`: отписать; 1 477 мест |

| `0x00408B80` | `(переменная*, слушатель*, force)`: то же без данных; 11 мест |
| `0x00408BB0` | `(переменная*, слушатель*, данные, force)`: то же с данными; 23 места |
| `0x00440590` | `thiscall` очередь`(переменная*, слушатель* или 0, f32 секунды, данные*, флаги)`: отправка с задержкой; очередь — `*0x01223420`; 62 места |
| `0x004760D0` | `thiscall` очередь`(переменная*, секунды, данные*, флаги)`: то же для всех слушателей; 3 места |
| `0x00440760` | обработчик очереди: по `iMsgRunningTick` (`0x012069C4`) шлёт записи, срок которых настал |
| `0x00440B80` | сброс очереди; записи с флагом 4 переживают сброс без `force` |
| `0x00408AF0` | применить отложенные правки списка слушателей записи |
| `0x0045CA00`, `0x0045CAC0` | конструктор и деструктор указателя на объект — данных сообщения (`0x00E31E2C`) |
| `0x00476C80` | копия указателя на объект в куче (12 байт) для очереди задержки |
| `0x007FFF40` | `(объект, переменная*)`: послать сообщение с указателем на себя |

Прежние документы называли отправкой с задержкой `0x004404F0`, а адресной
отправкой — `0x00408B70`. Оба адреса лежат внутри инструкций чужих функций;
настоящие — `0x00440590` и `0x00408BF0`. Время очереди — `*0x01205224`
(время симуляции, мс), а не `0x010F6F2C`.

**Сообщение** — `{u32 хэш, u32 данные, u8 доставляется}`; байт `+8` шина
ставит в 1 на время доставки и возвращает прежний.

**Переменная сообщения** («ручка») — `{u32 хэш, u16, u16 счётчик}`; у
объекта SimGroup это поле объекта (атрибут-сообщение), у кода движка —
глобальная переменная.

**Запись таблицы** (4096 корзин по `хэш & 0xFFF`): `[0]` следующая, `[1]`
первый блок слушателей, `[2]` последний блок, `[3]` (`+0xC`) отложенные
правки, `[4]` хэш, `+0x14` `u16` счётчик ручек, `+0x16` `u16`: бит 0 —
«идёт рассылка», остальное — число блоков.

**Блок слушателей** — по одному на приоритет: `[0]` следующий, `[1]`
предыдущий, `[2]` первый узел. **Узел** — `[0]` обратная ссылка, `+4`
следующий, `+0xC` слушатель, `+0x10` хэш, `+0x14` `u16` (бит 15 — удалён),
`+0x16` `u16` приоритет.

**Слушатель** — объект с таблицей методов: `+4` — обработчик
`thiscall(сообщение*)` (сам снимает аргумент); слово `+4` слушателя — флаги,
бит 0 — «включён». У объекта SimGroup слушатель лежит по `объект + 0x3C`.

## 3. Порядок доставки и повторный вход

- Блоки идут по убыванию приоритета: `0x00409090` ставит новый блок перед
  первым блоком с меньшим приоритетом, блок с тем же приоритетом берёт
  существующий. Почти все подписки — с приоритетом `0x8000`, то есть в одном
  блоке. [К]
- Внутри блока новый узел встаёт **в голову** списка (`узел.следующий =
  блок[2]; блок[2] = узел`): по коду последний подписавшийся зовётся первым.
  [К]
- На стенде четыре объекта `TestTimeOfDay` одного потока получили
  `aud_test_tod` в порядке возрастания их номеров в списке объектов модуля
  (5386…5389); их ответные сообщения шли в том же порядке — это порядок
  обхода таблицы. Соответствует ли список модуля порядку создания объектов,
  не установлено, поэтому «последний подписавшийся — первый» на стенде не
  подтверждено и не опровергнуто ([вопрос](../kb/questions/message-listener-order.md)). [С]
- Шина зовёт слушателя, если его бит «включён» стоит или `force` не ноль;
  удалённые узлы (бит 15) пропускает. [К]
- **Доставка синхронная и в глубину.** Ответы `aud_not_night`, `aud_not_dusk`,
  `aud_day`, `aud_not_dawn` четырёх `TestTimeOfDay` записаны между доставками
  `aud_test_tod` и до следующего сообщения кадра. [С]
- **Повторный вход разрешён.** Перед обходом шина ставит бит «идёт рассылка»
  записи и запоминает прежний; вложенная рассылка того же сообщения идёт
  сразу (на стенде: `iMsgTickUnLinked` приходит сущности, и та в обработчике
  доставляет его же своим компонентам). Подписки и отписки во время рассылки
  не трогают список: они копятся в `запись + 0xC`, и `0x00408AF0` применяет
  их, когда кончается самая внешняя рассылка. [К][С]
- Цикл без задержки (A → B → A) ничем не ограничен, кроме стека. [К]

### 3.1 Доставка одному слушателю

`0x00408BF0` проверяет те же бит и `force`, ставит запись в состояние «идёт
рассылка» и зовёт обработчик одного слушателя. Так шлют: `iMsgPostSpawnInitialize`
(`0x004464A5`, `0x00855DD1`…), `iMsgTrigger` объёма самому себе
(`0x004C1FF8`), `iMsgDamage` (`0x0099DF8E`), `iMsgBuildingChangedState`
владельцу (`0x006B4F6A`), `iMsgManagedEntityCreated`, сообщения сущности её
компонентам (`0x00482A86`: `footstep`, `audio: play`, `enable PA`…). На
стенде за 25 с игры в Гаване таких доставок 248 из 650 записанных сообщений.

Перехват модуля связи до этапа 78 стоял только на входе `0x00408A00` и этих
доставок **не видел**: ни журнал, ни точки останова, ни счётчики. С
протокола 8 модуль записывает их в журнал (§8); точки останова по сообщению
и счётчики `MessageCounts` по-прежнему считают только рассылку всем
([вопрос](../kb/questions/direct-delivery-breakpoints.md)).

### 3.2 Очередь задержки

`0x00440590`: при `секунды ≤ 0` сообщение уходит сразу — `0x00408A00` или,
если задан слушатель, `0x00408BF0`; `force = (флаги >> 1) & 1`. Иначе запись
`{слушатель, хэш, срок, данные, флаги}` встаёт в список по возрастанию срока:
срок = `*0x01205224 + секунды × 1000` (время симуляции, мс; константа
`0x00E2E220` = −1000,0 вычитается). Флаги: бит 0 — данные чужие, не удалять;
бит 1 — `force` (только для немедленной отправки); бит 2 — запись переживает
сброс очереди.

`0x00440760` — обработчик `iMsgRunningTick` — шлёт все записи, срок которых
не больше текущего времени: без слушателя — `0x00408A00(сообщение, 0)`, со
слушателем — прямо его обработчик (`0x00440819`), если слушатель включён.
После отправки объект данных удаляется (`vtable[0](1)`), если не чужой.
Место, которое поставило сообщение в очередь, к моменту доставки потеряно.

## 4. Слово данных [К]

Слово данных — 0 либо указатель на **объект данных**. Объект собирается на
стеке отправителя и живёт только во время рассылки; в очередь задержки
кладётся копия в куче. Первое слово объекта — таблица методов с одним
методом (удаляющий деструктор); RTTI у этих классов нет, имён в exe нет.
Какой объект лежит в данных, получатель знает по сообщению. Ключи видов
данных — в `data/gf2/messages.toml` (`data_type`), таблица — в заметке
[сообщения файлов игры](../kb/messages/game-messages.md).

### 4.1 Указатель на объект — `0x00E31E2C`

`{таблица, объект + 0x48, следующий}`: «безопасный указатель» — звено списка,
голова которого лежит в `[объект + 0x48 + 4]`; когда объект удаляется, звенья
обнуляются. В пометках читателей атрибутов этот тип назван
`BasePtrMsgData`. Конструктор `0x0045CA00(объект)`, 51 место отправки в
`bus_sites.tsv`. Объект — `[данные + 4] − 0x48`.

Что кладут выходы классов SimGroup (ключ `class_data` в `messages.toml`):

| Класс | Данные | Источник |
|---|---|---|
| `TriggerAuto`, `AndEventGate`, `OrEventGate` | указатель на **себя**; с задержкой — копия в куче | `0x00477F61` / `0x00477FAE`, `0x00479C08` / `0x00479C56`, `0x00479F06` / `0x00479FA8`; на стенде у `OrEventGate` объект в данных равен отправителю |
| `MultiManager`, `TriggerRandom`, `VariableSwitch`, `TestTimeOfDay` | **пересылают** слово данных пришедшего сообщения; с задержкой указатель копируется (`0x00476C80`) | `0x0047A1C0`, `0x0047AFEB`, `0x00476F02`, `0x0082632E` |
| `TriggerBase` и объёмы | данные пришедшего `iMsgTrigger` / `iMsgReverseTrigger`; при входе объём сам себе адресно шлёт `iMsgTrigger` с указателем на **вошедшего** (`0x004C1FF8`) | `0x004C13CA` |
| `InterestingObject` 3, 4 | указатель на **персонажа, который пользуется объектом** (этап 79: `0x00726E40` / `0x00726EC0` получают его от поведения персонажа `0x00740AD0`, вызов `0x00740E04`) | `0x00726E91`, `0x00726F21` |

### 4.3 Lua

`SendMessage(имя, второй, данные)` — `0x004C8510` → `0x004C82C0` →
`0x00408A00`. Данные берутся из **третьего** аргумента и только если второй
задан: число → указатель на `f32` на стеке, строка → указатель на копию
строки в куче (освобождается после рассылки), userdata → указатель на тело.
На стенде `SendMessage("s78_number", "x", 5)` дал слово данных `0x0031F14C`
(адрес в стеке), `SendMessage("s78_string", "x", "abc")` — `0x190F50B8`
(куча), а `SendMessage("имя", 5)` — 0. [К][С] В скриптах игры `SendMessage`
с данными не встречается. Как скрипт получает `data` в приёмнике — этап 74.

## 5. Отправители в коде движка [К]

`research/bus_sites.py` читает exe (нужен `capstone`) и пишет
`data/gf2/bus_sites.tsv` — 2 747 строк:

| `kind` | Что | Строк |
|---|---|---:|
| `name` | код называет переменную сообщения (`0x00408240` или `0x004DAFD0` → `0x00408260`) | 717 |
| `listen` | код подписывает слушателя | 1 072 |
| `send` | рассылка всем (`0x00408A00`, `0x0045C400`) | 744 |
| `direct` | доставка одному слушателю | 128 |
| `delayed` | очередь задержки | 86 |

Столбцы: `kind`, `site` (адрес вызова), `function` (ближайший выровненный
адрес после заполнения или возврата — ориентир, не доказанное начало
функции), `call` (что вызвано), `message`, `data`, `force`. `message` — имя,
`[obj+0x…]` (переменная в объекте: атрибут SimGroup или член класса),
`var:0x…` (глобальная переменная без найденного имени), `hash:0x…`, `?`.
`data` — `none`, `obj:0x<таблица методов>`, `obj:?`, `reg`, `mem`, `?`.
Место, которое шлёт одно из нескольких сообщений, даёт строку на каждое.

Как читается вызов: символьный проход по инструкциям перед ним (до 48, после
последнего возврата или перехода в сторону; ветвления вперёд внутри окна
проходятся все) — из какой переменной взят хэш и что записано в слово
данных. Чего проход не проследил, то `?`; догадок нет. Сохранённые регистры,
которые функция только обнуляет, считаются нулём.

Итог: имён с переменной в коде — 628 (74 из них не было в
`data/gf2/engine_messages.txt`: теперь в нём 645 имён); отправитель найден у
**320** имён, слушатель — у 262, то или другое — у 430. Из 320: у 208 все
места шлют без данных, у 29 на каждом месте объект данных, у остальных
данные прочитаны частью или не прочитаны. Без имени остались 30 рассылок и
18 доставок (хэш собирается не в окне), 14 — с переменной без имени.

Среди 74 новых имён — события анимации, которые сущность раздаёт своим
компонентам (`footstep`, `vfx: play`, `audio: play`, `item attach`,
`ragdoll window start`…). Четыре сообщения названы **текстом описания**
(«Sent to an entity to commence falling» и другие, `0x007F99E0`), а четыре —
именем типа данных (`StimulusData*`, `AvoidStreetEventData*`,
`AICombatEventData*`, `Stimulus_HearPressure_MsgData*`): так в коде, это
настоящие имена на шине.

На стенде у всех 650 сообщений, записанных за 25 с, место вызова нашлось в
`bus_sites.tsv`. [С]

Корпусный тест `types::the_bus_sites_are_calls_of_the_executable` сверяет
таблицу с exe: каждая строка — вызов названной функции, рассылок 688, имена
есть в exe и в списке движка.

## 8. Отправитель в живой связи (протокол 8) [С]

У сообщения нет поля «кто». Обходить стек по `ebp` нельзя: функции игры
собраны без кадров. Модуль связи (`crates/doctor-toolkit-live-asi`,
`journal.rs`) метит стек сам.

**Три места, где игра зовёт обработчик слушателя**, занимают по пять байт
целых инструкций без относительных операндов; модуль заменяет каждое на
`call` своего переходника:

| Адрес | Было | Где |
|---|---|---|
| `0x00408A8B` | `mov edx,[eax+4]; call edx` | рассылка всем `0x00408A00` |
| `0x00408C31` | `and bl,1; call edx` | доставка одному слушателю `0x00408BF0` |
| `0x00440819` | `and bl,1; call eax` | адресат записи очереди задержки `0x00440760` |

Переходник кладёт на стек **метку** `{предыдущая метка, слушатель}` прямо под
адресом возврата в игру, пишет адрес метки в переменную модуля, зовёт
обработчик с копией аргумента, возвращает переменной прежнее значение и
уходит, сняв аргумент, как это сделал бы обработчик. Пока обработчик
работает, цепочка меток повторяет вложенность доставок.

Когда игра зовёт шину, перехват `0x00408A00` читает:

- **место** — адрес возврата шины минус 5: строка `bus_sites.tsv`; если шину
  позвала обёртка `0x0045C400`, берётся место, которое позвало обёртку;
- **причину и отправителя** — верхнюю метку: хэш сообщения, которое
  обрабатывается, и слушатель; если слушатель — объект SimGroup
  (`слушатель − 0x3C`), его GUID и есть отправитель. Метке верят, только если
  она лежит в стеке текущего потока выше текущего кадра и рядом с ней один
  из трёх адресов возврата (`0x00408A90`, `0x00408C36`, `0x0044081E`);
- **объект в данных** — если данные — указатель на объект (`0x00E31E2C`),
  GUID объекта `[данные + 4] − 0x48`.

Два других переходника заодно записывают **доставку одному слушателю**
(место — вызвавший `0x00408BF0` или её обёртку; для очереди задержки место
неизвестно).

**Протокол `DTLV` 8** запросов не добавляет. Событие журнала `Message`
получило поле `from: Option<MessageFrom>` — `site`, `cause`, `sender`,
`data_object`, `direct`; на проводе это новый вид события 5 (те же поля, что
у вида 3, и после них происхождение). Клиент просит его битом
`mask::MESSAGE_SENDER` (16); без бита — и всем клиентам версий 1–7 — модуль
отдаёт прежний вид 3 и не показывает доставки одному слушателю. Старый
модуль бит не знает и снимает его сам.

Где видно: `doctor-toolkit live log --messages` дописывает к строке
`from <объект> on <сообщение-причина> at <место> data object <объект>` и
`[to one listener]`; в JSON — объект `from`. `TraceEvent::from_live` кладёт
отправителя в `sender`, и подсветка графа сужается до его проводов (если
отправитель есть на графе).

**Проверка на стенде** (§36): два сеанса в Гаване по 4–7 минут, исключений
нет. За 25 с записано 650 сообщений: 402 рассылки и 248 доставок одному
слушателю; место известно у всех и у всех есть в `bus_sites.tsv`; 338 посланы
из обработчика другого сообщения, у 102 отправитель — объект SimGroup, у 15 в
данных указатель на объект. Пример цепочки: Lua шлёт `aud_test_tod`
(`0x004C830A`) из обработчика `iMsgRunningTick` → четыре `TestTimeOfDay`
отвечают `aud_not_night`, `aud_not_dusk`, `aud_day`, `aud_not_dawn` из
`0x0082632E`, отправитель каждого — свой объект, причина — `aud_test_tod`.

**Ограничения.**

- Отправитель — слушатель, чей обработчик выполняется. Объект, который шлёт
  сообщение из своего обновления (его зовёт менеджер по `iMsgRunningTick`),
  отправителем не станет: причина — `iMsgRunningTick`, отправителя нет,
  известно только место.
- Переменная метки одна на все потоки. Шина работает на главном потоке;
  чужую или устаревшую метку отсекает проверка границ стека и адреса
  возврата, но не исключает полностью.
- Сообщение из очереди задержки приходит от очереди: кто его поставил, уже
  не узнать (нужно запоминать место при постановке, `0x00440590`).
- Точки останова и счётчики `MessageCounts` доставку одному слушателю не
  видят.
