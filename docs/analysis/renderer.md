# Рендер The Godfather II PC (этап 58)

Редакция от 2026-11-15. Исследован `godfather2.exe` PC 1.0.789.0 (тот же,
что в `live-link.md`: образ с `0x00400000`, без перемещаемых адресов).
Адреса — виртуальные. Инструменты: декомпилятор в пакетном режиме по копии
`exe`, разбор байткода шейдеров (`research/d3d9_shaders.py`), профиль
модуля связи (`live-link.md` §16), HUD DXVK и снимки стенда
(`game-bench.md` §27). Замеры и вопросы производительности —
`performance.md`.

**[П]** — доказано кодом и проверено в игре, **[К]** — доказано кодом
(декомпиляция, данные `exe`), **[Г]** — гипотеза.

## 1. Главное

- **Direct3D 9, шейдеры только SM 3.0.** 943 скомпилированных шейдера
  (808 `ps_3_0`, 135 `vs_3_0`) лежат прямо в `exe`; фиксированного
  конвейера и SM 2 нет. Из D3DX — только `D3DXGetShaderConstantTable` и
  `D3DXLoadSurfaceFromSurface` **[К]**.
- **Два потока.** Главный поток пишет команды кадра в буфер
  `*0x01206880`, поток рендера (`0x00485AE0`, имя потока `Presentation`)
  исполняет их — весь D3D идёт там. Кадр N рисуется, пока главный поток
  считает кадр N+1 **[П]**.
- **Сцена рисуется не в задний буфер**, а в свою цель A8R8G8B8 размером с
  экран (`*0x012058A4`); перед `Present` она копируется в задний буфер
  `D3DXLoadSurfaceFromSurface` (`0x00608DC0`). Это и есть место для
  постэффектов поверх готового кадра (сглаживание, FSR 1, резкость) **[К]**.
- **Широкий экран уже правильный.** Камера задаёт горизонтальный угол
  60° для 16:9 и пересчитывает его под текущее соотношение так, что
  вертикальный угол постоянен (Hor+): 36,0° по вертикали при 4:3, 16:9 и
  21:9. HUD прижат к углам, круглая мини-карта остаётся круглой **[П]**.
- **«Вертикальная синхронизация» в настройках — это 30 кадров/с.** Во
  весь экран игра просит `D3DPRESENT_INTERVAL_TWO` (каждый второй
  обновлённый кадр монитора), в окне — ждёт сама 33,3 мс между показами
  (`0x00608CA0`). Без неё ограничителя нет вовсе **[К]**.
- **Таблица текстур 4096 записей** заполнена на 65–68 % в плотных зонах
  обоих городов (2 670–2 800 записей, оценка 160–164 МБ) **[П]**. Все
  текстуры потоков — в пуле `MANAGED`.
- **Кадр — около 8 800 вызовов отрисовки** и 95 проходов рендера
  (Нью-Йорк, 1280×720, HUD DXVK): игра упирается в поток рендера и
  драйвер, а не в видеокарту (загрузка 18 %) **[П]**.

| | затем `CheckDeviceFormat(…, D3DUSAGE_QUERY_VERTEXTEXTURE, TEXTURE, R32F)` → байт `0x0120575B` (выборка текстур в вершинном шейдере) и `CreateQuery(D3DQUERYTYPE_EVENT)` → `*0x01205754` | [К] |
| `0x006073E0` | параметры показа: один задний буфер, без MSAA, `D3DSWAPEFFECT_DISCARD`, без автоматической глубины (у игры своя), `Windowed` = не весь экран; интервал — §4 | [К] |
| `0x0060E810` | размер заднего буфера `*(u16*)0x012058B8` × `0x012058BC`; `0x01205878` — соотношение `w / h` (float) | [К] |
| `0x00986D10` | применение настроек экрана: окно (`+0x70`), синхронизация (`+0x78`), ширина, высота, частота обновления (`+0x114`, `+0x110`, `+0x118`) → `0x00607790` (сброс устройства), `0x00412BD0(частота)` — она же частота такта часов игры (`performance.md` §5) | [К] |
| `0x00608250` | `Reset` (`+0x40`) с теми же параметрами, `0x00607E10` перед ним освобождает цели в пуле `DEFAULT` | [К] |
| `0x00608F10` | цели рендера кадра (через `0x00606C80`, §6): `*0x012058A4` — цвет сцены A8R8G8B8 w×h, `*0x012058A8` — глубина D24S8 w×h, `*0x012058AC` — D24S8 1024×1024 | [К] |

**Показ.** Главный поток в конце кадра ставит в список отложенных вызовов
(`0x01117BB0`) функцию `0x0040DF60` (`0x0040E066`); поток рендера
выполняет её после буфера кадра (`0x00485280`). Цепочка:

```
0x0040DF60  счётчики профилировщика игры (*0x01223380 +0x9C/+0xA0, QPC в +0xA8/+0xB0)
 └ 0x0060D8B0(bool)        ← перехват профиля модуля (0x0040DFA2)
    ├ 0x00608CA0(2)        ограничитель окна: ждёт 2 × 16,667 мс от прошлого показа (§4)
    └ 0x00608E90
       ├ 0x00608DC0        цель *0x012058A4 → задний буфер: GetSurfaceLevel, GetBackBuffer,
       │                   D3DXLoadSurfaceFromSurface (фильтр 1 = D3DX_FILTER_NONE)
       └ Present (+0x44)   D3DERR_DEVICELOST → байт 0x0119DA5E
```

На стенде показов ровно столько же, сколько проходов главного цикла
(2 503 и 2 507 за 89 с), поток вызова — `Presentation` **[П]**.

## 3. Поток рендера и буферы команд

| Адрес | Что | |
|---|---|---|
| `0x00485AE0` | тело потока рендера: маска сродства `1 << *0x01205420`, `TLS+0x34 = 1` (признак «поток рендера» для всего кода, который пишет команды), цикл: семафор `0x00E2E294`, взять готовый буфер из очереди `0x01206870`, выполнить команды (`{функция, данные…}` от курсора `+0x18` до `+0x14`), вернуть буфер в свободные `0x01206878`, отложенные вызовы `0x00485280` | [К] |
| `0x0068BAF0` | начало кадра на главном потоке: счётчик `*0x01129A8C += 1`, взять свободный буфер (`0x0040CB40`, `0x0040CBE0`), ждать семафор `0x00E2E298`, если поток не рендера, первые команды, сообщения `iMsgBeforeRender` и др. | [К] |
| `0x0068BCD0` | конец кадра: последняя команда, сообщение, `0x0040CB90` — буфер в очередь потока рендера, `0x00485D50` — отдать и ждать семафор `0x00E2E294`, если включён поток рендера (`0x012053CB`) | [К] |
| `0x00AB5130` / `0x00AB51E0` | семафор: ждать (таймаут по `GetTickCount`) / отпустить | [К] |
| `0x00AB4DB0` | замок: `TryEnterCriticalSection`, при таймауте — `Sleep(1)` в цикле | [К] |

Буфер команд кадра один на кадр, в полёте — кадр, который рисуется, и
кадр, который пишется: главный поток ждёт поток рендера в конце кадра.
`IDirect3DDevice9` создан с `MULTITHREADED` (каждый вызов берёт замок
устройства), хотя D3D зовёт только поток рендера и загрузчик текстур
внутри команд **[К]**.

Сообщения кадра (хэши — `0x0040D640`): `iMsgBeforeRender`,
`iMsgPreRender`, `iMsgDoRender`, `iMsgDoRenderFullScreen`,
`iMsgDoRenderFullScreenDebug`, `iMsgPreShowRaster`. По имени — проход
сцены, полноэкранный проход (постэффекты, интерфейс) и шаг перед показом
**[Г]**: порядок команд внутри них не разобран.

## 4. Вертикальная синхронизация и ограничитель частоты

| Адрес | Что | |
|---|---|---|
| `0x00F15A39` | «синхронизация» из настроек (по умолчанию 1; запись `0x0060E680`, чтение `0x0060E690`) | [К] |
| `0x0120587F` | весь экран (запись `0x0060E850`, чтение `0x0060E860`) | [К] |
| `0x00F15A48` | `синхронизация ? 2 : 0` (`0x00607B5A`, `0x006084D6`) — сколько «обновлений по 16,667 мс» ждать | [К] |
| `0x0120575A` | 1 — ждёт сама игра: окно или устройство без `INTERVAL_TWO` | [К] |
| `0x00608CA0` | ограничитель: пока прошло меньше `n × 16,6667` мс (`0x00E4465C`) от прошлого показа — `SleepEx(0)` и снова `QueryPerformanceCounter` (занятое ожидание) | [К] |

Интервал показа (`0x006073E0`):

| Режим | Синхронизация | Интервал | Итог |
|---|---|---|---|
| окно | любая | `D3DPRESENT_INTERVAL_IMMEDIATE` | без синхронизации: ограничитель `0x00608CA0` ждёт 33,3 мс → **30 к/с** |
| окно | выкл | `IMMEDIATE` | без ограничения |
| весь экран | вкл | `INTERVAL_TWO`, если адаптер умеет (иначе `ONE`) | каждый второй кадр монитора: **30 к/с при 60 Гц**, 72 при 144 Гц |
| весь экран | выкл | `IMMEDIATE`, если умеет | без ограничения |

То есть настройка «синхронизация» — это замок 30 к/с, а другой
ограничитель есть только в мёртвом коде: `0x0040D450` (ждать до
`тактов / частота` по `QueryPerformanceCounter`) никто не вызывает (нет ни
вызовов, ни указателей) **[К]**. На стенде синхронизация выключена
(`*0x00F15A39 = 0`), игра в окне: ограничителя нет, частоту задают
DXVK (`d3d9.maxFrameRate`) и вывод в X-сервер **[П]**.

## 5. Камера, угол обзора, соотношение сторон, HUD

| Адрес | Что | |
|---|---|---|
| `0x00422590` | новый вид (слот пула видов): `+0x148` дальняя плоскость 5000, `+0x14C` угол 1,0472 (60°), `+0x150` соотношение `*0x01205878` | [К] |
| `0x00422FB0` | `SetFov(угол, соотношение)` вида: `+0x14C`, `+0x150`, пересчёт проекции `0x00423900`; с главного потока — ещё команда потоку рендера | [К] |
| `0x009BD990`, `0x009BEB00` | камера игрока: угол из данных камеры `f` → `2·atan(tan(f/2) · aspect · 9/16)` → `0x00422FB0`; **пешком в игре не вызываются** (этап 59, трассировка всех 11 вызовов `SetFov`) | [П] |
| `0x004252E0` → `0x00425EA0` | менеджер камер: список камер по 0x1D0 байт (угол `+0x30`, режим `+0x38`: 2 — пересчёт под соотношение с опорой `+0x34`), каждый кадр отдаёт виду, которым рисуется кадр, угол через `SetFov` в `0x00425FE4` — **единственный вызов, меняющий картинку в игре** (60°, на бегу 67,5° при 16:9) | [П] |
| `0x00425240` | тот же пересчёт с опорой 16:9 или 4:3 (`0x00E447AC` = 1,7778, `0x00E447A8` = 1,3333) — для режима 2 | [К] |

Угол в данных — горизонтальный при 16:9; при другом соотношении
горизонтальный пересчитывается так, что вертикальный не меняется.
Проверка (`live camera`: угол по плоскостям пирамиды видимости):

| Размер | Соотношение | Вертикальный угол | Горизонтальный (расчёт) |
|---|---|---|---|
| 1024×768, 640×480 | 4:3 | 36,0° | 46,8° |
| 1280×720 | 16:9 | 36,0° | 60,0° |
| 1680×720 | 21:9 | 36,0° | 74,3° |

`tan(18°) · 16/9 = tan(30°)`: угол камеры игры — 60° по горизонтали при
16:9, то есть Hor+ без правок **[П]**. HUD (APT, `apx`) рисуется у углов
экрана: деньги и здоровье слева сверху, имя цели справа сверху,
мини-карта справа снизу — на 16:9 и 21:9 круглая, без растяжения
(снимки стенда `hud169`, `hud219`) **[П]**. Не проверено: ролики (камеры
`igc`/NIS — идут ли через `0x00425240` с опорой 4:3 и нет ли там
обрезки), меню во весь экран и список разрешений во весь экран (игра
берёт режимы адаптера, `0x0060EA60`).

Узкое место для широкого экрана не в камере, а в **угле**: 36° по
вертикали — узко для 21:9 и для мониторов вблизи. Ползунок угла сделан в
этапе 59 (`performance.md` §10.3): графический модуль стоит в вызове
`0x00425FE4` и умножает тангенс половины угла — вертикальный угол на
стенде 41,2° → 66,1° при `fov=90` **[П]**. Методы `0x009BD990`/`0x009BEB00`,
названные здесь раньше, пешком не вызываются (трассировка, этап 59).

Таблица и загрузчик — `live-link.md` §12.3. Здесь — предел.

| Адрес | Что | |
|---|---|---|
| `0x011A0F28` | 4096 записей × 0x38 байт (до `0x011D8F28`) | [К] |
| `0x011D8F28` | битовая карта занятости: 64 × u64 сразу за таблицей; `0x011D9128` — номер первого слова со свободным битом | [К] |
| `0x00606C80` | создать запись: номер из `0x00606B50` (поиск по битовой карте) или заданный, `0x00618640` — `CreateTexture`; номер ≥ 0x1000 или нет свободного → `0xFFFFFFFF`; как это переносят 23 вызывающих — не разобрано | [К] |
| `0x006065A0` | освободить запись | [К] |

На таблицу ссылаются 282 инструкции в 145 функциях (абсолютные адреса
полей `0x011A0F28`–`0x011A0F5F`) **[К]**. Занятость (профиль модуля):

| Где | Занято / 4096 | Создано | Цели рендера | `MANAGED` | Оценка | Из них `DEFAULT` |
|---|---|---|---|---|---|---|
| Гавана, старт, 1024×768 | 2 643 | 2 642 | 45 | 2 596 | 141,5 МБ | 54,3 МБ |
| Нью-Йорк, старт, 1680×720 | 2 740 | 2 739 | 45 | 2 693 | 163,3 МБ | 71,4 МБ |
| Нью-Йорк, 8 телепортов по городу | 2 674–2 795 | | | | 160,6–164,2 МБ | |

Старший занятый номер — 4095: записи раздаются не подряд. Запас — около
1 300 записей. Подмена текстур
HD-версиями **не тратит** записей (тот же ресурс), тратят только новые
текстуры модов. Пул `MANAGED` значит копию каждой текстуры в памяти
процесса (D3D9 или DXVK держат её для восстановления): в 32-битном
процессе это 2 ГБ на всё — HD-текстуры упрутся в адресное пространство
раньше, чем в таблицу (`performance.md` §3). DXVK в 32-битных играх держит
отображёнными не больше 128 МБ таких копий (HUD: «Mappable 128 MB, used
93 MB»), остальное выгружает.

## 8. Цепочка кадра и где вставить постэффекты

HUD DXVK (Нью-Йорк, 1280×720): 95 проходов рендера, 8 776 вызовов
отрисовки, 162 барьера, 12 отправок очереди за кадр. Цели, созданные при
старте устройства: цвет сцены, глубина D24S8 размером с экран, D24S8
1024×1024 (по размеру — карта теней) **[К]**; всего 45 целей рендера в
таблице (профиль). Порядок проходов (тени → сцена → постэффекты →
интерфейс) — по константам и сообщениям кадра **[Г]**.

Куда ставить свои постэффекты:

1. **Перед копией в задний буфер** (`0x00608DC0` на потоке рендера):
   цель `*0x012058A4` — готовый кадр. Модуль подменяет копию своим
   полноэкранным проходом (FXAA/SMAA 1x, FSR 1 EASU+RCAS, резкость CAS) из
   этой текстуры в задний буфер. Просто и надёжно; минус — интерфейс уже в
   кадре и тоже пройдёт через фильтр (текст HUD чуть размоется от FXAA,
   резкость сделает его жёстче) **[К]**.
2. **Между сценой и интерфейсом** — на `iMsgDoRenderFullScreen` или раньше
   первой команды APT: кадр без HUD. Требует разобрать порядок команд в
   буфере кадра **[Г]**.
3. **Рендер в меньшем разрешении + FSR 1**: цели `0x00608F10` создаются по
   `*0x0120587C`/`*0x01205880` (размер вида), а копия масштабирует в
   задний буфер — меньший размер вида при полном заднем буфере даёт
   масштабирование «бесплатно», FSR заменяет копию. Проверить, что вид и
   HUD берут размер отсюда, а не из заднего буфера **[Г]**.

## 9. Что можно исправить (рендер)

Сводный список с замерами — `performance.md` §8. Пункты рендера:

| Постэффекты (FXAA/SMAA, FSR 1, CAS) | **FXAA и резкость сделаны (этап 59)**: перехват вызова копии `0x00608E90`; FSR 1 — нет (`performance.md` §10.4) | M |

## 10. Шейдеры, свет и время суток (этап 66)

Разбор 943 шейдеров (`research/d3d9_shaders.py`), декомпиляция и живая
связь на стенде (`live time`, `live peek`; три города, 00:00–23:30).

### 10.1 Что рисует что

Байткод — 34 вида инструкций SM 3.0 (`mul`, `mad`, `add`, `dcl`, `mov`,
`texld`, `cmp`, `dp3` — 80 %; ветвлений `if` 257, циклов `rep` 35, вызовов
и предикатов нет). Семейства по константам и сэмплерам:

| Проход | Шейдеры | Константы |
|---|---|---|
| глубина и нормали (`Depth*PS`, `DeferredNormals*`) | ~140 | нормаль и степень блика в цель `g_nBuffer` |
| свет в буфер (солнце, точки, «коробки», тени) | ~130 | `g_nBuffer`, `g_zBuffer`, `g_lightColor`, `g_lightDirection`, `g_diffuseAmbient`, `g_shadowColor`, `g_shadowDensity`, `g_SHQuadricMtx*`, `g_lightColorSH`, `g_view_to_shadow` |
| освещённый проход мира (`gf_basic`, `gf_building*`, `gf_road`, `gf_pano`, вода, стёкла, деревья) | 132 | `g_DeferredLightingSampler` (буфер света по `vPos`), `g_ToneMappingTexture`, `m_FogColor`, `m_FogEndColor`, `m_FogStartEndParams` |
| персонажи и машины вперёд (без буфера) | ~30 | `g_WorldLightParameters` (4 источника × тип, позиция, цвет, направление, свойства), `g_SHMatrixR/G/B`, тени трёх каскадов |
| небо (`sky_dome`, `sky_clouds`) | 2 | `g_SkyColor`, `g_SkyColorLow`, `g_DiffusionColor*`, `g_DiffusionControl*`, `g_HazeBandElevationAngle`, `g_SunDirAndPower`, звёзды |
| постэффекты | ~250 | цветовые LUT 32³ (`gLUTTexture*`, `saturateColor`), блум, глубина резкости, размытие движения, виньетка |

**Освещение — light pre-pass** **[К]**: нормали → буфер света (8 бит на
канал) → освещённый проход. Солнце в буфере (`0x00CD5930`, с тенью
`0x00CD68A0`): `saturate(n·(−l) + g_diffuseAmbient.x) × g_lightColor`, в
тени `lerp(g_shadowColor, свет, тень × density.y + density.x)`, в альфе —
блик `pow(n·h, s³·255)`; рассеянный свет — квадратичная форма
`(n,1)ᵀ·M·(n,1)` трёх матриц × `g_lightColorSH` (`0x00D04930`).
Освещённый проход (`gf_basic`, `0x00ACEA68`):

```
albedo = base^2.2
light  = буфер(vPos);  t = g_ToneMappingTexture(lum(light))
colour = albedo × light × t × 2
f      = saturate((|P − eye| − start) × (1/(end − start)))
fog    = lerp(m_FogColor, m_FogEndColor, f),  сила lerp(z, w, f) (0, пока f = 0)
out    = pow(lerp(colour, fog, сила), 1/2.2)
```

«× 2» — свет до 2 при 8-битном буфере. Альфа — `base.a × g_Tint.w`.

### 10.2 Откуда константы: ключи времени суток

Таблиц света в `exe` нет. В потоке `gf2/<город>/local` два `TODSequencer`
(`TODSequencer_Cuba` и `TODSequencer_Int_Cuba` — улица и интерьеры), их
ключи — объекты семейства `TODMessage`: атрибуты 0–2 — часы, минуты,
секунды, 4 — GUID последовательности. Между ключами одного вида игра
интерполирует линейно, через полночь тоже (`0x0082DF70`); в Гаване на
улице 8 ключей тумана и 14 неба **[П]**.

| Класс | Атрибуты | Куда |
|---|---|---|
| `SetFogMessage` | 0, 1 цвета, 2 начало, 3 конец (м), 5, 6 сила в начале и конце | `m_FogColor`, `m_FogEndColor`, `m_FogStartEndParams` [К] |
| `SetSkyMessage` (`0x0D0F12E8`, имени в `exe` нет; чтение `0x009D5A00`) | 2 небо выше полосы дымки, 3 у горизонта, 6, 7 свечение вокруг солнца, 1 его сила, 8, 10 показатели, 12 высота полосы (рад) | `g_SkyColor`, `g_SkyColorLow`, `g_Diffusion*`, `g_HazeBandElevationAngle` [Г: по кадрам] |
| `LightingTODMessage` (`0x009D3680`) | 0 тень (насколько она темнит), 1 «обёртка» света | `*0x0110AC2C`, `*0x0110AC30` → `g_shadowDensity`, `g_diffuseAmbient` [П] |
| `GlobalSHTODMessage` | 0–2 матрицы R, G, B (16 чисел текстом) | `g_SHMatrix*` [К] |
| `ToneMappingTODMessage` (`0x00835D40`) | 1–4 (атрибут 0 нигде не задан) | `*0x01206A90…0x01206AAC` [П] |
| `LUTTODMessage` | 0 `vfx` таблицы цвета, 1 вес | `gLUTTexture1…6`, `gLUT_params1/2` [П], §10.9 |
| `NightDayControlTODMessage` | 0 ночь (1) или день (0, и когда не задан) | `g_NightControl` [К], §10.9 |
| `BloomTODMessage`, `RimLightingTODMessage`, `SheenTODMessage`, `WaterTODMessage` | блум, обводящий свет, блеск, вода | не перенесены |

Цвета — `0xAABBGGRR`: игра кладёт `value & 0xFF` в `x` (`0x009D5A00`);
только так полуденное небо Гаваны голубое сверху, а вечернее — бурое,
как в кадрах игры. На стенде в 12:03 `*0x0110AC2C` = 0,675 и `+4` = 0,25 —
ключ 12:03 Гаваны; в 00:03 — 0,393 и 0,221, ровно интерполяция ключей
21:03 и 04:03 **[П]**.

### 10.3 Тональная кривая

`g_ToneMappingTexture` — 128 значений `t(lum)`, которые строит
`0x0041D7D0`: гистограмма яркости буфера света (128 корзин, чтение
текстуры 64×64), минимум на корзину `*0x01206A94`, ограничение спада
`*0x01206A98`, накопленная сумма, смесь с прямой по `*0x01206AA0` и
множитель `4^x` по сплайну трёх «экспозиций» (`0x01206AB0…0x01206AE8`).
Включает её флаг качества (`0x0042C1F0` → `0x0041CF70`); при нулевых
экспозициях и `*0x01206AA0` = 0 игра берёт постоянную текстуру
(`0x0041DDF0`). На стенде так во всех трёх городах: экспозиции нули,
`*0x01206AA0` = 0, `*0x01205958` = 0 — кривая плоская, `t = 1` **[П]**.
Поэтому «тональная кривая» игры в кадре — это «× 2» и `pow(x, 1/2.2)`.

### 10.4 Солнце

Направление солнца — не ключ: игра ведёт его по своему пути, стоит с
04:00 до 06:00 и с 18:00 до 21:00 (луна), а у Нью-Йорка путь другой
(восход в другой стороне). Вектор света — `*0x01211240` (и копии в
командах кадра); снят каждые полчаса во всех трёх городах **[П]** и
лежит таблицей по часам в `time_of_day::sun_direction`. Цвет солнца в
буфере и доля рассеянного света (`g_lightColor`, `g_lightColorSH`)
задаются кодом, их значений не нашли: в редакторе они подобраны по кадрам
(§10.6).

### 10.5 Переводчик или порты

Переводчик байткода в WGSL возможен (34 инструкции, CTAB даёт имена всех
регистров), но сам по себе не даёт картинки: освещённые шейдеры читают
буфер света, нормалей и глубины по `vPos`, тени трёх каскадов, вершинные
шейдеры — форматы вершин игры и ~20 матриц на вызов. Пришлось бы повторить
весь конвейер игры с 45 целями. Семейства же сводятся к нескольким
формулам, поэтому выбраны **ручные порты** главного: буфер света (солнце с
обёрткой и матрицы рассеянного света), освещённый проход (× 2, гамма 2,2),
туман и небо — в `scene.wgsl` редактора, с ключами времени суток из данных
игры (`docs/viewers.md` §7a).

### 10.6 Сравнение кадров

Стенд: свой префикс, свой Xvfb, своя тень, модуль связи, 1280×720,
`live time ЧЧ:ММ --rate 0`, камера игры (`live camera`) в пресет вида
уровня (`eye`, `look`, `fov=36`, `time`). Гавана, Нью-Йорк, Майами в
12:03, 18:03 и 00:03. Земля в Гаване по яркости совпала во все три часа
(в среднем по участку: полдень 140/126/98 в игре и 139/131/112 в
редакторе, вечер 83/66/45 и 81/70/55, ночь 52/51/51 и 63/63/57) после
подбора `SUN_AT_NOON = 0,42`, `AMBIENT_SCALE = 0,2` и тёплого цвета
солнца. Не совпадают: тени и свет фонарей (нет), цветовая LUT и блум
(нет), оттенки материалов зданий и дорог (`g_BaseTintColor`, детальные
карты; вид уровня рисует только основную текстуру), небо Нью-Йорка в
полдень темнее игрового. Материалы мира сделаны на этапе 69 (§10.7), свет
после этого подобран заново (§10.8).

### 10.7 Материалы мира (этап 69)

Меши трёх городов (`gf2/cuba/local`, `gf2/queens/local`,
`gf2/miami/local`) рисуются 8 020 материалами мира (по городам, общий
материал двух городов считается дважды; корпусный тест
`every_world_material_of_the_cities_finds_its_textures`). Шейдеры
разобраны дизассемблером (`research/d3d9_shaders.py … dis <смещение>`;
ниже — смещения байткода в файле `exe`, байткод в репозиторий не кладётся).
Материал называет шейдер прохода нормалей (слот 0) и освещённого прохода
(слот 1), параметры у каждого прохода свои (`Material::shaders`: первый
параметр и число).

| Модель (`WorldModel`) | Освещённый шейдер | Материалов | Треугольников мешей | Цвет |
|---|---|---:|---:|---|
| `Detail` | `gf_building_detail` (`0x00A82198`, без блеска `0x00A82EF0`), `gf_road` | 4 251 | 8,35 млн | два слоя по маске (ниже) |
| `Building` | `gf_building` (`0x00A7FB30`), `gf_basic_tint_reflect` (`0x00A7DC18`) | 1 933 | 3,48 млн | `lerp(base, base·g_BaseTintColor, base.a)` |
| `Basic` | `gf_basic` (`0x00A7C0F0`), `gf_normal_spec*` (`0x00ACAFE8`), `UVanimation*`, `gf_vehicles` | 1 508 | 2,61 млн | `base` |
| `Window`, `Glass` | `WindowGlow` (`0x00AE9138`), `WindowParallax`, `WindowGlass` (`0x00AE27A0`) | 284 | 0,09 млн | передняя карта `g_FrontMap` и отражение |
| `Panorama` | `gf_pano` (`0x00ACCF40`) | 37 | 0,03 млн | `lerp(base, base·g_BaseTintColor, detail.b)` |
| `Water` | `WaterOcean*` (простой — `0x00ADDAD0`) | 4 | 0,05 млн | `WaterColor` × свет × 2 + блик |
| `Overlay` | `gf_overlay_vertex_ao` (`0x00ACC138`) | 3 | 0,14 млн | затемняет то, что под ним |

**Слои `gf_building_detail`** **[К]** (дороги, тротуары, земля, стены —
половина треугольников городов):

```
B = base^2.2;    B = lerp(B, B · g_BaseTintColor, base.a)       — основной слой
D = detail^2.2;  D = lerp(D, D · g_DetailTintColor, detail.a)   — детальный слой
m = mask.r · g_MaskRangeScale                                   — маска g_MaskSampler
albedo = lerp(D, B, m);   alpha = lerp(DetailTint.w, BaseTint.w, m) · vcolor.a · g_Tint.w
colour = (albedo · L + gloss.r · g_SpecNormMapParams.z · L · L.a) · vcolor.g
```

`L` — буфер света × тон × 2, `L.a` — блик солнца. UV задаёт вершинный
шейдер (`0x00A814F0`, `0x00A81730`): основной слой — UV меша, детальный —
`uv · g_DetailUVScaleAndOffset.xy + .zw`, маска —
`uv · g_MaskUVScaleAndOffset.xy + .zw` (без поправки `uv-offsets`
персонажей). Альфа текстуры у основного и детального слоя — маска оттенка
(у 980 из 4 247 основных текстур это DXT5), а не прозрачность. Детальный слой
часто та же текстура, что основной (2 666 из 4 247), но с другим оттенком и
масштабом: так игра и даёт «грязь» и пятна.

**Цвет вершин** **[К]**: вершинные шейдеры мира передают зелёный и альфу
цвета вершины (`mov o1.yw, v2`; при «низком» объявлении вершин —
распакованные из `normal.w`, `gHighQualDeclLowQualShaderParams`). Каждый
освещённый шейдер мира умножает цвет на зелёный — запечённое затенение,
в среднем по материалу 0,7–1, — и альфу на альфу; красный и синий не
читаются. Туман смешивается после этого умножения.

**Проход нормалей и блик** **[К]**:

| Шейдер прохода нормалей | Нормаль | Резкость блика `s` (альфа буфера нормалей) |
|---|---|---|
| `DeferredNormals` (`0x00D083B0`), `…Alpha` | `normalize(N + (x·T + y·B)·g_materialNormalMapScale)`, `(x, y) = (a, g)·2 − 1` карты `g_materialNormalMap` (`DXT5_NM`) | синий канал `g_materialSpecMap` (в трёх городах это всегда та же текстура, что `g_GlossMapSampler` освещённого прохода) |
| `gf_building_detail_depth` (`0x00A82C48`) | то же, `(x, y) = lerp(детальная, основная, m)` по той же маске (`g_materialNormalMapDetail`, `g_materialNormalMapMask` — всегда та же текстура и UV, что `g_MaskSampler`) | `g_SpecularExponent` |
| `DepthSpecExpNxy12PS` (`0x00A86AE0`) | карта `g_NormalMapSampler` | `gloss.b · g_SpecParams.x` |
| `DepthSpecExp…LowResPS` (`0x00A87B78`) | нормаль вершины | `g_SpecParams.x` |
| `DeferredNormalsFast*`, вода | нормаль вершины | не параметр (в редакторе 0,5) **[Г]** |

Буфер света (`0x00CC4300` и соседние, `g_lightColor`): блик
`pow(n·h, s³·255 + 1,5·10⁻⁵) · [n·l > 0] · saturate(n·l + wrap) ·
g_lightColor.w`. Освещённый проход добавляет его так:

| Шейдер | Блик в цвете |
|---|---|
| `gf_building_detail`, `gf_road` | `gloss.r · g_SpecNormMapParams.z · L · L.a` (и на свет) |
| `gf_building` | `gloss.r · g_SpecMapRange · L.a` |
| `gf_basic` | `g_SpecularScale · L.a` |
| `gf_normal_spec*` | `gloss.r · g_SpecColorAndScale.rgb · L.a` |
| `gf_basic_tint_reflect` | `g_SpecColorAndScale.rgb · L.a` |
| `WindowGlow`, `WindowParallax` | `g_SpecScale · L.a` |
| вода (простая) | `L.a` |

**Отражения** **[К]**: `gf_normal_spec_reflect` и `gf_basic_tint_reflect`
прибавляют после затенения `env^2.2 · g_ReflectionScale` (первый — ещё
× `gloss.g`), окна — `saturate(env^2.2 · (R.x + (1 − |v·n|)·R.y) · front.a)`
по `ReflectionRange`, где `env` — кубическая карта
`kEnvironmentMapSampler`, повёрнутая на 45° вокруг вертикали (у окон —
по `|y|`, небо в нижней половине зеркально). Карта — `runtime_generated/~cubemap.tga`:
её строит игра, в файлах её нет; редактор берёт вместо неё своё небо
(§10.1) **[Г]**.

**Окна** **[К]**: `WindowGlow` днём (`g_NightControl` = 0) —
`front^2.2 · L + отражение + блик`; ночью к свету прибавляется
`g_NightControl · m_LightColor · front.a` и окна светятся (переход —
`NightDayControlTODMessage`, этап 70). `WindowGlass` не освещается:
`front^2.2 · front.a + env · (R.x + (1 − |v·n|)·R.y)`, альфа
`(1 − front.a) · g_Tint.w` — доля того, что за стеклом **[К]**; режим
смешивания в шейдере не записан, по формуле это `ONE, SRCALPHA` (цвет
стекла поверх ослабленного фона) **[Г]**.

**Слои наложения** **[Г]**: материалы пятен, грязи, следов шин
(`*_overlay`, `ground_02` и т. п.) — те же шейдеры мира без флага
смешивания, но альфа вершин у них в среднем 30–80 из 255, а записи мешей —
слои наложения (`0x28` > 0, `DoNotRenderDepth`, `geometry.md`). Нарисованные
непрозрачно, они дают тёмные полосы и пятна, которых в кадрах игры нет;
со смешиванием по своей альфе — как в игре. `gf_overlay_vertex_ao` —
пятна затенения под предметами: цвет — туман (без тумана чёрный), альфа
`1 − g_VertexAOParams.y · vcolor.g`.

**Встроенные текстуры** **[К]**: 4 666 из 8 051 материала городов называют
текстуры, которых нет в файлах, — по имени без пути: `specular`
(хэш `e9930443`), `normal` (`7f00d6f1`), `color` (`3d115391`) и
`runtime_generated/~cubemap*.tga` (`0665231c`, `906bcc4b`). Игра создаёт их
при запуске по таблице `0x0110A450` (`{имя, 0xAARRGGBB}`): `color` —
`0xFFFFFFFF` (белая), `normal` — `0x80808080` (ровная нормаль),
`specular` — `0xFF000000` (чёрная: ни блика, ни резкости), `occlusion` —
белая, `lightmap` — чёрная. Остальные текстуры материалов мира находятся
все (корпусный тест).

**Альфа-тест** **[К]**: только у материалов с флагом `0x1` (`geometry.md`
§6) — проходы нормалей `…AlphaTest…`, `DeferredNormalsAlpha`; у прочих альфа
основной текстуры — маска оттенка.

**Не повторено**: ночное свечение окон и панорам (`g_NightControl`,
`m_LightColor`, `g_NightGlowColor` — этап 70), блеск дорог `gf_road`
(`g_breakUpMap`, `g_sheen*`), волны, пена и отражения воды высокого
качества (`WaterOceanHiRes`: волны Герстнера, FFT-карты), анимация UV
(`g_UVStepParams`, `g_UVScrollParams`), «комната за окном»
`WindowParallax` (`g_BackMap`), кубические карты окружения игры, карты
нормалей в DXT1 (28 материалов: игра читает из них `(a, g)` как из
`DXT5_NM`).

### 10.9 Тени, фонари и цвет (этап 70)

Декомпиляция (пакетный режим по копии `exe`), байткод шейдеров
(`research/d3d9_shaders.py`), объекты SimGroup и metamodel трёх городов,
`live peek` на стенде (свой префикс, свой Xvfb, своя тень игры).

**Цветовая коррекция** **[П]**. `LUTTODMessage` (атрибут 0 — GUID-ссылка на
`vfx`, 1 — вес, во всех ключах 1) — ключ последовательности времени суток,
как туман и небо. Ссылка ведёт на `vfx` эффекта `LUTVFXSequence`
(`gf2/globals_global`: `79a50ab1`, `a8a7042f`, `c9554e71`, `11d28535`,
`3f8b0444`, `5d0bed2d`; в `gf2/<город>/local` — `65b60937`, `a9a26838`). Сам
`vfx` таблицы не держит: в его блоке `rcs.` (12 байт после метки) — поле
имени в 16 байт, обрезанное с начала (`r_miami_day`, `iami_dawn`,
`i_night`), а таблица — объёмная текстура `tg4h` 32×32×32 RGBA8 с именем
`lutcolor_<…>` в `gf2/globals_global`: `lutcolor_miami_day`, `…_dawn`,
`…_dawn_g60`, `…_dusk`, `…_night`, `lutcolor_interior` (тождественная), а
также `lutcolor_dv_*`, `…_dons_view`, `…_poster` для меню и роликов. Все три
города берут таблицы Майами. Красный — по x, зелёный — по y, синий — по
срезам (`gLutBlueSlice`). Расписание улицы (одно на три города):

| Ключ | 04:03:34 | 05:47:34 | 06:02:34 | 06:47:34 | 11:01:34 | 12:06:34 | 15:30:34 | 18:01:34 | 21:02:34 |
|---|---|---|---|---|---|---|---|---|---|
| таблица | night | dawn | dawn_g60 | dawn | dawn | day | dawn | dusk | night |

Шейдер `AlchemyLUTShader` (`0x00C59B00` и ещё пять — до шести таблиц,
`0x0053D6E0` берёт их константы): `at = c · saturateColor · 31/32 + 1/64`,
`out = lerp(c · saturateColor, Σ wᵢ · LUTᵢ(at), gLUT_params1.x)`, где `c` —
готовый кадр (после `pow(1/2.2)`), веса — `gLUT_params1.yzw`,
`gLUT_params2`; `saturateColor` = 1, пока его не меняет эффект вспышки
(`0x0052A170`). Веса считает `0x0052EA40` из активных эффектов
(`0x01219388`…), текстуры и веса лежат в `0x0121930C` (6 × u32 номер в
таблице текстур), `0x01219324` (сила и веса), `0x01219344` (число). На
стенде в Гаване: 11:30 — `dawn` 0,5626 + `day` 0,4374; 12:03 — 0,0549 и
0,9451; 12:30 — `day` 0,8851 + `dawn` 0,1149; 18:03 — `dusk` 0,9921 +
`night` 0,0079; 00:03 — `night` 1; 06:15 — `dawn_g60` 0,7237 + `dawn`
0,2763. Это ровно линейная интерполяция соседних ключей по секундам, как у
прочих ключей (`(12:03:00 − 11:01:34) / 65 мин = 0,945`). Таблица `day`
светлит и греет полдень: серый 0,5 → 164/163/163, синий канал в тени
сохраняет; `night` греет ночь (0,5 → 191/177/169).

**Свечение (блум)** **[К]**. `BloomTODMessage` (атрибуты 0, 1, 3, 4 —
цвета `0xAABBGGRR`, 2, 5–8 — числа; улица: 8/12 и 1,0–1,75) задаёт
`bloom_tintColor`, `bloom_dcolor`, `bloom_blackcolor`,
`bloom_blacktintColor`; композит (`0x00C5B9A0`) прибавляет
`(bloom − 0,5) · tint` к кадру до таблицы цвета, сам `bloom_texture` строят
проходы размытия `gWeightBloom` (`0x00C46698`). Не перенесено.

**Тени солнца** **[К]**, **[П]** по кадрам. Цель тени — D24S8 1024×1024
(§2), три каскада (`g_shadowSampler`, `g_2ndShadowSampler`,
`g_3rdShadowSampler`, `g_CascadedShadowFadeControl`, `g_ZPlaneNear123`)
собираются шейдерами `0x00CDCCA8`… в экранный буфер ослабления
(`g_shadowAttenuationBuffer`), его читает проход солнца (`0x00CCD070`):
`out = shadowColor + k · (saturate(n·l + wrap) · lightColor − shadowColor)`,
`k = density.x + att · density.y`, блик × `k`. Плотность пишет `0x004317F0`
из `LightingTODMessage` (атрибут 0 → `*0x0110AC2C`) и таблицы
`0x0110AC40` (пары (0, 2) и (1, 2) для разных проходов): у прохода солнца
в тени остаётся `1 −` атрибут 0 (Гавана в полдень — 0,325). Тень
отбрасывают материалы с шейдером тени (первый из пяти проходов материала,
смещение `0x1C`: `264add01` у мира, `876dfaac` с альфа-тестом, `363a388f`
у персонажей и невидимых `shadowcaster`); стекло, слои наложения,
панорамы, вода и небо — без него. Направление: тени персонажей в кадрах
игры (Гавана и Майами в полдень — вправо от камеры, Нью-Йорк — назад, под
навес аэропорта) лежат обратно горизонтальной части измеренного вектора
света `*0x01211240` (§10.4): редактор берёт вектор с повёрнутым на 180°
азимутом и тем же наклоном — для тени и для света солнца. В сумерки
(18:00–21:00 игра держит «луну») тень игрока в Гаване уходит иначе —
не разобрано. Атрибуты 2, 3 `LightingTODMessage` (0,35/0,35 днём,
0,2/0,4 в сумерки) не разобраны.

**Фонари** **[К]**. Свет — части `EARSLight` и `TODEARSLight` метамоделей
(7 433 части в потоках `gf2`; `MobfaceEARSLight` — свет лиц в роликах),
свойства `EARSLight.CMD_Set_t_*`:

|---|---|

Шейдеры буфера света (`DeferredPointLight` `0x00CC4D00`,
`DeferredSpotLight` `0x00CC7F60`): `att = 1 − saturate((d − params.x) ·

`saturate(n·l + diffuseAmbient)`, у прожектора ещё
`1 − saturate((1 + l·dir − params.z) · params.w)` по конусу; свет
складывается в 8-битный буфер, как солнце. Отдельно — ресурс `lighttoc`

`f2400500`, u32 0x10, u32 0, u32 число; записи по 0xA0 байт: GUID, матрица

1, радиус, угол, …, имя `earslight_point` (28 байт) — в редакторе не
используется.
