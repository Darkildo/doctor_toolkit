# Lua-API движка: что игра даёт скриптам (этап 74)

The Godfather II, PC, издание 1.0.789.0. Адреса — виртуальные адреса
`godfather2.exe`. Источники: код exe (Ghidra и дизассемблер), скрипт
`research/lua_api.py`, 30 скриптов игры, опыты на стенде
(`game-bench.md` §35). Пометки: **[exe]** — прочитано в коде, **[стенд]** —
видели в запущенной игре, **[догадка]** — предположение.

Полный список функций с адресами, подписями и описаниями —
`data/gf2/lua_api.toml`; из него сделаны заметка базы знаний
[`kb/exe/lua-functions.md`](../kb/exe/lua-functions.md) и заглушка для
редакторов `data/gf2/schema/gf2-lua-api.lua`. Здесь — как это устроено и что
из этого следует для своих скриптов. Формат чанков и запуск скриптов —
`docs/formats/lua.md`, `docs/formats/mission-logic.md` §2–§3; узлы
визуальных скриптов — `docs/scripts.md`.

## 1. Что регистрируется и как это найдено

Игра регистрирует функции тремя способами **[exe]**:

1. встроенный `lua_register`: `push имя; push L; call lua_pushstring`
   (`0x625CA0`), замыкание C создаётся на месте (`0x638110`,
   `mov [eax+0xC], функция`) и кладётся в глобальные через `luaV_settable`
   (`0x633D60`) — так сделано большинство функций;
2. то же вызовом `lua_pushcclosure` (`0x625D70`) и `lua_settable`
   (`0x626030`) — полиция (`0x7874F0`) и транспорт (`0x880E30`);
3. массивы `{имя, функция}` с нулевым концом: `luaL_openlib` (`0x628260`)
   для стандартных библиотек и свой обход (`0x4AEB70`) для метатаблиц и
   таблицы `GroupManager`.

`research/lua_api.py scan` находит все три вида прямо в файле exe;
`check` сверяет с ним `lua_api.toml` в обе стороны (189 регистраций, 0
расхождений). То же правило закреплено корпусным тестом
`the_lua_functions_are_registered_where_the_data_says`. Второй тест
(`the_scripts_of_the_game_use_only_the_listed_functions`) проверяет обратное:
каждое глобальное имя, которое читают 30 скриптов игры, либо задано самими
скриптами, либо есть в списке, либо это одно из двух имён, которых в exe
нет (`SetWatchValue`, `ClearWatchValue`), либо одна из семи нигде не
заданных переменных (`yes`, `flag`, `UI`, `exterior`, `SFX_AMBIENT`,
`palmasSingerIsSpawned`, `set_protest_walla_quiet` — в скриптах игры они
равны `nil`; так, `PlayEmx(name, 1, 1, yes, 0, 1)` передаёт `nil`).

| Что | Сколько |
|---|---|
| функций всего | 195 |
| глобальных функций C игры | 74 (`EclipseLog` регистрируется дважды, по разу в каждое состояние Lua) |
| методов и метаметодов таблиц игры | 37 (`GroupManager` 3, `Group` 7, `Variable` 4, `UInt32` 7, `Int32` 9, `Base` 2, `MessageReceiver` 5) |
| функций встроенного текста Lua | 6 |
| функций стандартных библиотек | 78 (base 25, `coroutine` 5, `table` 8, `string` 12, `math` 24, `tolua` 4) |
| таблиц | 16 (6 библиотек, `GroupManager`, 6 метатаблиц, 3 таблицы встроенного Lua) |

У всех 117 функций игры подпись (аргументы, результаты, побочные эффекты)
прочитана в коде; 63 из них проверены на стенде (§12).

Подсистемы (ключ `group` в данных): эмиттеры звука, потоки музыки, эффекты,
потоки EARS, микшер и огибающие, таймеры и время, скрипты и вывод, позиции
и удары, переменные движка, целые 32 бита, объекты, группы, сообщения,
полиция, транспорт.

Общие свойства **[exe]**:

- Многие функции делают `return 1`, ничего не положив на стек: скрипт
  получает обратно свой последний аргумент (`SendMessage`, `VariableSet`,
  `AddMember`, `ForEachMember`, `EclipseLog`, методы `MessageReceiver`). В
  таблице данных это «(последний аргумент)».
- Неверные аргументы большинство звуковых функций молча пропускает;
  `luaL_error` с текстом есть у переменных, групп, `Base`, получателей.
- «Не найдено» — не `nil`: `PlayEmx`, `PlayEarsAudioStream`,
  `PrimeEarsAudioStream` возвращают light userdata с нулевым указателем,
  а оно в Lua истинно. `if handle then` неудачу не ловит **[стенд]**;
  отличить можно по `tostring(handle) == "userdata: 00000000"`.

## 2. Данные сообщений в Lua

Устройство самой шины — `docs/logic-graph.md` §1 и этап 78; здесь только
сторона Lua.

**Отправка.** `SendMessage(name [, dataType, data])` — `0x4C8510` →
`0x4C82C0` → синхронная рассылка `0x408A00` по `sdbm(lower(name))`. Данные —
одно слово сообщения, указатель **[exe]**:

| `data` | Что получает слушатель |
|---|---|
| нет, или `dataType` не строка | `NULL` |
| число | указатель на `float` на стеке вызова |
| строка | указатель на копию текста (освобождается после рассылки) |
| userdata | указатель на её память (например, позиция `CreatePosition`) |
| light userdata | сам указатель |

Текст `dataType` движок не читает: он нужен только затем, чтобы данные
вообще ушли. **[стенд]**: `SendMessage("m", nil, 7)` — слушатель получает
`nil`; `SendMessage("m", "t", 5)` — указатель, по которому лежит 5.

**Запрос с ответом.** `SendMessageEx(name, ...)` — `0x4C86D0`. Аргументы со
второго (до восьми) кладутся в структуру `EARS::Framework::Lua::MsgData`
(vtable `0xE365DC`; с `+4` восемь пар `{значение, тип}`: 0 `nil`,
1 указатель, 2 число, 3 boolean, 4 строка; счётчик — `+0x44`); сообщение
рассылается синхронно с указателем на неё, а всё, что слушатель дописал
после входных значений, возвращается скрипту (`0x4C8460`) **[exe]**. В игре
так отвечают `iMsgLuaGetPlayerVenue` и `iMsgLuaGetVenueStats` (имена задаёт
`0x6B01E0`; скрипт игры: `sVenueID, sVenueType, sVenueStatus,
sCurrentMonopoly, sVenueUnderAttack = SendMessageEx("iMsgLuaGetVenueStats",
params)`). **[стенд]**: `SendMessageEx("iMsgLuaGetPlayerVenue")` у ворот
аэропорта Гаваны вернул одну строку `"4"`; свой слушатель на
`SendMessageEx("doctor_s74_ex", 1.5, "two", true)` получил указатель на
структуру (второе слово — 1,5, третье — тип 2), результатов 0.

**Приём.** `MessageReceiverNew(handle)` (`0x4CE840`) создаёт объект движка —
получатель (конструктор `0x4CE090`, vtable `0xE36C60`: `+0x04` обработчик
шины `0x4CE720`, `+0x10` подписка `0x4CE180`, `+0x14` снятие `0x4CE3C0`,
`+0x18` снятие всех `0x4CE530`, `+0x1C` вызов Lua `0x4CE610`). На сообщение
`0x4CE720` находит подписку по хэшу и зовёт `0x4CE610`, а та — глобальную
функцию Lua `MessageReceiverReceive(handle, имя, имяТипа | nil, данные | nil)`
через `luaD_pcall` **[exe]**. Скрипты пользуются обёрткой из встроенного
текста (§9): `NewMessageReceiver(fn)`, и `fn` получает
`(self, имя, имяТипа, данные)`.

- `имяТипа` — то, что сам скрипт передал вторым аргументом
  `receiver:AddMessage(имя, имяТипа)`; движок его не проверяет и с
  сообщением не сверяет. Без него приходит `nil` **[стенд]**.
- `данные` — light userdata: сырой указатель из сообщения, либо `nil`,
  если указатель нулевой **[стенд]**.
- Читать память по указателю из Lua почти нечем: `GetPositionValues(data)`
  читает три `float` (так читается и одно число, посланное скриптом:
  первое значение — оно, остальные два — мусор стека) **[стенд]**;
  `GetImpactData(data)` разбирает пару `{объект, позиция}` удара;
  `SendMessageEx(…, data)` отдаёт указатель обратно движку. Скрипты игры
  данные почти не читают: передают их в обработчик (`lua_switch(msg,
  таблица, data)`), используют только `aud_havok_vfx.lua`
  (`GetImpactData`) и `aud_dons_view_sfx.lua` (`SendMessageEx`).
- Какие данные несёт каждое сообщение игры, зависит от его отправителя в
  коде движка; этого список не описывает (этап 78).
- `receiver:RemoveMessage(имя)` обёртки **сломан**: он зовёт
  `m_pReceiver:RemoveMessage`, а метод C называется `Remove` — ошибка
  «attempt to call method `RemoveMessage' (a string value)» **[стенд]**.
  Работает `receiver.m_pReceiver:Remove(имя)` и
  `receiver:RemoveAllMessages()`.

## 3. Объекты: `Base`

`Base(x)` (`0x46B7C0`; разбор аргумента `0x46B980`, создание `0x46B880`)
превращает GUID объекта в ссылку Lua — userdata `Base` (8 байт: слабая
ссылка, звено списка ссылок объекта `+0x48`; метаметоды `__gc` — он же
`DeleteBase` `0x46B7E0` — и `__tostring` `0x46BA70`, GUID текстом). Объект
ищется в реестре SimManager (`0x445FF0`) и принимается, если у него стоит
флаг `0x8000000` в `+0x14` (на стенде он есть у 8 620 объектов из 8 667)
**[exe]**.

**В этой сборке `Base` от строки не находит объектов игры.** Разбор текста
GUID (`0x46B4D0`, таблица позиций `0x0112865C`) собирает значение по
полубайтам, но сдвигает байт, а не слово (`shl dl, cl` на `0x46B59A`, запись
`or byte [esp+esi+0x14], dl`), и на выходе раскладывает четыре байта по
четырём словам (`0x46B5DA`–`0x46B5F9`). Из 32 цифр остаются восемь — байты
0, 4, 8 и 12 GUID, каждый один в своём 32-битном слове **[exe]**:

```
Base("{32C8D726-FA3D-AA11-464F-574C45523130}")
   ищет {00000026-003D-0000-4600-000045000000}
```

**[стенд]**: 230 объектов 91 класса (по три каждого) и отдельно объекты с
флагом — `Base` для всех вернул пустую ссылку (`tostring` даёт `nil`).
Текст из 32 цифр подряд разбор не принимает вовсе («ToBasePtr: Could not
turn '…' into a GUID.»).

Что из этого следует:

- у скрипта нет способа получить объект игры по GUID; данные сообщений
  несут сырые указатели, а не `Base`; функции, которой можно отдать такой
  указатель и получить `Base`, в списке нет;
- единственный источник настоящих `Base` — `Group:ForEachMember`, но в
  группу объект можно добавить только через `Base` (§4);
- **[догадка]**: объект мода с GUID вида `XX000000 YY000000 ZZ000000
  WW000000` (байты файла) `Base` нашёл бы; не проверено — открытый вопрос
  базы знаний.

## 4. Группы

`GroupManager` — глобальная таблица; методы зовутся через двоеточие
**[exe]**: `RegisterGroup(name)` `0x469DB0` (находит или занимает слот),
`FindGroup(name)` `0x469E60` (нет — `nil`), `RemoveFromAllGroups(base)`
`0x469F00`. Группа — userdata с номером одного из 64 слотов менеджера
`*0x1223414` (слот `0x1C` байт: хэш имени, счётчик ссылок, список, число
членов); принадлежность объекта — 64-битная маска в его компоненте
(`+0x148`, интерфейс `0x38523FC3`). Методы группы: `AddMember` `0x469F60`,
`RemoveMember` `0x469FF0`, `GetMemberCount` `0x46A100` (возвращает `UInt32`,
§6), `ForEachMember(fn)` `0x46A160` (`fn` получает `Base` члена; результат
отбрасывается, остановить обход нельзя).

- `IsMember` (`0x46A080`) и `Clear` (`0x46A0F0`) — **заглушки**:
  принадлежность не проверяется, группа не очищается; обе возвращают свой
  последний аргумент **[exe]**, `Clear()` на стенде вернул саму группу.
- **Падение игры.** `AddMember`, `RemoveMember`, `IsMember` и
  `RemoveFromAllGroups` берут объект через `0x46B980` и разыменовывают
  результат без проверки. Пустая ссылка `Base` или строка с GUID, который
  не найден, дают чтение по нулю: «Unhandled page fault on read access to
  00000000 at address 00469F85» **[стенд]** (у `AddMember`; остальные три —
  по коду). С учётом §3 это любой вызов с GUID объекта игры.
- **[стенд]**: пустая группа — `RegisterGroup` и `FindGroup` дают userdata,
  `GetMemberCount` — `UInt32` 0, `ForEachMember` на пустой группе ничего не
  зовёт. Группа с настоящим объектом не проверена: объект взять неоткуда.

## 5. Потоки EARS и звук

`PlayEarsAudioStream(nameOrHandle [, volume = 1 [, mixCategory]])` —
`0x438D10`, `PrimeEarsAudioStream(name [, volume [, mixCategory]])` —
`0x438F40` (общая часть `0x438BB0`) **[exe]**:

- имя хэшируется как есть (`sdbm(lower)`, `0x4DAFD0`) и ищется в каталоге
  потоков `*0x12233F8` (`0x456010`); расширение не добавляется и не
  отбрасывается — имя нужно с `.stx`;
- результат — light userdata со счётчиком запусков (менеджер
  `*0x122350C +0x1748`), не указатель; слотов пять (по `0x4A4` байта);
- нет такого потока — light userdata 0 без ошибки;
- вызов с handle от `PrimeEarsAudioStream` запускает подготовленный поток
  (`0x5E1FD0`), громкость при этом не читается;
- третий аргумент — имя категории микса (хэш), заменяет категорию потока.

`StopEarsAudioStream(handle)` (`0x439500`) гасит поток с временем
затухания из его данных (`0x5E2040`). `SetEarsAudioStreamStopMessage(handle,
messageName)` (`0x4395D0`) запоминает пару в карте `*0x12233F0+0x90`;
слушатель потоков `0x439580` по событию 3 шлёт сообщение синхронно и
стирает запись.

**[стенд]** (запись звука, уровень по секундам; фон у ворот аэропорта —
3 500–3 580 единиц, с потоком — 4 300–4 800):

| Вызов | Результат |
|---|---|
| `PlayEarsAudioStream("doctor_nope.stx")` | `userdata: 00000000`, уровень не меняется |
| `PlayEarsAudioStream("accomplishment_01")` (без `.stx`) | `userdata: 00000000`, уровень не меняется |
| `PlayEarsAudioStream("accomplishment_01.stx", 1)` | handle `00000004`; уровень 4 335–4 766, пока не вызван `Stop`; после `StopEarsAudioStream` уровень падает к фону за секунду. После одной остановки из трёх через 2 с был ещё подъём до ~4 500 на две секунды — причина не выяснена (звуки аэропорта или хвост потока) |
| `PrimeEarsAudioStream(…)`, через 6 с `PlayEarsAudioStream(handle)` | после `Prime` тихо; звук начинается с вызова `Play` |
| `SetEarsAudioStreamStopMessage(handle, "…")`, затем `Stop` | сообщение пришло получателю скрипта (с данными — указателем) |
| тот же поток без `Stop` | за 70 с игры не кончился, сообщение не пришло |
| громкость 0,2 | уровень 4 420–4 563 — внутри разброса при громкости 1 (4 335–4 880): на записи с громким фоном влияния аргумента не видно; как он переводится в громкость, не выяснено |

Потоки музыки (`PlayStream`, `PrimeStream`) ищутся иначе: к имени
дописывается `.exa` (`0x4D3CA0`), поиск — `0x456070`; `GetStreamStatus`
возвращает 0 (ошибка или остановка), 1 (буферизация), 2 (играет),
3 (свободен) **[exe]**; на стенде свободный поток 0 дал 3. `PlayEmx` с
неизвестным именем возвращает light userdata 0, с известным — handle
(`AD660024`) **[стенд]**. Пустые функции: `SetStreamEmitterLocation`,
`EclipseLog`; `GetVehicleRainVelocity` всегда 0.

## 6. Таймеры, время, целые числа

**Таймеры [exe]**: 128 слотов по `0x54` байта в `*0x122346C + 0x14` (`+0`
состояние Lua — владелец, `+4` остаток в мс, `+8` период, `+0xC` имя
функции до 63 символов, `+0x4C` «один раз», `+0x4D` остановлен, `+0x4E`
реальное время).

- `CreateTimer(имяФункции, oneShot [, useRealTime])` (`0x467710`) возвращает
  номер слота числом или −1 (имя не строка, пустое или длиннее 63; второй
  аргумент не boolean; нет слотов). Второй аргумент — «сработать один раз»;
  третий — считать по `timeGetTime()`, а не по игровым часам.
- `StartTimer(h [, мс])` (`0x467880`) задаёт остаток и период и запускает;
  возвращает остаток. `SetTimerRate`, `StopTimer`, `DeleteTimer`;
  `QueryTimer(h)` (`0x467D50`) — остаток в мс, 0 для чужого номера.
- Такт — обработчик сообщения `iMsgRunningTick` (`0x467690`, vtable
  `0xE31F08`) зовёт `0x467440`. Часы — игровые `0x01205224` (мс; стоят на
  паузе). Сработавший таймер сначала перезаряжается (`остаток += период`)
  или останавливается, затем **имя ищется в глобальных при каждом
  срабатывании**; если там функция, она зовётся через `luaD_pcall`
  (`0x467645`) с одним аргументом — номером таймера. Не функция — пропуск
  без ошибки (значение остаётся на стеке Lua: по слоту на срабатывание). Не
  больше четырёх срабатываний таймера за такт.
- **[стенд]**: номера 30, 31, 32; `CreateTimer(имя, true)` сработал один раз
  (через 516 мс при 500), `CreateTimer(имя, false)` — 8 раз за 5,6 с при
  700 мс; обработчик получил номер числом; таймер с несуществующей
  функцией игру не роняет; `CreateTimer("x")` и `CreateTimer("", true)` —
  −1; `QueryTimer` одноразового после срабатывания — −16.

**Целые [exe, стенд]**: число Lua в игре — `float`, поэтому время и
счётчики движок отдаёт объектами `UInt32` и `Int32` (userdata 4 байта).
`GetSimTime()` (`0x46A850`) возвращает `UInt32` — миллисекунды тех же
игровых часов; `VariableGet` и `variable:Get()` — `Int32`;
`Group:GetMemberCount` — `UInt32`. У объектов есть арифметика (`+ - * /` дают
новый объект, деление целое, деление на ноль — ошибка), сравнения между
собой и `__tostring`. С числами Lua они почти не сочетаются:

| Выражение | Что выходит на стенде |
|---|---|
| `GetSimTime() / 1000` | `UInt32` 9 при 9 616 мс — целое деление |
| `"t=" .. GetSimTime()` | ошибка «attempt to concatenate a userdata value» |
| `variable:Get() == 7` | `false` без ошибки (при значении 7) |
| `variable:Get() < 8` | ошибка «attempt to compare userdata with number» |
| `variable:Get() == Int32(7)`, `< Int32(8)` | `true` |
| `Int32ToNumber(x)` (`0x46AEA0`) | число Lua; принимает и `UInt32` |

Переменные движка: `FindVariable(name)` (`0x46A470`) ищет запись менеджера
`*0x1223428` по `sdbm(lower(name))` и создаёт её, если нет; `VariableSet`
возвращает свой последний аргумент.

## 7. Полиция и транспорт

- `GetFootPoliceIntensity` (`0x787470`) и `GetCarPoliceIntensity`
  (`0x7874B0`) побайтно одинаковы: `0.0`, если поле
  `CrimeManager(*0x112AA1C)+0x2C74` не нуль, иначе `nil` **[exe]**. Силы
  погони они не возвращают. На стенде без погони — `nil`, `nil`.
- Машина игрока — `[P-0x1F30+0x1E40]-0x48`, где `P = (*0x12233A0)[+4][0]`
  (`0x7FF880`). Пешком все функции дают 0, `GetVehicleSpeed()` — `0, false`
  (второй результат — «в машине») **[exe, стенд]**. `GetVehicleType` — поле
  `машина+0x980`; списка значений в exe нет, скрипты игры различают 1
  (спортивная) … 9 (полицейский фургон). `GetChaseVehicleStats(index)` —
  шесть результатов, пешком `false, userdata, 0, 0, 0, 10000000`.
- За рулём и при погоне функции на стенде не проверялись.
- `GetPlayerPosition(index)` (`0x469230`): номер игрока обязателен —
  без аргумента `nil`, с 0 — позиция (`283,9; 0,0; 371,8` у ворот), с 1 —
  `nil` **[стенд]**. Результат — указатель на общий буфер, следующий вызов
  его перезаписывает; `TEMP_POS(x, y, z)` — такой же временный буфер,
  `CreatePosition` — своя память.

## 8. Два состояния Lua

`LuaManager` (`*0x012233F4`) держит состояние скриптов `+0x18` (создаёт
`0x43E790`) и второе, `+0x1C` (создаёт `0x43E5D0`, вызов из `0x6826E5`)
**[exe]**:

- функции регистрируются в оба: `0x43E5D0` обходит список связок
  (`+0x38`) и зовёт у каждой `vtbl[+4](L2)` (`0x43E67C`); добавление связки
  (`0x43E2E0`, `0x43E363`) тоже регистрирует в оба. `EclipseLog`:
  `0x43E5EA` — во второе, `0x43E7AA` — в первое. Встроенные тексты Lua
  выполняются и во втором;
- чанки скриптов во второе не загружаются: единственная обёртка
  `0x4CB170` над `0x4CB0C0` не имеет ни вызовов, ни ссылок, а настоящие
  вызовы `0x4CB0C0` (`0x480E8E`, `0x4FFDB2`) берут `+0x18`;
- прочие обращения — снятие регистраций (`0x43E40E`, `0x43E710`),
  `lua_close` (`0x43E76B`), шаг сборщика мусора для обоих (`0x43E900`).

Итог: второе состояние живёт, но скриптов в нём нет. Проверены обращения
рядом с 84 чтениями `*0x012233F4`; доступ через другой указатель не исключён.

## 9. Запуск скрипта, `shutdown`, встроенный Lua

`LuaAudioScript` **[exe]**: атрибуты читает `0x480AF0` (0 — флаги `+0x74`,
1 — стартовое сообщение `+0x54`, 2 — стоповое `+0x5C`, 3 — GUID ресурса
`+0x64`). Обработчик сообщений `0x480D40` (вторая vtable `0xE33420`):
стартовое → `0x480D90`, стоповое → `CallLuaFunction(имя, "shutdown")`
(`0x480D66`); деструктор `0x480A00` тоже зовёт `shutdown` (`0x480A2E`).

Старт (`0x480D90`): ресурс по GUID (`0x4211E0`); `gGUID =
lightuserdata(объект)`; выполнение чанка (`0x4CB0C0`, вызов `0x480E8E`);
`gGUID = lightuserdata(NULL)`; `CallLuaFunction(имя, "startup")`
(`0x480F1D`). Сторона C `CallLuaFunction` (`0x468F40`) при пустом имени в
`объект+0x84` ничего не делает. Имя попадает туда через
`RegisterScriptName(имя, gGUID)` (`0x468E10`), которую зовёт встроенная
`RegisterFunction` при первом имени скрипта. Скрипт, не вызвавший
`RegisterFunction`, не получит ни `startup`, ни `shutdown`.

**[стенд]**: скрипт со стартом по `doctor_s74_go` и стопом по
`doctor_s74_stop` — после старта тики таймера каждую секунду; после
стопового сообщения обработчик `shutdown` выполнен, тиков больше нет;
повторное стартовое сообщение выполняет чанк заново и скрипт снова
работает; повторное стоповое снова зовёт `shutdown`.

Встроенные тексты Lua в exe **[exe]**:

| Адрес | Чанк, кто грузит | Что задаёт |
|---|---|---|
| `0x0110AA98` (78 байт) | «Global Lua Utility Functions», `0x4689E0` | пустые `debug_print(flag, str)` и `debug_screenprint(flag, str)` |
| `0x0110A6F0` (932 байта) | там же | `gFunctionRegistry`, `RegisterFunction(scriptName, functionName, fn)`, `CallLuaFunction(scriptName, functionName, ...)` |
| `0x011289F8` (1 233 байта) | «tolua: embedded Lua code», `0x4CE030` | `MessageReceiverRegistry`, `MessageReceiverMeta`, `MessageReceiverReceive`, `NewMessageReceiver` |

## 10. Сопрограммы

В игре библиотека `coroutine` открыта и работает **[стенд]**. ВМ тулкита
(`resource/lua/vm.rs`) теперь её поддерживает: `create`, `wrap`, `resume`,
`yield`, `status`; у каждой сопрограммы свой стек значений, открытые
upvalue знают свой поток. Как и в Lua 5.0, уступить можно только сквозь
кадры Lua: `yield` внутри `pcall`, метаметода или функции обратного вызова
библиотеки даёт «attempt to yield across metamethod/C-call boundary».

Сверка с игрой: один и тот же набор проверок (ошибка в сопрограмме, `yield`
через `pcall` и через `__index`, `yield` вне сопрограммы, возобновление
самой себя, обмен значениями, мёртвая сопрограмма) дал в игре и в ВМ те же
результаты и тексты ошибок. Отличие одно: `coroutine.create(print)` через
`pcall` в игре называет функцию `?` («bad argument #1 to `?'»), ВМ —
`create`. С настоящим Lua 5.0.3 вне игры ВМ не сверялась.

## 11. Макет API и узлы визуальных скриптов

Макет (`script::sim`) приведён к найденному: обработчик таймера получает
номер таймера, несуществующая функция пропускается; `CreateTimer` требует
boolean и возвращает −1; `StartTimer` и `QueryTimer` возвращают остаток;
`SendMessage` возвращает последний аргумент; `SendMessageEx` возвращает
заданный ответ (`Sim::answer`); `Base` читает из GUID те же четыре байта,
что игра (`sim::guid_the_game_reads`), и находит только объекты,
добавленные `Sim::add_object`; методы групп с ненайденным объектом дают
ошибку с адресом падения; `IsMember` и `Clear` — заглушки, как в игре;
`GetPositionValues` читает число из данных сообщения; пешком
`GetVehicleSpeed` — `0, false`. Тест `the_mock_has_every_function_of_the_game`
сверяет макет со списком.

Упрощение макета: `GetSimTime`, `VariableGet` и `GetMemberCount` возвращают
обычные числа, а не объекты целых; `Int32`, `UInt32`, `Int32ToNumber` только
отбрасывают дробную часть. Ошибку вида `"t=" .. GetSimTime()` макет поэтому
не покажет. Генератор кода её не делает: узлы приводят значения через
`Int32ToNumber`.

Что изменилось в узлах — `docs/scripts.md` §3: исправлены «Game time»,
«Get game variable», «Player position», «Member count», «Is member»,
«Clear group», «Add to group», «Remove from group», «Play stream»; новых узлов 15.

## 12. Что проверено на стенде и что открыто

Проверено в игре (`game-bench.md` §35) — 63 функции: время и целые, позиции,

сообщения с данными и получатель, `SendMessageEx`, таймеры, запуск и
`shutdown`, потоки EARS со звуком, `PlayEmx`, переменные, пустая группа,
сопрограммы, падение `AddMember`.

Открыто:

  естественный конец потока и стоповое сообщение при нём;

  и шестой, времена `StopStream` и `SetStreamVolume`, поля
  `SetGlobalEffect`, `SetMixValues`) — в данных помечены «guess:».
