# Подмена ресурсов в памяти (этап 100)

Редакция от 2026-11-16. Издание — только PC 1.0.789.0 (`godfather2.exe`,
`TimeDateStamp` `0x4AC976E5`, образ с `0x00400000`). Адреса — виртуальные.
Источники: байты `exe` и дизассемблер (`research/file_io_sites.py`:
`pefile` + `capstone`; Ghidra открылась к концу этапа — по ней сверены
ссылки на функции устройства, §2), корпус игры
(тест `composed_streams_are_the_files_apply_writes`), стенд
(`game-bench.md` §42).

Код: общий для модуля и тулкита — `doctor_toolkit_live::resources`
(`crates/doctor-toolkit-live/src/resources.rs`); модуль —
`crates/doctor-toolkit-live-asi/src/resources.rs`; сторона тулкита —
`doctor_toolkit::play::overlay` (`Streams::Patched`) и
`doctor_toolkit::workspace::deploy::resource_patch`; CLI — `play
--resources-in-memory`, `live install --resources-in-memory`, `live
resources`, `live resource`, `live resource-check`.

## 1. Главное

- **Что это.** До этапа 100 «Играть» и «Играть с модами» без записи в игру
  (этап 46, `live-link.md` §14) пересобирали каждый изменённый поток `.str`
  целиком в папке тулкита, а модуль связи подсовывал игре пересобранный
  файл. Теперь можно иначе: тулкит готовит только **заплатку ресурсов**
  потока — изменённые и добавленные ресурсы с их ключами (тип и четыре id
  заголовка `SHDR`) и сырыми данными, — а модуль собирает поток **в
  памяти**, когда игра его открывает, из её собственного файла и заплатки,
  и отвечает на чтение игры из собранного потока. Копия потока на диск не
  пишется, в папку игры не пишется ничего.
- **Выключено по умолчанию.** Переключатель: `play --resources-in-memory`,
  `live install --resources-in-memory`, флажок «Подставлять ресурсы в потоки
  в памяти» в настройках запуска редактора, флажок «Ресурсы в памяти» в
  Open Mod Manager (`resources_in_memory` в `mods.toml`), параметр
  `resources_in_memory` инструмента MCP `play`. Без него всё работает
  как раньше (§7).
- **Перехват чтения, не разбора.** Игра читает потоки через маленькое
  «файловое устройство» из пяти функций поверх `KERNEL32` (§2). Модуль
  меняет четыре места вызова в нём и использует уже стоящий перехват
  `ReadFile` (§4). Разборщик потока (`0x004D0DB0`), загрузчик ресурсов
  (`0x00421470`) и таблица загруженных ресурсов не трогаются: игра видит
  обычный поток, только другой.
- **Собранный поток равен результату `apply`.** Раскладку делает общий
  код модуля и тулкита (§3), он повторяет `ustream::rebuild_with` с сырым
  хранением изменённых ресурсов блок в блок. На всех 2300 потоках игры
  (2271 с ресурсами) собранный поток побайтно равен пересобранному
  (корпусный тест); на стенде потоки, собранные модулем внутри игры,
  выгружены на диск и сверены с результатом `workspace apply`, а ресурсы
  типов, которые игра держит в памяти как есть, сверены в памяти (§8).
- **Замеры** (§9): подготовка запуска с изменением в 172 зонах Гаваны —
  2,3 с и 13,6 МБ на диске вместо 4,4 с и 368 МБ; время загрузки уровня и
  зон и память игры — в пределах разброса прогонов, с модами и без.
- **Чего нет:** слияния SimGroup по объектам (оставлено место, §10);
  подмены ресурсов в архивах `.viv` (они и не ресурсы потоков; формат модов
  4 идёт прежним путём, §7); проверки на настоящей Windows (стенд — Wine).

## 2. Через что игра читает потоки

Открытие — `CreateFileW` из файловой системы игры (`0x00AC0BDF` в
`0x00AC0AD0`, `live-link.md` §14.1): только чтение, `OPEN_EXISTING`, без
`FILE_FLAG_OVERLAPPED`. Дальше с дескриптором работает набор функций над
записью `{дескриптор, ?, позиция: u64}` (позиция — `+8` и `+0xC`):

| Функция | Что делает | Место вызова `KERNEL32` |
|---|---|---|
| `0x00ABEBE0` | закрыть: `CloseHandle(запись[0])`, затем запись возвращается распределителю `*0x0113D190` | `0x00ABEBE8` |
| `0x00ABEC10` | прочитать: `ReadFile(дескриптор, буфер, длина, &прочитано, NULL)` — синхронно, без `OVERLAPPED`; прочитанное прибавляется к позиции записи | `0x00ABEC29` |
| `0x00ABEC40` | перейти: если позиция записи уже та — ничего; иначе `SetFilePointerEx(дескриптор, позиция, &новая, FILE_BEGIN)`; при отказе — `SetFilePointer(дескриптор, 0, NULL, FILE_CURRENT)` и позиция записи = ответ | `0x00ABEC64`, `0x00ABEC78` |
| `0x00ABECA0` | размер: `GetFileSizeEx`; при отказе 0 | `0x00ABECAE` |
| `0x00ABECD0` | обрезать (`SetFilePointerEx` через `EDI`, `SetEndOfFile`) — только для файлов на запись | `0x00ABECE1`, `0x00ABECF3` |

Все они стоят подряд в одной таблице методов — драйвера файлов Win32
файловой системы игры (библиотека `rw::core::filesystem`): `0x00D9B0C4`
открыть (`0x00AC0AD0`), `0x00D9B0C8` закрыть, `0x00D9B0CC` прочитать,
`0x00D9B0D0` записать (`0x00AC2650`), `0x00D9B0D4` перейти, `0x00D9B0D8`
размер, `0x00D9B0DC` обрезать; других ссылок на эти функции в `exe` нет
(Ghidra). То есть файл, открытый местом `0x00AC0BDF`, читается именно
ими.

Отображений файлов в память, `ReadFileEx`, портов завершения и
`GetOverlappedResult` в импорте `exe` нет (`research/file_io_sites.py`).
Чтение потока идёт кусками по 128 КБ с отдельного потока исполнения
(`performance.md` §4); на стенде игра прочитала каждый собранный поток
ровно целиком: счётчик прочитанных байт модуля равен длине собранного
потока (42 729 472 у `gf2/globals_global`, 9 568 256 у `gf2/cuba/local`).

Значит, чтобы игра получила другой поток, достаточно отвечать за
`ReadFile`, `SetFilePointerEx`, `SetFilePointer` и `GetFileSizeEx` для
дескрипторов нужных файлов; сам файл игры остаётся открытым как обычно.

## 3. Заплатка ресурсов и раскладка потока

### 3.1 Файл заплатки (`DTRP`)

Один файл на изменённый поток, лежит в подготовленной копии игры на месте
потока (`<кэш>/overlay-…/game/gf2/cuba/local.str`), начинается не с `3slo`,
а с `DTRP`:

| Смещение | Поле |
|---|---|
| `0x00` | `"DTRP"` |
| `0x04` | версия, 1 |
| `0x08` | число записей |
| `0x10` | `u64` длина файла потока, для которого сделана заплатка (0 — любая) |
| `0x18`, `0x1C` | смещение и длина пути этого файла (UTF-8), если это не поток папки игры (§3.4); иначе 0 |
| `0x20` | записи по `0x50` байт |
| … | путь, затем сырые данные ресурсов (как они лежат в памяти, без сжатия), каждые добиты нулями до 4 байт |

Запись: `+0x00` операция (0 — заменить, 1 — добавить, 2 — слить, не
реализовано, §10); `+0x08` тело `SHDR` (политика памяти, выравнивание, тип,
четыре id, размер данных); `+0x28` флаг «перед ресурсом», `+0x2C` его тип,
`+0x30` его id; `+0x40` смещение данных в файле.

Ключ ресурса — тип и четыре id в пределах потока (на всём корпусе тройка
«поток, тип, id» уникальна, `tests/corpus.rs`). У заменяемого ресурса
политика и выравнивание берутся из заголовка игры, как при `apply`.
Добавленные ресурсы одного места идут в порядке записей — том самом, в
котором их ставит `apply` (`Added::order`).

### 3.2 Разбор файла игры

`resources::scan` читает только заголовки блоков (`SHOC`/`FILL`, подтип,
тело `SHDR`) — те же проверки, что у `StreamLayout::parse` тулкита, данные
не читаются и не распаковываются. Чтение идёт окном 4 КБ: мелкие блоки
попадают в одно чтение, крупные стоят одного чтения каждый. На стенде:
`gf2/globals_global` (42 МБ, 2 956 ресурсов, 6 234 блока) — 1 186 чтений;
`gf2/cuba/local` (9 МБ, 715 ресурсов, 1 499 блоков) — 319. На весь корпус
(2 300 потоков, 9 ГБ) — 80 445 чтений по 4 КБ.

### 3.3 Раскладка (`resources::compose`)

Повторяет `ustream::rebuild_with` (`crates/doctor-toolkit/src/container/ustream.rs`):

1. всё до первого изменённого ресурса остаётся на своих местах (и `FILL`
   перед ним отбрасывается: он зависел от старой раскладки);
2. дальше каждый блок файла игры сохраняет свои байты (сжатые блоки `Rpak`
   не распаковываются и не пережимаются) и получает новое место по правилу
   страниц: блок размера `S` идёт в текущую страницу 128 КБ, если `S ==
   остаток` или `S + 8 <= остаток`, иначе остаток закрывает `FILL`
   (`stream.md` §6.2);
3. заменённый или добавленный ресурс — блок `SHDR` и сырые блоки `SDAT`,
   нарезанные по границам страниц так же, как их режет
   `StreamWriter::push_raw_data`;
4. последняя страница закрывается `FILL`.

Результат — не байты, а список кусков: «из файла игры со смещения X», «из
заплатки со смещения Y», «свои байты» (заголовки блоков и `FILL`), «нули».
Соседние куски одного источника склеиваются: у `gf2/globals_global` с
пятью заменами и тремя добавлениями — 70 кусков на 42,7 МБ, у
`gf2/cuba/local` — 68. `Composed::read` отдаёт любой диапазон собранного
потока по этому списку.

**Сырое хранение.** Изменённые ресурсы в собранном потоке всегда лежат
несжатыми блоками `SDAT`: сжатие `RefPack` модулю не нужно, а игре всё
равно (в её файлах сырые и сжатые блоки идут вперемешку). `apply` же
хранит изменённый ресурс так, как он хранился в оригинале (`StorageChoice::
Keep`). Поэтому собранный поток равен файлу `apply` **побайтно**, когда
`apply` хранит изменённые ресурсы сырыми, и равен ему **по ресурсам** —
те же заголовки в том же порядке, те же распакованные данные — в остальных
случаях; сам файл при этом длиннее (стенд: `gf2/cuba/local` — 9 568 256
байт против 9 306 112 у `apply`).

**Размер данных потока** (`Composed::data_size`, сумма размеров ресурсов)
тулкит получает из той же раскладки и пишет в TOC — в подготовленной копии
TOC тот же файл, что пишет `apply` (стенд: `cuba.toc`, `cuba_global.toc`,
`globals_global.toc`, `miami*.toc`, `queens*.toc` совпали побайтно). Это
вес потока в бюджете раздела мировой сетки (этап 84, `wgi.md` §4):
ресурс другого размера меняет его ровно так же, как при `apply`. Сам
эффект вытеснения соседних зон завышенным весом на стенде не проверялся —
проверено только равенство чисел.

**Что не собирается.** Заплатка для файла другой длины; заменяемый ресурс,
которого нет в потоке; добавляемый, который в потоке уже есть; две замены
одного ресурса; запись «слить»; поток не версии 2, с блоком не кратного 4
размера или big-endian. В этих случаях тулкит отказывает ещё при
подготовке (он собирает раскладку сам, чтобы получить размер данных), а
модуль, если до него такое всё же дошло, поток не трогает: игра читает
свой файл, отказ считается и пишется в журнал модуля, `live resources`
показывает его, `play` после выхода игры предупреждает.

### 3.4 Заплатка не к потоку игры

`apply` всегда пересобирает поток из **оригинала**; если поток в папке
игры уже записан раньше («Записать в игру»), оригинал — резервная копия
`_doctor_toolkit/backups/…`. Заплатка тогда сделана к резервной копии, и
собирать нужно из неё, а не из файла, который открыла игра. Поэтому строка
настройки называет файл-основу третьим полем, и модуль открывает его сам:

```text
resources=gf2/cuba/local.str|Z:\…\overlay-8177f4b9\game\gf2\cuba\local.str
resources=gf2/level.str|Z:\…\game\gf2\level.str|_doctor_toolkit/backups/gf2/level.str
```

Проверено тестом `a_patch_for_a_stream_written_earlier_names_its_original`
(на стенде этот случай не прогонялся).

## 4. Модуль: перехваты

Подмена живёт в **модуле связи** `doctor_live.asi`, а не в отдельном
модуле: место открытия файлов `0x00AC0BDF` уже заменено модулем связи
(этап 46), место чтения `0x00ABEC29` — тоже им (профиль, этап 58), а одно
место вызова не могут менять два модуля. Отдельному модулю пришлось бы
договариваться с модулем связи о цепочке перехватов; общего у подмены с
остальным модулем связи — проверка издания, настройка, журнал и протокол.

| Место | Было | Стало |
|---|---|---|
| `0x00AC0BDF` | перехват открытия этапа 46 | после настоящего открытия: если у файла есть заплатка и открытие только читает — разобрать, разложить, запомнить дескриптор |
| `0x00ABEC29` | перехват чтения этапа 58 (замер) | сначала спросить подмену; дескриптор не её — прежний путь |
| `0x00ABEC64` | `call [SetFilePointerEx]` | `call перехват; nop` |
| `0x00ABEC78` | `call [SetFilePointer]` | `call перехват; nop` |
| `0x00ABECAE` | `call [GetFileSizeEx]` | `call перехват; nop` |
| `0x00ABEBE8` | `call [CloseHandle]` | `call перехват; nop` — забыть дескриптор, затем настоящий `CloseHandle` |

Игра держит настоящий дескриптор своего файла: всё, чего модуль не
перехватывает, работает как обычно, а неизменённые блоки модуль читает
через этот же дескриптор своими импортами (`SetFilePointerEx` + `ReadFile`
модуля, не перехваченные места). Позицию в собранном потоке модуль ведёт
сам. Таблица «дескриптор → собранный поток» под `RwLock`; пока ни одного
такого дескриптора нет, перехваты пропускают вызов без блокировки (счётчик
`AtomicU32`). Номер дескриптора, который система выдала заново другому
файлу, забывается при каждом открытии через любое из 13 мест этапа 46.
Раскладка потока запоминается, пока длина файла-основы та же: зоны
открываются много раз.

Места `0x00ABD845`, `0x00ABD89A` (класс файла `0x00ABD6E0`) и `0x00ABECE1`
(обрезка) модуль не меняет: потоки через них не читаются.

**Проверка издания** — 159 мест (+24): ячейки таблицы поиска импорта и
имена `SetFilePointerEx` (`0x00E4E6BC`, `0x00E4EF7A`), `GetFileSizeEx`
(`0x00E4E6C0`, `0x00E4EF8E`), `SetFilePointer` (`0x00E4E7F4`,
`0x00E4EA9E`), `CloseHandle` (`0x00E4E7FC`, `0x00E4EA82`); тела четырёх
функций устройства по кускам вокруг заменяемых вызовов; `0x00421170`
(поиск ресурса в таблице), `0x004209C0` и `0x004D9AF0` (её хэш). На другом
издании модуль не ставит ничего и только отвечает, что издание не то;
тулкит в `auto` тогда пишет в игру по-старому, в `on` отказывает
(`overlay::availability`).

**Другие модули.** Модуль падений проверяет и меняет `0x00408A11` и
`0x00635A80`, графический — свои места; ни одно из мест подмены в их
таблицы проверок не входит и ими не меняется (тест
`resources::tests::the_hooks_lie_outside_what_the_other_modules_check`).
На стенде модуль падений стоял во всех прогонах.

## 5. Сторона тулкита

`Overlay::build_with(игра, источник, cmd.txt, папка, Streams::Patched)`:
подготовленная копия игры этапа 46 (папки и ссылки на файлы игры), к ней
тем же кодом применяется рабочее пространство или включённые моды в
порядке загрузки менеджера — но экземпляр игры помечен
(`GameInstance::stage_resource_patches`, доступно только внутри крейта), и
`Deployment::prepare_stream` вместо `rebuild_with` зовёт
`deploy::resource_patch`: тот же список замен и вставок уходит в файл
заплатки. Таблица подмен, таким образом, — это результат того же слияния
модов, что и при записи: порядок загрузки, конфликты и правила менеджера
(`mods.md` §3.2) действуют одинаково. Резервная копия оригинала в
подготовленной копии в этом режиме — ссылка на файл игры, а не копия.

Что остаётся подменой файлов этапа 46: TOC (маленькие, пересобираются),
**новые потоки** (файл целиком из ресурсов мода — он и так «только
изменённое»), накладной архив `.viv` и сдвинутые архивы игры, ролики,
`cmd.txt`. В настройке модуля — два списка: `redirect=` и `resources=`.

`play` после выхода игры сообщает, сколько потоков с заплаткой модуль
собрал, и предупреждает, если какой-то собрать не удалось (по журналу
модуля, `live::composed_in_log`).

## 6. Протокол 9 и CLI

- `Request::Resources` → потоки с заплатками: сколько раз открыт, сколько
  отказов, заменено и добавлено, длина файла игры и собранного потока,
  размер данных, микросекунды разбора и раскладки, прочитано байт, ошибка.
  `live resources`.
- `Request::Resource { ids }` → запись загруженного ресурса в таблице игры
  (§8.1): адрес данных, размер, счётчик ссылок, флаги. `live resource IDS
  [--out ФАЙЛ] [--compare ФАЙЛ]`.
- `live resource-check ПАПКА ПОТОК… [--original ИГРА]` — ресурсы потоков
  папки (результат `apply`) против памяти игры: изменённые и добавленные
  относительно `ИГРА` — целиком, остальные — по первым байтам, со сводкой
  по типам.
- `live install … --resources-in-memory [--resources-dump]`: с
  `--resources-dump` модуль пишет каждый собранный поток рядом с заплаткой
  (`<заплатка>.composed`, в папке тулкита).

Модуль отвечает на кадры версий 1–9; клиент со старым модулем видит, что
запросов нет (`Client::has_resources`).

## 7. Игрок: что меняется и что нет

| Как игрок играет | До этапа | Теперь |
|---|---|---|
| «Записать в игру», затем своя программа запуска (модуля связи нет) | потоки пересобраны в папке игры, оригиналы в резервных копиях | **то же**: подмена в памяти сюда не относится |
| «Играть с модами» (менеджер), переключатель выключен | зеркало, пересобранные потоки в кэше, подмена файлов | **то же** |
| «Играть с модами», «Ресурсы в памяти» включено | — | зеркало, заплатки ресурсов в кэше, модуль собирает потоки при загрузке |
| модуль связи нельзя использовать (нет загрузчика ASI, другое издание) | окно «нельзя без записи», предложение записать | **то же** |

- **Формат модов 4** (файлы архивов `.viv`, `mods.md` §1.5): записи
  архивов — не ресурсы потоков; они по-прежнему собираются в накладной
  архив `GODFATH0.viv` подготовленной копии, архивы игры сдвигаются на
  номер вверх подменой файлов (тест
  `patched_streams_hold_the_resources_applying_would_write`: запись архива
  и ролик рядом с заплатками).
- **«Записать в игру»** пишет пересобранные потоки, как раньше; заплатка в
  папку игры попасть не может: режим включается только у подготовленной
  копии внутри `Overlay`.
- **В папку игры** на время запуска кладётся то же, что и раньше:
  `scripts/doctor_live.asi`, `.cfg`, `.log` и `_doctor_toolkit/`.

Почему выключено по умолчанию: на стенде сверены три города, заплатки с
заменами того же и другого размера, добавленными ресурсами и новым потоком
и мод с новой зоной; но всё это — Wine, один стенд, минуты игры. Включать
по умолчанию стоит после прогонов на Windows и с большими модами.

## 8. Сверка

### 8.1 Таблица загруженных ресурсов игры

`*0x012053AC` → `{корзины, число корзин}`; корзина — `хэш % число`; хэш
(`0x004209C0`): четыре id с переставленными байтами (`0x004D9AF0`, то есть
старший байт первым), затем `h = h · 65599 + байт` по 16 байтам. Запись
(`0x00421470` заполняет, `0x00421170` ищет): `+0` счётчик ссылок, `+6`
флаги (`u16`), `+8` данные, `+0xC` размер, `+0x10` распределитель,
`+0x1C` четыре id, `+0x2C` следующая запись корзины. Модуль читает
таблицу проверенными чтениями и функций игры не зовёт.

**Данные в записи остаются не у всех типов.** На стенде (Гавана, 3 840
ресурсов пяти потоков, первые 4 КБ каждого против файла):

| После загрузки | Типы (сколько проверено) |
|---|---|
| данные те же, что в потоке | `lua` (32), `tob` (14), `grt` (1) |
| указатель `+8` — ноль, запись и размер на месте | `tg4h` (900), `tg4d` (900), `vfx` (804), `material` (262), `mesh` (141), `meshvolatile` (140), `apx` (68), `treemodel` (43), `sbk` (1) |
| данные на месте, но отличаются от потока | `chv` (170), `hkx` (126), `metamodel` (67), `shk` (53), `mix` (39), `bnk` (37), `rcb` (20), `graph` (5), `ffn` (3) и ещё 11 типов по 1–2 ресурса |

Нулевой указатель — образ отдан обработчику типа (у `tg4d` он после
заливки в видеокарту освобождается, этап 35; для остальных это догадка);
«отличаются» — вероятно, расставленные указатели (не разбиралось). В
Майами и Нью-Йорке картина та же (47 совпавших, 472 и 453 отличающихся,
3 032 и 3 081 с нулевым указателем). Поэтому побайтная сверка в памяти
возможна только для `lua`, `tob`, `grt`; для остальных сверяется запись
(ресурс с такими id загружен, размер тот) и поток, который игра
прочитала. Размер в записи совпал с ожидаемым у всех проверенных ресурсов
во всех прогонах («другого размера» — 0).

## 10. Место для слияния SimGroup по объектам

Сейчас два мода, меняющие один SimGroup, сталкиваются по ресурсу целиком:
побеждает последний по порядку загрузки (как и при записи в игру). Для
слияния по объектам оставлено:

- в формате заплатки — операция 2 (`Op::Merge`): данные записи — не новый
  ресурс, а изменения к ресурсу игры. Сейчас такая заплатка не собирается
  (`Error::Unsupported`), и тулкит таких записей не пишет;
- в коде — одно место, где встречаются оригинал и изменения:
  `deploy::resource_patch` в тулките (у него есть распакованный оригинал,
  список изменений всех модов в порядке загрузки и разборщик SimGroup) и
  `resources::compose` в модуле (у него есть заголовки потока игры и
  заплатка).

Слияние в тулките проще и не требует ничего нового в модуле: результат
слияния — обычная замена ресурса. Слияние в модуле (при загрузке, без
участия тулкита) потребовало бы распаковки `RefPack` и разбора SimGroup в
крейте без зависимостей; это отдельная работа. Какой из двух путей брать,
этап 100 не решал.

## 11. Ограничения и открытое

- Проверено только под Wine; на Windows путь `Z:\…` заменяется обычным,
  остальное то же, но прогона не было.
- Заплатка привязана к длине файла-основы, не к его содержимому: файл той
  же длины с другим содержимым, подменённый между подготовкой и запуском,
  модуль не отличит. Подготовка делается непосредственно перед запуском.
- Изменённые ресурсы читаются несжатыми: чтение с диска больше на разницу
  сжатия (у потоков стенда +3…+18 % длины файла).
- Чтение потока через другие функции (`0x00ABD6E0`, библиотека C) модуль
  не подменяет; на стенде потоки так не читались (журнал этапа 46).
- **Длина пути.** Игра собирает путь «папка игры/путь потока» в буфере 256
  байт без проверки (находка этапа 77: открытие `0x00AC37C0`), длиннее —
  падение. Подмена ресурсов имён не меняет: игра открывает свой путь, а
  заплатку модуль открывает сам (своим путём, через `std::fs` — буфер игры
  тут ни при чём). Ограничение по-прежнему касается новых потоков мода и
  длинной папки игры — как и при записи в игру. На стенде тень игры после
  этого сообщения держалась в короткой папке (`/tmp/claude-1000/s100/`).
- Эффект веса потока в бюджете раздела сетки при большом изменении размера
  не проверялся.
- Горячая подмена уже загруженного ресурса (без перезагрузки потока) — не
  эта работа: этап 35 умеет это только для текстур того же размера.
