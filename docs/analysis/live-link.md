# Живая связь с запущенной игрой (этапы 34, 49, 35, 48, 46)

Редакция от 2026-11-14. Исследован `godfather2.exe` PC 1.0.789.0
(SHA-256 `31f579a8…`, `TimeDateStamp` `0x4AC976E5`, `SizeOfImage`
`0x00E32000`, без перемещаемых адресов: образ всегда с `0x00400000`).
Адреса — виртуальные. Инструменты: дизассемблер с декомпилятором в
пакетном режиме (полный автоанализ копии `exe`), `objdump`, чтение памяти
игры самим модулем (`live peek`) и `tools/bench/gamemem.py`. Проверка —
стенд (`game-bench.md` §18, §21–§24).

Код: протокол, адреса и проверка издания — `crates/doctor-toolkit-live`;
модуль — `crates/doctor-toolkit-live-asi` (сборка
`tools/build-live-module.sh`); клиент, установка с откатом, поиск
загрузчика, поддельный модуль — `doctor_toolkit::live`; CLI —
`doctor-toolkit live`, `play --live`; редактор — панель «Связь» вкладки
«Игра» и метки во вкладке уровня (`docs/shell.md` §9.2).

## 1. Главное

- **Модуль работает под Wine.** `doctor_live.asi` (DLL i686, Rust, 474 КБ)
  кладётся в `scripts/` папки игры; его грузит ASI-загрузчик игрока
  (Ultimate ASI Loader как `dinput8.dll`, под Wine — с
  `WINEDLLOVERRIDES=dinput8=n,b`). Из Linux редактор говорит с ним по TCP
  на `127.0.0.1` — Winsock под Wine это обычный сокет хозяина.
- **Издание проверяется до любого действия:** заголовок PE и байты 103 мест
  кода, на которые модуль опирается (§6). На другой сборке модуль ничего
  не меняет и отвечает только «не то издание».
- **Данные игры — только в безопасных точках главного цикла:** чтение —
  перед каждым проходом цикла (перехват вызова `0x0068B04B`), запись —
  внутри кадра уровня, перед обновлением игры (подмена метода `+0x2C`
  таблицы `GameMainLoop`, §2).
- **Читается:** игрок (позиция, поворот — мировая матрица), камера
  (позиция, направление, угол обзора), состояние главного цикла, игровое
  время и время суток, загруженные потоки (61 на старте в Гавани), объекты
  SimGroup рядом с игроком (GUID, класс, позиция; обход 8 600 объектов —
  2 мс).
- **Умеет:** телепорт игрока тем же вызовом, что `PlayerTeleportRelay`;
  сообщение шины SimGroup — всем слушателям, как шлёт игра, или одному
  объекту по GUID; выполнение строки Lua 5.0 в состоянии скриптов игры с
  возвратом значений и ошибок.
- **Журнал игры (этап 49, §11):** вывод скриптов (`print` со скриптом и
  строкой) и `OutputDebugStringA` игры, ошибки Lua со стеком вызовов и
  строками, сообщения шины с получателями — событиями с номерами; **все
  объекты** SimGroup, и логика без матрицы, — с классом, потоком и
  состоянием слушателя; поиск по GUID и имени.
- **Отладка вживую (этап 35, §12):** пауза, шаг и точки останова (на
  сообщении — до доставки, на выводе узла Blueprint, на ошибке Lua) с
  чтением, пока игра стоит; свободная камера (игра рисует из камеры
  редактора) и вид редактора за камерой игры; **текстуры без
  перезапуска** — новые уровни загруженной текстуры того же размера и
  формата той же командой, что у загрузчика игры; модели — только
  перезапуском уровня; счётчики сообщений, которые журнал не пишет по
  одному.
- **Мир и состояние (этап 48, §13):** время суток и его скорость (небо,
  туман и свет следуют за часами), загрузка и выгрузка потоков по одному
  с ожиданием, деньги игрока, его команда, чекпоинты, переменные сюжета
  `variabledictionary` по имени — чтение и запись для проверок без
  прохождения. Дождя (`WeatherManager`) в одиночной игре нет.
- **Моды без записи в игру (этап 46, §14):** модуль подменяет файлы,
  которые игра открывает (`.str`, `.toc`, `.viv`, `.vp6`, `cmd.txt` — всё,
  что идёт через `CreateFileA`/`CreateFileW`), файлами из папки тулкита вне
  игры; тулкит собирает туда рабочее пространство или включённые моды тем
  же кодом, что пишет в игру. Папка игры не меняется, откатывать нечего.
- **Стенд:** координаты модуля совпадают с `gamemem.py` до миллиметра;
  телепорт переносит игрока (снимки до и после); сообщение
  `boundary_fade_out` гасит экран (яркость 85,7 → 1,2); 10 минут с модулем и
  модом игрока GF2ASI — без падений; `play --live` после выхода вернул
  тень побайтно (1381 файл).

## 2. Точки входа в главный цикл

`WinMain` (`0x0069D9D0`) → `0x0068AEB0`: цикл

```
do {
    if (0x00439FA0())            // call в 0x0068B04B
        go_on = 0x00683450(&dispatcher);   // кадр текущего состояния
    else ...
} while (go_on);
```

| Адрес | Что |
|---|---|
| `0x0068B04B` | `call 0x00439FA0` (`E8 50 EF DA FF`), раз за проход цикла; `cdecl`, без аргументов, результат в `AL` |
| `0x0112980C` | диспетчер состояний (указатель), `+4` — текущее состояние |
| `0x00D5A1F8`, `0x00D57758`, `0x00D57728` | таблицы `InitOnceMainLoop`, `FrontendMainLoop`, `GameMainLoop` (конструкторы `0x0067C590`, `0x0067C390`) |
| `0x00683450` | кадр: метод `+0xC` состояния; 2 — сменить состояние |
| `0x0067C290` | `GameMainLoop` `+0xC`: `0x0068BAF0(1)` (начало кадра) → метод `+0x2C` (обновление, `0x0067D160`) → `0x0068BCD0(1)` (конец) |
| `0x01206880` | буфер команд отрисовки кадра (указатель); задан только внутри кадра |

**Чтение** — первый перехват: модуль меняет 4 байта цели вызова в
`0x0068B04B` (адрес выровнен на 4 — запись атомарна) на свою функцию; она
снимает «снимок» (игрок, камера, время, состояние цикла), выполняет
задания чтения из очереди и вызывает `0x00439FA0`, результат которого
нужен циклу. Здесь главный поток стоит между проходами, Lua не выполняется.

**Запись** — второй перехват: слот `+0x2C` таблицы `GameMainLoop`
(`0x00D57754`, было `0x0067D160`). Сначала запись делалась в первой точке —
телепорт уронил игру: `Player::Teleport` начинает затемнение экрана
(`0x0093C210` → `0x0040C1F0`), а оно пишет команду в буфер
`0x01206880`, который вне кадра пуст (`Unhandled page fault on read access
to 00000014 at address 0040C278`). Внутри кадра буфер есть: здесь игра сама
обрабатывает сообщения и телепорты. Слот `+0x28` (метод `0x0067C560`)
оказался выходом из состояния и в игре не вызывается.

## 4. Объекты и потоки

**SimManager** (`*0x01223410`, конструктор `Base` `0x0046C590` → регистрация
`0x004467C0`). У объекта `+0x1C` — номер группы (маленькое число, ключ
таблицы ниже; это не класс), `+0x20` — GUID, `+0x30` — следующий в таблице
GUID (`+0x80` корзины, `+0x84` их число; поиск — `0x00445FF0`), `+0x3C` —
слушатель сообщений (его виртуальный `+4` вызывает шина).

Таблица групп: `+0x48` корзины, `+0x4C` их число; запись — `[0]` номер,
`[4]` первый объект, `[6]` следующая запись корзины; объекты группы связаны
через `+8`. Модуль обходит её без вызовов кода игры: позиция есть у объекта,
у которого в `+0xD0` лежит мировая матрица (строки единичные и
ортогональные, последний столбец 0, 0, 0, 1 — как у `Entity` и всех
классов от неё). На старте в Гавани — 57 групп, 8 600–8 700 объектов,
обход 1–2 мс (память проверяется по карте регионов `VirtualQuery`,
снятой один раз на задание, и не дольше 400 мс).

**Класс** — по реестру классов `0x004833A0`: отсортированный массив
`*0x012239BC`, `+4` число, запись `{хэш, фабрика, имя, размер}`. У каждого
объекта есть виртуальный `+0x10` `bool As(хэш, void** out)` (`Entity` —
`0x0046D450`, `PlayerTeleportRelay` — `0x007DCCD0`): модуль вызывает его со
всеми хэшами реестра и берёт самый большой подходящий класс. Только для
найденных рядом (десятки вызовов `As` на объект). Хэш имени —
`sdbm(lower(имя))` (`0x004DAFD0`): `Entity` = `0x38523FC3`. Рядом с точкой
по умолчанию `gf2/cuba`: `Player` (0 м), `CommonNPC` (1,8 м), два
`Destructible`.

**Потоки** — `*0x0122337C` (`StreamManager`): `+0x6C` список загруженных,
следующий — `+4`, имя — указатель `+8` и длина `+0xC` (`0x00405F40`).
Через 5 с после старта `-stream gf2 cuba`: 61 поток —
`gf2\globals_global.str`, `embedded:\gf2_patch_text_str.str`,
`gf2\cuba_global.str`, `gf2\cuba.str`, `gf2\cuba\local.str`, зоны
`gf2\cuba\local\…\low|medium|high\…`, персонажи, звук, транспорт.

## 5. Запись: телепорт, сообщения, Lua

**Телепорт** повторяет `PlayerTeleportRelay` (`0x007DD020`, обработчик
сообщения `0x007DD130`):

1. игрок не телепортируется, если в `Player+0x24A0` стоит бит 7 (ролик,
   машина, загрузка);
2. виртуальный `+0x14C` игрока с `(0x46F5C7B4, 1, 0)`;
3. `Player::Teleport` `0x0079E3C0` (`thiscall`, вызываемый снимает 16 байт):
   `(матрица 4×4, выровненная на 16; флаги 0; ручка сообщения «готово» —
   нулевая; список зон мира {4 указателя, число} — пустой)`. Модуль строит
   матрицу из нового положения и прежнего поворота игрока (или курса
   `yaw`). Зоны мира игра подгружает сама по положению игрока.

Игра переносит игрока на следующем кадре с затемнением экрана; с высоты
0,5 м игрок опускается на землю.

**Сообщение** — шина `0x00408A00` (`bool Send(Message*, bool force)`,
`cdecl`), сообщение `{u32 хэш, u32 данные, u8 отправлено}`, как его строит
Lua `SendMessage` (`0x004C82C0`). Хэш имени — `sdbm(lower(имя))`.
Таблица сообщений `*0x01162380` (4096 корзин по `хэш & 0xFFF`): запись
`[0]` следующая, `[1]` блоки слушателей, `[4]` хэш; узел блока — `+4`
следующий, `+0xC` слушатель, `+0x14` флаги (бит 15 — удалён). Шина зовёт
виртуальный `+4` слушателя, если у него включён бит 0 в `+4` (или `force`).

- **всем:** вызов шины — ровно как игра; модуль заранее считает слушателей;
- **одному объекту:** обход тех же слушателей, вызов только того, чей
  объект (`слушатель − 0x3C`) имеет нужный GUID. В игре адресной отправки
  нет — это обход шины, но вызов тот же.

**Lua.** Состояние скриптов игры — `*(*0x012233F4 + 0x18)` (`LuaAudioScript`
`0x00480D90`). Lua 5.0 вкомпилирован с нестандартными соглашениями
(LTCG), поэтому вызовы — на ассемблере:

- `luaL_loadbuffer` `0x00629280`: буфер в `ECX`, имя куска в `EAX`, `L` и
  размер в стеке;
- `luaD_pcall` `0x00636570`: `L` в `ESI`, обработчик ошибок в `EDX` (0),
  в стеке `f_call` `0x006261E0`, `{функция, LUA_MULTRET}` и смещение вершины
  — как в `0x006293C0` (`lua_dobuffer` игры).

После вызова модуль читает значения со стека (`TValue` 8 байт: тип и
значение; числа — `float`, строки — `TString`: длина `+0xC`, текст
`+0x10`) и возвращает вершину на место. Ошибка компиляции или выполнения
приходит текстом (`doctor_live:1: boom`).

### 5.1 Управление после старта сразу в уровень (этап 45)

**Симптом** (этап 33): после `-stream` игрок не ходит и камера не
поворачивается мышью; `Escape` открывает меню паузы, привязки клавиш в
Options → Controls на месте. После загрузки сохранения всё работает.

**Причина.** Ввод игрока идёт через порт контроллера:

| Адрес | Что |
|---|---|
| `*0x01129814` `+0x14` | менеджер контроллера: порт (байт) того, кто играет; `0x0F` — клавиатура и мышь, меньше `0x10` — устройство, `0x12`/`0x13` — нет |
| `0x007A2A5A` | конструктор `Player`: порт менеджера меньше `0x10` → `Player+0x2498` и `0x00444D20(порт, 1)` (байт «порт занят» у `*0x01223430`); иначе `Player+0x2498 = 0` (в сетевой игре `0x12`). Больше это поле никто не пишет |
| `0x0067D1ED` | обновление `GameMainLoop`: когда уровень загружен и порта у менеджера нет — даёт ему порт последнего устройства (`*0x012233B4 + 0x53D`) |
| `0x0079E920` | действие игрока: бит 1 `Player+0x249C` и `0x00465700(порт игрока, действие)` |
| `*0x01223464` | карты действий: на порт блок `0x168` байт, `+0x10` — число карт стека, `+0x14` — стек; `0x00465660` ищет действие только в картах порта |
| `0x0079B5EE` | игрок кладёт свою карту (`basic_aiming_player`) на свой порт: `0x00464960(порт, имя, 0)`; снимает — `0x00464A10(порт)` (деструктор, `0x007A7485`) |

Через меню порт назначает титульный экран («Press any key»), и игрок
создаётся уже с портом 15. При `-stream` меню нет: игрок создаётся раньше,
чем менеджер получит порт (тот назначается в конце загрузки), — в
`Player+0x2498` остаётся 0, и карта `basic_aiming_player` ложится на порт 0.
Клавиатура — порт 15, её действия ищутся в пустом стеке. Пауза работает,
потому что меню опрашивает все порты. Сравнение памяти двух сеансов (через
сохранение и `-stream`) нашло ровно эти два места: `Player+0x2498` (15 и 0)
и стек карт (на порту 15 и на порту 0); флаги `+0x249C` одинаковы.

Опыты: сообщение `iMsgPlayerControlEnable` (его слушает игрок, 1 слушатель)
не помогает; флаг `-inputwithoutfocus` не помогает; запись одного порта
(`Player+0x2498 = 15`) не помогает — нужна и карта.

**Исправление** — модуль (`fix_input` в `doctor_live.cfg`, по умолчанию
включено): раз на объект игрока, когда у менеджера уже есть порт, а игрок
читает другой (`doctor_toolkit_live::input_port_fix`), модуль делает то, что
сделал бы конструктор, — пишет порт в `Player+0x2498` и байт «порт занят»,
затем кладёт карты старого порта на новый по именам (`0x00464960`) и снимает
их со старого (`0x00464A10`). Всё — в перехвате главного цикла, между
кадрами. Журнал модуля: `player 0x… read input port 0, given the
controller's port 15 and moved action maps [basic_aiming_player]`. После
загрузки сохранения порты совпадают — модуль ничего не делает. Места кода
добавлены в проверку издания (§6).

**«Играть»**: при старте сразу в уровень (`play --stream`, поле
`play.start` редактора) модуль ставится на запуск сам, даже если живая
связь выключена (запись по сети выключена, только исправление ввода), и
убирается после выхода. Без ASI-загрузчика — предупреждение: игрок ходить
не сможет, нужен Ultimate ASI Loader или старт с сохранения.

Стенд (`game-bench.md` §20): `-stream gf2 cuba` с модулем — `w` 4 с
переносит игрока на 24,9 м, мышь поворачивает камеру; `play --stream
gf2/cuba` без `--live` через `play-command.sh` — игрок ушёл за ворота,
`cmd.txt` и модуль после выхода убраны.

## 6. Проверка издания

## 7. Протокол

TCP на `127.0.0.1:ПОРТ` (по умолчанию 47801; установщик берёт свободный).
Почему TCP, а не именованный канал или файл: Winsock в Wine — сокет хозяина,
к нему подключается обычная программа Linux без Wine; именованные каналы
Wine снаружи не видны, файлы в префиксе потребовали бы опроса. На Windows
то же самое работает без изменений.

Кадр: `DTLV`, версия (u16, сейчас 5), вид (u16: запрос, ответ — вид | 0x8000,
ошибка — 0xFFFF), номер запроса (u32), длина (u32, не больше 32 МБ; до
протокола 3 — 1 МБ). Первый
запрос — Hello с токеном из `doctor_live.cfg` (у установщика — случайный).
Запросы: Hello, Status, Player, Camera, Streams, Objects, Teleport, Send,
Lua, Peek; версия 2 (этап 49) добавила Events (журнал: «события после номера
N таких видов», §11.4) и World (все объекты с фильтром: точный класс,
список GUID, группа, с матрицей или без; до 16 000 в ответе, таблицы
классов и потоков отдельно); версия 3 (этап 35, §12.5) — Break, Control,
Debug, SetCamera, Texture; версия 4 (этап 48, §13.8) — TimeOfDay, SetTime,
Weather, StreamLoad, StreamUnload, StreamQueue, Money, SetMoney, Family,
Mission, Variables, SetVariable; версия 5 (этап 46, §14.4) — Files. Status, Player, Camera, Events, Break, Control,
Debug и SetCamera отвечаются
сразу (снимок последнего прохода цикла, кольцо журнала); остальные ждут
главного потока до 20 с (игра под llvmpipe — 1–2 кадра/с).

**Совместимость версий.** Модуль отвечает на кадры версий 1–5 в версии
запроса: клиенты этапов 34 и 49 работают как прежде; запрос новее кадра
получает `Unsupported`, незнакомые им виды событий журнала модуль им не
отдаёт. Кадр другой версии получает `Version`, и
модуль закрывает соединение — так модуль этапа 34 отвечает на Hello
версии 2; клиент тогда подключается снова с версией ниже (5 → 4 → 3 → 2 → 1) и
обходится без подмены файлов (`Client::has_files`), без мира и состояния (`Client::has_state`), отладки (`Client::has_debug`) или журнала (`Client::version`, `has_journal`; в редакторе флажок «Все объекты»
недоступен с подсказкой, CLI `live log` говорит, что модуль старый). Запись
выключается в конфигурации (`writes=0`), и модуль отвечает `Denied`.

Ошибки: `BadRequest`, `Version`, `Edition`, `NotReady` (нет уровня, нет
игрока, нет кадра), `Timeout` (цикл не дошёл до точки — пауза, свёрнута,
загрузка; запись, опоздавшая к сроку, не выполняется), `Denied`,
`Failed`, `Unsupported`.

## 8. Установка и откат

- **Тень стенда:** `doctor-toolkit live install ТЕНЬ [--writes] [--port N]`,
  `live uninstall ТЕНЬ`.
- **«Играть»** (CLI `play --live [--live-writes]`, в редакторе — флажок
  «Живая связь» в параметрах на панели «Связь»): модуль и
  `doctor_live.cfg` кладутся в `scripts/` на время запуска, после выхода
  убираются (`ModuleInstall`, как `cmd.txt` этапа 32): копии того, что
  записано, лежат в `_doctor_toolkit/live/`; чужой изменённый файл не
  трогается; `scripts/` удаляется, только если его сделал тулкит и он пуст;
  журнал модуля переносится в `_doctor_toolkit/live/last.log`; остаток
  прерванного запуска убирает следующий запуск (`restore_stale`).
- Загрузчик не скачивается: без него (нет `dinput8.dll` и др.) «Играть»
  запускает игру без модуля и говорит почему. Способ Wine сам добавляет
  `dinput8=n,b`; для Steam/Proton — строка запуска
  `WINEDLLOVERRIDES="dinput8=n,b" %command%`.
- Модуль не пишет файлы игры и не трогает сохранения; его единственный
  файл — журнал рядом с собой.
- **Без записи в игру (этап 46, §14):** `play`, «Играть» редактора, MCP
  `play` и `live install --apply|--mods|--cmd-txt` собирают изменения в
  папку тулкита вне игры и кладут в `doctor_live.cfg` строки `redirect=`;
  папка игры получает только модуль и его настройку на время запуска.

## 9. Ограничения и найденное

- Адреса привязаны к одной сборке (проверка издания это обеспечивает).
- Объекты без матрицы в `+0xD0` (логика, триггеры без `Entity`) в список
  «рядом» не попадают — для них запрос World (§11.5).
- Время суток пишется с этапа 48 (§13.1); сообщения адресно — только тем,
  кто слушает это сообщение.
- Первый вариант обхода объектов проверял каждое чтение вызовом
  `VirtualQuery`: под Wine это так медленно, что главный поток простоял
  более 3 минут (100 % ЦП) — заменено картой регионов и бюджетом времени.
- Мод игрока GF2ASI открывает своё окно консоли «GF2SE» и уводит фокус:
  окно игры свёрнуто, уровень не грузится, пока ему не вернуть фокус (на
  стенде — щелчок по кнопке игры на панели задач Wine). С модулем он
  уживается: в разные места (GF2ASI перехватывает `0x00403A50`,
  `0x00608930`, `0x00608250`, `0x0069DE10`, `0x0069E840`, `0x006817C0`,
  `0x00682860`, `0x009BCB30`).
- Сообщение `boundary_fade_out` затемняет экран без обратного затемнения
  (так игра выводит игрока за край мира) — для опыта годится, для игры нет.

## 11. Журнал игры и все объекты (этап 49)

Модуль записывает, что игра печатает, ошибки её Lua и сообщения шины
SimGroup в кольцо событий; клиент читает его запросом `Events` протокола 2
(§7). Все объекты SimManager — и логика без мировой матрицы — запросом
`World`. Перехваты ставятся в `DllMain` вместе с перехватом кадра, только
после проверки издания и только при `journal=1` в `doctor_live.cfg` (по
умолчанию; «Играть» без живой связи, только ради исправления ввода §5.1,
пишет `journal=0`). Код: `journal.rs` модуля, `doctor_toolkit_live::journal`
(кольцо, события) и `::world`.

### 11.1 Что игра печатает

Отладочный вывод выпущенной сборки почти весь вырезан: функции вида
`Debug::Printf` скомпилированы в пустые `ret` (`0x008D1330` — строки
статистики «---Player Rank,%d», «%.1f,Mission Success»; `0x005CCF50` —
«APTCallback_AssertFail:%s», «%s Shader Supports …»), и в журнал их
не поймать без правки мест вызова. Остались два живых канала:

| Канал | Место | Что модуль делает |
|---|---|---|
| `OutputDebugStringA` | слот импорта `0x00D550C4` (KERNEL32; имя в таблице поиска `0x00E4E65C` → `0x00E4EDB8`) | кладёт в слот свою функцию, она пишет строку в журнал и зовёт прежнюю. Через этот слот печатают printf отладки `0x0065BC40` (свой буфер 4 КБ, свои слушатели `0x01205A54`; статистика памяти `0x0064D030`, таймеры `0x0065E570`, сеть `0x00655EF0`), FESL (`0x00AF0C90`), проверки с `int3` (`0x006458F0`, `0x00649DB0`) |
| Lua `print` игры | `0x0046BCE0` (не стандартная `0x0062D560`, которая пишет в `stdout`) | `print` склеивает аргументы, берёт скрипт и строку вызвавшего (`lua_getinfo "Sl"`, `0x00632FB0`) и зовёт функцию из указателя `0x0110A6C0`: `cdecl (скрипт, строка, what, текст)` (`0x0046BF56`–`0x0046BF79`). В выпущенной сборке там пустая функция `0x0046BFC0` (`ret`), код указатель не пишет — вывод скриптов уходил в никуда. Модуль кладёт в указатель свою функцию и после записи зовёт прежнюю |

На стенде в уровне `OutputDebugStringA` игра не зовёт (за 10 минут — ни
разу); работу перехвата модуль проверяет сам: после установки печатает
через слот игры строку `doctor_live: OutputDebugStringA goes to the
journal`, она приходит событием `debug`. Скрипты печатают сразу после
загрузки уровня: `Global Lua Utility Functions:19: functionTable[startup]
is nil` (дважды).

### 11.2 Ошибки Lua

| Адрес | Что |
|---|---|
| `0x00635AB0` | `luaD_rawrunprotected(L, f, ud)`, обычный `cdecl` (внутри `setjmp` `0x00D3D380`/`longjmp` `0x00BA0B4C`); возвращает код Lua |
| `0x006365A0` | его вызов в `luaD_pcall` `0x00636570` — все защищённые вызовы: `lua_pcall` `0x00626200`, вызовы скриптов игрой (`CallLuaFunction` `0x00468F40`, `MessageReceiverReceive` `0x004CE610`, `0x0043E500`, `0x00437A80`, `0x00467440`, `0x00468EA0`), `lua_dobuffer` `0x006293C0` и `live lua` |
| `0x00636722` | его вызов в `luaD_protectedparser` `0x006366F0` — ошибки компиляции |
| `0x00636488` | его вызов в `lua_resume` `0x00636440` — ошибки сопрограмм |
| `0x006338A0` | `luaG_errormsg` (`L` в `ESI`): через неё идут все ошибки выполнения (`lua_error` из `luaL_error` `0x00627BD0`, `luaG_runerror`), пока интерпретатор, который их поднял, ещё работает; затем обработчик ошибок и бросок `luaD_throw` `0x00635A80` |

Все вызовы скриптов игрой проверяют код возврата и молчат: сообщение об
ошибке остаётся на стеке или выбрасывается (`0x0043E500`, `0x00468F40`
возвращают `false`), `lua_dobuffer` печатает его в `stderr`
(`0x006292E0`, `_ALERT` не задан). Модуль меняет цели трёх вызовов
`luaD_rawrunprotected` на свою функцию с той же подписью: при ненулевом коде
сообщение лежит на вершине стека (`L->top − 8`, строка — `TString`:
длина `+0xC`, текст `+0x10`; коды 1 — выполнение, 3 — синтаксис, 4 —
память, 5 — ошибка обработчика).

Стек вызовов к этому моменту ещё не раскручен (`L->ci` восстанавливается
после, `0x006365B9`), но строки внешних уровней Lua с флагом «кадр
интерпретатора» (бит 1 `CallInfo+8`) берутся из локальной переменной уже
ушедшего кадра — их не прочесть. Поэтому второй перехват — переход с
первых пяти байт `luaG_errormsg` (`mov eax,[esi+0x54]; test eax,eax`) в
свой переходник: он сохраняет регистры и флаги, читает стек, восстанавливает
их, выполняет эти пять байт (флаги после `test` проверяет следующая
инструкция) и идёт дальше с `0x006338A5`. Стек, снятый там, модуль
приписывает ошибке того же `L`, о которой затем сообщит
`luaD_rawrunprotected`.

Устройство (Lua 5.0, числа `float`; `0x00632AA0` `currentline`,
`0x00632D40` `funcinfo`): `lua_State` — `+8` вершина, `+0x14` текущий
`CallInfo`, `+0x1C` стек, `+0x28` первый `CallInfo`, `+0x54` обработчик
ошибок; `CallInfo` (0x18 байт) — `+0` база (функция — слот под ней: тип 6,
замыкание в значении), `+8` состояние (бит 0 — функция C, бит 1 —
`pc` в кадре интерпретатора), `+0xC` сохранённый `pc`, `+0x10` указатель на
`pc`, `+0x14` число хвостовых вызовов; замыкание — `+6` «это C», `+0xC`
`Proto`; `Proto` — `+0xC` код, `+0x14` строки инструкций, `+0x20` имя куска,
`+0x30` число строк, `+0x3C` первая строка функции. Строка уровня —
`lineinfo[(pc − code) / 4 − 1]`, проверяется, что `pc` внутри кода.

Пример (стенд, `live lua` из трёх строк):

```
#9 frame 1507     47.6s lua error: doctor_live:1: attempt to index local `y' (a nil value)
    doctor_live:1: in function <doctor_live:1>
    doctor_live:2: in function <doctor_live:2>
    doctor_live:3: in main chunk
```

Хвостовые вызовы Lua 5.0 занимают тот же `CallInfo` — такие уровни
помечены «(after N tail call(s))». Ошибки, которые скрипт ловит своим
`pcall`, тоже попадают в журнал: их не отличить от остальных.

### 11.3 Сообщения шины

Шина `0x00408A00` (§5) — 482 места вызова, поэтому перехват — на входе:
первые пять байт (`push ecx; mov edx,[esp+8]`, без относительных
операндов) заменены переходом в переходник, который сохраняет регистры и
флаги, зовёт запись `(сообщение, force)`, восстанавливает их, выполняет эти
пять байт и продолжает с `0x00408A05`. Запись идёт **до** доставки, только
пока клиент просит сообщения (15 с после последнего запроса с ними), и
читает то же, что шина прочтёт сразу после: таблицу `*0x01162380`, блоки
и узлы слушателей (`+0x14` флаги, бит 15 — удалён; `+0xC` слушатель; бит 0
слова `+4` слушателя — включён, без `force` шина зовёт только таких,
`0x00408A70`). Событие: хэш, данные, `force`, число слушателей, до 8
получателей — объектов SimGroup (слушатель − `0x3C`, таблица методов в
`.rdata`, GUID — NeoGuid: байты 8–15 — имя машины автора, заглавные буквы
и цифры; у прочих слушателей — системы движка, приёмники Lua — там другое),
отправитель (игра или `live send`; адресная отправка `live send --to` идёт
мимо шины, её модуль записывает сам).

Игра шлёт около 15 сообщений каждый кадр (`iMsgSystemTick`,
`iMsgRunningTick` — 343 слушателя, `iMsgRunningPostTick` — 1133,
`iMsgPreRender`, `iMsgDoRender` и др.): одно сообщение записывается не
чаще 4 раз за 5 секунд, остальные считаются потерянными. Имена сообщений
клиент берёт из SimGroup игры и рабочего пространства и из схемы логики
(сообщения движка).

### 11.4 Кольцо событий

`doctor_toolkit_live::journal::Ring`: 4096 последних событий с номерами
1, 2, …; клиент спрашивает «после номера N» и узнаёт, сколько потеряно
(кольцо обошло или сработал предел частоты: вывод — 200, ошибки Lua — 50,
сообщения — 300 в секунду). Текст события — до 2048 байт, стек — до 16
уровней. Вид события: вывод (`debug`, `print` со скриптом и строкой,
`module` — заметки самого модуля, то же, что его журнал), ошибка Lua (код,
сообщение, кусок, строка, стек), сообщение. Каждое событие несёт номер
кадра главного цикла и игровое время.

Перехваты не держат блокировку дольше записи в кольцо, ловят панику и
читают память игры через проверку областей (кроме таблицы сообщений,
которую шина читает сама). Lua-печать и `OutputDebugStringA` зовутся из
любых потоков игры.

### 11.5 Все объекты

`World` обходит ту же таблицу групп SimManager, что и «объекты рядом»
(§4), но берёт каждый объект: GUID, класс, группа, позиция (если в `+0xD0`
мировая матрица), слово флагов `+0x14`, бит 0 `+0x40` (слушатель
включён). 8 664 объекта у ворот аэропорта Гаваны — 7 мс.

**Группа — это поток.** Номер группы объекта `+0x1C` — идентификатор
потока, который его создал: создание из записи SimGroup (`0x00446E30`)
берёт его из загружаемого потока `*(StreamManager+0x84)+0x1C`
(`0x00446E9D`), а `0x00405F40` по ресурсу находит запись потока в списке
`+0x6C` и возвращает её `+0x1C`. Модуль читает этот номер у каждой записи
списка загруженных потоков и отвечает таблицей «группа → имя потока». На
старте: 6 080 объектов `gf2\globals_global.str`, по 100–330 в зонах
`gf2\cuba\local\…`, 203 — `gf2\cuba\local.str`; объекты, созданные игрой
на ходу (камера, GUID `efbe0000…`), — без потока.

**Класс — из кода, без вызовов.** Первый вариант звал у каждого объекта
`As` (виртуальный `+0x10`) со всеми хэшами реестра, как «объекты рядом»
для объектов с матрицей, — **игра зависла** (главный поток встал в
ожидании, связь перестала отвечать): у части объектов таблицы групп в
`+0x10` вовсе не `As` (в слоте `0xFFFFFFFF` или указатель вне кода). Теперь
класс читается из кода `As` таблицы методов объекта: первый хэш из
реестра, с которым она сравнивает аргумент (`cmp dword [esp+4], H` —
`81 7C 24 04`; `cmp eax|ecx|edx…, H` — `3D`, `81 F8+r`), с переходом по
`jmp` в `As` базового класса и через переходники `sub ecx, N; jmp` классов
с несколькими базами; функции, которые сравнивают, проверяются по `in_text`,
ничего не вызывается. `Base::As` (`0x0046C460`) ничего не сравнивает:
у объектов классов без своего `As` (1 958 из 8 664) класс модулю не
известен — клиент берёт его из SimGroup по GUID (с именами — ни одного
неизвестного). Фильтр класса в `World` — точный класс.

Логика на стенде: `MessageRelay` (36), `VariableSwitch` (35),
`TriggerRandom` (25), `PlayerTeleportRelay` (25), `GiveItemRelay` (20),
`InterestingObjectRelay` (14), `EnterExitTrigger` (8) и др.; 7 030
объектов без матрицы, у 86 слушатель выключен.

**Поиск.** По GUID — фильтр `World` (список GUID). По имени — на стороне
клиента: `live::names::LiveNames` читает все SimGroup игры (версия
рабочего пространства, где она есть): GUID → имя (`CMD_SetName`), класс,
поток, ресурс, номер объекта; хэш → имя сообщения (строки входов и
выходов схемы логики, сообщения движка). Имя ищется подстрокой, найденные
GUID уходят в `World`; чего нет в ответе — поток не загружен.

### 12.1 Где игра стоит

Модуль держит главный поток игры в безопасном месте, пока клиент не скажет
«дальше», и сам отпускает его через предел (`hold_s` запроса Break, по
умолчанию 120 с, не больше 900) — игру нельзя «забыть» на паузе. Пока она
стоит, остальные потоки игры (звук, загрузка, отрисовка) идут; модуль не
держит её блокировок, только спит и разбирает очередь запросов.

| Место (`StopPlace`) | Где | Что | Что отвечает, пока стоит |
|---|---|---|---|
| `frame` | перехват обновления `GameMainLoop` (`+0x2C`), до записей модуля и обновления игры | пауза, шаг, точка, сработавшая во время записи самого модуля | всё: чтение, телепорт, сообщения, Lua, камера, текстуры |
| `bus` | переходник шины `0x00408A00`, после записи в журнал, **до доставки** слушателям | точка на сообщении | только чтение (объекты, все объекты, потоки, память); запись и Lua — `NotReady` |
| `print` | перехват Lua `print` (`0x0110A6C0`) и `OutputDebugStringA` | точка на тексте вывода (узел Blueprint) | только чтение |
| `lua` | после неудачного `luaD_rawrunprotected` | точка на ошибке Lua | только чтение |

Внутри кода игры (шина, `print`, ошибка) писать нельзя: сообщение или Lua
оттуда вошли бы в код игры повторно посреди её вызова. Остановки — только
на главном потоке (его номер запоминает перехват кадра,
`GetCurrentThreadId`); на других потоках и во время запроса самой связи
(сообщение, которое шлёт `live send`, — клиент ждёт ответа на этот запрос)
точка не останавливает на месте, а ставит остановку на следующий кадр
уровня (место `frame`, причина та же). Пока игра стоит, точки не
срабатывают.

**Шаг** — «дальше» и остановка в следующем кадре уровня. **Пауза** —
остановка в следующем кадре. Точки (`BreakRule`): сообщение по хэшу (и,
если задан, только когда среди получателей объект с этим GUID —
получателей модуль считает так же, как журнал, §11.3, и только для таких
правил), текст вывода (подстрока), любая ошибка Lua; `once` — правило
снимается после первого срабатывания. Не больше 64 правил. Состояние —
запрос Debug (правила, где стоит, сколько стоит и сколько осталось, номер
журнала на момент остановки, ждёт ли пауза кадра, сколько было
срабатываний, свободная камера); отвечает сетевой поток сразу. Break,
Control и Debug не считаются записью (данные игры не меняют) и разрешены
при `writes=0`.

Поиск собственного флага «пропустить кадр» игры (`GameMainLoop` и
диспетчер `0x0112980C`) не понадобился: держать главный поток в перехвате
обновления — это и есть пауза; меню паузы игры (`Escape`) — отдельное
состояние, его модуль не трогает.

### 12.2 Свободная камера

Камера, которой рисует игра, — не статический объект: `0x01207DB0` — 12-й
слот пула видов `0x01206BB0` (16 видов по 0x180 байт, флаги занятости
`0x012053B4`, выделение `0x004224F0`/`0x00422590`). Вид: `+0` обратная
матрица, `+0x40` мировая (строки «вправо», «вверх», «вперёд», перенос),
`+0x80` плоскости, `+0x140` тип проекции, `+0x144`/`+0x148` ближняя и
дальняя плоскости, `+0x14C` угол обзора (рад), `+0x150` соотношение
сторон. Модуль берёт текущий вид так же, как отрисовка:
`*(*0x0122339C + 0x14)` при `+0x154 ≠ 0`, иначе слот 0 TLS `+0x24`.

За кадр: обновление `0x0067D160` → `0x0068BBE0` рассылает такты
(`0x0040EBB0`); на `iMsgRunningPostTick` менеджер камер (`0x00424D70` →
`0x004252E0`, описания камер по 0x1D0 байт) пишет вид (`0x00425EA0`).
Сразу затем `0x0068BBE0` зовёт отрисовку уровня `0x0040E1F0`
(`0x0068BC75`, `0x0068BC8A`): она **первым делом шлёт `iMsgBeforeRender`**
(хэш — в переменной `0x01206960`) через шину, потом выбирает вид и пишет
команды кадра. У потока отрисовки свои копии видов (карта
`*0x01223398 + 8`), их обновляют только команды с копией матрицы
(`0x0110B690` мировая через `0x00422C50`, `0x0110B67C` обратная) — поэтому
запись в `0x01207DB0` после обновления на экран не попала бы.

Модуль ставит камеру в своём переходнике шины, когда идёт
`iMsgBeforeRender`, штатным сеттером вида `0x00422D40`: `EAX` — вид,
`ESI` — матрица 4×4, выровненная на 16 (`MOVAPS`), в стеке `bool invert = 1`
(вызываемый снимает его, `RET 4`). Сеттер копирует матрицу в `+0x40`,
считает обратную (`0x0056C640`) и плоскости (`0x00423900`) и на главном
потоке пишет команду для копии вида потока отрисовки (`0x00422C50`). Так
отсечение, выбор детализации и слушатель звука (`0x0040E0A0`, внутри
отрисовки) видят новую камеру в том же кадре. Матрица строится из позиции
и направления (`live::pose_looking`: вправо = вверх × вперёд, без крена).
Угол обзора остаётся игры. Игра каждый кадр пересчитывает свою камеру —
модуль ставит свою каждый кадр, пока клиент её не снимет (`SetCamera
None`). Свободная камера живёт в перехвате шины, поэтому нужен
`journal=1`.

Ограничения: зоны мира игра грузит по игроку, а не по камере — вдали от
игрока мир пуст; ввод и прицел остаются привязаны к камере игрока.
Отладочной камеры в `exe` нет (строк FreeCam, DebugCam нет); классы
SimGroup `PushCamera`/`PopCamera`/`FixedCameraInfo` (реестр `0x00688AF0`)
дают только заранее поставленные камеры.

**Обратно (игра → редактор):** вид редактора следует за `Camera` модуля —
позиция, направление («вперёд» мировой матрицы камеры — то, куда она
смотрит: камера в 4,5 м позади игрока смотрит на него), угол обзора по
вертикали. Второй путь «редактор → игра» — телепорт игрока в точку камеры
редактора с её курсом (§5).

### 12.3 Текстуры без перезапуска

**Можно**, если у новой текстуры тот же размер, формат и число уровней,
что у загруженной, и её поток загружен. Сделано и проверено на стенде.

| Адрес | Что |
|---|---|
| `*0x01205750` | `IDirect3DDevice9` (создаётся в `0x00607990`: `HWVP | PURE | MULTITHREADED`) |
| `0x011A0F28` | таблица текстур: 4096 записей по 0x38 байт, «ручка» — индекс. `+0` состояние (0 свободна, 1 занята, 2–3 создана, 4 заблокирована), `+1` уровней, `+2`/`+4` ширина и высота (u16), `+8` формат (индекс таблицы `0x00F15860`: 30/31 DXT1, 32 DXT3, 33–35 DXT5, 3 A8R8G8B8, 8 L8, 9 A8, 10 A8L8), `+0xC` флаги (2 куб, 4 объём, 8 цель отрисовки, 0x200 системная память), `+0x14` `IDirect3DBaseTexture9*`, `+0x30` пул |
| `0x00618640` | создание текстуры (`CreateTexture` `+0x5C`); пул 1 (`MANAGED`) у всех текстур потоков, 0 (`DEFAULT`) только у целей отрисовки |
| `0x00611000` | текстура по хэшу имени: карта `*0x012058E0`, 4096 корзин по `hash & 0xFFF`, узел — объект текстуры: имя `+0x34`, следующий `+0x38`, ручка `+4`. Хэш — последний id ресурсов `tg4h`/`tg4d` (`0x00619CEB`) |
| `*0x01223558` | загрузчик `tg4` (методы `0x00E40F18`: загрузка `0x00619CB0`, выгрузка `0x00619D70`); загрузки в пути — `+0x20` (записи по 0x14 байт, ручка `+4`), их число `+0x24` |
| `0x00619EF0` | команда «залить уровни» в буфер кадра `*0x01206880`: `0x011278A4`, ручка, размер, данные (16 байт по курсору `+0x14`) |
| `0x0061A5F0` → `0x00619F50` → `0x00606AC0` | поток отрисовки исполняет её: по уровням `0x00606A40` — `LockRect` (`0x00606FD0` → `0x00618A70`, vtable `+0x4C`), копия с учётом шага строки (`0x00614ED0`), `UnlockRect` (`0x006071A0`); затем ответная команда `0x01127890` → `0x00619EA0` отмечает загрузку в пути, если она есть |
| `0x00485AE0` | поток отрисовки: `TLS+0x34 = 1`, исполняет буферы команд — весь D3D идёт там; буфер кадра уходит к нему в конце кадра (`0x0068BCD0` → `0x0040CB90`) |

Исходные данные `tg4d` игра после загрузки освобождает — копии в памяти
нет, модуль получает все уровни целиком (`Request::Texture`: хэш имени и
весь `tg4d`). Модуль в кадре уровня, на главном потоке: находит ручку по
карте (читает, `0x00611000` не зовёт), проверяет запись (состояние 2–3,
2D, формат из таблицы выше, длина данных ≥ суммы уровней с округлением до
блоков 4×4, `debug::texture_bytes`), что игра сама сейчас эту текстуру не
грузит (список `+0x20` загрузчика), и пишет в буфер кадра ту же команду,
что загрузчик. Данные живут у модуля 600 кадров (команда исполняется на
следующем кадре в потоке отрисовки). Другой размер или формат так не
подменить — нужно освобождать и создавать запись заново (`0x006065A0`,
`0x00606C80`), этого модуль не делает.

**Перезагрузка потока целиком** у игры есть, но дорогая и опасная: классы
SimGroup `LoadStream`/`UnloadStream` (`0x008139D0`, `0x00813BC0`; `ECX =
*0x0122337C`: `0x00405900(имя)` → id, `0x004025A0(id)` → запись,
`0x00404C40` → `0x004048C0`). Выгрузка идёт по счётчикам ссылок (`+0x54`
зависимостей, бит `0x20` в `+0x50` — «загружен явно»), рекурсивно
выгружает зависимости, зовёт выгрузку ресурсов загрузчиков и рассылает
`iMsgStreamBeginUnload/Unloading/UnloadComplete`. Поток читается с диска
заново, объекты SimGroup пересоздаются, два запроса потоков подряд роняют
игру (этап 32) — в зоне игрока это висячие ссылки. Вывод: годится только
для дальних зон-листьев; модуль этого не делает.

**Модели.** Загрузчик мешей `*0x01223458` (методы `0x00E31B00`: загрузка
`0x0045A560`, выгрузка `0x0045A820`); образ ресурса `mesh` и есть объект
меша, `meshvolatile` (вершины) находится через `0x004211E0(GUID)` и
запоминается в `mesh+0x9C`, данные живут, пока меш загружен. Буферы
создаёт `0x0045A2B0`: вершинные — `0x0060B620` → `0x0060B3B0`
(`CreateVertexBuffer` `+0x68`, объекты в `mesh+0x78` по 0x28 байт),
индексные — `0x0060C080` → `0x0060BE80` (`CreateIndexBuffer` `+0x6C`,
`INDEX16`, `mesh+0x7C` по 0x34 байт); меш всегда просит пул `MANAGED`.
Значит, вершины **того же числа и раскладки** переписать на месте можно
(`Lock` `+0x2C`/`Unlock` `+0x30` на `*(буфер+0)` из потока отрисовки или
своей командой), но это не проверено: у меша есть и свои копии (границы,
скин, коллизия Havok — отдельный ресурс), и новая модель редко совпадает
по числу вершин. Вывод: модели — только перезапуском уровня; правка
вершин на месте — возможное продолжение.

### 12.4 Счётчики сообщений

Предел журнала — одно сообщение не чаще 4 раз за 5 с (§11.3) — терял
частые сообщения целиком. Теперь переходник шины считает отброшенные этим
пределом по хэшу, и раз в секунду (перехват кадра) они уходят одним
событием `MessageCounts` (окно в мс, пары «хэш, сколько»; до 512 хэшей).
Это новый вид журнала (`mask::MESSAGE_COUNTS = 8`), его получают только
клиенты протокола 3: модуль и поддельная игра снимают незнакомые биты для
кадров версий 1 и 2 (`mask::for_version`), иначе старый клиент не прочёл
бы ответ. Получателей у счётчика нет — на графе он зажигает все провода
своего сообщения.

### 12.5 Протокол 3 и совместимость

Запросы: `Break {rules, hold_s}`, `Control(Pause | Continue | Step)`,
`Debug` → `DebugState`, `SetCamera {Option<CameraView>}` (запись),
`Texture {name, data}` (запись; ответ — `Done`). Предел полезной нагрузки
кадра поднят с 1 до 32 МБ (текстура с уровнями). Модуль отвечает на кадры
версий 1–3 в версии запроса; запрос новее кадра — `Unsupported`. Клиент
пробует версии сверху вниз: 3 → 2 → 1 (модуль этапа 49 отвечает на Hello
версии 3 ошибкой `Version` и закрывает соединение) — `Client::has_debug`
говорит, есть ли отладка; редактор прячет её разделы с подсказкой, CLI
пишет, что модуль старый. Проверка издания — 58 мест (+7: начало
отрисовки кадра и чтение хэша `iMsgBeforeRender`, сеттер вида и его
команда, поиск текстуры по имени, команда загрузчика текстур и её
исполнение, список загрузок в пути).

### 12.6 Сообщения на графе: общая форма

`doctor_toolkit::logic_graph::trace::TraceEvent` — «сообщение `hash`
(имя) от `sender` к `receivers` в `time_ms`», номер, кадр, сколько
слушателей, сколько раз (`count`, для счётчиков), источник (`game`,
`link`, `simulation`); строки JSON (`write_jsonl`/`read_jsonl`).
`TraceEvent::from_live` делает его из события журнала. `TraceMap` по графу
находит узлы по GUID получателей и провода этого сообщения в них (через
хаб, от узла движка), их источники — вероятные отправители; если провода
нет — узлы с выходом этого сообщения. `Activity` копит счётчики по узлам и
проводам, ленту последних 400 событий и сколько событий коснулось графа.
Та же форма годится для прогона логики без игры (этап 38): у прогона
отправитель известен, и подсветка сужается до его проводов.

## 13. Мир и состояние игры (этап 48)

Протокол 4 добавил чтение и запись мира и состояния игры для проверок без
прохождения: время суток и его скорость, погода, загрузка и выгрузка
потоков по одному, деньги, семья игрока, миссии (чекпоинты) и переменные
сюжета (`variabledictionary`). Пауза и шаг по кадру — этап 35 (§12),
здесь не повторяются. Код: модуль — `state.rs` крейта
`doctor-toolkit-live-asi`, протокол — `doctor_toolkit_live::state`; CLI —
`live time|weather|stream|money|family|mission|var`, редактор — раздел
«Мир и состояние» панели «Связь», MCP — `game_state`, `variables`,
`set_time`, `set_money`, `set_variable`, `stream_load`, `stream_unload`.

Чтение идёт в перехвате главного цикла, как остальные задания; запись — в
кадре уровня (перехват обновления `GameMainLoop`, §2), где игра сама
меняет время, начисляет деньги и запрашивает потоки. Каждый вызов модуля —
тот, что делает сама игра в том же месте с теми же аргументами (место
вызова указано в таблицах).

### 13.1 Время суток

Объект `TimeOfDayManager` (`*0x0112A53C`; фабрика класса `0x00684AE0`,
конструктор `0x00826EB0`, размер 0xB4; в игре один — в
`gf2/globals_global`, атрибуты: скорость 60, год 1950, час 16).

| Адрес | Что |
|---|---|
| `+0x5C`, `+0x60` | год (1950) и день года (0–364) |
| `+0x64`, `+0x68`, `+0x6C` | часы, минуты, секунды (`u32`; чтение — `0x00826510`) |
| `+0x70` | скорость: игровых секунд за реальную (`f32`, 60); такт менеджера `0x00826B70` на `iMsgSystemTick` двигает часы на неё, в начале нового часа шлёт `0x0112DB64`, в полночь `0x0112DB6C`, каждый такт — `0x0112DB7C` |
| `+0x74` | скорость уровня (атрибут 1 объекта; к ней возвращает флаг 2 `SetTimeOfDay`) |
| `0x008269F0` | `SetTime(this, год, день, час, минута, секунда)`, `thiscall`, `RET 0x14`: зажимает значения (`0x008268F0`), сбрасывает `+0x7C`/`+0x80` и состояние объекта `*0x0112A55C` (`0x007EC440`) и шлёт по шине `0x0112DB74`; на стенде небо и свет меняются в следующем кадре |
| `0x00825B90` | обработчик `SetTimeOfDay` (фабрика `0x00684B10`): текущие год и день, поля атрибутов, `0x008269F0` (`0x00825D43`), затем скорость: флаг 2 — `+0x70 = +0x74` (`0x00825D4E`), иначе атрибут, если он не меньше 0 (`0x00825D6A`) |

Модуль делает то же: `SetTime` с годом и днём, которые есть, и запись
скорости в `+0x70` (отрицательная — скорость уровня из `+0x74`, 0
останавливает часы). На стенде: 16:31 → 23:30 — за кадр ночь, горят
фонари; скорость 0 — часы стоят (23:30:00 через 70 с); 12:00 и скорость
уровня — день, часы идут.

### 13.2 Погода

Класс `WeatherManager` (фабрика `0x00684E60`, конструктор `0x00836CC0`
кладёт объект в `*0x0112AFF4`) — это дождь: случайный по таймеру
(`0x00837940`, вероятность — атрибут 11), начало и конец с плавным
переходом (`iMsgStartRainFadeIn`, `…FadeOut`, `…InTOD`, `…OutTOD`), под
крышей — без капель (`0x008371B0`). Сообщения управления — из атрибутов
0–5 объекта (`0x008369D0`): начать с переходом (`0x00837730`), закончить
(`0x00836820`), начать сразу (`0x00837860`), закончить сразу
(`0x008368B0`), запретить и разрешить случайный дождь.

**В одиночной игре дождя нет:** ни одна из 2 006 SimGroup игры не создаёт
`WeatherManager` (выгрузка всех SimGroup), на стенде `*0x0112AFF4 = 0`.
Модуль только читает его состояние, когда он есть (флаги `+0x84`, длина и
время дождя `+0xB0`, `+0xB4`); писать некуда — создавать объект класса
модуль не берётся.

Небо, туман, свет, тон и вода — ключи времени суток: объекты
`TODMessage` с часом и минутой в потоках (`SetSkyMessage` 234,
`SetFogMessage` 170, `LightingTODMessage`, `BloomTODMessage`…; конструктор
`SetFogMessage` `0x0082CDA0` регистрирует их в последовательности
`TODSequencer`). Поэтому «погоду» уровня меняет время суток (§13.1): на
стенде 23:30 даёт ночное небо и свет фонарей, 12:00 — дневные.

### 13.3 Потоки по одному

Классы `LoadStream`/`UnloadStream` (фабрики `0x00684960`, `0x00684990`) —
образец модуля (в SimGroup игры они не используются):

| Адрес | Что |
|---|---|
| `0x008139E7`–`0x00813A1F` | `LoadStream`: `0x00403A50(имя, приоритет, 0, 0, 0)` на `ECX = *0x0122337C` (приоритет по умолчанию 32768, `0x00E44690`) → id потока |
| `0x00403A50` | запрос потока, `thiscall`, `RET 0x14`; для имени без `.str` сам дописывает `.str` |
| `0x00813BCB`–`0x00813C01` | `UnloadStream`: `0x00405900(имя, 0)` → id, `0x004025A0(id)` → запись, `0x00404C40(запись)` — выгрузка (`RET 4`) |
| `0x004025A0` | запись по id: корзины `+0x50`, их число `+0x54`, узел `{id, запись, следующий}` |
| `+0x24` записи | состояние: 1 — запрошен, 3 — загружен (`0x00813C4A`), 2 и 4 — на выходе (`0x00403C40`) |
| `StreamManager+0x84` | поток, объекты которого игра создаёт сейчас (`0x00446E9D`); между загрузками 0 |

Два запроса подряд роняют игру (этап 32), поэтому модуль держит очередь из
одного запроса: новый запрос (загрузка или выгрузка) получает `NotReady`,
пока предыдущий запрос связи не выполнен (загрузка — состояние 3,
выгрузка — записи нет или она не в состоянии 3) или пока игра создаёт
объекты потока (`+0x84 ≠ 0`). Запрос, не выполненный за 120 с, перестаёт
держать очередь (`expired`). Имя приводится к виду игры
(`gf2/cuba/local.str` → `gf2\cuba\local`); поток, которого нет в папке
игры, модуль не запрашивает: для незнакомого имени игра заводит запись
«запрошен» навсегда (так было на стенде с `gf2\cuba\no_such_stream`).
Выгружать можно только то, что загрузила связь; поток, загруженный самой
игрой, — только с `force` (его объекты исчезают из-под ног игры, §12.3).
Запрос `StreamQueue` отвечает очередью связи (до 16 последних запросов с
состоянием и числом кадров) и тем, занята ли игра; список загруженных —
прежний `Streams`.

На стенде: `filler_056_01` (зона `yuri/high`, `ZoneRenderLOD` в (114,7;
0,3; 348,6)) — выгрузка за 1 кадр, загрузка за 3–33 кадра; свободная
камера над площадью: после выгрузки исчезают балконы и решётки жёлтого
дома, после загрузки возвращаются. Второй запрос сразу после первого —
отказ «not loaded yet … one request at a time».

### 13.7 Переменные сюжета

Менеджер переменных — `*0x01223428` (конструктор `0x00441E60`
регистрирует загрузчик ресурсов `VariableDictionary`); `+0x20` —
вместимость (320 на стенде), `+0x24` — записи по 0x14 байт, `+0x28` —
число (48 в Гаване).

| Поле записи | Что |
|---|---|
| `+0` | хэш записи `variabledictionary` (функция не SDBM, `logic-types.md` §1) |
| `+4` | `sdbm(lower(имя))` — загрузчик `0x004423F0` считает его по имени из ресурса; `FindVariable` Lua ищет по нему (`0x00442130`) |

рабочего пространства (`LiveNames`). Пара со стенда:
`global_tutorial_payday` — `+0` `0x001A01D2`, `+4` `0x93813AB9`.

показывает окно «SURVEY: Please pause…» (симуляция встаёт до `Enter`); с

## 14. Моды без записи в игру (этап 46)

До этапа 46 «Играть», стенд и `apply` писали изменённые потоки, TOC,
архив `.viv` с подменами и `cmd.txt` в папку игры, а после выхода
возвращали оригиналы. Теперь игра получает эти файлы из папки тулкита, а
её собственные файлы не меняются: модуль подменяет **открытие файла**.

### 14.1 Через что игра открывает файлы

Импорты `KERNEL32` в `godfather2.exe` для открытия файлов — `CreateFileA`
(слот `0x00D55120`), `CreateFileW` (`0x00D55254`), `GetFileAttributesA`
(`0x00D5528C`), `FindFirstFileA`/`W`; `OpenFile`, `_lopen`, `fopen` из DLL
и отображения файлов в память нет (список импортов). Свой C-рантайм
статический: его `_open`/`_wopen` тоже зовут эти слоты. Все обращения к
слотам в коде (поиск 4 байт адреса слота по `.text`, проверено
дизассемблером):

| Слот | Место | Инструкция | Что |
|---|---|---|---|
| `CreateFileA` | `0x00ABD73D` | `call [0x00D55120]` | открытие класса файла `0x00ABD6E0` (таблица `0x00D9AFC0`; режим → чтение или чтение и запись, `OPEN_EXISTING` по умолчанию) |
| | `0x00BCC4DD`, `0x00BCFC1E`, `0x00BCFC3D` | `call [0x00D55120]` | C-рантайм |
| | `0x00BCC18C` | `mov edi, [0x00D55120]` | C-рантайм (`_sopen`: вызов через `edi`) |
| `CreateFileW` | `0x00AC0BDF` | `call [0x00D55254]` | **открытие файловой системы игры** `0x00AC0AD0`: относительный путь (не с `/` или `\`) получает корень из объекта (`[ecx+4]+4`), UTF-8 → UTF-16 (`MultiByteToWideChar(CP_UTF8)`, слот `0x00D55068`), режим: бит 0 — чтение и запись, иначе только чтение; по умолчанию `OPEN_EXISTING`; `FILE_SHARE_READ`. Отсюда — все файлы данных (журнал ниже) |
| | `0x00ACF5C8` | `call [0x00D55254]` | открытие `0x00ACF580` (бит `0x200` → `CREATE_ALWAYS`, иначе `OPEN_EXISTING`, без общего доступа); на стенде не вызывалось |
| | `0x006987FA`, `0x006988FD` | `call [0x00D55254]` | запись файла профиля `0x006987C0` (`GENERIC_WRITE`, `CREATE_ALWAYS`/`OPEN_ALWAYS`) |
| | `0x00699C59` | `call [0x00D55254]` | чтение файла профиля (`OPEN_ALWAYS`) |
| | `0x00BC45A1` | `call [0x00D55254]` | C-рантайм |
| | `0x00BC424F` | `mov edi, [0x00D55254]` | C-рантайм (`_wsopen`) |
| `GetFileAttributesA` | `0x00C72505` | `call [0x00D5528C]` | обход папки `0x00C724C0` (`путь/*`, затем `FindFirstFileA`) |

Переходники `jmp [слот]` (`0x00B96224`, `0x00B960AA`, `0x00D3B5E2`) ни
разу не вызываются и не упоминаются в данных.

**Что открывает игра — журнал модуля** (`files_log=1`, стенд, `-stream gf2
cuba`, `game-bench.md` §24): `cmd.txt`, `GODFATH0.VIV` … `GODFATH12.VIV`
(монтирование `0x0068BF87`: `%sGODFATH%d.VIV` для 0…12, число 13 — в
`0x00E2F000`; существование — пробным открытием через файловую систему
игры `0x004019A0`), `text/localetable.txt`, `gf2\cuba.toc`,
`gf2\globals_global.toc`, затем потоки `.str` по мере загрузки — **все
через `CreateFileW` из места `0x00AC0BDF`** (у каждого места вызова свой
экземпляр перехвата, и журнал называет место: 77 открытий за запуск, все
`from 0x00ac0bdf`), полным путём `<папка игры>/gf2\cuba.str` (смесь `/`
и `\`), только чтение, `OPEN_EXISTING`. `CreateFileA` и
`GetFileAttributesA` за полторы минуты (до уровня и в нём) не вызывались ни разу. Данные
потоков и архивов игра дальше читает по дескриптору (`ReadFile`,
`SetFilePointer[Ex]`, `GetFileSize[Ex]`), поэтому подменять чтение не
нужно: достаточно открыть другой файл.

### 14.2 Перехват

**Не слоты импорта.** Первая версия ставила свои функции в слоты из
`DllMain`, как журнал этапа 49 ставит `OutputDebugStringA`. На стенде
игра не открыла через модуль ни одного файла: `live peek 0x00D55120 4` в
запущенной игре показал `0x7BB9B040` — снова `kernel32` (`/proc/PID/maps`).
Ultimate ASI Loader (`dinput8.dll`) сам ставит свои функции в слоты
`CreateFileA`/`CreateFileW` исполняемого файла (строки `CustomCreateFileA`,
`CustomCreateFileW` в нём), пока грузит модули, и после загрузки
возвращает сохранённые значения — затирая и то, что поставил модуль.

**Места вызова.** Модуль меняет 13 инструкций таблицы §14.1 (адреса —
`addr::CREATE_FILE_A_CALLS`, `CREATE_FILE_A_LOADS`, `CREATE_FILE_W_CALLS`,
`CREATE_FILE_W_LOADS`, `GET_FILE_ATTRIBUTES_A_CALLS`): шесть байт `FF 15
слот` → `E8 rel32 90` (`call перехват; nop`), `8B 3D слот` → `BF imm32 90`
(`mov edi, перехват; nop`). У каждого места — свой экземпляр перехвата (`create_file_w::<0x00AC0BDF>`
и т. д.), поэтому журнал (`files_log=1`) пишет, откуда открыт файл. Это
делается из `DllMain` после проверки издания, до того как игра читает `cmd.txt` (`0x0067BFA0` в инициализации
`0x0068D010`) и монтирует архивы. Перехват (`files.rs` модуля,
`stdcall` с теми же аргументами):

1. путь (ANSI → UTF-16 через `MultiByteToWideChar(CP_ACP)`) переводится в
   ключ: полный путь (относительный — от текущей папки процесса), часть
   внутри папки `godfather2.exe`, нижний регистр, `/` между частями, `.`
   и `..` разобраны (`doctor_toolkit_live::files::key_in`); пути вне папки
   игры не подменяются;
2. если ключ есть в списке и открытие **только читает существующий файл**
   (нет `GENERIC_WRITE`/`GENERIC_ALL`/`DELETE`/`FILE_WRITE_DATA`/
   `FILE_APPEND_DATA`/`FILE_WRITE_ATTRIBUTES`, `OPEN_EXISTING`), модуль
   открывает цель своим `CreateFileW` с теми же флагами; `GetFileAttributesA`
   отвечает атрибутами цели;
3. иначе — вызов того, что **сейчас** лежит в слоте (`kernel32` или
   перехват загрузчика, если включена его подмена из папки `update`):
   цепочка не рвётся.

Запись игра всегда делает в свою папку, как раньше (профили, сохранения —
вне папки игры): цель подмены может быть оригиналом игры под другим именем
(архивы на номер выше), писать в неё нельзя. Первое открытие каждой
подмены и неудачи (`files: cannot open …`) пишутся в `doctor_live.log`.

**Проверка издания** — 103 места (+19): ячейки таблицы поиска импорта
`0x00E4E6B8`, `0x00E4E7EC`, `0x00E4E824` и имена `CreateFileA` (`0x00E4EF6C`),
`CreateFileW` (`0x00E4EABC`), `GetFileAttributesA` (`0x00E4FC64`) — так
доказано, что слоты именно эти (номер ячейки в таблице поиска равен номеру
слота: `0x00E4E6B8 − 0x00E4E5D8 = 0x00D55120 − 0x00D55040 = 0xE0`), и
13 мест вызова с байтами `FF 15`/`8B 3D` и адресом слота. Тест
`matches_the_game_when_present` сверяет таблицу с `exe`.

**GF2ASI.** Мод игрока перехватывает `0x00403A50` (запрос потока) и
другие функции (§9) — не места §14.1; файлы он открывает своими импортами
(`CreateFileW` в его таблице импорта), их модуль не трогает. Проверено на
стенде с включённым и выключенным GF2ASI (`game-bench.md` §24): подмены
работают одинаково, поток мода грузится через тот же `0x00403A50`.

### 14.3 Список подмен и сборка изменений

`doctor_live.cfg` получает строки (не больше 65 536):

```text
files_log=0
redirect=gf2/cuba/local/yuri/high/terrain3.str|Z:\…\overlay-054fc1fb\game\gf2\cuba\local\yuri\high\terrain3.str
redirect=godfath1.viv|GODFATH0.viv
redirect=cmd.txt|Z:\…\overlay-054fc1fb\cmd.txt
```

`ПУТЬ|ЦЕЛЬ`: путь — в папке игры (ключ §14.2), цель — абсолютный путь
Windows (под Wine `Z:\…` — корень Linux) или путь в папке игры (для
оригиналов под другим именем). `#` и `|` в путях недопустимы; такой путь
даёт ошибку при сборке, и «Играть» пишет в игру по-старому.

Сборку делает `doctor_toolkit::play::overlay::Overlay::build`:

1. **Зеркало игры** в `<кэш>/doctor-toolkit/overlay-<crc32 пути игры>`
   (`~/.cache`, `%LOCALAPPDATA%`): настоящие папки и символическая ссылка
   на каждый файл игры, вместе с `_doctor_toolkit` (рабочее пространство,
   резервные копии, менеджер модов); 3 751 ссылка — 0,5 с.
2. **Применение тем же кодом**, что пишет в игру: рабочее пространство
   (`Workspace::apply`; оно открывается из зеркала, своё `applied.json`
   пишет туда же) или включённые моды (`ModManager::apply`). Атомарная
   запись переименовывает новый файл поверх ссылки и никогда не пишет
   сквозь неё; архив подмен `.viv` становится `GODFATH0.viv` зеркала, а
   ссылки на архивы игры сдвигаются на номер вверх.
3. **Подмены** — разница зеркала и игры: файл, переставший быть ссылкой
   (поток, TOC, архив подмен, ролик, новый поток мода) → абсолютный путь в
   зеркале; ссылка на другой файл игры → путь в папке игры
   (`godfath1.viv|GODFATH0.viv`). Папки тулкита (`_doctor_toolkit`,
   `_toolkit`) не подменяются: игра их не читает.
4. `cmd.txt` старта сразу в уровень — файл рядом с зеркалом и подмена
   `cmd.txt` (в папку игры `cmd.txt` не пишется).

После выхода игры зеркало удаляется (`remove_dir_all` удаляет ссылки, не
то, на что они указывают); остаток прерванного запуска убирает следующий
запуск (`overlay::remove_stale`), `live uninstall` — тоже. Тест
`the_game_sees_what_applying_would_write_and_its_folder_stays` сравнивает
файл за файлом: то, что игра увидит через подмены, равно тому, что
старый путь записал бы в копию игры (замена ресурса, новый поток, запись
архива, ролик, `cmd.txt`), а папка игры — включая `_doctor_toolkit` — не
меняется ни на байт; `enabled_mods_of_format_2_are_staged` — то же для
мода формата 2 из менеджера модов.

**Когда используется** (`OverlayMode`: `auto` по умолчанию, `on`, `off`):
модуль собран, в папке игры есть ASI-загрузчик, `exe` проходит проверку
издания `edition::check_file`, под Wine `Z:` указывает на `/`. В `auto`
без этого — прежний путь (запись и откат) с объяснением почему; в `on` —
отказ.

### 14.4 Протокол 5

Запрос `Files` (вид 30) — ответ: перехваты стоят, ведётся ли журнал всех
открытий, число подмен, по каждой (до 4 096, сначала открытые — в порядке
первого открытия) путь, цель, сколько раз открыта и сколько открытий цели
не удалось, и сколько открытий файлов папки игры прошло без подмены.
Отвечается сразу, без главного потока. Клиент: `Client::files`,
`has_files` (с модулем протокола 4 и старше — нет подмен); CLI `live
files`; поддельный модуль отвечает списком своей настройки (каждая
открыта один раз).

### 14.5 Подмена отдельного ресурса по GUID

Поток пересобирается из оригинала со всеми заменами (как при записи в
игру), и модуль отдаёт игре файл целиком — замена одного ресурса по GUID
этим уже покрыта: на стенде мод заменил 15 текстур одного потока зоны и
добавил новый поток, а игра открыла пересобранный файл. Свой загрузчик,
подменяющий ресурс по GUID в памяти при загрузке потока (без пересборки
файла), не сделан: размеры и смещения ресурсов записаны в заголовках
потока и TOC, а таблица загруженных ресурсов `0x00421170` (этап 5) общая
для всех потоков — подмена после загрузки — та же горячая подмена этапа
35 (текстуры того же размера), а до загрузки — подмена файла, которая
теперь и есть. Открыто: подмена без копии потока для очень больших
потоков (самый большой изменённый поток копируется целиком, например
`gf2/globals_global.str` — 42 МБ).
