# Поведение классов SimGroup (этап 79, волна 1)

Что делают самые используемые классы логики и мира The Godfather II (PC
1.0.789.0): на какие сообщения реагируют, что и когда шлют, что делают на
тике, как читают свои атрибуты. Всё прочитано в коде `godfather2.exe`;
адреса — виртуальные.

Данные — `data/gf2/class_behavior.toml` (50 блоков: 45 классов и 5 общих
пакетов базовых атрибутов; 142 реакции обработчиков, 462 атрибута). Из них
`doctor-toolkit kb-gen` делает разделы «Поведение» и «Атрибуты по коду» в
заметках классов (`docs/kb/classes/`), имена атрибутов и направления
сообщений уходят в схему графа логики (`research/class_behavior.py schema` →
`data/gf2/logic_schema.toml`), виды `bool` и секунды — в
`data/gf2/attr_types.toml`. Прогон логики без игры (`docs/logic-graph.md`
§9) сверен с этими данными. Этот документ — как всё устроено и что найдено
общего; подробности каждого класса — в его заметке.

## 1. Как класс устроен в exe

- **Регистрация.** `0x00688AF0` зовёт `0x004833A0(хэш, имя, фабрика, размер)`
  для 299 классов, `0x00829B00` — ещё для трёх. Фабрика — «выделить память,
  вызвать конструктор».
- **Конструктор** зовёт конструктор базового класса и пишет в объект свои
  таблицы методов. У логических классов (база `0x0046C590`) их три: `+0x00`
  — объект (слот 0 — деструктор, **слот 1 — читатель атрибутов**), `+0x3C`
  — слушатель сообщений (**слот 1 — обработчик**, слот 2 `0x00461F30` —
  выключить слушатель), `+0x48`. У классов-сущностей мира таблиц больше
  (`+0x50`, `+0x54`, `+0x58`), а слот 50 главной таблицы — «касание
  физического объёма».
- **Читатель** `thiscall(объект, пакеты)` открывает пакет своего класса
  (`0x0043AFF0(пакеты, хэш)`) и обходит атрибуты по номерам; читатель
  наследника сначала зовёт читатель базы. Строка-сообщение хэшируется
  (`0x004DAFD0`), попадает в ручку (`0x00408260`), и, если объект должен её
  слышать, слушатель подписывается (`0x004084D0`, `0x00407E60`, `0x00473EC0`…).
- **Обработчик** `thiscall(слушатель, сообщение*)` сравнивает `*сообщение`
  с ручками и делает дело; `сообщение[1]` — слово данных.
- **Обновление.** Отдельного «метода обновления» у логических классов нет:
  кому нужен тик, тот подписывается на `iMsgRunningTick` /
  `iMsgRunningPreTick` / `iMsgRunningPostTick` (иногда только на время —
  `TriggerBase`, `HudIndicatorControl`). Сущности мира попадают в списки
  обновления (`EnterExitTrigger` — список `0x19`, функция `0x00900B80`).

Код классов читается скриптами `research/ghidra/` (без графического Ghidra,
на копии проекта): `ClassDump.java` по фабрике класса выписывает цепочку
конструкторов, таблицы методов со слотами и декомпилирует всё, что класс
переопределяет; `ReadMem.java` читает слова образа (секция данных на диске
зашифрована, таблицы методов берутся из проекта); `Callers.java`,
`FindConst.java`, `DecompAt.java` — как раньше. Сколько объектов какого
класса в игре — `research/class_usage.py`.

Адреса читателей и обработчиков в `class_behavior.toml` сверены с таблицами
методов: читатель — слот 1 таблицы `+0x00` класса, обработчик — слот 1
таблицы `+0x3C` (у `MessageRelay` в слоте переходник `0x0047AA70` на
обработчик базы `0x004CF8D0`); сверка — `research/class_behavior.py tables`
по выводу `ClassDump.java`.

## 2. Общие правила, найденные по дороге

1. **Незаписанный атрибут — это 0, а не значение конструктора.** Обход
   пакета (`0x0043AFF0` и хвост цикла в каждом читателе) отдаёт читателю и
   те атрибуты, которых в двоичном пакете нет (бит маски стоит): со
   значением 0 или пустой строкой. Читатель записывает этот 0 поверх того,
   что положил конструктор. Значение конструктора остаётся, только если у
   объекта нет самого пакета. Примеры: `TriggerBase` без атрибута 8 выключен
   (108 из 965 объектов), `MultiManager` без атрибута 1 не сработал бы ни
   разу (в игре атрибут записан у всех 9 639).
2. **Создаётся ли объект, решает менеджер, а не класс** (`0x00446BF0` из
   `0x00446340`): по атрибуту 0 пакета `Base` (флаги создания) и по
   фильтрам хранилища состояния. В двоичной записи объекта этот атрибут
   продублирован: бит 1 байта флагов `0x1C` — «у объекта есть пакет
   `Base`», байт `0x1D` — значение его атрибута 0. Проверено на всех
   111 518 объектах игры (`research/class_behavior.py corpus`, корпусный
   тест `the_second_flag_byte_of_an_object_is_its_base_attribute`).
3. **Хранилище состояния** (`*0x01223418`, ключ — GUID объекта). Перед
   сохранением оно рассылает `iMsgStoreEntity` (`0x0043D260`), после
   загрузки — `iMsgRestoreEntity` (`0x0043D450`). Классы с флагом «помнить»
   кладут туда записи: `MultiManager` — остаток срабатываний
   (`0x5E1F74A6`), `TriggerBase` — счётчик и включённость (`0x9BC8A380`),
   `VariableWatcher` — число срабатываний (`0x8C207D80`). Запись-метка
   `0x137726B7` значит «объект отработал»: фильтр создания `0x0043D650`
   больше не создаёт объект с такой меткой — ни после загрузки сохранения,
   ни при повторной загрузке потока. Её ставят `TriggerAuto` (бит 0
   флагов), `MultiManager` (счётчик дошёл до 0, бит 1 флагов),
   `MultiRemoveTarget` (бит 0 флагов — для удаляемых объектов),
   `TriggerBase` (счётчик дошёл до 0, бит со значением 8).
4. **«Отработал» — значит выключил слушатель.** `0x004088C0` /
   `0x00449E90` зовут слот 2 слушателя (`0x00461F30`: снять бит 0 слова
   `+0x40`) и подписывают объект на `iMsgDeleteEntity`. Так поступают
   `MultiManager` (счётчик 0), `TriggerAuto` (после отправки),
   `VariableSwitch` и `VariableWatcher` (переменной нет), `TriggerBase`
   (счётчик 0). Выключенный слушатель не получает сообщений без `force`.
5. **Слово данных.** `MultiManager` и `TriggerRandom` пересылают слово
   данных пришедшего сообщения; `TriggerAuto`, шлюзы, `VariableWatcher`,
   `VariableCombiner` кладут указатель на себя; триггеры — сущность,
   которая коснулась объёма; `MessageRelay` — объект атрибута 4 или 0.
   У `InterestingObject` в сообщениях 3 и 4 — персонаж, который объектом
   пользуется; у `SpawnPoint` в сообщении 6 — появившийся персонаж; у
   `FuncSpawn` в сообщении 1 — созданный объект.
6. **Переменные сюжета** живут в таблице `0x01223428`; создаёт переменную
   только `0x00442170` — его зовёт читатель `VariableOperator` при
   загрузке. `VariableSwitch`, `VariableWatcher`, `VariableCombiner` при
   первом обращении к несуществующей переменной выключаются (п. 4).

## 4. Что изменилось в понимании

- **`MultiManager`** (`0x0047A1C0`, читатель `0x0047A320`). Атрибут 1 —
  остаток срабатываний (`+0x60`; −1 — без конца; уменьшается, только пока
  больше 0; при 0 слушатель выключается). Атрибут 2 — флаги `u16`
  (`+0x5E`): бит 0 — одна пара на срабатывание, по кругу; бит 1 — помнить
  остаток в хранилище состояния; бит 2 — отложенные отправки ставятся в
  очередь с флагом 4 (переживают сброс очереди). В игре: атрибут 1 = −1 у
  9 015 объектов, 1 у 623, 9 у одного; атрибут 2 = 4 у 1 469.
- **`TriggerAuto`** (`0x00477EF0`). Подписка на `iMsgPostSpawnInitialize` —
  в конструкторе `0x00477DB0`, с приоритетом `0x7FFF` (а не `0x8000`, как
  почти везде); `0x00477DA0`, записанный раньше как «подписка», — переходник
  деструктора другого класса. Флаги (атрибут 2): бит 0 — после срабатывания
  ставится метка `0x137726B7` (настоящий «один раз на сохранение»; без неё
  объект срабатывает при каждой загрузке своего потока); бит 1 — флаг 4
  очереди. В игре встречается только значение 2 (85 объектов).
- **`TriggerBase`** (`TriggerBox`, `TriggerSphere`, `TriggerHurt`;
  `0x004C1260`, читатель `0x004C1550`) — **датчик касания, а не «вход и
  выход»**. Срабатывает на каждое сообщение физики о касании (слот 50), не
  чаще интервала атрибута 10 (секунды; 0,2 у 846 объектов). Атрибут 8 —
  флаги: 1 — включён при загрузке (без него выключен), 4 — различать
  направление, 8 — помнить состояние, `0x10` — порог скорости атрибута 11
  (мили в час). Атрибут 7 — не «выход», а сообщение касания против оси Z
  объёма (при флаге 4), с той же задержкой атрибута 5. Атрибут 9 = 1 —
  сработать один раз, когда сущность перестала касаться. Атрибут 6 — счётчик
  срабатываний (при 0 объект выключается). Кого пускать, решает пакет
  `TriggerFilter` (атрибут 0: по умолчанию 6 — игрок пешком или в машине).
  Сообщения 0 / 1 / 2 — переключить / включить / выключить.
- **`EnterExitTrigger`**: обработчик — `0x00900E20` (слот 1 таблицы
  слушателя `0x00D817D8`); прежний адрес `0x00900B30` лежит в деструкторе.
  Вход, выход и «внутри» считает обновление `0x00900B80`: выход 0 — вошёл,
  1 — вышел, 2 — «внутри», повторяется с периодом атрибута 3 (это период, а
  не задержка). Флаги — атрибут 6: 1 — включён при загрузке, 4 — учёт по
  сущностям, 8 — при выключении разослать «выход».
- **`MessageRelay`** (слот — переходник `0x0047AA70` → `0x004CF8D0` →
  `0x004CF950`). «Чёрных ящиков» нет: атрибут 4 — объект, который кладётся в
  слово данных (на получателя не влияет); получатель по убыванию
  приоритета — ответ отправителю (флаг базы), объект атрибута 3, группа
  движка по имени атрибута 2 (`GroupNPC`, `GroupVehicle`, `GroupDoors`… —
  таблица `0x0110ABA0`), иначе все. Бит 0 флагов базы — `force`.
- **`TriggerRandom`**: бросок берётся по сумме всех восьми весов, а тройка
  без сообщения пропускается — её вес и есть шанс «ничего не послать»
  (в игре таких объектов не меньше 18).
- **`AndEventGate`**: условия проверяются раньше `reset`, сравнение идёт
  после любого из них — шлюз без условий срабатывает на `reset`.
- **`VariableWatcher`**: предел срабатываний проверяется только при
  активации; **`VariableSwitch`**: атрибут 2 читателем не читается;
  **`VariableOperator`**: операция 3 прочитана (0 → 1, иначе → 0), операции
  больше 3 ничего не делают, `trigger_2` не делает ничего (14 объектов игры
  заданы только им и не работают).
- **Спавн.** `SpawnPoint` сам никого не создаёт: это место, которое
  записывается к заказчику (`NPCRequester`, атрибут 0 — его GUID);
  заказчик просит персонажей у очереди движка и расставляет их по свободным
  точкам. `FuncSpawn` создаёт объект по шаблону атрибута 2 на сообщение
  атрибута 0.
- **Реле** (`AttributeRelay` и наследники) действуют на три набора целей
  сразу: объект из данных сообщения (при флагах `0xA`), объект или список
  `EntityList` по GUID атрибута 2, именованная группа атрибута 1.
- **Потоки.** `StreamSet`: атрибут 0 грузит, атрибут 1 — выход «загружено»
  (за ним `iMsgStreamSetCommandComplete`), атрибуты 20–22 — вложенные
  наборы. `EnableDisableStreams`: до 4 потоков включить (атрибуты 2–5) и до
  10 выключить (7–16) одним сообщением; флаги 17 (обычное значение 6 — «не
  выгружать сразу»), удаление объекта отменяет его заявки.
  `ZoneStreamEnable`: коробка ±0,5 в осях объекта, ячейка сетки ищется один
  раз при чтении.
- **`CSystemCommands`**: из 46 мест кода, открывающих пакет, 45 берут
  только атрибут 1 (матрицу), читатель сущности `0x0046F500` — ещё атрибут
  4. Атрибуты 2 и 3 (в игре всегда 1) не читаются.

## 5. Деление значений на int, float, hash и bool

Вид значения по коду записан у каждого из 462 атрибутов
(`kind` в `class_behavior.toml`): `float` 89, `msg_in` и `msg_out` по 72,
`guid` 68, `int` 65, `flags` 33, `hash` 29, `enum` 13, `bool` 12, `string`
6, `vec3` 2, `matrix` 1. С видом, выведенным из файлов игры
(`data/gf2/simgroup_schema.txt`), расходятся четыре
(`research/class_behavior.py kinds`): `InterestingObject` 11 и
`SendStimulus` 3 — флаги со старшими битами, принятые за хэш;
`UIHudMiniMapMarker` 6 — цвет, принятый за хэш; `GenomeFilter` 8 — в файлах
float, в коде поле хранится как слово (использование не прочитано). 67
атрибутов в файлах игры не записаны ни разу — их вид известен только по
коду.

Догадки этапа 73 (`attr_types.toml`): из шести `bool` подтверждены кодом
четыре (`Destructible` 0, 3, 5; `Door` 4), два (не из разобранных классов)
остались догадками; ещё семь `bool` и шесть `seconds` добавлены по коду; две
догадки-ссылки сняты — код берёт любой объект, а не класс
(`MessageRelay` 3, `PlaySound` 5). Типы `money` — у классов этапа 75, здесь
не проверялись.

## 6. Прогон логики без игры

Что исправлено в модели (`crates/doctor-toolkit/src/logic_graph/run/`,
каждое закреплено тестом): начальное состояние триггеров берётся из флагов
(было «неизвестно»); `TriggerBase` — датчик касания: `exit:` у него шлёт
сообщение только в режиме атрибута 9, атрибут 7 не считается «выходом»,
счётчик атрибута 6 выключает объект; `TriggerRandom` оставляет вес пустой
тройки; `AndEventGate` проверяет условия раньше сброса; `VariableWatcher`
проверяет предел только при активации; `VariableSwitch` не берёт переменную
из атрибута 2; `MessageRelay` с атрибутом 4 больше не «чёрный ящик», с
группой (атрибут 2) — остаётся им (состав группы прогону неизвестен).

## 7. Что не выяснено

Полный список — в разделах «Что не выяснено» заметок классов. Главное:

- как часто физика зовёт «касание» для стоящей в объёме сущности — от этого
  зависит точный смысл режима «сработать при уходе» у `TriggerBase` и
  возможность ложного «выхода» у `EnterExitTrigger`
  (`docs/kb/questions/trigger-touch-frequency.md`);
- когда запись хранилища состояния попадает в файл сохранения и когда
  метка `0x137726B7` снимается (`docs/kb/questions/state-store-records.md`);
- очередь «управляемых сущностей» движка (`0x008F0BB0`, `0x008EBF00`,
  `0x008EADD0`) — там предел числа персонажей заказчиков и `FuncSpawn`;
- путь урона и гибели `Destructible` (базовый обработчик сущности
  `0x0046EFC0`), обновление двери `0x007968E0`;
- 115 имён атрибутов помечены `guess`: значение читается и хранится, а
  использование не найдено или не прочитано.

Что проверено в запущенной игре — `docs/analysis/game-bench.md` §41.
