# Проект: мод как папка исходников

Этап 36: работа с модом как с проектом движка —
ресурсы лежат файлами в обычных форматах по потокам, с понятными именами и
метаданными; **сборка** записывает в рабочее пространство только то, что
изменилось; из проекта собирается мод.

Код: `crates/doctor-toolkit/src/project/` (библиотека),
`crates/doctor-toolkit-cli/src/project_cmd.rs` (CLI `project …`),
`crates/doctor-toolkit-gui/src/app/project.rs` (вкладка **Project**),
`crates/doctor-toolkit-py/src/project.rs` (Python `Project`). Руководство —
глава 19.

Проект продолжает `unpack`/`pack` (`docs/navigation.md` §5) и внешние
редакторы (этап 22): те же преобразования и импортёры, но с постоянной
папкой, кэшем сборки, общими ресурсами, правками объектов поверх экспорта и
модом. Идеи раскладки взяты из рабочей папки конвертера другого редактора
(манифест на поток, `shared/` без дублей, отдельное дерево правок автора,
GUID новых объектов из имени) — только идеи, кода оттуда нет.

## 1. Папка проекта

```text
my_mod/
├── project.toml                    игра, издание, язык, зависимости, настройки
├── src/
│   ├── gf2/frontend.str/           папка потока: имя потока + .str
│   │   ├── stream.toml             манифест потока: ресурсы, файлы, метаданные
│   │   ├── tg4h/buttons.png        текстура (tg4h + tg4d)
│   │   ├── apx/frontend.apx        как есть
│   │   └── ffn/buttons.bin
│   ├── gf2/text/dd7d7050.str/
│   │   └── lh2/9e583c54.json       таблица строк
│   └── mp_rooftops/mp_rooftops.str/
│       ├── mesh/door_01.glb        модель (mesh + meshvolatile)
│       ├── simgroup/00000004.json  игровая логика
│       ├── graph/1a2b3c4d.json     навигационный граф (документ, этап 42)
│       ├── rcb/5e6f7a8b.bin        данные …
│       └── rcb/5e6f7a8b.view.json  … и просмотр только для чтения
├── shared/                         ресурсы, одинаковые в нескольких потоках
│   ├── shared.toml
│   └── tg4h/brick.png
├── patches/                        правки объектов SimGroup автором (§5)
│   └── mp_rooftops/mp_rooftops.str/simgroup/00000004.toml
├── .doctor/
│   ├── base/                       данные, на которые накладываются строки и логика
│   └── build.json                  кэш сборки (можно удалить)
└── .gitignore                      исключает .doctor/build.json
```

- Папка потока — путь потока с `.str` на конце (`src/gf2/cuba.str`,
  дочерний поток — `src/gf2/cuba/local.str`): папки типов внутри не
  спорят с дочерними потоками.
- Имя файла — `<тип>/<имя>.<расширение>`: имя ресурса из индекса игры
  (`docs/navigation.md` §1), иначе id (`ids[3]` или четыре id через точку);
  при совпадении имён добавляется id, затем номер ресурса.
- В `shared/` уходит ресурс (или текстура, модель), который в двух и более
  выбранных потоках имеет те же тип, ids, политику памяти и данные; файл
  один, ключей — по одному на каждый поток. Правка такого файла собирается
  во все потоки. Отключается `shared = false` (`--no-shared`).
- Всё, кроме `.doctor/build.json`, стоит хранить в системе контроля версий.

## 2. `project.toml`

```toml
format = 1

[project]
name = "HQ Billboards"
id = "hq-billboards"        # id мода; от него зависят GUID новых объектов
version = "1.0"
author = "me"
description = ""
url = ""

[game]
path = "/games/The Godfather II"    # каталог игры на этом компьютере (--game меняет)
profile = "The Godfather II (PC)"
edition = "PC 1.0.789.0 (build of 2009-10-05)"
executable_sha256 = "31f579a8…"    # другой exe — предупреждение
language = "English"                # первый язык из text/localetable.txt

[dependencies]
mods = ["other-mod"]                # нужны установленными и включёнными

[build]
workspace = "…"     # куда собирать; нет — рабочее пространство игры
textures = "png"    # png или dds (кубические и объёмные — всегда DDS)
models = "glb"      # glb, fbx, obj, usd, usda, usdc, usdz
shared = true
```

`format` больше поддерживаемого — отказ; неизвестный формат моделей —
понятная ошибка. `project status` и сборка предупреждают о другом
исполняемом файле и о модах из `dependencies`, которых нет или которые
выключены в менеджере модов.

## 3. Манифесты и метаданные ресурса

`stream.toml` (у `shared/` — `shared.toml` без `stream`):

```toml
format = 1
stream = "gf2/text/dd7d7050"

[[resource]]
name = "9e583c54"                 # имя из индекса или id
kind = "strings"                  # вид (§4)
type = "lh2"                      # тег типа главного ресурса
ids = "9e583c54"                  # его четыре id (GUID в потоке)
policy = "default"                # политика памяти
files = ["lh2/9e583c54.json"]     # файлы; первый — главный, он же id записи
keys = ["gf2/text/dd7d7050:lh2:9e583c54"]   # ресурсы, в которые собирается
exported = "efb31843…"            # отпечаток файлов при создании
base = "4b5bd52e…"                # SHA-256 данных из .doctor/base (строки, логика)
```

Идентификатор записи — путь главного файла от корня проекта
(`src/gf2/text/dd7d7050.str/lh2/9e583c54.json`); так её называют `status`,
ошибки сборки и `--only`.

## 4. Виды ресурсов и круговой путь

«Круг» — распаковать в проект → изменить файл → собрать → игра читает.
Последний столбец — что проверено в игре раньше (этапы 18, 24 и др.), а не
в этом этапе: игру этап 36 не запускал.

| Вид (`kind`) | Типы | Файлы | Сборка | Неизменённый файл, собранный заново (`--force`) | В игре |
|---|---|---|---|---|---|
| `texture` | `tg4h` + `tg4d` | PNG (первая поверхность), DDS для кубических и объёмных или с `textures = "dds"` | `import_texture` (как `texture-import`) | **другие данные**: картинка кодируется в DXT заново | да (`texture-import`, `game-bench.md` §13) |
| `strings` | `lh2` | JSON как `text-export` | строки накладываются на базу | те же данные | да (новая строка, этап 18) |
| `logic` | `simgroup`, `metamodel`, `variabledictionary`, `partsdb` | JSON как `logic-export` | `logic_import::apply_json` на базу, затем патч SimGroup (§5) | те же данные | да (SimGroup и metamodel, этап 24; `partsdb`, этап 17) |
| `document` | `dlg`, `chv`, `trinity_seq_master`, `graph` | JSON всего документа | разбор JSON → запись (`to_bytes`); при создании проверяется, что документ пишется побайтно, иначе — `raw` | те же данные; у `graph` сборка приводит длины рёбер, R-дерево и таблицу путей к правке (`formats/navigation-graph.md`) | ролики — этап 29; диалоги — отложено; `graph` — этап 45 |
| `script` | `lua` | исходник Lua 5.0 (декомпиляция) | компиляция с числами float32 и именем исходного чанка | без изменений или иная отладочная информация; скрипт, чья декомпиляция компилируется в другой код, остаётся `raw` (`.luac`) | да (этап 28) |
| `model` | `mesh` + `meshvolatile` | glTF (`.glb`), FBX, OBJ, USD; текстуры рядом в `<имя>_textures/` | `import::model::plan` поверх меша (как `model-import`) | **другие данные**: меш строится заново | да (этап 24) |
| `animations` | `bnk` | данные `.bin` и события клипов `.events.json` | данные из `.bin`, события изменённых клипов — `BankImage::set_events` | те же данные | события — не проверялись |
| `view` | `rcb`, `mobface` | `.view.json` рядом с `.bin` | не собирается; правка — предупреждение, править `.bin` | — | — |
| `raw` | всё остальное: `apx`, `hkx`, `material`, `vfx`, `wgi`, `ffn`, `sbk`, `smb`, `tob`, `covernodetable`, `treemodel`, `rcb`, … | распакованные данные (`.bin`, `.apx`, `.luac`) | запись данных как есть | те же данные | по типу |

Числа на корпусе (тест `a_project_builds_only_what_changed_and_as_a_direct_import_would`,
семь потоков, 713 ресурсов): 476 записей — 78 текстур, 2 таблицы строк,
34 логики, 18 документов, 30 моделей, 15 банков анимаций, 8 просмотров,
291 `raw`; ни одно преобразование не откатилось в `raw`. Принудительная
сборка всех 468 записей прошла без ошибок; те же данные дали все строки,
логика, документы, события анимаций и `raw`; текстуры и модели — другие
(перекодирование), поэтому сборка без `--force` неизменённые файлы не
трогает.

**Не замкнуто в этом этапе** (остаётся `raw` или только просмотр):

- `covernodetable` — записи разобраны (`points.rs`), но писателя нет; та же
  правка на месте — после проверки, что точки не дублируются в другом месте;
- `treemodel` — формат разобран (`formats/treemodel.md`), читатель пишет обратно побайтно, но в проекте модель дерева пока хранится как `.bin`;
- звуковые банки `sbk` как WAV — импорт звука есть (`sound-import`), но
  перекодирование неизменённых звуков при сборке банка целиком — не сделано;
  банк — `raw`;
- события анимаций замкнуты по данным (`set_events`), в игре не
  проверялись; клипы анимаций — через `anim import`, не через проект;
- новые ресурсы (файл, которого нет в манифесте) не добавляются — они
  показываются как «не входит в проект»; удаление ресурса — ошибка записи.

## 5. Правки объектов поверх экспорта (`patches/`)

Экспортированный JSON SimGroup — снимок; свои изменения автор может вести
отдельно, в `patches/<поток>.str/simgroup/<имя>.toml`:

```toml
[[object]]
guid = "0102030405060708434852495354…"   # или name = "door_01" (CMD_SetName)
position = [10.0, 0.0, -4.5]
rotation = [0.0, 90.0, 0.0]               # градусы вокруг X, Y, Z
scale = [1.0, 1.0, 1.0]
set = { "Entity.CMD_SetModel" = "2f4fcbd4", "NPC.18" = "" }   # пустое — по умолчанию

[[new]]
name = "doctor_lamp_1"      # имя объекта, из него — GUID
copy = "lamp_02"            # шаблон: имя или GUID объекта группы
position = [12.0, 0.0, -4.5]
```

- Патч накладывается при каждой сборке на результат JSON, по объекту;
  изменение патча — изменение записи (входит в её отпечаток).
- Запись `[[object]]`, чьего объекта больше нет в группе (игра или JSON
  изменились), — **предупреждение**, остальное применяется; так же —
  шаблон `[[new]]`, которого нет. Ошибка значения или атрибута — ошибка
  записи с путём патча.
- Новый объект — копия шаблона с именем (`CMD_SetName`, если у шаблона он
  есть) и **GUID из имени**: канонический NeoGuid тулкита
  (`resource::neoguid`, машина `XDOCTORTKX`, `docs/formats/simgroup.md` §5)
  для текста `<id мода>:simgroup:<ids группы>/<имя>`. Та же группа и то же
  имя дают тот же GUID на каждой сборке, поэтому ссылки на объект
  (сообщения, `-playerspawn`) переживают пересборку; занятый GUID —
  следующая попытка `neoguid::new_guid`. В заметках сборки — GUID и его
  текст (`XDOCTORTKX_…_…_v3`). Python: `project_object_guid(scope, name)`.

## 6. Создание

```sh
doctor-toolkit project new "$GAME" my_mod --stream gf2/frontend --stream gf2/text/dd7d7050 \
    [--type tg4h]… [--name NAME] [--id ID] [--author A] [--dds] [--model-format fbx] \
    [--no-shared] [--no-index] [--workspace-dir DIR]
doctor-toolkit project new "$GAME" my_mod --from-workspace     # из рабочего пространства
```

- Источник данных — версия рабочего пространства: его правка ресурса или
  оригинал игры (из резервной копии, если файл игры уже переписан).
- `--from-workspace` берёт ресурсы, которые рабочее пространство заменяет
  (с парами текстур и моделей); добавленные ресурсы и новые потоки в
  проект не входят.
- Папка должна быть новой или пустой; второй проект в той же папке — отказ.
- Кэш сразу записывает состояние рабочего пространства, поэтому только что
  созданный проект — «без изменений», и сборка ничего не делает.

## 7. Состояние и сборка

```sh
doctor-toolkit project status [ПАПКА] [--all] [--game DIR] [--workspace-dir DIR]
doctor-toolkit project build  [ПАПКА] [--only ПУТЬ]… [--force] [--dry-run] [--apply]
doctor-toolkit project pull   [ПАПКА] [ПУТЬ]…
doctor-toolkit project mod    [ПАПКА] -o mod.zip [--preview pic.png] [--build]
```

Состояние записи:

| Состояние | Когда | Сборка |
|---|---|---|
| `unchanged` | файлы как при создании, рабочее пространство — как тогда | нет |
| `modified` | файлы (или патч) изменились после последней сборки | да |
| `built` | изменённые файлы собраны, рабочее пространство держит результат | нет |
| `out of sync` | файлы собраны, но в рабочем пространстве теперь другое (отмена, откат, правка в редакторе) | да: возвращает версию проекта; `pull` — наоборот, берёт версию рабочего пространства в файлы |
| `missing` | нет файла | ошибка записи |
| `view changed` | изменён просмотровый файл | нет, предупреждение |

Как определяется «изменилось»:

- **Отпечаток входов** записи — SHA-256 от путей и SHA-256 её файлов и
  патча. Файл читается заново, только если изменились его размер или время
  (и не в пределах 2 с от прошлого хэширования — защита от правки в ту же
  метку времени), иначе хэш берётся из `.doctor/build.json`.
- **Отпечаток результата** — SHA-256 данных каждого ключа записи (и
  ресурсов, которые её сборка добавила или изменила, например материалов
  модели) в рабочем пространстве после сборки; `null` — ресурс не изменён.
- Запись собирается, если отпечаток входов не равен записанному или
  рабочее пространство держит не то, что записала прошлая сборка. Без кэша
  (удалён) запись, чьи файлы равны `exported`, считается неизменённой.

Сборка:

1. Все записи к сборке собираются по очереди; каждая — своими импортёрами
   (§4) в **рабочее пространство**, не в игру. Ошибка одной записи —
   сообщение `путь: ошибка`, остальные собираются; запись с ошибкой
   остаётся `modified`.
2. Все операции сборки склеиваются в одну (`Workspace::squash`, «Build
   project NAME (n file(s))»): одна отмена убирает всю сборку. Сборка без
   изменений операции не создаёт и рабочего пространства не заводит.
3. Строки и логика накладываются на **базу** — данные ресурса при создании
   проекта (`.doctor/base/`), поэтому результат зависит только от файлов,
   а не от прошлых сборок, и повторная сборка даёт те же данные.
4. `out of sync`-запись, чья прошлая сборка оставила ресурсы без изменений
   (`null`), не собирается заново, а **откатывается** в рабочем
   пространстве: так возвращаются точно исходные данные, без
   перекодирования картинки.
5. После сборки отпечатки результата обновляются у всех записей, чьи ресурсы
   она затронула.
6. `--apply` после сборки пишет рабочее пространство в игру
   (`workspace apply`); «Играть» и моды берут сборку оттуда же.

`--force` собирает все записи (кроме просмотров), даже неизменённые: для
замера и проверки; текстуры и модели при этом получают перекодированные
данные (§4).

**Скорость** (корпусный тест, release, 7 потоков, 713 ресурсов, 476 записей,
23 МиБ файлов): создание — 1,0 с; состояние — 0,03–0,05 с; сборка без
изменений — 0,03–0,06 с; сборка четырёх изменённых файлов (текстура, строка,
SimGroup, модель; с построением индекса ресурсов для модели) — 0,33–0,51 с;
полная сборка всех 468 записей — 12–15 с (почти всё — перекодирование 78
текстур и 30 моделей).

**Совпадение с прямым импортом** (тот же тест): после правки текстуры
(PNG), строки (JSON), SimGroup (положение объекта в JSON) и модели (glb со
сдвинутыми вершинами) сборка затрагивает ровно эти записи, а данные всех
изменённых ресурсов совпадают с тем, что дают в чистом рабочем пространстве
`import_texture`, импорт JSON внешнего редактора, `logic_import` и
`model-import` тех же файлов.

## 8. Мод из проекта

`project mod -o mod.zip` (GUI — **Build mod…**, Python — `build_mod`)
пишет мод формата 2 (`docs/mods.md`) из изменений рабочего пространства,
которые принадлежат проекту: ключи записей и ресурсы, добавленные их
сборкой (`mods::build_from_workspace` с выбором ключей). Метаданные — из
`[project]`. Версия манифеста — наименьшая нужная (1 без добавленных
ресурсов, 2 с ними). Без сборки мод пуст — отказ «build it first»;
`--build` сначала собирает.

## 9. GUI

**Tools → Project browser** (палитра команд — «Project»), вкладка
**Project**:

- без проекта — **Open project…** и форма **New project** (потоки через
  запятую или «из изменений рабочего пространства», папка — диалогом);
- дерево: папки потоков и `shared`, внутри — типы, внутри — файлы с цветной
  меткой состояния; папки и типы с изменениями раскрыты; поиск по пути,
  имени и типу, флажок «только изменённые», счётчики состояний;
- справа — запись: тип, ids, политика, файлы, патч, ключи (щелчок открывает
  ресурс), **Open in external editor** (программа из настроек этапа 22 по
  виду файла: картинка, модель, текст), **Open resource**, миниатюра PNG
  текстуры;
- **Build (n)** — собрать изменённое в рабочее пространство редактора (одна
  операция, Ctrl+Z отменяет), **Build all**, **Build mod…**, **Refresh**,
  **Show folder**; состояние файлов перечитывается раз в 2 с и после
  каждой правки рабочего пространства.

GUI собирает в рабочее пространство открытой игры (по умолчанию); проект
