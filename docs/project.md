# Проект: мод как папка исходников

Этап 36: работа с модом как с проектом движка —
ресурсы лежат файлами в обычных форматах по потокам, с понятными именами и
метаданными; **сборка** записывает в рабочее пространство только то, что
изменилось; из проекта собирается мод.

Код: `crates/doctor-toolkit/src/project/` (библиотека),
`crates/doctor-toolkit-cli/src/project_cmd.rs` (CLI `project …`),
`crates/doctor-toolkit-gui/src/app/project.rs` (вкладка **Project**),
`crates/doctor-toolkit-py/src/project.rs` (Python `Project`). Руководство —
глава 19.

Проект продолжает `unpack`/`pack` (`docs/navigation.md` §5) и внешние
редакторы (этап 22): те же преобразования и импортёры, но с постоянной
папкой, кэшем сборки, общими ресурсами, правками объектов поверх экспорта и
модом. Идеи раскладки взяты из рабочей папки конвертера другого редактора
(манифест на поток, `shared/` без дублей, отдельное дерево правок автора,
GUID новых объектов из имени) — только идеи, кода оттуда нет.

## 0. Проект как документ редактора (этапы 106–108, 111)

С этапа 106 проект — ещё и **документ редактора**: папка со своим рабочим
пространством. Правки и их история лежат в ней, отдельно от папки игры и от
других проектов; работа над двумя модами — два проекта. Исходники (`src/`,
§1) такому проекту не обязательны: он наполняется правками в редакторе, а
исходники всего, что держит его рабочее пространство, пишутся в любой
момент (`project sources`, кнопка **Write sources**, §7.1) — вместе с
ресурсами, которые мод добавляет, и потоками, которые он создаёт.

```text
my_mod/
├── project.toml        [build] workspace = "workspace"; база [base] (§0.2); наборы зон [[zones]]; пути к игре в нём нет
├── workspace/          manifest.json, log.json, payloads/ — правки и история
├── .doctor/local.toml  game = "/games/The Godfather II" — путь на этой машине
├── .doctor/editor.json что редактор показывал в прошлый раз: зоны уровня, камера (этап 113)
├── .gitignore          local.toml, editor.json, applied.json, lock, staged/, кэш сборки
└── src/ shared/ patches/   исходники (§1) — по желанию автора
```

Код: `project/document.rs` (`create_document`, `LocalSettings`,
`EditorState`, `Project::game_path`, `adopt_workspace`), редактор —
`app/document.rs`, `app/zone_sets.rs`.

**В редакторе** (меню File):

| Команда | Что делает |
|---|---|
| New project… | папка (новая или пустая, её имя — имя проекта) → пустой проект открытой игры, сразу открыт |
| Open project…, Recent projects | открыть проект: его игра открывается сама, если открыта другая или никакая; проект без известного пути к игре берёт открытую игру и запоминает её |
| Make a project of the workspace… | рабочее пространство игры — правки и история — переезжает в новый проект (`adopt_workspace`); отказ, пока правки записаны в игру: сначала **Revert game** |
| Install project into Mods | проект ставится в менеджер модов игры как мод (§0.1); доступна, когда у проекта есть правки |
| Take the base from the mods in the game | моды, записанные менеджером в игру, становятся базой проекта — `[base]` в `project.toml` (§0.2) |
| Bring the mods to the project's base | нынешняя расстановка модов сохраняется набором, моды базы включаются в её порядке и записываются в игру (§0.2); доступна, когда моды игры — не база и все моды базы установлены |
| Close project | игра остаётся открытой со своим рабочим пространством |

Имя проекта — в заголовке окна и в строке состояния; недавние проекты — на
Welcome; при запуске редактор открывает проект, который был открыт последним
(если включено «открывать последнюю игру»). Вкладка Project (§9) показывает
открытый проект. `DOCTOR_TOOLKIT_GUI_OPEN_PROJECT=<папка>` открывает проект
без рук.

**Проект в файлы игры сам не пишется** — ни редактором (Apply to game и
прямой режим для проекта недоступны), ни его рабочим пространством из
любой другой программы (§0.1). В игру он попадает как мод менеджера модов.
У файлов игры поэтому один владелец, кроме рабочего пространства самой
игры, — менеджер модов, и два проекта за них не спорят.

**Наборы зон и состояние редактора** (этап 113, `docs/levels.md` §13).
Наборы зон, сохранённые в панели Zones при открытом проекте, — его:
таблицы `[[zones]]` в `project.toml` (§2), они едут вместе с проектом. То,
что редактор уровня загрузил в прошлый раз, и место камеры — состояние
одного компьютера: `.doctor/editor.json` (`project::EditorState`), вкладка
уровня открывается с ним. Файл исключён `.gitignore` проекта; у проекта,
созданного до этапа 113, строка добавляется при первой записи файла (если
`.gitignore` — тот, что написал тулкит). Ключи, которых эта версия не
знает, в файле сохраняются. Без проекта то же лежит в настройках редактора
для игры.

```json
{
  "zones": ["preset:gf2/miami/bonita", "preset:gf2/miami/bonita:missions"],
  "camera": { "eye": [-402.5, 31.0, 512.0], "yaw": 0.6, "pitch": -0.4 }
}
```

**Мод проекта** со своим рабочим пространством — все его изменения
(`Project::changed_keys`): и собранные из файлов, и сделанные в редакторе.

**Командная строка, Python, MCP** работают с рабочим пространством проекта,
как раньше: `project …` читает `[build] workspace`, команды правки берут
`--workspace-dir <проект>/workspace`, сервер MCP — `--project`. С этапа 112
пустой проект создаётся и вне редактора: `doctor-toolkit project new GAME
DIR` без `--stream` и `--from-workspace`, `Project.create(game, path,
empty=True)`, инструмент `project_new` без `streams` и `from_workspace`.
Перенос рабочего пространства игры в проект — `doctor-toolkit project new
GAME DIR --move-workspace` (§6); у сервера MCP его нет намеренно: сервер
работает с тем рабочим пространством, с которым запущен.

Тесты: `project/tests.rs` (`a_document_project_has_its_own_workspace_and_no_sources`,
`the_workspace_of_the_game_moves_into_a_project`,
`zone_sets_and_the_editor_state_of_a_project`), редактор без окна —
`app/document_tests.rs` (проект — документ; проект открывает свою игру;
рабочее пространство игры становится проектом; проект не пишется в игру;
проект играется и ставится как мод) и `app/zone_sets_tests.rs` (наборы зон
проекта и игры; вкладка уровня открывается с загруженным в прошлый раз).

### 0.1 Проект в игре — через менеджер модов (этап 107)

Код: `play/overlay.rs` (`Source::Project`), `project/document.rs`
(`Project::install_into`, `project_of_workspace`), `workspace/mod.rs`
(`Owner`), `mods/manager.rs` (`Payloads`, `install_workspace_with`),
`mods/lock.rs`; редактор — `app/play.rs`, `app/document.rs`
(`install_document`).

| Что | Как |
|---|---|
| **Играть** в редакторе | проект со своим рабочим пространством играется только через оверлей (`docs/shell.md`; издание 1.0.789.0, собранный модуль, загрузчик ASI) и всегда со своими правками. Источник оверлея — `Source::Project(папка проекта)`: в подготовленной копии игры менеджер модов **копии** ставит проект последним модом и пишет моды в копию (`docs/mods.md` §4). Игра показывает «включённые моды и проект поверх» — и когда моды записаны в файлы игры (до этапа 107 оверлей проекта там отказывал), и когда только включены. Папка игры и реестр менеджера не меняются |
| «Играть» без оверлея | недоступно: кнопка называет причину (нет модуля, нет загрузчика ASI, другое издание) и путь через установку. На время игры в папку игры ничего не пишется (решение владельца) |
| **File → Install project into Mods**, `doctor-toolkit project install ПРОЕКТ [--build]` | `Project::install_into`: мод с id, именем, версией и автором из `project.toml`, включённый, последний в порядке загрузки; стоял раньше — обновляется и снова встаёт последним. Редактор открывает окно Mods на этом моде. В файлы игры мод попадает при записи модов (**Apply to game** окна Mods, `mods apply`). Раздел сборки окна Mods при открытом проекте заполнен данными проекта, поэтому его **Install as mod** ставит тот же мод |
| `workspace apply`, прямой режим, `project build --apply`, инструмент `apply` | отказ с сообщением, как проект попадает в игру (`docs/workspace.md` §4): отметка `owner = "project"` в манифесте рабочего пространства |
| `play GAME --workspace-dir ПРОЕКТ/workspace`, `live install --apply --workspace-dir …`, инструмент `play` сервера MCP | `Source::of_workspace`: рабочее пространство проекта идёт как `Source::Project`, любое другое — как раньше |

Зависимости мода проекта (`Project::mod_of`): у проекта с базой (§0.2) —
моды базы с её условиями на версии и больше никакие; без базы — моды из
`[dependencies] mods` (условие `*`) и моды, записанные в игру, на данных
которых сделаны правки (`mods::add_suggested_dependencies`: зависимость
`>=версия`). В обоих случаях данные зависимости, которые проект заменяет,
становятся в моде оригиналом ресурса (`made_on`): проект, меняющий ресурс
базового мода, сверяется с данными этого мода и выигрывает у него как патч
(`docs/mods.md` §3.3).

Проверка в игре на стенде — `docs/analysis/game-bench.md` §51: проект,
отданный подменами поверх базового мода, записанного в файлы игры; в памяти
игры — то же, что после записи обоих модов менеджером; папка игры после
сеанса побайтно прежняя.

Что остаётся за автором:

- **Мод проекта, записанный в игру, — уже не база.** После «Install project
  into Mods» и записи модов редактор читает файлы игры вместе с этим модом.
  Правки по-прежнему записываются против оригинала игры (резервной копии), и
  «Играть» показывает нынешнее состояние проекта — установленное заменяется
  в копии. Но ресурс, правку которого вы убрали из проекта, в окне редактора
  останется изменённым, пока мод записан: верните оригиналы или выключите
  мод проекта в окне Mods. У проекта с исключающей базой это расхождение
  называет полоса вверху окна (`OwnMod`, §0.2), и «Привести моды к базе
  проекта» выключает мод проекта вместе с остальными лишними.
- **Ролики** (`file:movies/…`) мод не несёт (`docs/mods.md` §1.5): «Играть»
  их показывает (оверлей кладёт их в копию файлами), установленный мод — нет.
- Пока в игру записано рабочее пространство самой игры, менеджер копии
  отказывает, как и настоящий (`docs/mods.md` §4): сначала **Revert game**
  без проекта.

**Замер** (`tests/corpus/project.rs`,
`a_large_project_is_installed_as_a_mod`; сборка `release`, игра 1.0.789.0
через ссылки, временные папки в домашнем каталоге с шифрованием eCryptfs,
один компьютер): проект с правкой самого большого ресурса в каждом из 483
потоков `gf2/cuba/` (411 МБ файлов потоков, 184 МБ новых данных, 107 МБ в
317 разных файлах данных).

| Что | Копирование данных (до оптимизации) | Ссылки и повторное использование (как сейчас) |
|---|---|---|
| «Install project into Mods», первый раз | 5,6 с | 4,1 с |
| то же ещё раз, проект не менялся | 6,0 с | 0,37 с |
| то же после правки ещё одного ресурса | 5,7 с | 0,38 с |
| подготовленная копия для «Играть», проект как мод, пересборка потоков | 26,5–27,9 с; 956 МБ в 1 287 файлах | 15,4–15,8 с; 849 МБ в 970 файлах |
| то же, заплатки ресурсов (этап 100) | 14,8–15,8 с; 291 МБ в 804 файлах | 7,35–7,43 с; 184 МБ в 487 файлах |
| для сравнения: одно рабочее пространство, как до этапа 107 (пересборка / заплатки) | 19,4–21,7 с / 8,9–11,0 с | 14,9–17,0 с / 6,4–6,8 с |

Два столбца — два прогона теста в разное время; строка «для сравнения» в
них делает одно и то же и показывает разброс между прогонами (в первом
машина была занята ещё и сборкой), поэтому сравнивать стоит строки внутри
столбца. Вывод: установка копированием стоила проекту 5–7 с на каждое
«Играть» и на каждую повторную установку — почти всё уходит на запись 317
файлов с `fsync` каждого. Поэтому:

- в подготовленной копии данные мода проекта — **символические ссылки** на
  файлы `payloads/` рабочего пространства проекта (`Payloads::Linked`):
  ничего не копируется, и «Играть» с проектом стоит столько же, сколько
  раньше с рабочим пространством (в пределах разброса: +0,6–1 с с
  заплатками — открытие менеджера копии, установка и сверка мода);
- при установке в менеджер игры (`Payloads::Copied`) данные, которые уже
  есть у прежнего состояния этого мода, не копируются: файл данных назван
  хэшем содержимого и не переписывается, поэтому в новую папку мода он
  попадает жёсткой ссылкой. Первая установка по-прежнему копирует всё: мод
  в менеджере не должен зависеть от папки проекта.

### 0.2 База проекта (этап 108)

Редактор читает файлы игры, поэтому проект сделан на том, что менеджер
модов **записал в игру**, пока автор работает. До этапа 108 это
подразумевалось: «что стоит, на том и сделано». База называет это в
`project.toml` (§2):

```toml
format = 2

[base]
exclusive = true            # в игре стоят только эти моды

[[base.mod]]
id = "new-new-york"
version = "^1.1.0"          # с какими версиями проект согласен работать
built_on = "1.1.0"          # на какой версии сделан
sha256 = "3f6c…"            # хэш манифеста этой версии
```

Код: `project/base.rs` (`Base`, `BaseMod`, `BaseDifference`,
`Base::record`, `differences`, `arrangement`, `bring`;
`ProjectConfig::base_differences`, `check_base`, `record_base`,
`mod_dependencies`), `project/config.rs` (`BASE_FORMAT`, `write_base`),
`mods/manager.rs` (`ModManager::in_game`, `arrange_and_apply`,
`free_set_name`), `mods/mod.rs` (`ModManifest::sha256`, `add_made_on`);
редактор — `app/document.rs` (`BaseBar`), окно Mods —
`ModsPanel::bring_to_base`.

| Поле | Смысл |
|---|---|
| `exclusive` | `true`: в игре стоят только моды базы — любой другой включённый мод считается расхождением, а «привести к базе» его выключает. `false` (и когда поля нет): рядом с базой могут быть включены другие моды |
| `[[base.mod]]` | моды базы **в порядке загрузки** |
| `id` | id мода |
| `version` | условие на версию (`docs/mods.md` §1.3), с которым мод проекта зависит от этого мода; нет поля — `*` |
| `built_on` | версия, на которой проект сделан; для сведения и для сообщений |
| `sha256` | SHA-256 манифеста этой версии, как его пишет программа (`ModManifest::sha256`: манифест называет каждый файл данных по хэшу, поэтому две сборки одной версии с разными данными различаются). Нет поля — не сверяется |

**Формат.** `project.toml` с разделом `[base]` записывается с `format = 2`:
программа до этапа 108 неизвестные таблицы пропускает и открыла бы такой
проект как сделанный на чистой игре, а мод собрала бы без зависимостей —
молча. Версию 2 она отвергает («has format 2; this tool reads up to 1»).
Проект без базы по-прежнему пишется с `format = 1` и побайтно так же, как
раньше (тест `a_project_without_a_base_is_written_as_before` сравнивает с
записью прежней структурой). `ProjectConfig::write_base` меняет в файле
только таблицы базы и строку `format`; остальной текст и комментарии автора
остаются.

**Запись базы** — только по команде автора: **File → Take the base from the
mods in the game**, кнопка в полосе, `project base --record`
(`ProjectConfig::record_base`, `Base::record`). В базу идут включённые моды,
которые менеджер **записал в игру** (`ModManager::in_game`), в порядке
загрузки, кроме мода самого проекта; `built_on` и `sha256` — нынешние,
`version` — `^<built_on>` (в пределах старшей версии; для версии, которая не
читается как semver, — `*`). Включённый, но не записанный мод в базу не
попадает и называется: редактор показывает игру без него. При повторной
записи условие, написанное автором, остаётся, если версия в игре под него
подходит, и `exclusive` остаётся как был; первая запись даёт `exclusive =
true`. Проект, созданный или открытый на игре с записанными модами и без
базы, получает **предложение** записать их (полоса: «Record them as the
project's base», «Not now»); сама база не записывается никогда.

«Мод записан в игру» (`ModInGame::written`): мод включён, и по записи
менеджера (`applied.json`) и состоянию файлов каждый его ресурс и файл
архива лежит в игре с его данными — или с данными включённого мода, который
выигрывает этот ресурс, — а каждый созданный им поток существует. Мод,
ожидающий записи в тот же поток, чужой записанности не отменяет. Исполняемый
код в расчёт не входит: это не данные, которые читает редактор.

**Сверка** (`Base::differences` → `Vec<BaseDifference>`) — при открытии
проекта, раз в 2 секунды по изменению `project.toml`, `registry.json` и
`applied.json`, после каждой записи модов окном Mods, перед **Play** и при
**Install project into Mods**; в командной строке — `project base`, `project
status` и сборка (`Project::game_warnings`), в MCP — `warnings` инструмента
`project_status`.

| Расхождение | Когда | «Привести» убирает |
|---|---|---|
| `NotInstalled` | мод базы не установлен | нет: его надо установить |
| `Disabled` | установлен, но выключен (или повреждён) | да |
| `NotWritten` | включён, но в файлах игры его нет | да |
| `Version` | версия не подходит под `version` | нет |
| `Changed` | версия подходит, но хэш манифеста не равен `sha256`: **база изменилась с тех пор, как на ней сделан проект**. Предупреждение; правки, сделанные на прежних данных мода, находит и переносит перебазирование (§0.3) | нет: решает автор — вернуть прежнюю сборку мода или записать базу заново |
| `Order` | включённые моды базы загружаются в другом порядке | да |
| `Extra` | `exclusive`: включён мод не из базы (записан он или нет — сказано) | да |
| `OwnMod` | `exclusive`: мод самого проекта записан в игру — редактор показывает игру с его установленным состоянием | да |
| `Leftover` | `exclusive`: в файлах игры остались ресурсы выключенных или удалённых модов | да |

Расхождения показывает **полоса вверху окна** (под панелью инструментов):
первое — текстом, остальные — в подсказке; кнопки **Bring the mods to the
project's base**, **Take the base from the game** (записать базу заново) и
**Mods…**. Перед **Play** расхождение, с которым мод проекта не применить
(`NotInstalled`, `Disabled`, `Version` — зависимости мода), останавливает
запуск с объяснением; остальные называются предупреждением, и игра
запускается.

**Привести моды к базе** (`Base::bring`; в редакторе — через окно Mods,
которое показывает ход и итог; `project base --apply`):

1. мод базы, который не установлен или повреждён, — отказ с его именем,
   ничего не меняется;
2. нынешняя расстановка сохраняется набором менеджера `Before <имя
   проекта>` (если такое имя занято — `… (2)`), когда она не совпадает ни с
   одним сохранённым набором; иначе путём назад служит тот набор;
3. моды базы включаются в её порядке: с `exclusive` они встают первыми, а
   остальные выключаются; без него остальные остаются как и где были, а моды
   базы занимают места модов базы (`Base::arrangement`);
4. моды записываются в игру — одной операцией с расстановкой
   (`ModManager::arrange_and_apply`): если запись отвергнута или не удалась,
   возвращается прежняя расстановка, а сохранённый для неё набор удаляется.

Вернуться — выбрать набор в списке **Set** окна Mods (или Open Mod Manager)
и записать моды; это первое применение наборов `sets.json` самим редактором.
**Undo** окна Mods возвращает прежнюю расстановку (не запись).

**Зависимости мода** (`Project::mod_info`, `mod_of`): моды базы с условиями
из `version` — и те, что включены, но не записаны в игру (догадка по
`applied.json` их не находит, `docs/mods.md` §8), — и никакие другие.
Оригинал правки в рабочем пространстве проекта остаётся немодифицированной
игрой; связь с базой делается при сборке и установке мода: для ресурса,

### 0.3 Перебазирование (этап 111)

Правка начинается с игры **как она есть** — с модами, которые менеджер
записал в неё (`Workspace::current_data`), поэтому данные изменённого
ресурса в рабочем пространстве — «то, что дала база, плюс моя правка».
Когда мод базы обновляется (расхождение `Changed`, §0.2) или моды в игре
становятся другими, правка по-прежнему хранит то, что база давала
**тогда**. Мод, собранный из неё на новой базе, вернул бы обновление назад:
убрал бы то, что оно добавило, и вернул то, что оно убрало. Оригинал правки
здесь не помогает — это немодифицированная игра, а не данные базы.

Код: `workspace/rebase.rs` (`Stale`, `Given`, `RebaseRequest`,
`RebaseReport`, `RebaseOutcome`; `Workspace::stale`, `rebase`, `keep_mine`,
`take_base`, `rebase_given`, `base_detail`), `workspace/mod.rs`
(`Change::made_on`, запись в `plan_set`), `resource/delta/mod.rs`
(`operations`), `project/rebase.rs` (`Project::given`, `stale`, `rebase`,
`stale_warning`), `mods/mod.rs` (`game_without_mod`, `BuiltMod::stale`,
`stale_note`, `BuildReport::stale`); редактор — `app/document.rs`
(`BaseBar::stale`, `check_stale`, `BrowserApp::rebase`), `changes_view.rs`.

**На чём сделана правка.** Когда ресурс потока игры меняется впервые и
данные, с которых правка началась (файл игры как он есть), не равны
оригиналу, правка запоминает их: поле `made_on` (хэш и размер; сами данные
— в `payloads/`, `docs/workspace.md` §3.1). Поле сохраняется при следующих
правках того же ресурса, при отмене и повторе, и уходит вместе с правкой.
Правка на немодифицированной игре поля не имеет, поэтому рабочее
пространство без модов под ним пишется побайтно как раньше, а версия
формата не менялась. Правка, записанная до этапа 111, считается сделанной
на оригинале.

**Устаревшие правки** (`Workspace::stale` → `Vec<Stale>`): правки, чей
ресурс игра сейчас даёт не таким, на каком правка сделана. «Игра даёт» —
файл игры как он есть, для потока, который это рабочее пространство само не
записывало; читаются только потоки с резервной копией (то есть кем-то
записанные), по одному ресурсу на правку в них. Добавленные ресурсы и новые
потоки не устаревают: кроме рабочего пространства, их никто не даёт.

Одна поправка — **собственный мод рабочего пространства**
(`Workspace::given`, `mods::game_without_mod`). Автор ставит рабочее
пространство модом и записывает моды, чтобы увидеть его в игре, и правит
дальше; файл игры тогда держит установленное состояние его же правки, а не
то, на чём она стоит. Для таких ресурсов берутся данные остальных
включённых модов (их свёртка, как в `suggested_dependencies`), иначе
оригинал. Своим считается мод, **установленный из этого рабочего
пространства** (`install-workspace`, **Install as mod** окна Mods, Install
project into Mods: менеджер записывает папку рабочего пространства в
`registry.json`, поле `workspace`, `InstalledMod::workspace`), у проекта —
ещё и мод с id проекта (`Project::given`), в редакторе без проекта — мод с
id из формы сборки окна Mods. Без этой поправки перебазирование «на файл»
убрало бы правку ради её собственной установленной копии.

**Перебазирование** (`Workspace::rebase`, `Project::rebase`) — одна
отменяемая операция на все затронутые правки:

| Ресурс | Что делается |
|---|---|
| вид с дельтами (`delta::kind_of`: `simgroup`, `lh2`, `partsdb`, `wgi`) | `ops = operations(на чём сделано, моё)`, `моё′ = apply(ops, что даёт игра)`; у правки новые данные и новое `made_on`. Для SimGroup операции берутся по содержимому, без побайтной проверки и без раскладки (`delta::operations`): раскладка привязана к прежней базе. Операция, чьей цели в новых данных нет, пропускается; операция поверх значения, которое изменила и база, применяется (значение автора остаётся) — оба списка идут в отчёт по объекту или строке с причиной (`delta::Applied`) |
| то же, но изменение не выражается операциями, или правка добавляет элемент, который теперь есть в игре (тот же GUID, тот же хэш строки) | правка не трогается, в отчёте — `Undecided` с причиной |
| остальные (текстуры, меши, материалы, сырые данные) | не сливаются: `Undecided`. Решений два — **оставить моё** (`keep_mine`: правка остаётся как есть, `made_on` становится нынешними данными игры) и **взять из базы** (`take_base`: правка убирается) |
| после слияния от правки ничего не осталось (все операции пропущены или игра уже даёт то же) | правка убирается, в отчёте `removed` |

Перебазирование, которому нечего менять, ничего не записывает. Отмена
(Ctrl+Z, `workspace undo`) возвращает правки точно такими, какими они были,
— вместе с `made_on`.

**Сборка не молчит.** `mods::mod_from_workspace` сравнивает `made_on` каждой
заменённой правки с тем, на чём собирается мод (`Relations::made_on` —
данные зависимостей; без них оригинал игры). Не совпало — ключ идёт в
`BuiltMod::stale`, а в отчёт сборки первой строкой встаёт предупреждение
(`BuildReport::notes`, `stale`; при установке — `InstallReport::warnings`):
«N change(s) were made on other data than the mod is built on…». Его
печатают `project mod`, `project install`, `mods build` и `mods
install-workspace`, показывают окно Mods (сборка и установка), кнопка Mod
вкладки Project и File → Install project into Mods; в MCP и Python оно в
`notes` сборки.
Сверка идёт с тем, на чём мод **собирается**, поэтому она срабатывает и
тогда, когда игра стоит не на базе (включён лишний мод, меняющий тот же
ресурс; база включена, но не записана), и когда мод собирают без оглядки на
моды игры, хотя правки сделаны на них.

**Решение: устаревшие правки не останавливают ни сборку, ни Play, ни
установку** — в отличие от отсутствующего мода базы (§0.2), с которым мод
проекта просто нельзя применить. Причины: (1) мод из устаревших правок
применим, ничего не теряется и не пишется безвозвратно — перебазируйте и
соберите снова; (2) «Играть» показывает ровно то, что показывает редактор:
изменённый ресурс в нём — данные рабочего пространства; (3) остановка
потребовала бы ключа «всё равно собрать» в четырёх интерфейсах, а автору
«оставить моё» и так доступно. Зато предупреждение есть везде, где мод
собирается, ставится или запускается, и `project rebase --check` даёт
ненулевой код возврата для сценариев.

**В редакторе.** Полоса вверху окна (§0.2) получает строку «N edits were
made on other data of the base» с кнопками **Rebase** (все устаревшие
правки одной операцией) и **Changes**. Кнопка полосы и команда **File →
Rebase the edits onto what the game gives now** доступны, когда игра стоит
на базе (единственное допустимое расхождение — `Changed`): правка
переносится на то, что даёт игра, поэтому сначала «Привести моды к базе
проекта». Панель **Changes** помечает такие правки (`stale`), показывает
их число с общей кнопкой **Rebase**, а у выбранной правки — три кнопки
**Rebase** / **Keep mine** / **Take the base's** и сравнение «что игра
изменила под этой правкой» (тем же видом, что сравнение правки с
оригиналом: строки, логика, текстура, байты). Итог — сколько правок
перенесено, оставлено, убрано, сколько операций пропущено и наложено
поверх чужого значения, что ждёт решения — уходит в строку состояния и в
журнал, вместе со строками отчёта по объектам. Проверка — при открытии
рабочего пространства, при каждой сверке базы (смена модов, запись модов
окном Mods), после отмены, повтора и самого перебазирования; обычная правка
игру не перечитывает (новая правка устаревшей быть не может). После
перебазирования расхождение `Changed` остаётся, пока база не записана
заново (**Take the base from the game**).

**Командная строка.**

```sh
doctor-toolkit project rebase my_mod --check          # список; ошибка, если есть устаревшие
doctor-toolkit project rebase my_mod                  # перенести всё, что сливается
doctor-toolkit project rebase my_mod --only yard      # только правки, чей ключ содержит текст
doctor-toolkit project rebase my_mod --keep 0b1f55    # «оставить моё» для этой правки
doctor-toolkit project rebase my_mod --take-base tg4d # «взять из базы»
doctor-toolkit workspace rebase "$GAME" [--dir DIR]   # то же для рабочего пространства без проекта
```

Все ключи одного вызова — одна операция. Команда печатает каждую правку и
пропущенные операции; если что-то ждёт решения, код возврата ненулевой.
`project status` называет устаревшие правки предупреждением. MCP:
инструмент `rebase` (`check`, `only`, `keep`, `take_base`), предупреждение в
`project_status`. Python: `Workspace.stale()`, `Workspace.rebase(only=…,
keep=…, take_base=…)`.

**Исходники проекта.** Перебазирование меняет рабочее пространство; файлы
`src/` получают его версию через **Pull** / `project pull` (записи будут
*out of sync*, §7).

Ограничения:

- Строку из таблицы убрать нельзя и языки менять нельзя — такое изменение
  не выражается операциями (`docs/formats/delta.md`), правка уйдёт в
  `Undecided`. То же для SimGroup с изменённым заголовком, порядком
  объектов, классом или флагами объекта.
- Правка, сделанная до этапа 111 на игре с модами, считается сделанной на
  оригинале и поэтому сразу значится устаревшей; слияние для неё обычно
  отказывает (операции содержат и то, что добавила база: «an object … is
  already in the group»). Для неё верное решение — **Keep mine**: правка
  останется как есть и запомнит нынешние данные игры.
- Рабочее пространство, собранное из одних исходников (§7.2), запоминает
  данные игры на момент сборки, а не те, на которых исходники писались.
- Пока мод проекта записан в игру, а его правку вы убрали, новая правка
  того же ресурса начинается с файла игры вместе с установленным
  состоянием (§0.1) и сразу значится устаревшей — перебазирование уберёт из
  неё прежнее установленное состояние.
- Мод, собранный из рабочего пространства **без проекта** в файл и
  установленный из файла, своим не считается: менеджер не знает, из какого
  рабочего пространства он сделан. Пока такой мод записан в игру, его
  правки значатся устаревшими, и перебазировать их нельзя (правка без
  добавлений была бы убрана как «уже есть в игре»; отмена её вернёт).
  Выключите мод и запишите моды, либо поставьте его из рабочего
  пространства (`mods install-workspace`, **Install as mod**). Проекта это
  не касается: его мод узнаётся по id.
- Редактор замечает смену модов по файлам менеджера только при открытом
  проекте; для рабочего пространства самой игры проверка идёт при его
  открытии, после записи модов окном Mods, после отмены и повтора.
- Файлы вне потоков (звук `.viv`, ролики) в сверке не участвуют.

Тесты: `workspace/rebase/tests.rs` (запись `made_on` только при отличии от
оригинала, правки, отмена, повтор, открытие заново; рабочее пространство
без поля; ресурс без элементов — оставить и взять; правка, добавляющая то,
что уже есть; правка, от которой ничего не осталось; слияние, «оставить» и
«взять» одной операцией), `project/rebase/tests.rs` (основной сценарий:
базовый мод 1 добавляет A; проект добавляет B и двигает C; базовый мод 2
добавляет D и убирает C; `stale`; сборка предупреждает; `rebase` — A, B, D
без C, сдвиг C назван пропущенным; мод — дельта из одной операции;
установленный поверх новой базы, он даёт в игре A, B, D; мод проекта в
игре не делает правку устаревшей; то же для строк с пропуском и
конфликтом, и мод, установленный из рабочего пространства без проекта),
редактор без окна —
`stale_edits_are_told_in_the_bar_and_rebased`, командная строка —
`project_rebase_moves_stale_edits_onto_the_updated_base`, MCP —
`stale_changes_are_rebased_kept_or_given_up`, корпус
(`tests/corpus/rebase.rs`): шесть случайных правок каждой из 2 006
SimGroup, перенесённые на базу, изменённую другими правками, дают то же,
что те же правки руками на новой базе; рабочее пространство на копиях 12

  Проекту со своим рабочим пространством этого достаточно, чтобы собрать
  рабочее пространство заново (§7.2): папку `workspace/` можно в git не
  класть.

```toml
    "gf2/miami/local/bonita/high/terrain06",

```

`[[zones]]` пишет редактор (панель Zones → Saved sets) и можно писать
руками. Запись — имя потока (именно этот поток, даже если под ним лежат
другие), папка зон (`gf2/miami/local/bonita/high`) или пресет
(`preset:gf2/miami/bonita`, `docs/levels.md` §13.2); поток, которого в игре
нет, при выборе набора пропускается с сообщением. Сохраняя набор, редактор
заменяет в файле только таблицы `[[zones]]`; комментарии и остальной текст
остаются как были (`ProjectConfig::write_zones`). Прежние версии программы
раздел пропускают, поэтому `format` не менялся.

`format` больше поддерживаемого (сейчас 2) — отказ; неизвестный формат
моделей — понятная ошибка. Раздел `[base]` требует `format = 2`
(`ProjectConfig::required_format`: программа пишет наименьший нужный, файл
без базы — `format = 1`, побайтно как до этапа 108); манифесты потоков и
кэш сборки остаются формата 1. База с неправильным id, повтором мода,
условием или хэшем, которые не разбираются, или с самим проектом в списке —
ошибка при открытии проекта (`Base::validate`).

`project status` и сборка предупреждают о другом исполняемом файле и о
расхождениях модов игры с тем, на чём сделан проект: с базой (§0.2) и с
модами из `dependencies`, которых нет или которые выключены в менеджере
модов. Мод из проекта (формат 3, `docs/mods.md` §1.3) получает моды базы в
`depends` с их условиями, моды из `dependencies` — с условием `*`.

## 3. Манифесты и метаданные ресурса

`stream.toml` (у `shared/` — `shared.toml` без `stream`):

```toml
format = 1
stream = "gf2/text/dd7d7050"

[[resource]]
name = "9e583c54"                 # имя из индекса или id
kind = "strings"                  # вид (§4)
type = "lh2"                      # тег типа главного ресурса
ids = "9e583c54"                  # его четыре id (GUID в потоке)
policy = "default"                # политика памяти
files = ["lh2/9e583c54.json"]     # файлы; первый — главный, он же id записи
keys = ["gf2/text/dd7d7050:lh2:9e583c54"]   # ресурсы, в которые собирается
exported = "efb31843…"            # отпечаток файлов при создании
base = "4b5bd52e…"                # SHA-256 данных из .doctor/base (строки, логика)
```

Идентификатор записи — путь главного файла от корня проекта
(`src/gf2/text/dd7d7050.str/lh2/9e583c54.json`); так её называют `status`,
ошибки сборки и `--only`.

Ещё четыре поля пишет программа, когда файлы записаны из изменённого
рабочего пространства (`--from-workspace`, `project sources`, `pull`):

| Поле | Что |
|---|---|
| `outputs = ["sha…", ""]` | SHA-256 данных каждого ключа в том рабочем пространстве (пусто — оно этот ресурс не меняло). По нему проект собирается в рабочее пространство, у которого ещё нет кэша сборки (§7.2) |
| `storage = ["keep", "refpack"]` | сжатие ресурса игры по ключам (`keep` — как у ресурса игры, `raw`, `refpack`), когда рабочее пространство задало другое, чем у игры; у добавленного ключа сжатие — в его таблице `added` |
| `template = ["sha…", "sha…"]` | данные картинки или модели, сделанной рабочим пространством, в `.doctor/base/` (§4.1) |
| `[[resource.added]]` | где и как ресурс, которого нет в игре, встаёт в поток (§3.1) |

### 3.1 Добавленный ресурс (этап 112)

Ресурс, которого в игре нет, — запись с таблицами `[[resource.added]]`, по
одной на каждый ключ, который мод добавляет:

```toml
[[resource]]
name = "sparks"
kind = "raw"
type = "vfx"
ids = "00005201"                   # ids ресурса — его ключ: пишутся, а не выдаются заново
policy = "default"
files = ["vfx/sparks.bin"]
keys = ["gf2/level:vfx:00005201"]

[[resource.added]]
key = "gf2/level:vfx:00005201"     # какой из ключей записи добавляется
policy = "default"                 # политика памяти: имя или хэш; по умолчанию default
alignment = 16                     # по умолчанию 16
before = "gf2/level:mesh:00003333" # перед каким ресурсом потока игры; нет — в конец
order = 4000000                    # порядок среди добавленных в одно место; по умолчанию 0
storage = "refpack"                # сжатие; нет или "raw" — без сжатия
```

- Такую запись можно написать руками: `exported`, `outputs`, `policy`,
  `alignment`, `order` и `storage` не обязательны. Файл манифеста с
  добавленными ресурсами или описанием нового потока получает `format = 2`:
  программа старше этапа 112 приняла бы папку за ресурсы игры и отказала бы
  на каждой записи «not in the game», а так говорит сразу, что формат ей не
  по силам. Манифесты без добавленного остаются с `format = 1`.
- `order` — то же число, что хранит рабочее пространство
  (`Added::order`): редактор считает его от истории (номер операции ×
  1 000 000 + место в операции), исходники хранят его как есть, поэтому
  сборка в пустое рабочее пространство ставит ресурсы в том же порядке.
  Равные `order` упорядочены по ключу. В новом потоке мест нет (`before`
  — ошибка): его ресурсы пишутся по `order`, SimGroup — последними
  (`docs/workspace.md` §3.4).
- Сборка записывает добавленный ресурс под ключом записи
  (`Workspace::put_added_resources`): нет его в рабочем пространстве —
  добавляет, есть — заменяет данные, место, порядок и сжатие на записанные.
  Один и тот же файл даёт одну и ту же правку, что бы ни было в рабочем
  пространстве раньше.
- **Удалённый файл — удалённый ресурс.** Запись, все ключи которой
  добавлены, с исчезнувшим главным файлом получает состояние `removed`:
  сборка убирает ресурс из рабочего пространства и запись из манифеста.
  Для ресурсов самой игры пропавший файл остаётся ошибкой записи
  (`missing`): ресурс игры удалить нельзя. Запись, убранная из
  `stream.toml` руками, ресурс не удаляет — он остаётся в рабочем
  пространстве, и `project sources` напишет его исходник снова.
- Ключ может быть добавлен и не весь набор записи: у меша игры без
  `meshvolatile` импорт добавляет его (`docs/model-import.md` §2.4) —
  запись модели держит ключ меша игры и добавленный ключ с таблицей
  `added`.

### 3.2 Новый поток (этап 112)

Папка потока, которого в игре нет, несёт его описание — таблицу `[new]`
своего `stream.toml` (то, что рабочее пространство хранит в `NewStream`):

```toml
format = 2
stream = "gf2/town/annex"

[new]
guid = "0102030405060708090a0b0c0d0e0f10"   # GUID потока, 32 шестнадцатеричные цифры
parent = "gf2/town"                          # от какого потока зависит
load = "on_demand"                           # on_demand (по умолчанию), with_parent, auto_load
tocs = ["gf2/level.toc"]                     # в каких TOC перечислен
# hash = "0badf00d"                          # только если хэш не свёртка GUID
# [new.toc_parents]                          # другой родитель в отдельных TOC
```

- `load` — как в **Tools → New stream…** (`zone_ops::StreamLoad`): по
  запросу данных игры, дочерний поток после включения, дочерний поток с
  каждой загрузкой родителя.
- Сборка создаёт поток (`Workspace::put_stream`) до его ресурсов; правка
  таблицы меняет описание потока, ресурсы остаются. Ошибка описания (нет
  родителя, TOC, занятый хэш) — ошибка `…/stream.toml`.
- **Удалённая папка — удалённый поток.** Сборка помнит папки новых потоков
  в кэше (`.doctor/build.json`, `streams`: поток и отпечаток его описания,
  по которому видно, что `[new]` правили руками); папки нет, а рабочее
  пространство поток ещё создаёт — сборка убирает поток со всем, что в него
  добавлено (`status` показывает `removed stream`). Если кэш удалён, сборка
  об исчезнувшей папке не узнает: поток уберите `remove-stream` или
  кнопкой в редакторе.
- Ячейку мировой сетки новой зоны исходники держат как обычную замену
  ресурса `wgi` корневого потока уровня (`raw`).

## 4. Виды ресурсов и круговой путь

«Круг» — распаковать в проект → изменить файл → собрать → игра читает.
Последний столбец — что проверено в игре раньше (этапы 18, 24 и др.), а не
в этом этапе: игру этап 36 не запускал.

| Вид (`kind`) | Типы | Файлы | Сборка | Неизменённый файл, собранный заново (`--force`) | В игре |
|---|---|---|---|---|---|
| `texture` | `tg4h` + `tg4d` | PNG (первая поверхность), DDS для кубических и объёмных или с `textures = "dds"` | `import_texture` (как `texture-import`); добавленная — кодирование поверх своего заголовка (§4.1) | **другие данные**: картинка кодируется в DXT заново; у текстуры, сделанной рабочим пространством, — те же данные (§4.1) | да (`texture-import`, `game-bench.md` §13) |
| `strings` | `lh2` | JSON как `text-export` | строки накладываются на базу | те же данные | да (новая строка, этап 18) |
| `logic` | `simgroup`, `metamodel`, `variabledictionary`, `partsdb` | JSON как `logic-export` | `logic_import::apply_json` на базу, затем патч SimGroup (§5) | те же данные | да (SimGroup и metamodel, этап 24; `partsdb`, этап 17) |
| `document` | `dlg`, `chv`, `trinity_seq_master`, `graph` | JSON всего документа | разбор JSON → запись (`to_bytes`); при создании проверяется, что документ пишется побайтно, иначе — `raw` | те же данные; у `graph` сборка приводит длины рёбер, R-дерево и таблицу путей к правке (`formats/navigation-graph.md`) | ролики — этап 29; диалоги — отложено; `graph` — этап 45 |
| `script` | `lua` | исходник Lua 5.0 (декомпиляция) | компиляция с числами float32 и именем исходного чанка | без изменений или иная отладочная информация; скрипт, чья декомпиляция компилируется в другой код, остаётся `raw` (`.luac`) | да (этап 28) |

### 4.1 Что мод делает заново: добавленные ресурсы, картинки и модели рабочего пространства (этап 112)

Добавленный ресурс собирается тем же преобразованием, что и ресурс игры
того же вида, но ему не на что опереться в игре — всё нужное лежит рядом с
исходниками:

| Вид | Добавленный ресурс | На что опирается сборка |
|---|---|---|
| `raw`, `document`, `animations` | материал, коллизия `hkx`, эффект, любой сырой ресурс; документ | только файлы |
| `strings`, `logic` | таблица строк; SimGroup новой зоны, metamodel нового набора | `base` — данные на момент записи исходника, как у ресурсов игры |
| `script` | добавленный `lua` | `base` — скомпилированный скрипт (имя чанка и размер чисел берутся из него) |
| `texture` | текстура, клонированная или импортированная под новыми id | `template` — её заголовок и данные |
| `model` | меш нового набора (с `meshvolatile`) | `template` — меш и его `meshvolatile` |
| `view` | — | не собирается; рядом лежит `raw` с ключом |

**Картинки и модели, сделанные рабочим пространством.** PNG и glTF — не
ресурс: кодирование даёт другие байты, и на настоящих текстурах игры они
другие при каждом новом круге «раскодировать → закодировать» (DXT не
возвращает свои блоки; замер в `tests/corpus/project.rs`). Поэтому у
текстуры и модели, которые рабочее пространство **сделало** — добавило или
импортировало поверх игровых, — исходник хранит и сами данные (`template`,
файлы в `.doctor/base/`):

- файл **не менялся** с момента записи (его отпечаток равен `exported`) —
  сборка кладёт ровно те данные, из которых файл был записан. Рабочее
  пространство, собранное из исходников, совпадает с исходным побайтно,
  вместе с текстурами и моделями, и мод из него получается тот же;
- файл **изменён** — сборка кодирует его заново: текстуру — с форматом,
  именем и цепочкой мипов её заголовка (`texture::from_png`/`from_dds`),
  модель — геометрией файла поверх прежнего меша
  (`import::model::rebuild_added`: имя, кости, виды записей и форматы
  вершин — от него). Это «другие данные», как у текстур и моделей игры.

Цена — место: `.doctor/base/` держит копию данных каждой такой текстуры и
модели (столько же, сколько они занимают в игре), и она нужна для сборки —
это часть исходников.

**Модель нового набора целиком.** Импорт модели новым набором
(`model-import --new`, окно Import model) добавляет меш с `meshvolatile`,
metamodel, при `--collision` — `hkx`, а для изменённых материалов — клон
материала и текстур. В исходниках это отдельные записи — модель, логика
(`metamodel`), `raw` (материал, коллизия), текстуры — каждая со своими id и
местом, и собираются они независимо:

- правка `.glb` меняет только меш и его `meshvolatile`, под теми же id;
  ничего не добавляется. Материал части — материал прежнего меша с именем
  материала glTF (иначе материал рабочего пространства или игры с таким
  именем, иначе самый частый материал меша, с предупреждением);
- **изображения файла модели не импортируются**: текстуры набора — свои
  записи, правьте их PNG. Иначе у одной текстуры было бы два исходника, и
  чистая сборка зависела бы от порядка записей. Папка `<имя>_textures/` у
  такой модели — для просмотра в редакторе моделей;
- то же относится к модели, импортированной **поверх** меша игры: её
  запись получает `template` и собирается так же, а клон материала,
  сделанный тем импортом, — своя запись `raw`. (Модель неизменённой игры,
  как и раньше, импортируется через `import::model::plan`: изменённое
  изображение клонирует материал.) Модели собираются последними в сборке:
  к этому моменту материалы набора уже в рабочем пространстве.

Что остаётся `raw` у нового набора: материал (`material`) и коллизия
(`hkx`) — правятся в редакторе (окно материала, `collision build`) и
забираются в файлы `pull`; меш, у которого нет `meshvolatile` (вершины без
него не читаются), — с примечанием при записи исходников.

**Не замкнуто в этом этапе** (остаётся `raw` или только просмотр):

- `covernodetable` — записи разобраны (`points.rs`), но писателя нет; та же
  правка на месте — после проверки, что точки не дублируются в другом месте;
- `treemodel` — формат разобран (`formats/treemodel.md`), читатель пишет обратно побайтно, но в проекте модель дерева пока хранится как `.bin`;
- звуковые банки `sbk` как WAV — импорт звука есть (`sound-import`), но
  перекодирование неизменённых звуков при сборке банка целиком — не сделано;
  банк — `raw`;
- события анимаций замкнуты по данным (`set_events`), в игре не
  проверялись; клипы анимаций — через `anim import`, не через проект;
- файл, которого нет в манифесте, по-прежнему не собирается («не входит в
  проект»): новый ресурс добавляет запись с `[[resource.added]]` (§3.1), а
  не появление файла; удалить ресурс **игры** нельзя (пропавший файл —
  ошибка записи);
- файлы вне потоков (звук `.viv`, ролики) исходников не имеют — остаются в
  рабочем пространстве.

## 5. Правки объектов поверх экспорта (`patches/`)

Экспортированный JSON SimGroup — снимок; свои изменения автор может вести
отдельно, в `patches/<поток>.str/simgroup/<имя>.toml`:

```toml
[[object]]
guid = "0102030405060708434852495354…"   # или name = "door_01" (CMD_SetName)
position = [10.0, 0.0, -4.5]
rotation = [0.0, 90.0, 0.0]               # градусы вокруг X, Y, Z
scale = [1.0, 1.0, 1.0]
set = { "Entity.CMD_SetModel" = "2f4fcbd4", "NPC.18" = "" }   # пустое — по умолчанию

[[new]]
name = "doctor_lamp_1"      # имя объекта, из него — GUID
copy = "lamp_02"            # шаблон: имя или GUID объекта группы
position = [12.0, 0.0, -4.5]
```

- Патч накладывается при каждой сборке на результат JSON, по объекту;
  изменение патча — изменение записи (входит в её отпечаток).
- Запись `[[object]]`, чьего объекта больше нет в группе (игра или JSON
  изменились), — **предупреждение**, остальное применяется; так же —
  шаблон `[[new]]`, которого нет. Ошибка значения или атрибута — ошибка
  записи с путём патча.
- Новый объект — копия шаблона с именем (`CMD_SetName`, если у шаблона он
  есть) и **GUID из имени**: канонический NeoGuid тулкита
  (`resource::neoguid`, машина `XDOCTORTKX`, `docs/formats/simgroup.md` §5)
  для текста `<id мода>:simgroup:<ids группы>/<имя>`. Та же группа и то же
  имя дают тот же GUID на каждой сборке, поэтому ссылки на объект
  (сообщения, `-playerspawn`) переживают пересборку; занятый GUID —
  следующая попытка `neoguid::new_guid`. В заметках сборки — GUID и его
  текст (`XDOCTORTKX_…_…_v3`). Python: `project_object_guid(scope, name)`.

## 6. Создание

```sh
doctor-toolkit project new "$GAME" my_mod                      # пустой проект со своим рабочим пространством
doctor-toolkit project new "$GAME" my_mod --stream gf2/frontend --stream gf2/text/dd7d7050 \
    [--type tg4h]… [--name NAME] [--id ID] [--author A] [--dds] [--model-format fbx] \
    [--no-shared] [--no-index] [--workspace-dir DIR]
doctor-toolkit project new "$GAME" my_mod --from-workspace     # из рабочего пространства
doctor-toolkit project new "$GAME" my_mod --move-workspace [--no-sources]   # рабочее пространство переезжает в проект
```

| Вызов | Что получается | Куда собирается |
|---|---|---|
| без `--stream`, `--from-workspace`, `--move-workspace` | пустой проект-документ (`project::create_document`, §0): `[build] workspace = "workspace"`, исходников нет | своё рабочее пространство |
| `--stream …` | исходники ресурсов потоков — вместе с тем, что рабочее пространство в эти потоки добавило | рабочее пространство игры (или `--workspace-dir`) |
| `--from-workspace` | исходники всего, что рабочее пространство меняет: заменённые ресурсы (с парами текстур и моделей), **добавленные ресурсы и новые потоки** | то же рабочее пространство |
| `--move-workspace` | проект-документ, в который **переезжает** рабочее пространство игры (или `--workspace-dir`) — правки и история (`project::adopt_workspace`), — и исходники перенесённого (`--no-sources` — без них) | своё рабочее пространство; прежнее исчезает |

- Источник данных — версия рабочего пространства: его правка ресурса или
  оригинал игры (из резервной копии, если файл игры уже переписан).
- `--move-workspace` назван по действию: рабочее пространство игры после
  него пусто. Отказ, пока его правки записаны в файлы игры (сначала
  `workspace revert GAME --game`), — до создания папки проекта; с другими
  способами выбора ресурсов не сочетается. `--dds` и `--model-format`
  задают формат исходников проекта.
- `--type` с пустым проектом и `--workspace-dir` с ним — отказ: у пустого
  проекта рабочее пространство своё.
- Папка должна быть новой или пустой; второй проект в той же папке — отказ.
- Кэш сразу записывает состояние рабочего пространства, поэтому только что
  созданный проект — «без изменений», и сборка ничего не делает.

## 7. Состояние и сборка

```sh
doctor-toolkit project status [ПАПКА] [--all] [--game DIR] [--workspace-dir DIR]
doctor-toolkit project build  [ПАПКА] [--only ПУТЬ]… [--force] [--dry-run] [--apply]
doctor-toolkit project pull   [ПАПКА] [ПУТЬ]…
doctor-toolkit project sources [ПАПКА] [--no-index]
doctor-toolkit project mod    [ПАПКА] -o mod.zip [--preview pic.png] [--build]
doctor-toolkit project install [ПАПКА] [--build]
doctor-toolkit project base   [ПАПКА] [--game DIR] [--record] [--check] [--apply [--force] [--ignore-compatibility]]
```

`project install` (этап 107) ставит изменения проекта в менеджер модов игры
как мод проекта — §0.1; `project build --apply` для проекта со своим рабочим
пространством отказывает до сборки и называет эту команду.

`project base` (этап 108, §0.2) без ключей печатает базу проекта и чем от
неё отличаются моды игры (`differs: …`). `--record` берёт базу из модов,
записанных в игру, и пишет `project.toml`; `--apply` приводит моды к базе
(сохраняет расстановку набором, включает моды базы, записывает моды в игру;
`--force` и `--ignore-compatibility` — как у `mods apply`); `--check`
завершает команду ошибкой, если расхождения есть. Ключи сочетаются и
выполняются в этом порядке: `--record --check`, `--apply --check`.

Состояние записи:

| Состояние | Когда | Сборка |
|---|---|---|
| `unchanged` | файлы как при создании, рабочее пространство — как тогда | нет |
| `modified` | файлы (или патч) изменились после последней сборки; либо записи нет в кэше сборки, а рабочее пространство не держит того, что записано в `outputs` (свежая копия исходников, §7.2) | да |
| `built` | изменённые файлы собраны, рабочее пространство держит результат | нет |
| `out of sync` | файлы собраны, но в рабочем пространстве теперь другое (отмена, откат, правка в редакторе) | да: возвращает версию проекта; `pull` — наоборот, берёт версию рабочего пространства в файлы |
| `missing` | нет файла | ошибка записи |
| `removed` | нет главного файла записи, все ключи которой мод добавляет | да: ресурс убирается из рабочего пространства, запись — из манифеста (§3.1) |
| `view changed` | изменён просмотровый файл | нет, предупреждение |

Как определяется «изменилось»:

- **Отпечаток входов** записи — SHA-256 от путей и SHA-256 её файлов и
  патча. Файл читается заново, только если изменились его размер или время
  (и не в пределах 2 с от прошлого хэширования — защита от правки в ту же
  метку времени), иначе хэш берётся из `.doctor/build.json`.
- **Отпечаток результата** — SHA-256 данных каждого ключа записи (и
  ресурсов, которые её сборка добавила или изменила, например материалов
  модели) в рабочем пространстве после сборки; `null` — ресурс не изменён.
- Запись собирается, если отпечаток входов не равен записанному или
  рабочее пространство держит не то, что записала прошлая сборка. Без кэша
  (удалён, или это свежая копия исходников) запись, чьи файлы равны
  `exported`, считается неизменённой, когда файлы — из неизменённой игры
  (нет `outputs` и `added`) или рабочее пространство держит ровно то, что
  записано в `outputs`; иначе она `modified` и собирается.
- Потоки, которые проект создаёт, — не записи: `status` показывает поток
  `modified`, пока рабочее пространство не создаёт его так, как описано в
  `[new]`, и `removed`, когда папки нет, а поток ещё есть (§3.2).

Сборка:

1. Сначала потоки: убираются потоки исчезнувших папок, создаются и
   приводятся к описанию потоки `[new]` (§3.2) — в них добавляются ресурсы.
   Затем все записи к сборке собираются по очереди, модели — последними
   (§4.1); каждая — своими импортёрами (§4) в **рабочее пространство**, не
   в игру. Ошибка одной записи — сообщение `путь: ошибка`, остальные
   собираются; запись с ошибкой остаётся `modified`.
2. Все операции сборки склеиваются в одну (`Workspace::squash`, «Build
   project NAME (n file(s))»): одна отмена убирает всю сборку. Сборка без
   изменений операции не создаёт и рабочего пространства не заводит.
3. Строки и логика накладываются на **базу** — данные ресурса при создании
   проекта (`.doctor/base/`), поэтому результат зависит только от файлов,
   а не от прошлых сборок, и повторная сборка даёт те же данные.
4. `out of sync`-запись, чья прошлая сборка оставила ресурсы без изменений
   (`null`), не собирается заново, а **откатывается** в рабочем
   пространстве: так возвращаются точно исходные данные, без
   перекодирования картинки.
5. После сборки отпечатки результата обновляются у всех записей, чьи ресурсы
   она затронула.
6. `--apply` после сборки пишет рабочее пространство в игру
   (`workspace apply`); «Играть» и моды берут сборку оттуда же.

`--force` собирает все записи (кроме просмотров), даже неизменённые: для
замера и проверки; текстуры и модели игры при этом получают
перекодированные данные (§4), сделанные рабочим пространством — те же
(§4.1).

### 7.1 Исходники рабочего пространства: `project sources`

`doctor-toolkit project sources [ПАПКА]` (вкладка Project — **Write
sources**, Python — `Project.sources()`, MCP — `project_pull` с `sources`;
библиотека — `Project::export_workspace`) приводит `src/` к рабочему
пространству проекта:

1. записи `out of sync` получают версию рабочего пространства, как `pull`,
   — и модели тоже (с индексом игры, откуда берутся материалы и текстуры);
   запись добавленного ресурса, которого в рабочем пространстве больше нет,
   убирается вместе с файлами;
2. для каждой правки, у которой записи нет, — новая запись: заменённые
   ресурсы (с парами), добавленные ресурсы, описание новых потоков; имена
   файлов не пересекаются с уже лежащими в папке. Описание потока, которое
   в рабочем пространстве изменилось, переписывается; описание, изменённое
   в `stream.toml` и ещё не собранное, остаётся — с примечанием;
3. папка нового потока, которого рабочее пространство больше не создаёт,
   убирается, когда в ней не осталось записей (папка, написанная руками и
   ещё не собранная, остаётся).

Файлы, которые вы изменили и ещё не собрали (`modified`), не трогаются.
Второй вызов подряд ничего не пишет. Команда — только для проекта со своим
рабочим пространством (`[build] workspace`): рабочее пространство игры
может держать чужую работу; его содержимое берёт `project new
--from-workspace` или `--move-workspace`. В `shared/` новые записи не
попадают: общие ресурсы выделяются при создании проекта. Файлы вне потоков
(звук `.viv`, ролики) остаются в рабочем пространстве — с примечанием.

`pull` после этого держит исходники вслед за рабочим пространством:
правка добавленного ресурса в редакторе — `out of sync` → `pull` пишет
файл; ресурс убран из рабочего пространства — `pull` убирает запись.

### 7.2 Рабочее пространство из одних исходников

```sh
git clone … my_mod && cd my_mod            # src/, shared/, patches/, .doctor/base, project.toml
doctor-toolkit project build . --game "$GAME"
```

У свежей копии нет ни `workspace/`, ни кэша сборки. Записи, файлы которых
были записаны из изменённого рабочего пространства (`outputs`,
`[[resource.added]]`), и потоки `[new]` тогда `modified`, и сборка
записывает их в пустое рабочее пространство одной операцией. Результат
равен рабочему пространству, из которого исходники записаны: те же ключи,
те же данные (картинки и модели — тоже, пока их файлы не менялись, §4.1),
те же место, порядок, политика памяти и сжатие каждого добавленного
ресурса, те же описания новых потоков. Проверено модульным тестом
`the_sources_of_a_workspace_build_the_same_workspace` (замены, добавленные
ресурсы в потоке игры, новый поток с SimGroup и ячейкой мировой сетки,
модель новым набором с коллизией, модель поверх меша игры) и на настоящем
уровне (`tests/corpus/project.rs`,
`the_sources_of_a_workspace_with_a_new_zone_build_it_again`: зона в
`mp_rooftops`, модель уровня новым набором, клоны текстуры здания — 8
правок, 5 записей, исходники за 0,1–0,25 с, сборка в пустое рабочее
пространство за 0,4–0,8 с; затем правка модели и картинки — меняются только
меш и данные текстуры, под теми же ключами).

**Скорость** (корпусный тест, release, 7 потоков, 713 ресурсов, 476 записей,
23 МиБ файлов): создание — 1,0 с; состояние — 0,03–0,05 с; сборка без
изменений — 0,03–0,06 с; сборка четырёх изменённых файлов (текстура, строка,
SimGroup, модель; с построением индекса ресурсов для модели) — 0,33–0,51 с;
полная сборка всех 468 записей — 12–15 с (почти всё — перекодирование 78
текстур и 30 моделей).

**Совпадение с прямым импортом** (тот же тест): после правки текстуры
(PNG), строки (JSON), SimGroup (положение объекта в JSON) и модели (glb со
сдвинутыми вершинами) сборка затрагивает ровно эти записи, а данные всех
изменённых ресурсов совпадают с тем, что дают в чистом рабочем пространстве
`import_texture`, импорт JSON внешнего редактора, `logic_import` и
`model-import` тех же файлов.

## 8. Мод из проекта

`project mod -o mod.zip` (GUI — **Build mod…**, Python — `build_mod`)
пишет мод (`docs/mods.md`) из изменений рабочего пространства, которые
принадлежат проекту: ключи записей и ресурсы, добавленные их сборкой
(`mods::build_from_workspace` с выбором ключей); у проекта со своим рабочим
пространством — все его изменения. Метаданные — из `[project]`. Без сборки
мод пуст — отказ «build it first»; `--build` сначала собирает.

С этапа 108 файл мода собирается так же, как мод ставится в менеджер
(`Project::build_mod_on` → `mod_of`, §0.1): зависимости — моды базы с её
условиями (без базы — `[dependencies] mods` и моды, записанные в игру, на
которых сделаны правки), а для ресурса, который меняет такой мод,
оригиналом в манифесте становятся его данные. Поэтому мод, сделанный поверх
базы, у игрока сверяется с базой, а не с чистой игрой. Мод с зависимостями
и условием на менеджер — формата 3. `Project::build_mod` (без игры)
оставлен для сборки без взгляда на моды игры: зависимости — как названы в
`project.toml`, оригиналы — игры.

Версия манифеста — наименьшая нужная: 6, когда изменённые SimGroup, таблицы
строк, базы частей или мировые сетки пошли в мод дельтами — правками,
которые менеджер объединяет с другими модами (`docs/mods.md` §1.7). Дельты
включены по умолчанию; `[build] deltas = false` в `project.toml` оставляет
ресурсы целыми (мод ставится и менеджером старше формата 6) — так же
собирается мод проекта при **Install project into Mods** и **Play**.

## 9. GUI

**Tools → Project browser** (палитра команд — «Project»), вкладка
**Project**:

- без проекта — **Open project…** и форма **New project** (потоки через
  запятую или «из изменений рабочего пространства», папка — диалогом);
- дерево: папки потоков и `shared`, внутри — типы, внутри — файлы с цветной
  меткой состояния; папки и типы с изменениями раскрыты; поиск по пути,
  имени и типу, флажок «только изменённые», счётчики состояний;
- справа — запись: тип, ids, политика, файлы, патч, ключи (щелчок открывает
  ресурс), **Open in external editor** (программа из настроек этапа 22 по
  виду файла: картинка, модель, текст), **Open resource**, миниатюра PNG
  текстуры;
- **Build (n)** — собрать изменённое в рабочее пространство редактора (одна
  операция, Ctrl+Z отменяет), **Build all**, **Pull**, **Write sources**
  (§7.1; доступна у проекта со своим рабочим пространством; без рук —
  `DOCTOR_TOOLKIT_GUI_SHELL=sources`), **Build mod…**, **Refresh**,
  **Show folder**; состояние файлов перечитывается раз в 2 с и после
  каждой правки рабочего пространства. **Build** и **Refresh** читают
  манифесты заново: записи и папки, написанные или удалённые руками, видны
  без повторного открытия проекта; под счётчиками — потоки, которые сборка
  создаст или уберёт.

GUI собирает в рабочее пространство открытой игры (по умолчанию); проект
другой папки игры — предупреждение. Для снимков:
`DOCTOR_TOOLKIT_GUI_PROJECT=<папка>` открывает вкладку с проектом.
Строки — группа `project.*` в `crates/doctor-toolkit-mods/i18n/{en,ru}.toml`.
